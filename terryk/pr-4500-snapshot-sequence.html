Four pages on this PR. This one: the exact order of a save and a restore, read from the code.

Background. Gym runs each rollout as a run. r7#0 means rollout r7, Gym attempt 0. gA and gB are two copies of the Gym servers. The recovery ledger is RL's list of which runs each copy holds. TQ holds finished rollout data until training uses it. Dotted words have a short explanation: hover or tap them.

The PR description has its own 15-step version of this diagram. I rebuilt it from the code to check it. The order matches. But six steps are missing or drawn differently (marked ◆), and most of them are where a snapshot can be lost. The example: copy gA has two runs in flight. r7 is mid-turn, and r9's last reply is already on its way back. Copy gB still runs r4, which RL already dropped.

Save: one snapshot

Where the PR's diagram differs from the code ◆

  • Step 5. The PR says every participant parks at a turn boundary. That is true only when every Gym agent and tool server can save a run mid-way. Any other agent blocks prepare until the 300 s limit, and three failed snapshots in a row stop the run. #1 · gym_checkpoint_adapter.py:208
  • Step 14 is missing. The check for a finished train step runs after the whole Gym phase. A step that ends while Gym is parked throws the snapshot away after the full pause. #6 · single_controller.py:4906
  • Step 19 is missing. The PR's diagram ends at "reopen the gate", but the snapshot only counts once the temp folder is renamed, after Gym has already resumed. If that last write fails, the previous snapshot stays the latest one, which is safe.
  • Step 11. gym_checkpoint.json is written at commit, not with the TQ save. Step 15 rewrites it only when a dropped run has to be left out.
  • Steps 2 and 7 are missing. Pausing the rollout time limits and renewing Gym's lease are what stop a long pause from timing runs out, or letting Gym reopen by itself.

How a save fails: a prepare timeout (step 5) or a drain timeout (step 12) counts as one failed snapshot, and three in a row stop the run. A parked run that Gym did not save stops the run at once.

Restore: at startup

This matches the PR's flowchart on the main points. The saved runs must equal the ledger's runs. Each restored run moves to Gym attempt 1 and goes back to the same Gym copy. Two paths are missing from the flowchart ◆:

  • Step 3. When there is no Gym file (restoring from a trainer checkpoint), turn runs start over from their prompt. This needs the gym_restart_fallback.json marker; without it, the restore fails.
  • Step 8. The flowchart cleans up only when Gym's restore fails. The code also retires r7#1 when a later RL step fails, which is right. When Gym's restore itself fails, Gym gets resumed twice. #19 · gym_checkpoint_coordinator.py:537

So what. The PR's diagram gets the order right, but it leaves out the four places where a snapshot is lost or the run stops: the prepare timeout (step 5), the drain timeout (step 12), the train-step check (step 14) and a lost resume (step 17). Those are review comments #1, #2–3, #6 and #7. The PR's diagram should show them, so readers can see where a snapshot can fail.

How an external vLLM server gets new weights, next to the vLLM that NeMo-RL runs itself

NVIDIA-NeMo/RL #4674 (adds policy.generation.backend: remote_vllm). Permalinks pin head 69c7ea3.

Before
NeMo-RL could only refit a vLLM it started itself, as Ray workers inside the training job.
This PR
Adds a second backend: a vLLM 0.29.0 server someone else started. NeMo-RL talks to it over HTTP and sends weights straight to its GPUs over NCCL.
Status
New feature, in review. The design holds up and the wire format matches vLLM 0.29.0. One small open issue shows in the figure (orange): each refit pauses the server twice. Other asks, such as checking max_model_len against the server at startup, are in the review comments.
Background. In RL training, the trainer updates the model and the inference server (here vLLM) generates the next rollouts. After every step the trainer must copy its new weights into the server; that copy is the refit. Both paths below do it over NCCL, the GPU-to-GPU network library: trainer GPUs and server GPUs join one group, and the trainer broadcasts. Dotted words have a short explanation: hover or tap them.

The two paths share the whole trainer side. Both call the same policy.init_collective and policy.broadcast_weights_for_collective, so the Megatron-to-HF conversion and the broadcast are the same code. They split on the receiving side. The managed path tells its own vLLM workers to receive through Ray calls into NeMo-RL code (CollectiveWeightSynchronizer). The external path cannot run NeMo-RL code inside the server, so it uses vLLM's own weight-transfer API over HTTP (RemoteVllmNcclWeightSynchronizer).

Packing ruleNeMo-RL's defaultvLLM's rule, including tensors bigger than one buffer

LimitsAny policy backend; colocated or notMegatron policy, Gym rollouts, one deployment, no quant_cfg, no draft weights, no fleet health

Why keep both? The managed path is simpler to run and can recover from a failed refit. The external path lets you scale, upgrade or place the server on its own, and keep its software stack apart from the training stack, in exchange for a stricter, stop-on-failure refit.

The small open issue. SingleController already pauses the server with your recompute_kv_cache_after_weight_updates setting and resumes it afterwards (single_controller.py:5519). The new synchronizer pauses a second time with clear_cache=true hard-coded. In vLLM 0.29.0 that drops the cached state of every request in flight (core.py:842), so setting it to false does nothing: every request in flight is computed again after each refit. That costs speed, not correctness, and the default (true) only pays two extra HTTP calls. The fix is to delete the synchronizer's own pause and resume, as the managed path does.

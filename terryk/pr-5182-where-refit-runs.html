What changes when the refit runs in its own Ray actor

NVIDIA-NeMo/RL #5182 · adds async_rl.refit_actor.enabled · all permalinks pin the PR head 9d350e7f.

Before
The single controller runs the whole refit itself: a thread in its process calls every train worker and every generation leader, then waits for all of them.
This PR
With the flag on, the same refit code runs in a separate 1-CPU Ray actor. The controller keeps a stand-in that forwards each call and only waits for the answer.
After review
Proposed in the pending review, not done yet: a dead refit actor stops the run with a clear error (C1, page 2); the actor uses public members instead of the transports' private fields (C2); tests for the new wait path, and shorter docstrings (C3–C5).
Status
New, off by default, under review. One open bug in it is on the next page.

Two pages on this PR — this one: what the new path is and where it joins the old one.

Background. A refit copies new weights from the trainer to the vLLM engines after each step. In the single controller, one process also dispatches rollouts, finishes groups and computes advantages. The PR's motivation: on big runs a busy controller slowed the refit, and a slow refit tied up a controller thread. Dotted words have a short explanation: hover or tap them.

Two paths, one transfer

Both lanes end in the same sync_weights of the same two NCCL transports. What differs is the process it runs in and how the controller waits: today a controller thread blocks on the workers; with the flag, the controller awaits one answer from the actor on its event loop. The stand-in class is RemoteWeightSynchronizer; it is built at setup, right after the first refit (setup.py), so setup itself is unchanged.

Where it applies

async_rl: refit_actor: enabled: true # default false policy: generation: colocated: enabled: false # required: a colocated refit is the engine waking itself up
RunUses it?
v1 loops (grpo.py, ppo.py, distillation)No. They build their own synchronizer and never read async_rl.
v2 single controller, non-colocated, NCCL transport (collective or nccl_reshard)Yes, when the flag is on.
v2, colocatedRejected when the config is checked (config.py).
v2, any other refit transportRejected at setup, after the workers are up (setup.py).
So what. In the author's one-run-each test (16 train + 12 vLLM GPUs, 7 refits), total refit time went from 18.5 s to 13.1 s (1.41×), and every refit was faster. At that size refit is under 1% of step time, so the flag is meant for large runs where the controller is busy. It is off by default, so today's runs do not change. The one thing to check before turning it on is what happens if the actor itself dies — see page 2.

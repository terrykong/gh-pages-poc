Background. In NeMo RL, a training step asks the NemoGym actor to run a batch of prompts. The actor calls a Gym agent's /run once per prompt, and each /run talks to one of several vLLM engines. Results stream back to the driver one row at a time. Dotted words have a short explanation: hover or tap them.

The PR changes two places. In the actor, it asks Gym's collector for a failure row instead of an exception (route_failures_to_sidecar=True), classifies it with _typed_gym_failure, and streams a one-key marker row in place of the result (L1166-L1179). A 4xx that describes the request itself still raises at once. In the driver, _merge_nemo_gym_instance_streams sees the marker and starts a new one-row stream for that prompt on the same actor.

Two places now retry a failed row, with two different knobs

The single-controller path already had a row-level retry loop: it re-sends any row of a prompt group that did not come back. This PR feeds the same marker into that loop. Each cell shows the three states: main today, PR at head, and review once the proposed changes are applied.

Changes proposed in the review (C = comment number). Each item is tagged with the path it changes. None of these blocks the feature. The review is not posted yet; comment links work for others once it is.
  • v1C7: one name for one setting. Rename the v1 setting to max_row_attempts, default 3, to match v2, and say in the doc that v1 has no group-level retry above it.
  • v1C8: check the setting at setup, not at the first rollout after vLLM and Gym have started.
  • v1C12: don't throw away other actors' work. With a budget of 1 and more than one Gym actor, the first failed row cancels every stream, so groups that finished on healthy actors never reach the buffer. Main kept draining them.
  • v2C13, for the maintainer to decide: on v2, re-send a failed row at once instead of after its stream ends, so a group with one failure doesn't finish later than it did on main. See failure rows on both paths.
  • v1+v2C1: the metric reads differently on the two paths. 10 rows sent again across 64 prompt groups logs 10 on v1 sync and about 0.16 on v2; v1 async is also diluted. Fix in shared code: sum this key in aggregate_rollout_metrics, as total_turns is. That fixes v2 and v1 async.

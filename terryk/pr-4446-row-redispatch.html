What happens to a training step when one NeMo-Gym rollout hits a dead engine

NVIDIA-NeMo/RL #4446 (typed /run failure rows and bounded re-dispatch). Permalinks pin the PR head 8fecfa2; old code is linked at the merge base 8338530.

what #4446 does use the single controller

Two pages on this PR, one question each. This one: what the PR changes.

Before
One failed /run (say, a 503 from a dead vLLM engine) ended its whole actor stream. The rollouts still running on that stream were thrown away, and the step failed.
This PR
NeMo-Gym hands back the failed rollout as a data row. The other rollouts keep running, and only the failed one is sent again, up to a set number of tries.
Status
New feature, in review. Off by default: max_infra_attempts_per_rollout defaults to 1, which keeps today's "one failure ends the step". The review found no blocking bug, but asks for 4 follow-up changes (listed at the end).
Background. In NeMo RL, a training step asks the NemoGym actor to run a batch of prompts. The actor calls a Gym agent's /run once per prompt, and each /run talks to one of several vLLM engines. Results stream back to the driver one row at a time. Dotted words have a short explanation: hover or tap them.

The PR changes two places. In the actor, it asks Gym's collector for a failure row instead of an exception (route_failures_to_sidecar=True), classifies it with _typed_gym_failure, and streams a one-key marker row in place of the result (L1166-L1179). A 4xx that describes the request itself still raises at once. In the driver, _merge_nemo_gym_instance_streams sees the marker and starts a new one-row stream for that prompt on the same actor.

One batch, one dead engine: before and after

Two places now retry a failed row, with two different knobs

The single-controller path already had a row-level retry loop: it re-sends any row of a prompt group that did not come back. This PR feeds the same marker into that loop. Both paths read the marker from the same actor method, then split on when they re-send.

What the review asks the author to change. None of these blocks the feature. Each has a review comment (the links work for others once the review is published).
  • The metric reads differently on the two paths. 10 rows sent again across 64 prompt groups logs 10 on the driver path and about 0.16 on the single controller. Fix: sum this key in aggregate_rollout_metrics, as total_turns is.

    review comment — rollout_manager.py:1487

  • The design doc's note on refused connections is out of date. The Gym version this PR now pins caps those retries when route_around_failing_endpoints is on, which is the setting the doc recommends.

    review comment — nemo-gym-integration.md:52

  • A retry can go back to the same dead engine. When Gym's rollout tracking is on (observability_enabled), Gym picks the engine from the rollout id, and the retry sends the same id. Fix: send a copy of the row with _ng_attempt_index set, as Gym's own retry does.

    review comment — rollouts.py:1949

  • No test checks the copied Gym key names against real Gym. Renaming Gym's status key leaves all 16 failure-row tests green. Fix: one nemo_gym-lane test that builds the row with Gym's own _agent_request_failure_row.

    review comment — nemo_gym.py:319

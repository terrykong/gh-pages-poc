How a checkpoint copies a running vLLM call's tokens without stopping it

Explainer for NVIDIA-NeMo/RL #4506. RL permalinks pin the PR head d33e3628, vLLM links pin the v0.29 commit the repo uses (98dff2a8), and Gym links pin 5911d628. The token ids and logprobs in the example are made up, to show the shape.

Before
Turn-level recovery only. Nothing reads a call while it is still decoding. After a crash, the call starts again from the start of its turn.
This PR
Adds a second HTTP route on each vLLM worker. During a checkpoint, Gym calls it to copy the tokens each running call has decoded so far into TQ. After a restore, the call continues from those tokens.

Six pages on this PR, one question each. This one covers where the decoded tokens live, how the checkpoint copies them, and what happens to the running call.

Background. By default, vLLM v0.29 runs in two processes. The engine core holds the scheduler, the model and the KV cache on the GPU. The front end runs inside the NeMo-RL worker process, next to its OpenAI-style HTTP server. After every decode step, the engine core sends the front end only the new token ids and their logprobs. The front end appends them to plain Python lists, one set per request. It needs those lists anyway to build the final chat response. A generation cut is this PR's name for copying those lists during a checkpoint. Dotted words have a short explanation: hover or tap them.

Where the tokens live, and how the cut copies them

You never reach into GPU memory. The cut reads the front end's per-request lists, in the worker's own process. Each request's state holds detokenizer.token_ids, a growing list[int] that vLLM extends at every step (output_processor.py:621-704, detokenizer.py:36-43). It also holds the matching logprobs. So yes, it works much like streaming: the lists grow by one entry per step, and the cut copies however many entries exist right now. To copy them safely from another thread, the worker wraps vLLM's process_outputs in a lock (enable_generation_progress_reads). The cut takes that same lock, so it always sees whole decode steps. The worker finds which vLLM request belongs to which Gym call through a map it fills when the chat request is submitted (vllm_worker_async.py:578-582).

Step by step, for one call (chat-A) with a 7-token prompt, max_tokens 20, and 5 tokens decoded when the checkpoint arrives:

  1. ① Each step, the engine core sends chat-A's one new token id and its logprobs. The front end appends them under the lock.
  2. Gym's checkpoint lists the calls still running and POSTs that list to each worker (Gym model.py:1018-1040). This is a separate HTTP request from the chat call. The worker runs it on a one-thread pool of its own (generation_cut_capture.py:615-625).
  3. ③ The cut takes the lock and copies token_ids[0:5] for every listed call in one pass (read_generation_progress). So all calls are read at the same step boundary. The cut waits for at most one batch of outputs. The code comment measures 1-4 ms this way, against a 52 ms median when the read was queued on vLLM's own event loop.
  4. ④ After it lets go of the lock, the cut reads logprobs for those 5 positions only. vLLM only ever appends to these lists, so positions it has already published do not change.
  5. ⑤ The cut writes the tokens past the last cut as one chunk to TQ (freeze, stage_generation_prefix). It replies to Gym with the TQ key and the count, 5.

Reading another thread's lists like this is only safe on the exact vLLM release it was checked on, with the GIL turned on. The worker refuses to start otherwise (vllm_worker_async.py:634-646).

So each chunk in TQ is just two short lists, token ids and one logprob per token, plus a mask that marks them as generated. No GPU state is saved.

What happens to the running call, and after a restore

If nothing crashes, the cut changed nothing. The chat call never knew it happened. It finishes, and its normal final row goes to TQ. The cut's chunks are then out of date, and the worker deletes them. Nothing is swapped back in, because nothing was taken out: the cut only made a copy.

If the run crashes, the KV cache is lost with the process. After the restore, Gym sends the same call again, with a note naming the saved TQ chunks. The worker fetches them and checks their hash (_resolve_generation_cut). It then adds the 5 tokens to the end of the prompt and lowers the output limit by 5 (vllm_worker_async.py:2219-2256):

The reply is then fixed up so Gym sees what an uninterrupted call would have returned. The usage moves the 5 prefix tokens from the prompt count back to the completion count, so it reads prompt 7 rather than 12 (_count_restored_prefix_as_completion). The training row joins the 5 saved logprobs with the new tail's logprobs. A setting that cannot carry over to the restored call skips the cut for that call, and it decodes again from its turn (_generation_cut_blockers). Examples are stop strings, multi-token bad words, presence or frequency penalties, and a seed.

So what. The cut is a read-only copy of two Python lists that vLLM already keeps in the worker process. It does not pause or change the running call, and it never reads GPU memory. The costs are a few milliseconds holding vLLM's output lock, a dependency on vLLM's private OutputProcessor fields (pinned to one release), and one prefill of the saved tokens after a restore.

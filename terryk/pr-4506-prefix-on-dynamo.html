Six pages on this PR, one question each. This one: what #4506 and #4979 each need so the two work together.

Two facts make this smaller than it looks. First, in #4979 the "Dynamo worker" is the same NeMo-RL vLLM worker Ray actor: Dynamo's Rust worker runs inside it and calls DynamoVllmAdapter._serve_gym_call, which generates through the same _AsyncLLMHTTPClient (adapter.py:450). So the token lists the cut reads, and the TQ writer it uses, are where #4506 expects them. Second, each worker still starts its own HTTP server when Dynamo is on (vllm_worker_async.py:644), so the cut route has somewhere to land. What does move is the restore splice: in #4979 the token ids are built in the frontend, before the KV router picks a worker, so a cut must be spliced there.

Where each piece lives, without and with Dynamo

The same checkpoint behind Dynamo

The controller side does not change. The write hold (①, ⑫) is a Ray call to the same worker actors, and Gym's prepare, commit and resume do not involve the chat path. Only the cut (⑤–⑧) and the restore (R4–R7) change. The step numbers match the checkpoint sequence page, and the example is the same: chat-A, 7 prompt tokens, max_tokens 20, 5 tokens decoded at ckpt-9.

Why ⑤ fails. Gym sends the cut to the base URL the call went to (generation_cut_requester). Behind Dynamo that is the frontend, and Dynamo 1.5.1 lets Python add only GET routes with no body (frontend_routes.rs). Gym already has the escape hatch: generation_cut_control_url gives one control URL per base URL (app.py:375, :598). Behind Dynamo there is one base URL but M workers, and only the KV router knows which worker holds chat-A. So the control URL has to be a small fan-out that posts the inventory to every worker and merges the receipts. Merging is simple because a worker that never saw a call says so ("no_capture_or_completed_state"), and the merge keeps the one ack that is not that. No Gym change is needed.

Turn recovery is the smaller case. Every turn step is also a prefix step, and turn recovery never calls the worker during a save. It needs what #4979 already carries: the ng_capture admission, one TQ write per call, the commit coordinates in the reply, and a failed capture when a call is dropped (adapter.py:375). So once prefix works behind Dynamo, turn works too. The reverse does not hold. Still, no Dynamo test runs either level.

For #4506, which lands first: move the restore logic out of the native chat-server closure into plain module functions that take values, not worker_self:

  • One function plans the splice: prompt ids, cut, max_tokens, min_tokens in; new prompt ids, new limits and the saved tokens out (from L2219–2256).
  • One function fixes the reply: saved text in front, and usage counted as completion (wrapping _detokenize_restored_prefix and _count_restored_prefix_as_completion).
  • _resolve_generation_cut splits in two. One half fetches the chunks and needs only a TQ reader. The other half checks the weight version and needs the worker.

#4979 deletes that closure and moves the chat server to chat_server.py, so the second PR must move this code anyway. With plain functions, that move is a few calls instead of a copy.

For #4979, after the rebase: add the cut fan-out. Call the two functions from _splice and respond. Pass the cut to _begin_request_capture, and report outputs in the adapter. Then add a turn-recovery run and a prefix-recovery run behind Dynamo to the validation runs already asked for in its review comment C43. The prefix run passes only if its restored-prefix count is above zero, because a cut that silently fails falls back to the turn path and still looks green.

So what. Nothing in #4506's controller or Gym steps has to change for Dynamo. The work is on the chat path:
  • a fan-out so the cut request reaches the workers;
  • the splice and reply fix as plain functions, so the frontend can call them;
  • two missing calls in the adapter.
Asking #4506 for the plain functions now is the cheap moment. After it lands, #4979 would have to pull that code apart from inside a closure it deletes.

Two pages on this PR. This one: why cooker options break, and the fix.

Energon stores facts about a cooker as attributes on the function object. @stateless sets __stateless__ = True, and Energon reads it back with getattr(fn, "__stateless__", False). When a file-backed cooker has options, the PR wraps it in a new object, partial(cooker_function, **options). A partial object does not copy the function's attributes, so the mark is gone, and Energon's check before every cook (base.py:421) fails.

What Energon sees, with and without options

The fix: copy the function's attributes onto the wrapper

Where the fix lands: RL only, one function. _task_encoder in sft_dataloader.py, plus its import. No Energon change: Energon's check is right; the wrapper just has to carry the mark.

update_wrapper copies the function's __dict__ onto the partial, which is where __stateless__ and __cooker_need_cache__ live. Checked: the wrapped partial reports __stateless__ = True and __cooker_need_cache__ = True, and calling it returns "P:hi". With the fix applied to a copy of the PR, the same plugin cooks the sample instead of raising. The review also asks for a test that builds _task_encoder with a file-backed @stateless cooker plus options and calls cook_crude_sample, since the only options test today checks config parsing.

So what. Passing settings to your own cooker is the main reason to give it options, and today that stops training at the first batch with an error that points at Energon, not at the YAML. Cookers without options are not affected. The fix is one wrapper call; please take it in this PR so the plugin feature ships working.

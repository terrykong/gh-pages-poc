When a restart runs, what it waits for, and how a shard re-enters

Companion illustration for NVIDIA-NeMo/RL #3592. Permalinks pin the PR head 5b4a732.

Four pages on this PR, one question each — this one: the order things happen in.

Short answer up front: the restart itself is fully asynchronous and is queued behind nothing. It starts on the next fleet-health tick after the shard is marked DEAD, and it runs on a thread, so training and generation carry on underneath it. What is queued is everything after the engine comes back: re-entering the collective waits for the next refit, and on the NeMo-Gym path taking traffic again waits for one more fleet-health tick after that. On the default path — native Ray calls, no router — traffic resumes the moment the refit promotes it.

Every timeline below uses the same run: 4 generation shards, shard 2 dies, with the shipped defaults probe_interval_s: 5, unhealthy_threshold: 3 and refit_timeout_s: 300. Time axes are not to scale — a model reload takes minutes while a probe takes milliseconds — so each tick is labelled.

The four loops, and where a restart actually runs

The SingleController runs four asyncio tasks on one event loop. One loop means they never truly run at the same instant — they take turns, handing control over at each await. Anything that would block for a long time is pushed onto a thread so the other three keep their turns. Note what that does and does not buy: moving work to a thread keeps the loop free, but the task that awaits that work is still stuck until it finishes.

"On a thread" and "asynchronous" are not the same thing, and the two boxes on the right differ exactly there. Both the restart and the weight transfer are pushed off the loop, so neither freezes the other three pumps. But the weight transfer is awaited by the train pump: the refit is step 6 of a training step, right after step 5 trains the policy, and the pump cannot start the next step until it returns. So the weight transfer is synchronous with respect to the train pump — it is moved off the loop to protect the watchdog and the probe, not to let training run ahead of it. The restart is the opposite: it is started and then nobody waits for it at all.

Two more things worth stating plainly. First, nothing takes a lock: there is no mutual exclusion between a restart and a refit, and no queue that one waits in for the other. Second, generation is not paused during a refit on this path: nothing waits for in-flight rollouts to finish before weights start being written, and the code marks adding that as a known TODO.

Two ways a shard is marked DEAD, and why they take different times

Before any restart can start, the shard has to reach DEAD. How long that takes depends on how it failed, and the difference is large.

How it failsWhat the probe seesTime to DEADWhy
Crash — the process is gone RayActorError one probe, so ≤ 5s Ray only reports this once the process is really gone, so it is conclusive. It goes straight to DEAD with no threshold.
Hang — alive but not answering timeout three probes, so ≈ 15s A timeout is ambiguous — it could be a blip. It counts one failure, so the shard sits in SUSPECT until unhealthy_threshold is reached.

A crash also does one extra thing, and it needs a sentence of background first. Every refit arms a timer inside each trainer worker. If the weight transfer has not finished within refit_timeout_s (300s by default), that timer breaks the NCCL communicator so the trainers stop waiting on a rank that is never going to answer. It is the safety net for a generation shard that goes silent mid-transfer.

On a confirmed death, the controller cancels that timer — the code calls this "standing the deadline down". Cancelling the safety net sounds backwards, so here is why it is right. A process that has genuinely died closes its sockets, and NCCL sees that and unblocks the survivors by itself, which is the clean way out. If the timer fired first it would break the communicator instead, and breaking it strands GPU work already queued on the trainers' own streams — leaving their devices in a state no rebuild can use. So on a confirmed death, doing nothing is strictly better than intervening.

A frozen-but-alive rank never produces a confirmed death, so its timer is never cancelled and still fires. That is the case the timer exists for.

A detail that surprises people: the probe only walks serving_shards(), which is HEALTHY plus SUSPECT. So a shard is not probed while it is DEAD, RESTARTING or STALE. That is deliberate for the first two, but it does mean a freshly restarted STALE shard is unwatched in the window between its engine coming up and the refit that promotes it.

Scenario A — it dies between refits

The common case, and the one the feature is built for. Shard 2 crashes while the run is generating. Nothing is mid-collective, so nothing is stuck.

Two things about the right-hand end. First, the refit step is not reloading anything — the model was loaded from disk minutes earlier, during the restart. What the refit does is rebuild the NCCL group so it includes shard 2 again, and then send it the current weights. That is why the shard has to wait for a refit at all: it has a model, but the wrong version of it.

Second, the shard becomes HEALTHY at the end of that refit, when _promote_refit_shards runs — not at the start. The little gap after it is a real wait, and whether it costs you anything depends on how rollouts are routed:

So your guess about the router was right, but only for the Gym path — and that push matters there for a specific reason: the restarted engine binds a new port, so without it Gym keeps talking to a socket nobody is listening on.

Scenario B — it dies during a refit

Now the timing is different, because the trainers are inside a collective that needs every rank. This is where the refit deadline earns its keep.

What exactly is retried: the weight transfer, and nothing else. Not the request, not the training step, not the whole refit from the top. The controller calls _sync_weights_within(kv_scales, "first"), and when that raises it runs the recovery and then calls the same function again with "retry" — the same weights, in the same training step, over a communicator that has been rebuilt without the dead shard. The two labels are only there to tell the attempts apart in the logs.

The recovery in between does three things, in this order (_recover_from_failed_refit):

  1. Probe every shard immediately, instead of waiting for the 5s tick, so the membership is a lookup rather than a race.
  2. If the failure was an abort, mark the surviving shards STALE (mark_weights_partial). An abort stops a transfer mid-flight, so every engine that was receiving holds a mix of old and new weights — none of them may serve until a transfer finishes. This is the part that surprises people: a hang in one shard briefly takes the whole fleet out of service.
  3. Rebuild the communicator without the dead shard. If nothing is absent but exactly one shard is already SUSPECT, that one is condemned as the silent participant and the rebuild is redone — with several suspects, or none, it gives up rather than guess and condemn a healthy shard.

Notice how far apart two of those moments are. With the defaults the ledger marks shard 2 DEAD after three failed probes — about 15 seconds. The trainers stay blocked for the full refit_timeout_s, 300 seconds, because nothing connects the ledger's verdict to an in-flight collective. Knowing a shard is dead does not interrupt a transfer that is already waiting on it. The only thing that ends the wait early is a confirmed process death, and that does the opposite — it cancels the deadline so NCCL can unblock the survivors by itself. So a hang costs the full 300s; a crash costs seconds.

"But those shards are healthy — why are they STALE?" They are healthy. That is the point: STALE is not a verdict about the process.

Every other state describes the process — HEALTHY and SUSPECT are answering or not, DEAD and RESTARTING and RETIRED are gone or coming back. STALE describes the weights. An abort cuts a transfer off mid-flight, so every engine that was receiving holds a mix of old and new weights. Generating rollouts from a half-updated model is silently wrong, which is worse than generating nothing. The mark_weights_partial docstring puts it in one line:

"STALE rather than DEAD: the process is alive and refits normally, it just must not serve until a refit completes."

So the same state means one thing — this engine's weights are not the current ones — and it is reached two ways: a restarted engine holding what it loaded from disk, or a survivor holding a half-finished transfer. Both are cured by the same event, a completed refit, which is why both sit in the group (so the refit can reach them) and out of the serving set (so nothing reads from them meanwhile).

One nicety worth knowing: the ledger remembers what the shard was before it went stale. Without that, a shard that was SUSPECT would come back as HEALTHY and the recovery would quietly erase the failure count — which is the only counter that can condemn a wedged engine that still answers probes.

Then the second attempt runs, and on success _promote_refit_shards puts the survivors back into service. Once only — a second failure is treated as a real fault rather than a membership problem, and the run ends.

And the answer to the original question: the restart is not queued behind any of this. Once shard 2 reaches DEAD, the next probe tick starts its restart on a thread, and the second attempt at the transfer proceeds over the surviving shards at the same time. A RESTARTING shard counts as absent, so the rebuild correctly leaves it out.

One case does not recover. On the nccl_reshard transport, a fault while the bulk transfer is in flight cannot be recovered in-process: aborting the communicator does not retire CUDA work already queued on the trainers' own streams, so no rebuild can bootstrap on those devices. The run detects this and ends in seconds with a named cause rather than wedging. On the collective transport the same fault recovers.

Scenario C — it finishes restarting during a refit

The third case is the one that falls out of everything above: the restart takes minutes and the loop is free the whole time, so a restart can finish at any point — including in the middle of a refit, after that refit has already decided who is in the group.

refit starts membership settled as {0,1,3} — shard 2 is RESTARTING, so absent | | ...weight transfer in flight, the loop is free... | +-- restart finishes -> mark_loaded -> shard 2 becomes STALE | refit ends promote every STALE shard -> shard 2 becomes HEALTHY

Shard 2 is promoted by a refit it was never part of, and so has never received weights. The promotion step _promote_refit_shards promotes every shard that is STALE when it runs, with no check that the shard took part. Until this PR nothing could turn a shard STALE mid-refit, so that held.

This is a live bug, raised in review and not yet fixed. The shard serves one step of rollouts generated from the checkpoint it loaded off disk, mixed into the training batch with nothing marking it. It self-corrects at the next refit, so the damage is bounded to one step — but it is silent, and the metric meant to catch it is written by the same call, so it reports a healthy-looking weight version. The fix is to promote only the shards the refit actually wrote to.

So: is the restart synchronous with anything? No. It is started from the fleet-health tick and immediately handed to a thread, and nothing waits on it — not the refit, not training, not generation. The supervisor's tick() returns as soon as it has started the work, and a shard already being restarted is skipped on later ticks so a slow reload cannot pile up.

The waiting is all on the way back in, and it is deliberate: a restarted engine holds whatever weights it loaded from disk, so it must sit out until a refit gives it current ones. That is what STALE means — in the group, so the refit reaches it, but not in the serving set.

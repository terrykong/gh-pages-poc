Does the new “status below 400 means infrastructure” rule change what the single controller retries? Mostly no. One case flips.

NVIDIA-NeMo/RL #4446 · permalinks at head 8fecfa2, removed code at the merge base 8338530, Gym at ad4f480

Before
When Gym's /run reply broke after a 200 status, Gym raised the error itself. A cut body or a dropped connection reached RL as its own type and counted as an infrastructure failure. A 200 reply whose body was not valid JSON counted as a data failure.
This PR
Gym now returns a failure row that records the reply's status, which is 200 for all three. RL counts any failed request with a status below 400 as infrastructure.
Status
In this PR, and it changes the single controller too. Cut bodies and dropped connections: no change, because the rule is what keeps them infrastructure. A 200 reply that is not JSON: data → infrastructure.
what the PR does use the single controller failure rows on both paths the <400 rule

Four pages on this PR, one question each. This one covers the status-below-400 rule.

Every failed rollout goes into one of two buckets. Infrastructure means the prompt is fine but something broke on the way. It gets a large budget of retries with waits in between. Data means the prompt itself is bad. It gets a small budget. Both the single controller and the v1 loop use one function to choose the bucket: classify_rollout_failure. Dotted words have a short explanation: hover over them or tap them.

The PR has Gym return a failed /run as a row instead of raising, so one bad row no longer ends the whole stream. Gym fills in that row's status from the error. When the error has no status, it uses the reply's status line instead (rollout_collection.py L3729-L3731). A reply that broke while its body was being read therefore arrives with status 200. Under the old rule, 200 is not 5xx, so all of these would have turned into data failures. The new rule (http_status_is_infra) counts them as infrastructure. The rule lives in shared code, so the single controller follows it too.

The change, and why it is needed

Where it lands: RL only, one line. failures.py · http_status_is_infra. Two places call it. The Gym actor calls it to type each failure row (_typed_gym_failure), on both paths. Every single-controller retry loop also calls it through _is_infra. No Gym change: Gym already records the reply's status on the row.

@@ failures.py L202 (merge base) → L205 (head) · http_status_is_infra
-    return status >= 500 or status in _RETRIABLE_HTTP_STATUSES
+    # A failed request whose status says success: the reply broke mid-body.
+    return status < 400 or status >= 500 or status in _RETRIABLE_HTTP_STATUSES

Without this line, the PR's switch to failure rows would turn every cut body into a data failure. Data failures get 2 tries and then stop the run. That would be a regression, so the rule is needed. It only changes the bucket for one kind of failure: a body that arrives in full but is not valid JSON. Gym parses it with orjson.loads, and the old path raised that error as a ValueError, which counts as data.

Only Gym hits this rule. A status below 400 reaches the classifier only through a Gym failure row. Every other HTTP client in RL raises only on statuses of 400 and up (_http_status reads statuses only from aiohttp response errors). v1 loop: at the default budget of 1 dispatch per row, a changed failure still ends the rollout. It now ends with GymTransportError from record_infra_failure instead of a RuntimeError raised after the other streams finish.

Timing: which training step gets the group

A retried group arrives later. Where it ends up depends on the sampler:

  • in_order (the default, config.py L481) stamps each prompt with the step it is for. A step takes only the groups stamped for it (staleness_sampler.py L689). A slow retry makes its step wait. It does not move the group to a different step.
  • ready_first and weight_fifo fill a step from whatever is ready (ready_first, weight_fifo). With them, a group that now retries for longer can end up in a later step than it would have before.
What this means for the single controller
  1. No change for a cut body or a dropped connection. The rule keeps their old behavior once Gym returns rows. This also means the rule does not remove a bias against long replies, because cut bodies were already retried before.
  2. One real change: a 200 reply that is not JSON used to get 2 group tries. It now gets up to 15 sends with waits in between. With the drop budget from the suggested single-controller config, that prompt is dropped and replaced instead of stopping the run.
  3. How often this happens was not measured. If it is a real agent bug, it fails every time, so it now uses up the bigger budget before it stops. That decision belongs to the maintainer.

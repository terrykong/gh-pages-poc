Before

step number on every span async_save is always true

Two pages on this PR, one question each. This one: the async_save tag bug.

The tag is set from whether the caller passed a wait function: async_save=wait_fn is not None. But every training loop passes one on every save, sync or async (e.g. grpo.py:4125; all 12 callers do the same). With async save off, that function does nothing, but it is still not None. The PR's test for the sync case (test_checkpoint_spans.py:196) passes no wait function at all, which no real caller does.

The same tag for two different saves

The tag answers "was a function passed", which is always yes. So a short finalize span still cannot be read as "sync save" or "async save that had already finished", which is the question the tag was added for (span-groups.md:130).

The fix — proposed, not in the PR

Where the fix lands: RL only. Nothing below is implemented. Remove the tag. The real setting lives in two backend-specific places (Megatron's checkpoint.async_save, Automodel's is_async), and passing it through all 12 save sites only to label a span costs more than the tag is worth. The same change also deletes the constant at instrumentation.py:101, the docs row, and the sync-case test.

🔴 review comment — checkpoint.py:489

The finalize span itself stays. Its duration is still the time from staging to "resumable", and a reader who needs the save mode can read it from the run config.

So what. Nothing breaks in training. But every dashboard that splits checkpoint time by rl.checkpoint.async_save puts all sync saves in the async bucket, so the one question the tag exists for gets the wrong answer, quietly.

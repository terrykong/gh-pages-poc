Is this a good design?

What is clean

  • Calls go one way: controller → three objects → Gym. Nothing below calls up into the controller. It reads the controller's step counters through one callback, read_progress().
  • The saver and the restorer never call each other. They share only RolloutParts, and the only thing in it they change is RolloutRuntimeState.
  • All Gym-specific checkpoint code now sits behind one object. The do-nothing backend replaces the old "is Gym present?" checks in the controller.
  • The controller's whole contact with checkpointing is 15 calls in 6 of its methods.

What to watch

  • C2: two Protocol classes describe the environment object, but only Gym implements them, and the do-nothing backend doesn't use them. Naming the two real classes is enough.
  • C5: GymEnvironmentSnapshot.check_against_cut only calls back into its parent's validate_cut. That is the one arrow that points back up.
  • C3: the controller's setup code (L713–L749) is copied by hand into a test helper. Both copies must be edited together.
  • Gym is four hops deep: environment object → coordinator → Ray actor → adapter. Only the first hop is new. The other three came with #4500, so this PR is not the place to merge them.
  • The recovery ledger is the shared hub: the restorer, the saver and the Gym object all read it, and it lives in RolloutManager.
So what. The split is sound, and it is the right shape to build the next 10 PRs on. The extra pieces are small and each has a review comment. None of them changes behavior, so they can be fixed in this PR before later PRs copy the pattern.

What happens when a refit goes wrong while generation is frozen

NVIDIA-NeMo/RL #3929 · all links pinned at c877a8e2

1 · stale KV across a refit 2 · when the refit fails

Two pages on this PR, one question each — this one: what the failure paths do.

This PR freezes every in-flight generation request while the new weights are copied in, then unfreezes it. Page 1 covers why that is the right thing to do. This page is about the other half: the freeze is a piece of state living on remote engine processes, and the code that sets it does not guarantee it is ever cleared. Three separate ways out of one span of code skip the unfreeze.

One span, three exits

Exit 2 is the one worth pausing on. The recovery inside the try exists to survive a generation shard dying around refit time — its own docstring says letting that escape once "killed a run whose data transfer had already succeeded." But the pause is the first thing that talks to the engines, and it sits above the try. A shard that dies during the pause raises there, uncaught, and the recovery built for exactly that failure never runs.

the recovery and its docstring · the bare ray.get in pause · "the last unbounded wait on the refit path"

Nothing reaps a request that stays frozen

A frozen request is not cancelled — it is kept, to be continued later. If its engine is never resumed, what stops it waiting forever? The natural answer is the 900-second per-generation limit, NRL_VLLM_ASYNC_TIMEOUT_SECONDS. That limit does not apply, and the reason is the line above it:

sample_result_ref = await anext(worker_gen_proxy) # no timeout sample_result = await asyncio.wait_for(sample_result_ref, timeout=900)

vllm_generation.py:1068-1082

In Ray 2.56.1 — the version this repo resolves to — anext waits for the value with no limit, and fetches it before returning. Ray's own source says so, with a # TODO(swang): Avoid fetching the value sitting on the line. By the time wait_for runs, the value is already in local memory, so it returns at once. The 900s budget covers a sliver, not a frozen request.

The two limits that would catch it are both off unless an operator sets them:

generation_timeout_s = None · rollout_timeout_s = None

There is a second way to reach a permanently frozen engine, and it does not need the run to fail at all. When a shard stops answering the refit, the fleet can mark it dead while its process is still alive. That drops it from the group the resume talks to, so the resume skips it — and its requests stay frozen on a live engine that nothing will ever wake. This needs generation_fleet_health.enabled: true, which is off by default.

marking a live shard dead · the resume only talks to the current group

What would fix it

Two changes, and they have to go together. Bounding the pause where it stands would raise a timeout outside the try, which still ends the run; moving it inside without a bound still hangs. So: move the pause inside the try so a dying shard reaches the existing recovery, and give it the same deadline the refit already has.

try: await self._call_gen_within(self._gen.pause_generation_for_refit, clear_cache=clear_cache) # bounded, like the refit await self._sync_weights_within(kv_scales, "first") except (RefitAborted, RayActorError) as failure: ... # probe, rebuild, retry once finally: await self._resume_best_effort() # never leave engines frozen

One caveat on that finally, because the obvious version is worse than nothing. On the branch where the refit lost the trainers' CUDA contexts, the run is ending on purpose — a resume that hangs there just adds a second unbounded wait on the way out. Whatever goes in the finally has to be bounded, best-effort, and must not replace the original error.

the branch that ends the run on purpose

What this means in practice. With the shipped defaults these paths end the run, so a frozen engine dies with the process and costs nothing. They start to matter when you turn on generation_fleet_health.enabled — which is exactly the setting you turn on because you want a refit failure to be survivable. That is the case where a shard can be dropped while alive and left frozen, and where the pause sitting outside the try removes the recovery you enabled it for. If you run with fleet health on, also set generation_timeout_s or rollout_timeout_s, so a request that gets stranded is eventually reaped instead of waiting forever.

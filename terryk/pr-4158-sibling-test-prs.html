#3469
Fixed by #4158. It reports that dynamic sampling splits a prompt group when leave-one-out makes one rollout's std exactly zero. The whole-group mask added in #4158 keeps all four rollouts in both of its failing cases.
#3467
Not fixed, and not the same bug. It reports that a response whose tokens are fully masked still counts in the per-prompt baseline. #4158 does not touch that path, and its four cases still fail on the branch.

Recommendation for each

#3469 — close it, but keep its cases. The bug it reports is fixed by #4158, and #4158 currently has no regression test for either of its two failing shapes. Its three parametrized cases (single-success, single-failure, balanced) are exactly the right coverage for the new whole-group mask. Fold those cases into #4158 rewritten against the current config API, rather than merging #3469 as-is — its end-to-end grpo_train harness is where all three API drifts live, and a direct test of the mask function is both cheaper and less likely to rot.

#3467 — keep it open, but retarget it. The concern is real: on every path except SingleController, a fully-masked response still moves the baseline for its peers. But the test blames the estimator, and the estimator is fine — it has a valid_mask parameter that produces the expected numbers. The fix belongs at the call sites, so the test should assert that grpo.py passes a valid mask derived from the sample mask, not that the estimator guesses it from the token mask. Do not fold this into #4158: different layer, different fix, and #4158 is already carrying two changes.

The thing worth acting on first. Both tests were written to fail on purpose and then left open, and in that time all four of the APIs they touch moved. A deliberately-red draft that nobody merges quietly stops describing the code it was written against — #3467 now fails for a constructor signature, which looks identical from CI to failing for the bug it documents. If a red draft is worth keeping, it is worth a note saying which commit it was red against.

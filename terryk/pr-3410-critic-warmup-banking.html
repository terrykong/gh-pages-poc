Async PPO: training stops waiting for generation — and what that needed for critic warmup

Companion illustration for NVIDIA-NeMo/RL #3410. All permalinks pin the PR head bac4a8c.

PPO already worked in NeMo-RL, in two placements: generation sharing the training GPUs (colocated, the default) or generation on its own GPUs (non-colocated). Both ran the same schedule — generate a batch, train on it, generate the next — because generation happens inside the training step (ppo.py:1404), so with separate GPUs the two sets take turns and each sits idle while the other works. This PR adds a third mode, async_ppo_train, where rollouts are produced without stopping on one set of GPUs while the policy and value models train on the other. It runs non-colocated only (run_ppo.py:67), so the picture below compares it against sync non-colocated — the like-for-like baseline; colocated PPO is untouched by this PR. Most parts are reused from async GRPO — the replay buffer, weight versioning, in-flight weight updates — but one idea is genuinely new, and the rest of this page is about it: what to do while the critic warms up.

The new idea: banking rollouts while the critic warms up

Every rollout is tagged with the policy weight version that made it, and the trainer refuses any rollout older than max_trajectory_age_steps versions (default 1) — replay_buffer.py:225. PPO can start with critic warmup: for the first policy_training_start_step steps only the value model trains and the policy is frozen. A frozen policy means those rollouts are not really going stale, so you would like to run further ahead and pile up more of them. This PR adds one knob for that, warmup_max_trajectory_age_steps. There is no knob for the cut-off — it is worked out from the two you already set, policy_training_start_step + max_trajectory_age_steps (ppo.py:2072), and it is enforced from both ends: the collector never generates a rollout aimed past it, and the age limit drops back to normal as soon as training goes past it. So three numbers drive the whole mechanism — policy_training_start_step, max_trajectory_age_steps, warmup_max_trajectory_age_steps — and nothing else.

Two numbers control the collector, and this PR is the first time they differ. Lead is how many future steps it may generate for. Age limit is how old a rollout may be and still be accepted. Everywhere else in the codebase they are the same number.

The four rows, in plain words. Hover a row label for more.
  • batch used — the version number of the policy that produced this step's batch. This counter goes up every single step, even while the policy is frozen and not changing at all.
  • its real weights — the model actually behind that version. The policy does not train until step 3, so v0, v1, v2 and v3 are all the same weights W0. A batch labelled v2 is not stale; it came from the same model as v0.
  • version gap — step − version. This is all the replay buffer can see; it has no idea the policy was frozen. Anything above the limit is thrown away. That is what W changes: it raises the throw-away line during warmup so these still-good batches are kept.
  • updates behind — how many times the policy really trained in between. Not a running total — it is this batch's staleness. It never exceeds 1, whatever W you choose.
The whole idea: the version counter says a batch is old, the weights say it is not. W lets you keep it.

The two numbers, computed

Both are small pure functions in ppo.py, and they are the two ends of the cut-off — the first limits what gets made, the second limits what gets used. Each is called once at startup and again after every weight update, then pushed to the collector with set_generation_window(). Same numbers as the figure: P=3, A=1, W=2.

lead(step) # how many future steps may I generate for? if step >= P: return A # policy is training -> normal lead # still in warmup: run ahead, but never past step P+A return max(A, min(W, (P + A) - step)) step 0 -> max(1, min(2, 4-0)) = 2 # generate for steps 0, 1 AND 2 <- the banking step 1 -> max(1, min(2, 4-1)) = 2 # W is the binding one here, not the frontier step 3 -> 1 # step >= P, back to normal # W is a request, (P + A) - step is the cap. The smaller one wins: # W=1 -> banks 2 steps W=2 -> 3 (drawn) W=3 -> 4 W>=4 -> 5, capped

age_limit(step) # how old may a rollout be and still be used? frontier = P + A # = 4 if P > 0 and step <= frontier: return W # keep the banked ones valid return A # back to normal steps 0..4 -> 2 # a 2-generation-old rollout is still accepted step 5 -> 1 # back to the normal limit

Does it work?

Yes for the mechanism, on a small real run. The functional test launches a 2-node Megatron job with the same shape at smaller settings — P=1, A=1, W=2, so its frontier is 1+1=2 — and checks the collector's own log lines. These are values printed by a running job, not a mocked assertion:

grep -q "Updated generation window: version=0, lead=2, max_age=2" run1.log grep -q "Updated generation window: version=1, lead=1, max_age=2" run1.log grep -q "Updated generation window: version=3, lead=1, max_age=1" run2.log # after restart

ppo_async_megatron.sh:71-72, 85 — run2 restarts from the run1 checkpoint, so it also proves the banked rollouts survive a resume.

For end-to-end quality, the PR reports 40-step runs — AutoModel on 1 node × 8 GPUs and Megatron on 2 nodes × 8 GPUs — that hit their reward and validation-accuracy gates, plus a matched sync-vs-async Megatron pair on the same node split showing no obvious regression. Curves are in the PR description.

The honest gap: those 40-step runs use policy_training_start_step: 0 — warmup is off. So the banking path drawn on this page is only covered by the 2-step + 4-step test above. Nobody has run warmup banking at convergence scale.

What to take away. The number that keeps this correct is the frontier, policy_training_start_step + max_trajectory_age_steps. Below it, generation-version age and policy-update age are different things, and only the second one matters; above it they are the same again. If you set warmup_max_trajectory_age_steps, note two things: it needs policy_training_start_step > 0 or the config is rejected at load, and the replay buffer grows to num_prompts_per_step × max(age, warmup_age) × 2 — so doubling the warmup age doubles the resident buffer.

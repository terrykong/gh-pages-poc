How async PPO banks extra rollouts while the critic warms up — without training on stale data

Companion illustration for NVIDIA-NeMo/RL #3410 (async PPO). All permalinks pin the PR head bac4a8c.

In async PPO, one set of GPUs generates rollouts while another set trains. Every rollout is tagged with the policy weight version that produced it, and the trainer refuses any rollout older than max_trajectory_age_steps versions (default 1) — replay_buffer.py:225. PPO can also start with critic warmup: for the first policy_training_start_step steps only the value model trains and the policy is frozen. A frozen policy means those rollouts are not really going stale, so you would like to generate more of them and get further ahead. This PR adds warmup_max_trajectory_age_steps to do exactly that — and a cap so the banked rollouts are never actually used too late.

Why running further ahead is safe while the policy is frozen

Two numbers control the collector, and this PR is the first time they differ. Lead is how many future steps it may generate for. Age limit is how old a rollout may be and still be accepted. Everywhere else in the codebase they are the same number.

Age filter: replay_buffer.py:225 · which steps the collector may generate for: trajectory_collector.py:188

The two numbers, computed

Both are small pure functions in ppo.py, called once at startup and again after every weight update, then pushed to the collector with set_generation_window(). Same numbers as the figure: P=1, A=1, W=2.

lead(step) # how many future steps may I generate for? if step >= P: return A # policy is training -> normal lead # still in warmup: run ahead, but never past step P+A return max(A, min(W, (P + A) - step)) step 0 -> max(1, min(2, 2-0)) = 2 # generate for steps 0, 1 AND 2 <- the banking step 1 -> 1 # P reached, back to normal

_async_ppo_generation_lead_steps — ppo.py:2045

age_limit(step) # how old may a rollout be and still be used? frontier = P + A # = 2 if P > 0 and step <= frontier: return W # keep the banked ones valid return A # back to normal steps 0,1,2 -> 2 # a v0 rollout is still accepted at step 2 step 3 -> 1 # v0 is now 3 generations old -> dropped

_async_ppo_buffer_max_age — ppo.py:2064 (the step <= frontier comparison on line 2073 is what keeps step 2 valid)

Does it work?

Yes for the mechanism, on a small real run. The functional test launches a 2-node Megatron job with exactly the config above, then checks the collector's own log lines for the three windows — so these are values from a running job, not a mocked assertion:

grep -q "Updated generation window: version=0, lead=2, max_age=2" run1.log grep -q "Updated generation window: version=1, lead=1, max_age=2" run1.log grep -q "Updated generation window: version=3, lead=1, max_age=1" run2.log # after restart

ppo_async_megatron.sh:71-72, 85 — run2 restarts from the run1 checkpoint, so it also proves the banked rollouts survive a resume.

For end-to-end quality, the PR reports 40-step runs — AutoModel on 1 node × 8 GPUs and Megatron on 2 nodes × 8 GPUs — that hit their reward and validation-accuracy gates, plus a matched sync-vs-async Megatron pair on the same node split showing no obvious regression. Curves are in the PR description.

The honest gap: those 40-step runs use policy_training_start_step: 0 — warmup is off. So the banking path drawn on this page is only covered by the 2-step + 4-step test above. Nobody has run warmup banking at convergence scale.

What to take away. The number that keeps this correct is the frontier, policy_training_start_step + max_trajectory_age_steps. Below it, generation-version age and policy-update age are different things, and only the second one matters; above it they are the same again. If you set warmup_max_trajectory_age_steps, note two things: it needs policy_training_start_step > 0 or the config is rejected at load, and the replay buffer grows to num_prompts_per_step × max(age, warmup_age) × 2 — so doubling the warmup age doubles the resident buffer.

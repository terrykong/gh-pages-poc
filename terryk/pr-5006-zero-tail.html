Why the new "zero tail" rule switches off part of score centering even when replay is off

NVIDIA-NeMo/RL #5006, head 77d3b094. Raised first by a reviewer in this thread.

Before
#4818's estimator scales the trainer's tail by ρ = sampler tail ÷ trainer tail, with the trainer tail clamped at 1e-6.
This PR
Sets ρ = 0 whenever the trainer tail is at most 1e-6 (score_centering.py L74-L81), for every caller, replay or not.
Status
Open — not fixed in this PR. The review adds a +1 with numbers and the fix (comment C2). The gradient only matters for replay-off runs where the trainer is very sure and the sampler is not.

Three pages on this PR, one question each. This one: what the new ρ = 0 rule does outside replay.

Background. Score centering adds a correction built from vLLM's captured top-K list. Tokens outside the list (the "tail") are unseen, so their share is estimated as ρ · p: the trainer's own tail probabilities, scaled so the total matches vLLM's missing mass. Under replay the list holds every token vLLM could sample, so there is no tail. There, any ρ gives the same gradient; only the logged loss value changes (with #4818's formula it can jump from −1.42 to +140), which is why the author set it to 0.

The same token, either side of 1e-6

The reviewer's example, replay off: the trainer gives p = 0.6, 0.4 − t, t to three tokens; vLLM gives q = 0.5, 0.3, 0.2 and captured only the first two (K = 2). The tail token holds 0.2 of vLLM's mass. Values computed on CPU with the base and head versions of the function.

  1. The right gradient on the tail token is about qtail − ptail = 0.2 at every t.
  2. #4818 gets close and fades smoothly as t shrinks (0.18 at t = 9e-7), because of its 1e-6 clamp.
  3. This PR gives the full 0.2 at t = 1.1e-6 and nothing at t = 9e-7: the tail correction switches off. Under truncated IS the whole correction goes to about 0.

The fix — proposed in review comment C2, not in the PR

Where the fix lands: RL only. compute_score_centering_term gets a sampler_replay argument, passed by ClippedPGLossFn, which is built where the single controller already reads policy.generation (setup.py).

+    # Under replay the head holds all of p: rho cannot move the gradient, and a
+    # nonzero rho only inflates the logged loss. Elsewhere keep #4818's estimate.
+    rho = (
+        torch.zeros_like(head_mass)
+        if sampler_replay
+        else (1.0 - head_mass).clamp(min=0.0) / trainer_tail.clamp(min=1e-6)
+    )

The else branch is #4818's line (linked at the base, since this PR replaced it). Keep the PR's new slots mask, which stops 0 × −inf from becoming NaN. The PR's no-tail test feeds a list with no −inf slot, so it tests the replay-off case and needs a replay-shaped input; a new test pins the 0.2 gradient at t = 9e-7 and 2e-6.

So what. The rule is right for replay and wrong elsewhere. Tying it to the replay setting instead of to the trainer's tail size keeps replay's logged loss clean and gives plain score centering back the tail gradient it had in #4818.

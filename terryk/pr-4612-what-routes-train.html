Three pages on this PR — this one: what the feature does, compared with a run that never restarted.

Background. In an MoE model each token goes to a few experts. Router replay saves vLLM's choice for every position as one route row. Row t is the experts used when token t was the input (trainer). Prefix recovery saves a running call's tokens at each checkpoint, so after a restart it resumes instead of starting over. Dotted words have a short explanation: hover or tap them.

At each cut, freeze_for_checkpoint stores the route rows for the new tokens next to them in the saved row. On resume, _generation_cut_route_extras checks and joins those pieces. vLLM then re-reads the saved tokens with the new weights, so it computes new routes for them too. When the call ends, _merge_generation_cut_routed_experts keeps the saved rows for the old tokens and the new rows for everything after them. From there the row goes through the same final save as any call.

Same call, three ways

The numbers come from the PR's own test, test_router_replay_survives_repeated_prefix_cuts_and_resume. It cuts after 12, 13, cuts again after 14, resumes, and generates 15. It asserts the final rows are [1, 2, 3, 4, 5, …].

Why keep the old rows instead of the resumed call's own

Using the resumed call's own routes (lane 2) would delete almost all of this PR. But tokens 12–14 were sampled with the old weights and routes, and their saved sampling probabilities come from that run. Training them with routes 92, 93 would make training's probabilities differ from the saved ones. Also, by default recompute_kv_cache_after_weight_updates is False. So a run that never restarts also keeps the old routes for tokens it already read, and uses new routes only after a weight update (lane 1). The PR reproduces that.

One thing does differ: after a restart, token 15 is sampled while reading 10…14 with the new weights, not from the old cache. Neither choice avoids that; it is the cost of resuming without a saved cache.

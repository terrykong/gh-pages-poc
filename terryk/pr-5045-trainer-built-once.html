Why the Megatron trainer was built twice at startup, and how a 20-second wait builds it once

NVIDIA-NeMo/RL #5045. All permalinks pin the PR head 586831d. Times are from the run in the PR description.

Before
On the NeMo-Gym + vLLM + separate-GPU path, the trainer started building before the dataset loaded. When the dataset then lowered max_num_steps, the finished trainer was shut down and built again: about 280 s lost.
This PR
The trainer build waits up to 20 s for the dataset. If it arrives, the trainer is built once with the right step count. If not, it falls back to the old behavior.
Status
Fixed by this PR for any dataset that loads in under 20 s. The review asks for small follow-ups (below); none blocks the fix.
Background. Megatron's learning-rate schedule needs the total number of training steps (train_iters) when the trainer is built, and a resume checks it against the saved schedule. That number is max_num_steps, capped at max_num_epochs × batches per epoch (_clamp_max_num_steps). The batch count is only known once the dataset is loaded. The example configs set max_num_steps: 1000000 and max_num_epochs: 1, so the cap almost always lowers the number. Dotted words have a short explanation: hover or tap them.

Three ways startup can go

Example from the PR: max_num_steps = 100, the dataset holds 12 steps per epoch, max_num_epochs = 1, so the trainer must be built with train_iters = 12. The load took 1.5 s and one trainer build takes about 280 s. Generation and Gym build in parallel in every lane and are not affected.

Scale: 1 px ≈ 0.83 s. The slow-load lane uses a made-up 50 s load to show the fallback.

The fix: hold the trainer back, wait at most 20 s, then submit

Where the fix lands: RL only, one function. setup.py · the build step of setup_single_controller, plus the constant _TRAINER_BUILD_DATASET_WAIT_S = 20.0. No config change.

In order: (1) a trainer that has a Megatron train_iters is left out of the first round of builds; (2) the dataset loads on its own thread while generation and Gym build; (3) if it finishes within 20 s, train_iters is set to the capped value (12) and the trainer is built once; (4) if not, the trainer starts with 100 and the existing rebuild check replaces it, as before. A trainer without Megatron never waits. (Print lines and comments are left out of the diff above.)

So what. Runs on this path that cap their step count by epochs, which includes every config built from the examples, now start training about 280 s sooner, and slow-loading datasets lose at most 20 s. The review's main ask: the new submit calls _build_trainer_and_value by name instead of build_tasks["trainer"]. Open PR #4914 swaps a CPU stand-in trainer into build_tasks["trainer"], so once both merge, its runs would quietly build the real Megatron trainer. The review also asks for two tests the new branch lacks, and for one startup time measured with the fix.

Four pages, one question each — this one: #3590 · the ledger.

The confusing part of this PR is that it looks like three watchers doing the same job. They are not. The GenerationFleetMonitor is a ledger — a plain-Python table of per-shard health that watches nothing by itself. Two things write facts into it: a probe loop that asks every serving vLLM shard "are you alive?" every 5 seconds (single_controller.py:718), and the generate path, which reports failures it hits on real requests (vllm_generation.py:910). Three things read it: the shard picker for the next request, the membership push to the NeMo-Gym router, and the watchdog. The watchdog is a different animal — it does not care about shards; it checks one number every 30 seconds (how long since any rollout finished?) and kills the run if the answer is "too long" (:715). On the NeMo-Gym path there is one more piece: a router actor that all Gym requests flow through. The ledger's serving set is pushed into it — at review time the router asked nothing and reported nothing back. The same map after the review fixes

Same layout, current head 5c9b813. Green marks what changed. Everything got renamed for what it watches (GenerationFleetHealth, gen fleet probe loop, stall watchdog, controller liveness watch, GenerationRouter), and one arrow is new: the router now counts the failures it sees on real traffic and the probe tick pulls those counts into the ledger — the router is no longer silent, and a wedged engine that passes every probe is condemned anyway.

One dead engine, step by step

Two shards, default settings: probe every 5 s, 3 failures to condemn, floor of 1 serving shard. Kill shard 1's engine at t=0.

twhat happensshard 1 statewho acted
5 sprobe fails (1 of 3)SUSPECT — still takes trafficprobe loop
~6 sa real request hits shard 1, fails, is retried on shard 0SUSPECT (2 of 3)generate path
10 sprobe fails (3 of 3) → quarantined, epoch 0→1DEADledger rule
10 s+picker skips shard 1; next 5 s tick pushes [shard0] to the Gym routerDEADreaders
30 s tickwatchdog publishes fleet/shards/dead=1; 1 serving ≥ floor → run continuesDEADwatchdog

If shard 0 also died, the watchdog's floor check would end the run with GenerationFleetExhausted — the failure names the cause. Without this PR, the only backstop is the stall watchdog noticing silence minutes later and saying RolloutStall — true, but it names the symptom. A restarted engine does not come back on its own: answering probes again proves nothing about its weights, so re-entry requires a completed weight sync (that machinery lands in parts 3–4 of the stack).

What to remember. The ledger never acts on its own — observers write it, readers consult it, and it is now named for that (GenerationFleetHealth, not "monitor"). The watchdog stays even with fleet health on, because it answers a question no per-shard probe can: is the run as a whole still making progress? The router is no longer a silent reader of pushes: it counts the failures only real traffic can reveal, and the probe tick pulls them into the ledger — see the wedge-quarantine page for that path in detail. And enabling the router without generation_fleet_health.enabled=true now warns at setup and disarms the router's reflex drop, instead of silently staying health-blind.

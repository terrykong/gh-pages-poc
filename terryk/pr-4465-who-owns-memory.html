Who owns Mooncake memory — and so who every checkpoint save has to wait on

Explainer for NVIDIA-NeMo/RL #4465 (faster Mooncake CPU-RDMA checkpoints). All permalinks pin the PR head 7847eeb.

Before
Every Mooncake process held data in its own RAM, including the vLLM serving workers. A save had to call all of them, and the vLLM ones answered late because they were busy serving rollouts.
This PR
vLLM workers stop holding data. An opt-in mode moves all data into small CPU-only "storage unit" actors, so no GPU process is called during a save.
Status
Works as described for the SingleController path. Open review items on a few combinations — see the last section.

Background. The data plane moves rollout rows between processes. With the mooncake_cpu backend, every process is a Mooncake client (it puts and gets rows over RDMA), and most are also an owner: a block of their RAM, the segment, holds rows. A checkpoint save writes each owner's rows to disk, so the save must call every owner and waits for the slowest. Dotted words have a short explanation: hover or tap them.

A process takes part in a save only if its segment is bigger than 0 (tq_mooncake_checkpoint.py:1390). So "who is on the save path" is just "who has a segment". The PR changes that in two steps. vLLM workers now attach with segment_size=0 (vllm_worker_async.py:559). And when mooncake_cpu.storage_unit_segment_size > 0, every client gets 0 (transfer_queue.py:859) and new MooncakeStorageUnit actors own all memory (mooncake_storage_unit.py:42). That is the same shape the simple backend already had with TransferQueue's SimpleStorageUnit.

The save code itself did not change. Both layouts run the same save: call every process with a segment (:1388-1391). The only difference is which processes have one. The simple backend gets the same node picker through simple.storage_unit_placement, which pins TransferQueue's own storage units to chosen nodes (transfer_queue.py:740).

What the review asks for

The design holds; a few combinations need a guard. These are in the review comments (the review is still pending, so its links work only for its author until it is published):
  • Megatron generation + token capture + storage units stops at setup with a TypeError: only vLLM accepts the new storage_segments argument.
  • Storage units outside the SingleController (run_grpo.py, SFT v2) leave no process owning memory, so every put fails with a Mooncake error that never mentions storage units.
  • One object over 2 GiB now fails. The old pool registered big payloads one at a time; Mooncake's pool rejects anything above max(4 × staging_buffer_size, local_buffer_size).
  • Per-node cost of a placement. The example configs set 2 units per node of the whole cluster, so placement: inference puts all of them on the vLLM nodes.

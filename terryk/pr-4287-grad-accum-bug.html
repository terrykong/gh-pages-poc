Three pages on this PR, one question each. This one covers whether false brings back a bug NeMo-RL fixed.

Gradient accumulation runs one training step as several small microbatches, adding their gradients before the optimizer steps. It is supposed to give the same answer as running the whole batch at once. It only does if every microbatch divides its loss by the token count of the whole step. If each one divides by its own token count instead, the answer depends on how the batch was split. That is the bug the linked post describes, and the reason NeMo-RL's loss-functions.md exists.

The PR's false mode hands Megatron each microbatch's local loss sum and local token count (train.py#L894). Megatron then divides by that local count and by the number of microbatches (schedules.py#L335-L341). That is "average of averages". The figure runs the same 7 tokens through both modes, split two different ways.

The blog, fact by fact, against false mode

What the blog saysfalse mode in this PR
Cross-entropy for a batch is the summed token loss divided by the number of trained tokens. Same loss per token (NLLLossFn), but each microbatch returns its own sum and its own token count (train.py#L894).
The bug: take each microbatch's own mean, then scale by 1/G (G = accumulation steps). That is not the full-batch loss when microbatches hold different token counts. Megatron divides by the microbatch's own count, then by the number of microbatches (schedules.py#L335-L341). Same math as the bug.
Symptom: the loss changes with the accumulation setting; more accumulation steps gave a higher loss than full-batch training. The gradient changes with micro-batch size, and also with data-parallel and context-parallel size, because each rank's average is averaged again (the figure: 6 vs 4.71 for the same data).
The fix: compute the denominator for the whole step first, and divide every microbatch by it. That is true mode: every loss gets the step's token count, global_valid_toks (loss-functions.md). false turns it off.

So is the PR bringing the bug back?

Answer
Is false the same math as the bug?Yes. It is the "average of averages" the linked post shows, and the example loss-functions.md calls "in general, not equivalent to the full-batch loss".
Does the PR remove the fix?No. true still divides by the step's token count, unchanged.
Why add false at all?It is Megatron-LM's default. The author wants an SFT run that can be compared directly with a Megatron-LM run. That is a real use, but only as an opt-in.
Who gets false today?Anyone who sets it, and any config that leaves the key out: the latest push falls back to False (setup.py#L1942). An SFT config written before this PR would quietly go back to the old averaging. That is the part that turns an opt-in into a regression.

What the review asks — proposed, not in the PR

Where the fix lands: RL only. Make the key required again and set it to true in the example YAMLs, so nobody gets false without asking for it (the diff is on page 2). Then document what false costs next to the existing explanation in loss-functions.md.

So what. false mode does not compute the full-batch loss: it is the average-of-averages the blog calls a bug, and its gradient moves with micro-batch size and GPU count. It is Megatron-LM's default, so it is useful only as an explicit choice for a run that must match Megatron-LM. It must not be the default, and with the fallback in the latest push it is: a config that says nothing gets it.

Six pages, one question each — this one: what the author did with it.

Every comment was checked against the code at the new head, not against the commit messages. All 17 are addressed. Fourteen were fixed cleanly and need no reading. Three are worth your time: one was fixed by the route the comment explicitly asked the author not to take, one was fixed and then partly reverted after an experiment disproved it, and one was fixed better than the comment suggested.

The three worth reading

read this  #17 · Condemn a wedged shard instead of ending the run

single_controller.py:1576 · the comment · fixed in 1e4d5fc8c, then 2f762b8d8 reverted by 02b7dd0d6

The ask. On a refit abort where no shard is DEAD, the code raised and ended the run. The comment argued the ledger already knows the culprit — a wedged engine is sitting in SUSPECT from its timed-out generations — so condemn it, rebuild smaller, and retry.

What landed, and stayed. Exactly that, including the "exactly one suspect, or not at all" rule:

# the abort is independent evidence that something stopped participating;
# SUSPECT says which. Exactly one, or not at all.
suspects = self._gen_fleet.suspected_shards()
if len(suspects) == 1:
    culprit = suspects[0]
    ... "condemning it as the silent participant and retrying"

What was added on top, and then reverted. The author went further in 2f762b8d8 — actually ray.killing the written-off shard rather than just relabelling it. An experiment then disproved it, and it was reverted:

"job 6523731 is the disproof: ray.kill reached the victim before the rebuild was dispatched, in the right order, and both trainers wedged in init_nccl_communicator exactly as they had without it."

Why killing the shard cannot help. Aborting a communicator does not retire CUDA work already queued on a stream — and those orphaned kernels are on the trainers' devices, not the victim's. So nothing done to the remote rank retires them. A py-spy dump from job 6521181 shows both trainers inside init_nccl_communicator, threads still in ncclCommAbort 25 minutes later, unable to bootstrap a new communicator on a device holding a half-aborted one.

Where it leaves the behaviour — now split by transport, which is more precise than the comment had it:

TransportWedged-but-alive shard
packed broadcastrecovers — condemned by attribution, run continues
nccl_reshardrun ends attributably in <900 s — out of scope by design

The design said so before the comment was written, in sync_stream_within: "Recovering a frozen-but-alive rank on this transport stays out of scope." The comment stated the ask as universal; it was right for one transport and wrong for the other.

read this  #14 · Rank double-count at the initial build

vllm_backend.py:288 · the comment · fixed in 1847b135b

The ask. With expert_parallel_size > tensor_parallel_size, init_nccl_reshard_comm_group added the shard offset twice, putting the higher shards' NCCL ranks past the end of the group — at the initial build, before anything dies. The comment asked for the setup guard (comment #12) and said explicitly:

"Please do not fix this by routing :285 through resolve_rollout_rank. That helper decides 'am I in external DP?' by testing get_world_size() == rollout_world_size, and this PR is what made rollout_world_size change under it — so that route would fix the initial build and leave a quieter version of the same bug on the rebuild path."

What landed. That route:

gen_rank_in_group = train_ranks_per_stage + resolve_rollout_rank(...)

Why it is nonetheless safe today. Comment #12 also landed — check_nccl_reshard_refit_support is now called from setup_single_controller, and it rejects expert_parallel_size outside {1, tensor_parallel_size}. So external data parallelism cannot reach the reshard path on SingleController at all, and the branch that would flip never flips.

What to watch. The correctness now rests on the guard rather than on the arithmetic. If that precondition is ever relaxed — and the config check is a list of restrictions people do relax over time — the latent form of this bug returns on the rebuild path, where it is quieter than it was at setup. Worth a comment at the call site saying so, if you want it pinned.

read this  #10 · The split children are never aborted

stateless_process_group.py:133 · the comment · fixed in 1ce2cadc3

The ask. The Python reshard path splits the communicator per replica group and caches the children. NCCL gives a split child its own abort flag unless splitShare is set, and it defaults to 0 — so aborting the parent never reaches them. A rank blocked on a child is never released, the guarded block never returns, and __exit__ never runs. No exception-translation fix can reach a hang. The comment proposed calling the existing clear_xferdtensor_python_caches before the parent abort.

What landed — better than the ask. A new helper that aborts the children rather than running the cleanup path:

# Before the parent: once nccl_communicator is None the cache keys derived
# from it cannot be recovered, and the children would be stranded as well
# as un-aborted.
from nemo_rl.weight_sync.xferdtensor_python import (
    abort_xferdtensor_python_subcommunicators,
)
abort_xferdtensor_python_subcommunicators(self)

Abort is the right teardown here for the same reason the parent uses it — finalize/destroy are collectives a dead rank cannot join. The comment suggested the cleanup helper, which would have run that unsafe teardown. This is the better fix, and the docstring now carries the splitShare reasoning so the next reader does not have to rediscover it.

Where this leaves the PR

Two of the review's four critical findings — the abort escaping as the wrong exception type (#2) and the split children never being aborted (#10) — are fixed at the mechanism level, not patched at the call site. The recovery now has a real default (#16), a guard that runs on the path that needs it (#12), and a rule for attributing a silent participant (#17).

The one thing the review got wrong is worth recording: #17 was stated as universal and is only true for one transport. The author's experiment established that a wedged rank on the reshard path cannot be recovered at all, because the orphaned CUDA work is on the trainers' devices and nothing done to the remote rank retires it. That is a stronger result than the review asked for, and it came from implementing the ask and measuring it rather than arguing about it.

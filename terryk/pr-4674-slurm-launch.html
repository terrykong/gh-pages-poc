Seven pages on this stack, one question each. This one: how the processes start.

Background. A Slurm heterogeneous job asks for two node sets in one job. ray.sub does not know about groups. It reads the whole job's node list. Main already works around this in run_in_allocation.sh: it runs ray.sub with the node list cut down to group 0. Dotted words have a short explanation: hover or tap them.

The server needs nothing from the trainer to start: it loads the model from Hugging Face weights by itself. Everything else flows from one string, the server's URL. The trainer reads it from remote_vllm_cfg.base_url and hands it to Gym. The NCCL address goes the other way: the trainer picks its own node's IP and a free port, then tells vLLM to connect to it (init_communicator). The figure uses an 8-GPU trainer (2 nodes × 4) and one vLLM server with 2 GPUs (TP=2), so the NCCL group has 8 + 2 = 10 ranks.

Your questions, answered

  1. One vLLM container or two? One server process and one image are enough. Main's vllm extra already pins vLLM 0.29.0, and the image builds that vLLM env under /opt/ray_venvs. Group 1 can run the training image with that env's Python. Not run yet. The L1 test instead installs vLLM from PyPI each run. The vLLM server can still use TP/PP/DP across several GPUs inside that one process tree.
  2. Is ray.sub a heterogeneous job now? No. Nothing in the stack touches it. The natural shape is one sbatch with two groups: group 0 runs ray.sub unchanged (Ray, trainer, Gym), and group 1 runs vLLM. Main's judge-pool launcher already does exactly this for fixed judge models. It splits node lists, passes URLs through a placeholder in COMMAND, watches both sides, and shares teardown.
  3. Does one side have to start first? Both groups start together, and that's fine: vLLM needs nothing from the trainer to load. What matters is that the trainer's first call must wait until vLLM is up. Today it doesn't (red arrow 3). Only the test script waits, by polling /health 300 × 2 s.
  4. Who passes which address? The launcher passes the vLLM URL to the trainer (step 2). The trainer passes it to Gym (step 4). The trainer passes its own NCCL address to vLLM (step 5). In capture mode, the trainer also passes a bridge URL and a random token to the plugin (step 7). The API key is the odd one out: the trainer reads it from an env var, but nothing tells vLLM to start with the same --api-key. The launcher has to set both sides.

What would fix the gap — proposed, not in the PR

_wait_for_health retries connection errors until the deadline, then raises the same error as today. startup_timeout_s would be a new config field. The checks after /health stay one-shot, because once the server answers, a wrong version or world size will not fix itself.

So what. The feature works today only when a person starts vLLM first and waits. To run it as one Slurm job, add a wait to preflight, then reuse main's two-group launcher instead of writing a third one. Also open firewall paths from the vLLM nodes to the trainer nodes, because NCCL (and the #4676 bridge) connect in that direction. A failed refit leaves vLLM paused, and only a restart of both sides recovers it, so tying their lifetimes together in one job is the safer default.

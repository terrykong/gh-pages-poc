Why the logprob backward can write its grad into the logits, and when that is safe

NVIDIA-NeMo/RL #4776, commit 4a8997dba · all links pinned to head 96ec8a36

Before
The chunked logprob backward made a second tensor the full size of the logits to hold the grad. The PR estimates about 12 GiB for a 98k-token shard with an fp32 LM head.
This PR
A new opt-in flag, reuse_logits_storage, writes the grad into the logits' own memory, one chunk at a time. Only the fused packed loss turns it on.
Status
Correct on today's code: nothing else reads those logits after backward. The review agrees with moving this commit to its own PR and lists three asks for it (last section, proposed, not in the PR).

Three pages on this PR, one question each. This one: how the memory change works.

The policy loss needs the log-probability of each chosen token. ChunkedDistributedLogprob computes it in chunks of tokens to save memory, and saves the logits for backward. In backward, each chunk's grad is one_hot(target) − softmax(logits), scaled by the incoming grad. Before, every chunk was copied into a new zeros_like(logits). Now, when the flag is on, it is copied back into the logits. Each chunk is read before it is written, so the math does not change.

One buffer instead of two

Tiny example: [1, 6, 4] = [sequences, tokens, vocab on this GPU], fp32 logits, chunk size 2, so 3 chunks. The picture is backward, halfway through chunk 1.

Only fp32 logits qualify, because the grad is fp32. With bf16 logits the old path runs. No shipped config sets fp32_lm_head: true, so no recipe or nightly test reaches this code today.

Why it is safe today, and what would break it

After backward, the logits tensor holds the grad. Anything that reads it as logits later gets wrong numbers. If that reader saved the logits for its own backward, PyTorch raises "modified by an inplace operation". If it kept them some other way (a ctx attribute, .data), it reads the grad silently. The review checked every reader on the one path that turns the flag on:

Reader of the packed logitsAffected?
This logprob opReads each chunk before overwriting it.
Second logprob call for the unfiltered KL termNo. It runs only with top-k/top-p, which turns chunking off, so the reuse never runs. But the "sole consumer" comment is wrong.
Packed draft loss (speculative decoding head)No. It copies the logits with torch.roll during forward.
MTP loss, context-parallel gatherNo. They use hidden states and logprobs, not these logits.

A CPU check gave the same weight and input grads with the flag on and off, including the pre-packed view path and temperature scaling.

Where each GTP GPU gets its data: the layout NeMo-RL already had does it, and the PR's new axis breaks other calls

Explainer for NVIDIA-NeMo/RL #4512 (SFT processor config and GTP data placement). All permalinks pin the PR head 339e2020; Megatron-LM at b4d72b79.

Before
The driver laid GPUs out in 4 named axes (PP, DP, CP, TP) and did not count GTP in its world-size check.
This PR
Adds a fifth axis for GTP, plus code in the Energon loader planner and the SFT v2 train dispatch that sends one batch per (DP, GTP) pair.
Status
Open, not fixed in this PR. The fifth axis is not needed, and every call except SFT v2 training would skip two thirds of the GPUs. The review asks to keep the 4-D layout.

Two pages on this PR, one question each. This one: which GPUs get work.

Background. GTP splits each layer's weights across G more GPUs. Unlike tensor parallelism, every GPU in a GTP group trains on its own batch. The driver gives every call a layout: a grid of GPU numbers with named axes. A call names the axes it splits data over and the axes that get a copy. Any other axis only gets the call at index 0. Dotted words have a short explanation: hover or tap them.

Megatron numbers GPUs TP fastest, then CP, then GTP, then DP, then PP (parallel_state.py:602-618), and its data-parallel rank already counts GTP GPUs as separate lanes by default (parallel_state.py:2225-2231). So the old 4-D layout's data_parallel index for GPU (d, g) is d·G + g, which is exactly the lane the SFT loader already asks Megatron for (sft_worker.py:82) and the number the PR now computes by hand (topology.py:89). The PR's fifth axis gives the same lanes for SFT v2 training, but every other call still splits only data_parallel.

Both layouts number the same 6 lanes the same way

A lane here is a group of GPUs that trains on its own batch. With DP = 2 and GTP = 3 there are 6 lanes, and each lane is 4 GPUs (the TP group). Layout A gives each lane one number directly. Layout B gives it two coordinates, and the PR combines them into one number. The figure lines the numbering up per lane.

Why A already matches: Megatron numbers GPUs TP fastest, then GTP, then DP, so GPU r = t + 4·(g + 3·d). Reshaping 24 GPUs as (pp=1, -1, cp=1, tp=4) leaves r // 4 = 3·d + g on the middle axis, which is the same lane number B computes by hand. So splitting the producer's batches along A's data_parallel axis already sends batch k to lane k.

How SFT v2 feeds each lane: the loader never needs (dp, gtp).
  1. One loader per lane. SFT v2 builds a loader on every GPU with TP = CP = PP = 0: GPUs 0, 4, 8, 12, 16, 20, the same 6 GPUs in either layout (sft_v2.py:268-272).
  2. Each loader asks Megatron which lane it is. It calls get_data_parallel_rank() and get_data_parallel_world_size(), which count GTP by default, so the answers are 0..5 of 6. Energon reads shard k of 6 from that (sft_worker.py:82-83, unchanged by the PR).
  3. The driver collects the 6 batches in lane order. It already checks they come back as exactly 0..5 (sft_v2.py:300-305).
  4. The driver sends batch k to lane k. Before the PR: split on data_parallel (6 entries) (tq_policy.py:801-803, base). The PR: the same list reshaped into [[0,1,2],[3,4,5]] and split on (dp, gtp) (tq_policy.py:763-770). Same GPUs, same batches.
The only place G has to be known is Megatron itself (the PR's setup calls, which stay) and the driver's world-size check (page 2). The PR's (dp, gtp) code builds the pair from one number and turns it straight back into that number (topology.py:88-89).

Same 24 GPUs, two layouts, two kinds of call

In layout B the other calls see gtp_weight_remat as an axis they neither split nor copy, so only index 0 runs (worker_groups.py:1188-1196). The PR's only guard is on SFT v2 training (tq_policy.py:813-818).

What would fix it: proposed, not in the PR

Where the fix lands: RL only. Keep the 4-D layout in Policy.__init__; delete GTP_WEIGHT_REMAT_AXIS (named_sharding.py), the GTP loop in topology.py, and the GTP nesting and guard in tq_policy.py. Keep the GTP setup calls in setup.py. No Megatron change: Megatron's default data-parallel group already includes GTP.

So what. The PR's per-(DP, GTP) code only does what the old layout already did, and only for SFT v2 training. Every other call (logprobs, the older train path, scoring) would skip the GTP GPUs and wait forever. Keeping the 4-D layout makes all calls correct and deletes about 60 lines.

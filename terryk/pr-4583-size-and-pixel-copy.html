The pixel copy is only used to compare — proposed, not in the PR

At the first cut, the call's pixels are written to TQ (:1179-1182). On restore they are read back, compared byte for byte with the freshly processed image, and returned in place of the fresh copy (:1156-1169). By then the two are equal, so returning either one gives the same result. The final row writes the pixels again anyway (:1361-1365), and training reads media only from final rows (rollout_reassembler.py:512). A hash of the pixels does the same check without the copy.

Where the fix lands: RL only. vllm_worker_async.py (write the hash, compare it), captured_media.py (one pure hash helper, next to CapturedMedia), and deletions in tq_token_sink.py and generation_cut_capture.py. No Gym change: the hash rides in the same digest-covered extras dict that already carries media_spans.

+def media_tensor_sha256(tensors: dict[str, torch.Tensor] | None) -> str:
+    # Covers name, dtype and shape too, so it checks as much as torch.equal did.
+    h = hashlib.sha256()
+    for name in sorted(tensors or {}):
+        t = tensors[name].detach().cpu().contiguous()
+        h.update(f"{name}|{t.dtype}|{tuple(t.shape)}|".encode())
+        h.update(t.view(torch.uint8).numpy().tobytes())
+    return h.hexdigest()

So what. Each checkpoint writes every in-flight image call's pixels to TQ one extra time, one call after another, under the checkpoint's time limit. Calls the cut does not reach in time are thrown away and generated again, with only a warning in the log (generation_cut_capture.py:803-815). A hash removes that write, the second read on restore, and about 55 source lines. The check stays exactly as strict. In a stack this size, every step that stays small makes the next review easier.

Two pages on this PR — this one: what a shared-prefix batch looks like, step by step.

Background. In GRPO each prompt gets several sampled completions, called a group. Before a training step, the policy runs a forward pass over every row to get log probabilities, then trains on them. Rows are packed into forwards under a token budget, and the batch is split across data-parallel ranks. Dotted words have a short explanation: hover or tap them.

The example: 4 prompts (A–D, 80–120 tokens) with 3 completions each, 12 rows, 1655 tokens. Data-parallel size 2, token budget 600, no tensor or context parallelism. The figure is real planner output: the same calls the driver and worker make, run on these lengths.

The steps, with the example's data

  1. The rollout records where each prompt ends. One number per row, e.g. row A0 → 120. Group identity is the existing group tag. rollout_reassembler.py
  2. The trainer takes whole groups, in multiples of the rank count. 4 groups ÷ 2 ranks. num_prompts_per_step must divide by the rank count, or setup fails. single_controller.py
  3. The driver gives each rank whole groups, longest first, to the lightest rank. Group sizes A 460, C 425, B 395, D 375 → rank 0 gets A and D, rank 1 gets B and C. preshard.py → plan_group_coherent_shards
  4. Each rank packs its rows into bins using their full (unshared) length. This is the normal packer, so the forward count stays what dense would need: 2 per rank here. plan_dense_training_bins
  5. All ranks agree on the forward count in one all-reduce. If a rank has fewer forwards, real rows are split to make up the difference. No dummy rows are ever added. A planning error on one rank travels in the same all-reduce, so every rank raises. megatron_policy_worker.py
  6. Each bin is rebuilt as a forest: rows with the same group and identical prompt tokens become one star (at most 16 branches). If any row in a bin can't share, the whole bin runs dense, like rank 1's first forward. share_prefixes_in_dense_training_bins
  7. The model runs the forest. Each completion attends to its own prompt and its own earlier tokens, never to a sibling. train.py · model_forward → Megatron-LM attention
  8. Log probabilities are copied back into the usual [rows, S−1] tensor, and the GRPO loss runs unchanged. train.py · scatter → loss input

Source: PackedTreeLayout stores start, length and parent per node, and computes positions. Mamba layers copy the recurrent state at a chunk boundary inside the prompt into each branch, then replay the rest of the prompt per branch; see the Megatron-LM doc.

Where the two paths meet, and what still differs

Both paths end at the same loss: a [rows, S−1] log-probability tensor with the same masks and the same token counts. They differ before that point in three ways:

  • Which rank gets which rows: dense scatters a group, shared keeps it on one rank.
  • How many tokens each forward computes: 1255 instead of 1655 here.
  • How the numbers are added up: shared and dense are both valid arithmetic, but in BF16 their gradients are not bit-identical. The PR's design doc measures that difference and says it is still open.
So what. At the same budget, shared mode does the same number of forwards, each with fewer tokens (24% fewer here), because the budget still counts every row at full length. Raising the budget also cuts the number of forwards: at 3× (1800) this example becomes one forward per rank, 855 tokens instead of 1655. The PR's large-scale run changed both at once, so its speedup mixes the two effects. One thing can undo it: a failed-rollout placeholder row cannot share, and it makes its whole bin run dense.

Why setting quantization_ignore_patterns can silently corrupt the MoE router in an FP8 refit

NVIDIA-NeMo/RL #4122. NeMo-RL permalinks pin the PR head 6908199; TensorRT-LLM permalinks pin the version the repo builds, f94eeb3.

Before
There was no FP8 refit for TensorRT-LLM, so this could not happen.
This PR
Adds trtllm_cfg.quantization_ignore_patterns. When set, the worker decides on its own which incoming weights to send as FP8.
Status
Open — not fixed in this PR. Raised in the PR review. The default setup (no patterns) is not affected.
FP8 refit vs BF16 refit ignore patterns cast FP8 into BF16

Two pages on this PR, one question each — this one: what goes wrong when the user sets ignore patterns.

Two places decide whether a weight is FP8, and they must agree. The engine decides once, when it builds each layer. The refit worker decides again for every incoming tensor: once quantization_ignore_patterns is set, it sends every 2-D .weight the patterns do not match as FP8 plus a scale (_is_quantized_weight). But TensorRT-LLM builds the MoE router, shared_expert_gate and the MTP fc in BF16 no matter what the list says (router, gate). When FP8 bytes reach a BF16 weight, TensorRT-LLM copies them with a plain type cast and never reads the scale (self.weight.copy_, src.to(dst.dtype)). Nothing raises.

What would fix it — proposed, not in the PR

Where the fix lands: NeMo-RL only, one file, trtllm/quantization/fp8.py. No TensorRT-LLM change is needed, though it would help if its copy raised on an FP8 → BF16 cast.

Nothing below is implemented. With all three hunks, the PR's 23 FP8 unit tests still pass (CPU run), and the router stays BF16 in the example above. Not run on a GPU.

Hunk 1 keeps the modules TensorRT-LLM never quantizes out of the FP8 path. Hunk 2 matches names the way the engine does for Qwen3.5 (engine strips the prefix). Hunk 3 copies the engine's own .* rule (modeling_utils.py:277). A sturdier long-term rule is the one the vLLM path uses: look at the dtype of the engine weight each tensor lands in (vllm fp8.py:513), and fail at setup on any mismatch.

So what. With the default setup (no patterns), refit and engine agree for Qwen3.5 and Qwen3 MoE, so this only bites users who set quantization_ignore_patterns. But the docs suggest exactly that, and the result is rollouts from a broken router with no error anywhere. Until fixed, keep the router, gates and MTP fc in the list, written to match both model.layers.* and model.language_model.layers.*.

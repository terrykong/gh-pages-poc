How a trained weight reaches an SGLang engine — and what #3612 rebuilds

Companion illustration for NVIDIA-NeMo/RL #3612 (re-cut of #3190). All permalinks pinned to b86aa8e.

In RL training the trainer and the text generator hold two copies of the same model. After every training step the new weights have to be copied from the trainer into the generation engine. That copy is called a refit, and it happens once per step, so it sits directly on the critical path. NeMo-RL routes every refit through one class, a WeightSynchronizer, so the training loop never has to know which engine is on the other end. For SGLang that class existed, but the transport under it only covered one of the two ways NeMo-RL can train a model. This PR replaces it with two transports that cover both.

Before: SGLang refit worked for one policy backend only

NeMo-RL can train with two different policy backends: FSDP2 (also called DTensor) and Megatron. Before this PR, SGLang refit already moved the weights over CUDA IPC: the trainer and the engine share the same GPU memory, so no weight data is copied at all. HTTP carried only the short handles that say where that memory is — a few hundred bytes per chunk. The old function was called stream_weights_via_http, which names the message channel, not the weights. That path was fully wired for FSDP2, but the Megatron worker never implemented it, so a Megatron policy with SGLang rollouts hit NotImplementedError. Trainer and engines on separate GPUs raised too.

So the colocated change here is a swap of the message channel (HTTP → Ray), not a faster way to move weights. The two things that are genuinely new are Megatron support and a transport that works when the two sides do not share GPUs — CUDA IPC cannot cross that boundary, so that one has to send the real bytes, over NCCL.

What actually got called, before. One refit, colocated, FSDP2 policy. Note there is no pause and no update session — weights are swapped while the engine is live:

What one refit does now, and where a guard is missing

The new path adds three things the old one had no equivalent for: it stops the engine first, it drops the KV cache, and it wraps the transfer in an explicit update session. The last hop also changes from an HTTP POST to a Ray call — but as above, both only ever carried handles.

Read the two red markers together with the figure below: both calls sit above the try whose finally is supposed to undo them.

An SGLang engine cannot take new weights while it is generating text, and its cached attention values (the KV cache) belong to the old weights. So a refit is a small protocol: stop generating, throw away the cache, open a weight-update session, send the weights in chunks, close the session, start generating again. Six steps, and the last one has to run even when an earlier one fails — otherwise the engines stay stopped and the run hangs with nothing in the log explaining why.

Five of the six steps are wrapped correctly. The first one is not.

The fix is to move one line inside the block that already exists:

pause_mode = self._generation.pause_generation_mode - self._generation.pause_generation(mode=pause_mode) # a failure here skips the resume try: + self._generation.pause_generation(mode=pause_mode) ... finally: self._generation.continue_generation() # now reached on every path

The same shape appears once more, at sglang_weight_synchronizer.py:252: the call that gives the engine its weight buffers runs before the block whose finally restores the trainer's memory, so an out-of-memory error there leaves the trainer's weights parked on CPU.

Does it work?

Nobody has run this tree. That is stated in the PR description, and the CI run does not change it. The author asked for tests on this exact commit, and the run stopped before any test started:

So there is no number to report: no reward curve, no refit timing, no comparison against the vLLM path. Two things are worth asking for before this merges, and one of them is nearly free. The 1n8g SGLang recipe already existed on the old transport, so a reward curve on that recipe is a direct before-and-after on the same config. And the disaggregated NCCL path is a new transport, a new process group and a new recipe all at once, with no exercised evidence at all — a passing 450-step nightly on the 2-node recipe would be the first real signal that it works.

What to take away. The shape of this change is right: SGLang refit now goes through the same one class every other backend uses, and backend-specific code moved out of the training loop. But the three things bundled here carry very different risk. The colocated FSDP2 path is a message-channel swap on a mechanism that already ran in production. Megatron support and the non-colocated NCCL transport are new code, a new process group and a new recipe — with no run behind them. Get the lint errors cleared and the branch rebased first; that alone turns the existing nightlies into real evidence, and it is worth asking whether the non-colocated transport should land separately from the Megatron support.

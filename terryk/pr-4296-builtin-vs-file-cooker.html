Two pages on this PR. This one: how the new path compares to the old one. The PR's packing-config and loss-mask changes are covered in the review comments.

Background. NeMo-RL's SFTv2 reads data with Energon. A cooker turns one raw dataset row into a conversation (a list of messages). A task encoder then tokenizes and batches those conversations. Energon calls the cooker inside its loader workers, and it checks a mark on the function, @stateless, before each call. Dotted words have a short explanation: hover or tap them.

The YAML picks each cooker. A built-in one is a registry key, which LazyRegistry.resolve turns into an imported function. A file-backed one is a path: the registry checks it, hashes it, and runs the file as a fresh module (_file_details, _load_file_module). Both go through one method, resolve_configured, and both end up in the same Energon Cooker(...) object.

Two ways to pick a cooker, side by side

Where they meet, and what still differs

They become one at the Cooker(...) call in _task_encoder. After that, Energon cannot tell them apart. Two things still differ:

  • What a resume checks. A built-in cooker is pinned by its registry key and version. A file-backed one is pinned by path, name, and a sha256 of the file (of every .py under the folder when you point at an __init__.py), so a changed plugin fails at resume instead of silently running different code (_source_bytes).
  • Options. The built-in cooker takes none and refuses any at setup. A file-backed cooker gets its options bound with functools.partial, and that wrapper is where the new path breaks — page 2.

Why keep both. Built-in names cover the conversations NeMo-RL ships support for, and need no files on the cluster. The file path lets a team run its own model-specific cooker or task encoder without copying it into NeMo-RL. The cost is that the code lives outside the repo, so NeMo-RL only checks it at setup (absolute path, .py, readable, declares its model families) and pins it by hash. Energon starts its loader workers by forking (savable_loader.py:775), so the module loaded from the file is already there in each worker.

Three pages on this PR — this one: the one resume path that has no routes.

Background. Router replay saves which experts each token went to in an MoE model while vLLM generates. Training then forces the same experts. Prefix recovery saves the tokens a call has generated so far at each checkpoint (a "cut"). After a restart, the call resumes from them instead of starting over. Dotted words have a short explanation: hover or tap them.

A cut can land after vLLM has produced a call's last token but before the call's final row is saved. It can also land when the saved tokens already hit the output limit. On resume, _classify_restored_prefix_terminal sees this and skips decoding. _build_restored_prefix_terminal_output then builds a fake vLLM output with no routed_experts. With router replay on, the reply always goes through the route-attach step, and that step raises when there are no routes. The saved routes were fetched and checked, then never used.

What happens

Side effect: the generated_len == 0 case in the new merge, replace_len = restored.shape[0] if generated_len == 0 else …, is written for exactly this call, but the call never gets there. No test covers a finished resume with router replay on. A GPU run with router replay and a forced restart would have shown it.

The fix — proposed, not in the PR

Nothing below is implemented, and it has not been run.

Where the fix lands: RL only, one file, vllm_worker_async.py. No Gym change: the saved routes are already fetched and checked on resume. They only need to be handed to the fake output.

On the example: the fake output now carries [1, 2, 3, 4]. The route-attach step adds a -1 for the last position (same as every normal reply), giving [1, 2, 3, 4, -1]. That is exactly what the call would have saved if no restart had happened. The merge then has no special case left. A simpler fallback is to refuse the cut, so the call regenerates, when routes are on and the call is already finished. That works today only because the last token and its finish signal are recorded under one lock.

So what. This PR removes the setup check that kept these two features apart. Any MoE run with both on can now fail a resumed call this way. Gym uses a saved prefix only once (a used cut is not handed back), so nothing loops: the episode fails, and the prefix the checkpoint saved is wasted. The fix is about 15 lines plus one test, and it removes a special case from the merge.

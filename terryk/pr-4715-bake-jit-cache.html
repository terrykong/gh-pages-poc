Status
Proposed — not implemented. The review asks the author to rewrite the PR along the lines below. Nothing on this page exists in code yet.
Background. When a vLLM engine starts, it compiles the model with torch.compile (through Inductor and Triton) and captures CUDA graphs. That takes minutes on a large model. vLLM saves the result under VLLM_CACHE_ROOT in a folder named by a hash, the cache key. The key covers the model, the parallel layout, vLLM settings and the vLLM source files. The next start with the same key loads the saved result. The PR measured engine start going from 177 s to 40–55 s with a warm cache (on vLLM 0.25.1). Dotted words have a short explanation: hover or tap them.

Where the cache lives: shared filesystem vs. the image

The PR keeps the cache on a shared network filesystem and syncs it with every node (cache_sync.sh: copy in, write back every 60 s, a lock per folder, age rules). Many NeMo-RL deployments have no such filesystem: Kubernetes without a shared volume, or cloud runs that keep data in S3. On a large job it is also hard on the filesystem: at start, every node copies the whole cache file by file, so hundreds of nodes open the same small files at once. The repo's own large-model launcher reads one tarball per cache to avoid exactly that. The proposal keeps the same cache in the image instead. A GPU warms it once, the image build bakes it in, and every job copies it to local disk at start. Example below: one image baked for two models, then three different runs.

  1. On any machine with a GPU, warm.py starts vLLM through NeMo-RL's own worker once per profile, with dummy weights (the weights are not part of the key), and saves the cache plus a manifest.json. It then starts once more from the saved copy with VLLM_FORCE_AOT_LOAD=1, which errors on a miss, so a bad bake fails at build time. If the profile includes the trainer, warm.py also runs one training step (real checkpoint) and saves Megatron's Inductor and Triton caches under megatron/<profile>/.
  2. A tiny Dockerfile copies that folder into the same image that warmed it. Same image matters: the key includes the paths and contents of vLLM's traced source files.
  3. At job start, each vLLM worker looks for a profile whose manifest matches its own run. It copies only that one into its own writable cache folder. No match, or no folder at all (a normal image): nothing changes.

What the author would write

Where the fix lands: RL only. New: docker/Dockerfile.jit-cache, tools/jit_cache/{warm.py,bake.sh}, nemo_rl/utils/jit_cache.py, a small vLLM patch in patches.py, docs in docs/docker.md. Deleted: cache_sync.sh and the cache parts of run_in_allocation.sh. The Megatron trainer cache stays, as a second entry in the same design. docker/Dockerfile is not touched, so normal builds stay exactly as they are.

The bake step follows the empty-stage pattern docker/Dockerfile already uses for uv-cache-seed and custom-setup: an empty FROM scratch stage that --build-context replaces. S3 users download to a folder first, or push the cache as an image and pass docker-image://….

# syntax=docker/dockerfile:1
# docker/Dockerfile.jit-cache: adds baked caches to an image that already exists.
ARG NEMO_RL_IMAGE
# Empty unless the build passes --build-context jit-cache=<dir | docker-image://ref>
FROM scratch AS jit-cache
FROM ${NEMO_RL_IMAGE}
COPY --link --from=jit-cache / /opt/nemo_rl/jit_cache/

A profile is a NeMo-RL config plus overrides, so the warm-up builds vLLM exactly as training will. One command warms every profile and builds the image:

# profiles/qwen3-8b-tp2.yaml
backend: vllm
config: examples/configs/grpo_math_8B.yaml
overrides: [policy.generation.vllm_cfg.tensor_parallel_size=2]

# warm on a GPU host, then bake (the build itself needs no GPU)
tools/jit_cache/bake.sh --image nvcr.io/nvidia/nemo-rl:<tag> \
  --profile profiles/qwen3-8b-tp2.yaml --profile profiles/qwen3-0.6b-tp1.yaml \
  --tag <registry>/nemo-rl:<tag>-jit

The runtime check picks one profile, or none. It is generic: each backend lists which cache folders it owns, so SGLang can be added later as one more entry.

# env var -> folder inside a profile. SGLang would add its own entry.
BACKENDS = {
    "vllm":     {"VLLM_CACHE_ROOT": "vllm"},
    "megatron": {"TORCHINDUCTOR_CACHE_DIR": "inductor", "TRITON_CACHE_DIR": "triton"},
}

def restore(backend, run: dict, dest: dict[str, str]) -> str | None:
    root = Path(os.environ.get("NRL_JIT_CACHE_DIR", "")) / backend   # the image sets it
    if not root.is_dir():                      # plain image: nothing to do
        return None
    for prof in sorted(root.iterdir()):
        want = json.loads((prof / "manifest.json").read_text())["match"]
        diff = [k for k in want if want[k] != run.get(k)]
        if not diff:
            for var, sub in BACKENDS[backend].items():
                if not non_empty(dest[var]):   # launcher already filled it: leave it
                    copy_tree(prof / sub, dest[var])
            return prof.name
        log.info("JIT cache %s not used: %s differ", prof.name, diff)
    return None

# run = {"model_name": "Qwen/Qwen3-8B", "tp": 2, "pp": 1, "ep": 1,
#        "gpu_name": "NVIDIA GB200"}   # the manifest only picks what to copy;
#                                        # vLLM's own key still decides hit or miss

Two details the warm-up must get right. It must use the exact policy.model_name string of the real run, because the model path is part of vLLM's key. A local path and a Hugging Face id for the same weights are two different keys. And the engine should leave TRITON_CACHE_DIR unset, so Triton kernels land inside VLLM_CACHE_ROOT and get baked with it.

Why it cannot break another model or another user

SituationWhat happensWhy
Image built without --build-context jit-cacheNo changedocker/Dockerfile is untouched; restore() finds no folder.
Model not baked (Run 3)Compiles, as todayNo manifest matches, nothing is copied, a log line says which fields differed.
Big and small model, same imageBoth hitOne folder per profile; each run copies only its own.
Warmed on GB200, run on H100Compiles, as todayThe GPU name is in the manifest, and in vLLM's own key.
Image rebuilt with new codeCompiles, as todayThe cache lives inside the image that warmed it. A rebuilt image has none until it is baked again, and vLLM's key covers its source files anyway.
Launcher already filled the engine's cache folder (big-model scripts do)Launcher's files winrestore() only copies into an empty folder.
Trainer (Megatron) on the same nodesHitsIts own megatron/ profile and its own folders, set only in the trainer's worker; vLLM's folders are never shared with it.
Read-only image (Apptainer, enroot)HitsThe baked files are only read; vLLM writes to the per-engine copy on local disk.

Even when the manifest is wrong, the worst case is a slow start, not a wrong model: vLLM checks its own key, and a different key means it compiles.

One blocker for any shared cache, this PR's or the proposal's. vLLM 0.29.0's key includes VLLM_RAY_BUNDLE_INDICES, and it is not on the ignore list. NeMo-RL sets it per engine when TP×PP > 1: engine 1 gets "0,1", engine 2 gets "2,3". Two keys, so a cache warmed by one engine never hits the other. The value only picks GPUs, so it is safe to leave out of the key. vLLM fixed this upstream in vllm#61211, but no vLLM release has the fix yet. The PR description mentions a patch for this; the diff does not have it. The rewrite needs it in patches.py.

So what. Baking makes the cache work anywhere the image runs: Slurm, Kubernetes, cloud, with or without a shared filesystem. It also removes the rsync, the locks and the sidecars. The cost is one extra build step per image and some image size per profile. Most of the current diff goes away; the review comments only cover what carries over.

Two pages on this PR, one question each. This one: what runs where, and what each new process copies.

Background. A vLLM worker has two halves. The frontend is CPU work in Python: HTTP, chat template, processor, and NeMo RL's token capture. The engine core is always a separate process: AsyncLLM starts it and talks to it over local ZMQ sockets. It schedules requests and runs the model on the GPUs. With many Gym calls in flight, one Python frontend can be the limit while the GPUs still have room. Dotted words have a short explanation: hover or tap them.

Each column follows one Gym call through seven steps: ① receive the call, ② apply the chat template, ③ read the earlier tokens from TQ and splice them in, ④ pick a server, ⑤ turn images into pixels, ⑥ run the model and write the call to TQ, ⑦ reply. Dashed boxes are OS processes, and the boxes inside are the classes that run each step.

One Gym call, three setups

What each child copies, and what stays shared

Copied into each child (CPU only): the whole frontend half of VllmAsyncGenerationWorkerImpl. That is the uvicorn server and routes, the NeMoRLOnlineRenderer (template + processor), the capture code with its own TQ client, and an AsyncLLM client with its own client_index. The child calls the same methods as frontend 0, on an object built with __new__ instead of the worker's constructor (run_api_process). Not copied: the model weights, the GPUs, the engine core, refit, pause and sleep. Those stay with frontend 0 and act on the one engine core, so they also cover calls that came in through a child.

Why keep both

count = 1 adds no processes and no pipe, and works with every option. count > 1 is for runs where the frontend's CPU work is the limit: many parallel Gym calls, long templates, big prompts to tokenize. It costs CPU and host memory per frontend, not GPU memory. It needs async_engine and expose_http_server, vLLM's own data parallelism of 1, a refit that is not sparse, and fleet health off (config checks, docs).

So what. The GPU side does not change: one engine core, one batch, the same refit. The PR copies the frontend half of the worker into more processes, so the CPU work of many Gym calls runs in parallel. The review keeps that layout and changes two boxes: build the child through the worker class (C18), and make a failed pipe command stop only the children, not the engine core (C15, next page).

How several HTTP frontends share one vLLM engine, next to today's single frontend

NVIDIA-NeMo/RL #5074 · all links pinned to head 908f05fa · vLLM 0.29.0

Before
Each vLLM worker ran one HTTP server inside its Ray actor. That one Python process parsed every request from NeMo Gym, applied the chat template, and tokenized the request and the reply, for every request sent to that engine.
This PR
Adds vllm_cfg.http_api_server_count: N. The worker starts N−1 extra frontend processes. All N share one listening socket and send work to the same engine.
Status
New option, in review. The default is 1, which keeps the old path. Open review items are in the review comments on the PR.
one vs. many frontends a failed query stops the engine

Two pages on this PR, one question each. This one covers what the feature is and how it differs from the existing path.

Background. A vLLM engine has two halves. The frontend is CPU work in Python: HTTP, chat templates, turning text into token ids and back. The engine core is a separate process that schedules requests and runs the model on the GPUs. They talk over local ZMQ sockets. With many requests in flight, one Python frontend can become the limit while the GPUs still have room. Dotted words have a short explanation: hover or tap them.

With one frontend, the worker builds its client with AsyncLLM.from_engine_args, as before. With a count above 1, MultiAPIServerPool.create_engine starts the engine core itself, then attaches N clients to it: one inside the worker and N−1 in new spawned processes. This copies the steps of vLLM's own --api-server-count launcher. Each child gets the worker's already-listening socket, so NeMo Gym keeps one URL and the OS gives each new connection to one of the N processes.

Where they become one, and what still differs

The two paths merge at the engine core. With 3 frontends there is still one scheduler, one batch and one copy of the weights on the GPUs. Above that line, every frontend holds its own copy of some state, and the worker has to keep the copies the same.

Why keep both

count = 1 adds no processes and no pipes, and works with every option. count > 1 is for runs where the CPU work in the frontend is the limit: many parallel Gym requests, long chat templates, big prompts to tokenize. It costs CPU and host memory per frontend. It needs async_engine and expose_http_server, vLLM's own data parallelism of 1, a refit that is not sparse, and fleet health off (config checks, docs). The new nightly recipe runs 8 frontends per engine on 4 generation GPUs with TP = 2, so 2 engines and 16 frontends.

So what. The GPU side does not change: one engine, one batch, the same refit. The new parts are the extra frontend processes and the pipe that keeps their state in step with frontend 0. Review the pipe and the hand-built child setup most closely; the next page shows what happens when one pipe command fails.

Do refit or checkpoint saving need a GTP axis on the driver? No: both learn GTP from Megatron on each GPU

Explainer for NVIDIA-NeMo/RL #4512. NeMo-RL permalinks pin the PR head e3248a60; Megatron-Bridge at ec835530, Megatron-LM at b4d72b79 (the PR's pins). Read from the code; nothing here was run on a GPU.

Before
The driver lays GPUs out in 4 named axes (PP, DP, CP, TP). Refit and checkpoint save already go to every GPU.
This PR
Adds a fifth driver axis for GTP. It does not touch the refit or checkpoint code.
Status
Driver axis not needed. Neither refit nor checkpointing picks GPUs by a GTP axis. Two gaps are open, and neither is fixed in this PR: GTP refit exports the wrong weights, and a GTP checkpoint save will likely fail on one RNG entry. Both fixes belong in Megatron-Bridge, on the GPU side.

Three pages on this PR, one question each. This one: whether refit or checkpoint saving need the PR's GTP axis.

Background. GTP works like FSDP inside each TP slice. Each GPU keeps 1/G of its TP slice of a weight. Before a layer runs, the G GPUs in a GTP group all-gather the weight (gtp.py:1565), and after backward they reduce-scatter the gradients (gtp.py:2271). Each GPU in the group trains on its own batch. Refit is the copy of trained weights into vLLM. The driver decides which GPUs run a call. Megatron on each GPU knows its own TP and GTP rank. Dotted words have a short explanation: hover or tap them.

The example below uses TP = 2, G = 3 and one model copy, so 6 GPUs. Megatron numbers them TP fastest, then GTP: GPU r = t + 2·g (parallel_state.py:602). One weight W has 24 rows. TP splits the rows in half, and GTP splits each half in 3, so each GPU holds 4 rows (gtp.py:619). The driver sends all three calls that matter here to every GPU, without naming an axis.

Refit: vLLM needs no GTP support; Bridge must gather GTP first (fix proposed, not in the PR)

Every GPU runs Bridge's export_hf_weights (megatron_policy_worker.py:3372). Bridge hands the local weight to the mapping as-is (model_bridge.py:2459), and the mapping gathers over TP only. Bridge's only GTP code is training setup (training/gtp.py). vLLM never sees trainer slices: it receives full Hugging Face tensors and splits them for its own TP (vllm_backend.py:1615), so vLLM needs no GTP support. Once each GPU gathers its GTP group, every GTP peer holds the full TP slice and the rest of refit works unchanged.

Where the fix lands: Megatron-Bridge export, plus the same gather in NeMo-RL's NCCL-reshard refit path (megatron_policy_worker.py:3463, which ships local slices the same way). No driver change: refit already runs on every GPU, and it never picks senders by axis. The broadcast path sends from GPU 0, which is hard-coded (:3735).

Checkpoints: Megatron already writes GTP pieces; one RNG entry collides (fix proposed, not in the PR)

The driver sends save_checkpoint to every GPU (figure), and each GPU loads at start-up (sft_v2.py:579). Megatron describes each GTP weight piece by its place in the full weight, t·G + g of TP·G pieces, and marks model copies as replicas (utils.py:1130, gtp.py:2854). The optimizer reuses the same replica marks (distrib_optimizer.py:1804). The only state saved per data lane is the SFT loader. Its lane number comes from Megatron on the GPU (sft_worker.py:82). The owners are picked by skipping only TP, CP and PP copies (sft_v2.py:385), which gives r0, r2 and r4 under both the 4-axis and 5-axis layouts.

The gap is the RNG state. Bridge keys it by the data-parallel group without GTP (process_groups_config.py:274), so all 3 GTP peers write the same key as the main copy. Bridge already has a helper that fixes exactly this for weights (checkpointing.py:4085), but the RNG code does not use it. No test saves with GTP > 1: the PR has none, and Bridge's GTP functional test turns saving off (test_pretrain.py:202).

Where the fix lands: Megatron-Bridge, one function. get_rng_state should use _checkpoint_dp_cp_group. Stopgap in NeMo-RL: set save_rng=False when GTP > 1. NeMo-RL already loads with load_rng=False (setup.py:1985). No driver change.

In the example, the key's last coordinate becomes 0, 1 and 2 for r0, r2 and r4, so the 6 GPUs write 6 different RNG entries instead of 2 keys claimed 3 times each.

So what. The worry is reasonable, but neither refit nor checkpointing chooses GPUs by a GTP axis. Every GTP detail they need lives in Megatron on each GPU, so the driver can keep its 4-axis layout. The check did find two real gaps, both in Megatron-Bridge. Refit is out of SFT v2's reach and is blocked by C3. The RNG save is in SFT v2's path: a GTP run will likely fail at its first checkpoint, so ask whether the author's GTP runs ever saved one. Decide the layout before anyone saves: the loader's placement check includes the layout's axes (topology.py:114), so a checkpoint saved under one layout will not resume under the other.

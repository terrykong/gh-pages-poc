Why save_consolidated: true can hang training after the Automodel r0.6.0 bump

Companion illustration for a review comment on NVIDIA-NeMo/RL #3498. NeMo-RL permalinks pinned to 7b5e3a0f; Automodel permalinks to 94387e43.

Turning on save_consolidated asks Automodel to also write plain Hugging Face weight files at each checkpoint. Building those needs the GPUs to talk to each other. Automodel knows that traffic must not mix with training traffic, so it makes a separate channel just for it — but it decides whether to make that channel once, when the Checkpointer object is built. NeMo-RL builds that object before it knows the setting and fills the real value in later, so the separate channel is never made. The consolidation work then runs on the main training channel, from a background thread, while training is still using it.

Two threads, one channel, different order on each GPU

Two fair questions first, because the answer is not obvious.

Where does the training traffic come from? FSDP2, not from anything NeMo-RL writes. Every backward pass reduce-scatters gradients across GPUs, and every forward pass all-gathers parameters. That happens on every single training step.

Isn't training stopped while the checkpoint is written? No — and that is what makes this reachable. There are three separate hops, none of which blocks the training loop: is_async=True hands the state to dcp.async_save, which stages it and returns; the HF consolidation is then pushed onto a background thread inside the worker; and even the waiting for those to finish runs on another background thread on the controller. The join only happens at the next save, or at shutdown. So the background thread stays alive across many training steps.

Now the collision. A NCCL channel is an ordered queue. Every GPU must call the same operations in the same order — the 1st call on GPU 0 is matched with the 1st call on GPU 1, whatever those calls actually are. Nothing checks that they agree.

The order flips between GPUs because the consolidation thread starts whenever that GPU's checkpoint write finished — that is wall-clock timing, not something the ranks agree on.

Where the setting gets lost, and how to fix it

Three moments in one worker's life. The value is right at the end; the channel decision was already made at the start.

t1 worker starts up _init_checkpoint_manager(config_updates={... "is_async": True}) # no save_consolidated -> Checkpointer(config=base_cfg, ...) # no process_group= passed save_consolidated = False -> separate channel NOT created

dtensor_policy_worker_v2.py:279-288 and checkpoint.py:189-207

t2 first checkpoint — the real value finally arrives setattr(cfg, "save_consolidated", SaveConsolidatedMode.EVERY) self._rebuild_checkpointer_addons() # rebuilds the addon list only -> channel still NOT created

checkpoint.py:240-245 — this is the step that succeeds when it should not: the config now says "on" while the object was built for "off".

t3 the save runs defer_consolidation = should_write and is_async and not single_rank # True consolidation_process_group = self._consolidation_process_group # None or self.process_group # also None -> None means the DEFAULT NCCL channel threading.Thread(target=_consolidate, daemon=True).start() -> dist.all_gather_object(..., group=None) # on the training channel

checkpointing.py:615-620, :1331-1334, consolidate_hf_safetensors.py:966-969

Nothing joins that thread before training continues. The join happens inside finalize_async_save, which is itself called from a background thread on the controller at checkpoint-promotion time — many training steps later.

When is it literally the same channel? Worth being precise, because the answer depends on your parallelism settings.

Consolidation always ends up on the default (world) channel, because process_group is None. FSDP2 runs on whichever mesh axis it shards over — dp_shard. PyTorch reuses the default channel for a mesh axis that spans every GPU: in device_mesh.py, when a mesh dimension covers the whole world and no backend override is given, it returns default_group itself. Automodel relies on that too — its own mesh code skips the override for world-sized axes so it does not allocate a second channel.

ConfigWhat happens
tp=1, cp=1
FSDP shards over every GPU		 Same channel. This is the picture above: two different operations matched against each other, so the run stalls or a reduction returns wrong values.
tp>1 or cp>1
FSDP shards over a subset		 Two different channels driven at once from two threads. Weaker, but still unsafe: GPUs can enter the two channels in different orders and deadlock.

So the worst and clearest case is the plain one — no tensor parallel, no context parallel, which is what most small-model recipes run.

Does it happen today, and what to do

Nobody has hit this yet, and that is the only reason it is not on fire. Every one of the 23 save_consolidated settings in the repo — across examples/ and the reference configs — is false, and the default is False. So no test and no shipped recipe turns it on. There is no failing run to point at; the case for the bug is the code path above, read end to end.

It is also new. At the previous Automodel pin 24b47e85, the all-ranks consolidation was gated on not self.config.is_async — and NeMo-RL always sets is_async=True, so this work never ran at all and no background thread existed. The r0.6.0 bump is what introduced the deferred path.

Two ways to fix it, cheapest first:

OptionWhat it does
Refuse it for now Have _normalize_supported_save_consolidated reject true with a clear message, exactly the way it already rejects final two lines up. The user finds out at startup instead of hanging at the first checkpoint.
Rebuild the Checkpointer When save_consolidated changes, build a new Checkpointer instead of writing over the old one. That re-runs __init__, which creates the separate channel. Safe to do because every GPU applies the same update, so they all create it in the same order.
If you turn this on today. Set save_consolidated: true on the Automodel (DTensor v2) backend with more than one GPU and the run will reach the first checkpoint, start writing, and then either stall until the watchdog kills it or complete a reduction with wrong values. Nothing warns you first. Until one of the two fixes lands, keep save_consolidated: false and convert to Hugging Face format after training instead. Section 1.2 of the new design doc also needs a line: calling _normalize_save_consolidated() after setattr is not enough on its own, because the separate channel still has to be created.

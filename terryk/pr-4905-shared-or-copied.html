Six pages on this stack (#4905 and #4979), one question each. This one: does the Dynamo path reuse NCCL refit, TQ token capture and the prefix splice, or copy them?

What both paths share now, and what is still written twice

Gym's chat calls reach vLLM one of two ways. Natively, each vLLM worker runs its own chat server (chat_server.py). Through Dynamo, NeMo RL's chat engine runs in Dynamo's frontend process, and an engine adapter runs inside the vLLM worker. Token capture and the prefix splice run on both. Dotted words have a short explanation: hover or tap them.

"Same function, different inputs": what it meant, and how it was fixed

The earlier version of this page said the splice on the two paths was "same function, different inputs". It meant this. At c4fe2bd5 both paths called splice_prefix_tokens. It counts how many turn-end tokens the old history holds (N), then cuts the new prompt at its N-th turn end and puts the model's own tokens before the cut. The native server called it at vllm_worker_async.py L1432, the Dynamo engine at native_engine.py L559. Only the model's own tokens from TQ were the same on both. The other three inputs came from different places:

So every turn-2 call with a prefix failed through Dynamo on such a model, while the native path served it. gpt-oss has the same shape: a tool-call turn ends on <|call|>, which is not its tokenizer's EOS. That was review comment C16. The other two inputs did not break this example, but they could make the two paths cut in different places: counting in the model's prefix goes wrong if the model wrote an EOS id as ordinary text, and the Rust renderer is a different program from the checkpoint's own template.

Fixed at a2c74e6, in #4979, RL only. 0b7894a4 added turn_end_token_ids (stop ids + generation-config EOS + tokenizer EOS) and made eos_token_id required. 43efaba3 moved Dynamo's splice into the frontend, where the render pool runs the same _render_chat_call as native, so both get the same new prompt and the same history render. 53d7c9df deleted the None mode. The turn_end_not_eos parity case now checks the prompt matches.

So what. The splice and the capture core are now one copy, so the bug above cannot come back on one path only. The risk that is left is drift in what is still written twice: the order of steps 2–6, the staged message, the error mapping, and the native-only top_logprobs check. The next change to land there is #4506 (prefix recovery). It adds restore steps between the TQ read and the splice, but only in the native chat path (vllm_worker_async.py L1568-L1600 at 7d75696). Moving steps 2–6 into one shared method before #4506 lands would give it one place to go.

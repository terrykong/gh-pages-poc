Five pages on this stack (#4905 and #4979), one question each. This one: do the Dynamo paths reuse NCCL refit, TQ token capture and the prefix splice, or copy them?

Before
The native chat server runs the Gym capture steps in one place: read the capture context, resolve a forest-training "candidate", fetch the earlier turns from TQ, splice, begin capture, stage.
This stack
#4905 (rollouts) reuses everything. #4979 (Gym) calls the same helpers but copies the order of steps into _generate_gym, and the copy leaves out step 2.
Status
Open — not fixed in either PR. Traced in code, not run: with token_capture.forest_training on, Gym calls through Dynamo fail at begin capture. Staged as review comments C26 (the fix) and C27 (one shared method, tested first) on #4979, not yet published.

The three features, one line each

Feature#4905: NeMo RL rollout via Dynamo (lane D)#4979: Gym via Dynamo (lane E)
NCCL refit Shared. Dynamo serves the worker's own AsyncLLM, so refit is the worker's update_weights_from_collective_async, picked by the vLLM weight-sync factory. The PR deletes the old Dynamo refit code and the dynamo entry in that factory. Shared, same worker and same call.
TQ token capture Shared. Rollouts carry no Gym capture. _generate_rollout calls the worker's own _serve_rollout, the same function the Ray path uses. Helpers shared, step order copied. The TQ sink, the TQ read, begin and finish are the worker's own methods. The 100-odd lines that call them in order exist twice.
Prefix token check (splice_prefix_tokens) Not needed. Rollouts send token ids, so nothing is re-rendered. Same function, different inputs. Native renders the history to count EOS tokens and counts the stop ids too. Dynamo has no messages, so #4979 adds a None mode that counts EOS in the model's own prefix, using the tokenizer's EOS only (already review comment C16 on #4979).

Gym capture, step by step: native server vs Dynamo engine

Each row is one step. Both sides call the helper in the middle; the arrows show who calls what. Step 2 exists only on the left. Gym sends a candidate context when forest training sets parent_resolution: source_history and its sink finds an earlier call whose history matches. Gym's begin_call then refuses it: "The framework must resolve candidate admission before capture." On the native path step 2 turns it into token_in first. On the Dynamo path nothing does.

Steps 1, 3, 5, 6 and 8 are true reuse. Step 4 calls the shared function, but with a different way of finding the cut. Step 2 cannot just be copied over: decide_capture_input checks message roles at the cut, and the Dynamo engine never sees messages, because the frontend renders them into tokens. So the sender has to pass the roles along.

What I'd change — proposed, not in any PR

Nothing below is implemented.

Where the fix lands: Gym and RL, in #4979. Gym's Dynamo dialect, which already sends the ng_capture: annotation, also sends the chat messages' roles. RL's _generate_gym runs step 2 on them.

🟡 review comment C27 — native_engine.py:492

So what. #4905 is clean: refit, capture and the rollout code are the worker's own, and it deletes the old Dynamo copies. The copying starts in #4979, which repeats the native server's capture steps instead of calling one shared method.

How an Energon + HybridEP config can pass the new check and still run with padding turned off

Explainer for NVIDIA-NeMo/RL #4515 (SFT precision and packed-training fixes). All permalinks pin the PR head 1091d533.

Before
SFT setup rejected every run that combined Energon packing with HybridEP.
This PR
Allows the combination when model_overrides.moe_hybridep_pad_uneven_dispatch_inputs is true, so each MoE layer pads uneven inputs.
Status
Open, not fixed in this PR. One more setting, the one the docs recommend for HybridEP + packing, turns that padding back off after the check passes. The review asks for one extra check.
Background. In a mixture-of-experts (MoE) model, each layer sends tokens to experts on other GPUs. HybridEP does that exchange, and it needs every GPU in the group to send the same number of tokens. Energon packing builds each GPU's packed row on its own, so rows differ in length across GPUs. There are two ways to even them out: pad inside every MoE layer, or pad the whole row once before the forward pass. Dotted words have a short explanation: hover or tap them.

The PR's new check reads the user's YAML: if model_overrides.moe_hybridep_pad_uneven_dispatch_inputs is true (pad inside every MoE layer), Energon + HybridEP is allowed (sft_v2.py:517-524). But later, on every Megatron worker, existing setup code sets that same field back to False whenever moe_hybridep_prepad_packed_inputs (pad once before the forward pass) is on (setup.py:988-992). The pad-once option only runs for NeMo-owned packing, never for Energon packs (data.py:442 vs :457). And the docs tell HybridEP + packing users that they need the pad-once option (sequence-packing doc).

Same check, two configs, one ends with no padding

Setup turns the per-layer padding off on purpose: with pad-once on, it trusts the pad-once step to even out the rows instead. For Energon packs that step never runs, so in config B nothing evens them out. Megatron's field doc says to turn this padding on exactly when "local HybridEP input token counts can differ across ranks" (transformer_config.py:997-1002).

What would fix it: proposed, not in the PR

Where the fix lands: RL only, one function. setup_sft_v2 in sft_v2.py, plus one test case in test_sft_v2.py. No Megatron change: setup turning the field off is right for NeMo-owned packing; the new check just has to refuse the one case where nothing replaces it.

Nothing below is implemented. It adds one more refusal to the same check, so config B fails at setup with a clear message instead of reaching the GPUs:

So what. A user who follows the HybridEP + packing docs sets both options, passes the new check, and trains with no padding on uneven inputs, which is the exact failure the check was written to stop.

Seven pages on this stack (#4905 and #4979), one question each. This one: how to split a Gym call so both paths run the same code.

Background. NeMo-Gym sends chat calls. On turn 2+, the earlier turns are swapped for the exact tokens the model made (the splice), read from TQ. The clamp fits the output budget. A restore resumes a call a checkpoint cut. Dynamo's KV router picks a worker by token ids. Dotted words: hover or tap.

On native, every step runs in one vLLM worker process (VllmAsyncGenerationWorkerImpl). On Dynamo, the KV router needs the final token ids first, so the frontend (NemoRLChatEngine) prepares the prompt and the worker (DynamoVllmAdapter) captures it. A restore must run on the worker, since it checks the saved tokens against the worker's weight version. So cut the call there, make each side one shared function, and send the prepared prompt as JSON.

Today's native code, then the same three boxes in both lanes

Across a row, both boxes are one function with the same input and output. On Dynamo, the prepared prompt crosses to the worker as JSON beside the token ids and is rebuilt with PreparedPrompt.from_json. The restore sits in B, not A: A prepares the normal spliced prompt, and B swaps in the saved one when a cut resolves. Gray stays per path: native keeps vLLM's own serving; the adapter keeps its short copy of vLLM's SamplingParams build.

Native's preprocess_chat shrinks to A then B. The frontend calls the same A and sends prepared_prompt.to_json(). The worker rebuilds it, checks the queue before capture, calls the same B (which now holds the restore order), and maps errors through abort_capture. Both serving chats get C from ResumedCallReplyMixin. The sketch makes three small behavior changes, each toward one answer: native now splices and clamps before resolving a restore (Dynamo's order); Dynamo sets a restored call's budget from the client's own max_tokens (native's rule); and a restored call with images keeps its media keys on Dynamo too.

Before
With vLLM tensor parallel > 1, profiling a generation run produced no usable inner-worker traces at all — the files existed but could not be opened.
This PR
Gives the inner workers a profile that starts and stops on command, and writes each rank's report before teardown kills the process.
Status
Fixed by this PR. The author's run shows one vllm_tp_worker_* trace per rank where there were none.

When vLLM runs with tensor parallel > 1, the model is split across several processes. vLLM starts those itself — they are its own Ray workers, not NeMo-RL's. Profiling the generation side means getting an nsys trace out of each one.

Take one engine split across two ranks, worker A and worker B, and a profile window of steps 3 to 5.

Why the old traces were unusable

Two things had to change to get from the top row to the bottom one.

How the PR gets there

1. give the inner workers a profile that waits to be told when to start the config vLLM uses by default records from launch and never stops. NeMo-RL swaps in one with capture-range=cudaProfilerApi, so nsys sits idle until the code calls cudaProfilerStart. the catch: that config is built inside vLLM's EngineCore process, which is started fresh and re-imports vLLM, so editing the class in NeMo-RL's own process has no effect there. fix: register a vllm.general_plugins entry point. vLLM loads those in every process it starts, including that one. 2. write each rank's report while the process is still alive at the end of the window each inner worker calls cudaProfilerStop, then runs `nsys stop --session`, which writes its .nsys-rep there and then. Teardown can kill the process afterwards — the file is already complete.

The plugin is vllm_nsight_plugin.py:55-77, registered at pyproject.toml:123-124. The write-before-teardown step is vllm_backend.py:1691-1700. On the async engine the start/stop calls also had to be awaited, or they never reached the inner workers at all — vllm_worker_async.py:229-253.

How you can tell it worked. The filenames say which config the inner workers actually got. vLLM's stock one writes worker_process_<pid>.nsys-rep; NeMo-RL's writes vllm_tp_worker_<window>_<pid>.nsys-rep (the template). If you see vllm_tp_worker_ files, one per rank, the plugin reached the EngineCore process and the traces are real. That is the check the author used, and it is worth keeping — a run that simply finishes proves nothing, because the broken version finished too.

There is a separate problem in the new code — the condition that decides whether a worker runs that nsys stop at all. That is page 2.

With capture on, the environment stops returning tokens entirely. Its Ray reply carries an empty message_log and one small dictionary called a receipt (nemo_gym.py:768-773). The receipt is a list of which model calls happened, in what order, and where each call's tokens were parked in TransferQueue — about 100 bytes per call, no token ids anywhere. Everything after that is a join: the receipt says which rows, TransferQueue holds what is in them, and BlackboxFinalizer puts the two together (blackbox_finalizer.py:353).

How the pieces join

A rollout with 2 model calls and one tool result in between. The prompt is 5 tokens, the model writes 3 then 4, and the tool result adds 2 — a 14-token row of which 7 are trained on.

One receipt holds every call — but only one path through them trains

A receipt is not one model call. Its manifest is a list of every call the rollout committed, and each row names its parent_call_id. That makes the manifest a tree, not a list: a retry, a rejected sample or an abandoned branch all appear as rows too. Only the path from the terminal call back to its root is turned into a training row. _terminal_chain starts at terminal_model_call_id, follows parent_call_id backwards until it hits a row with no parent, then reverses the list (rebuild.py:201-216). Anything not on that path is verified and then ignored — its tokens stay in TransferQueue and never reach the trainer.

Each call's delta is new prompt text first, then what the model wrote. That is literally how it is built (digest.py:281-284):

prompt_delta = prompt_token_ids[prev_len:] # whatever is new since the parent ended token_ids_delta = prompt_delta + generated_token_ids token_mask_delta = [0.0]*len(prompt_delta) + [1.0]*len(generated_token_ids)

So yes — a tool result is carried on the next call, as masked-out prefix. The finished row really is [prompt, gen, tool+gen, tool+gen, …], and the mask is 0 over every carried stretch and 1 over every generated one.

What happens when the context is rewritten? Nothing silently — two independent checks catch it.

At staging time the gate compares the real generation prompt against the prefix it authorized: prompt_token_ids[: admission.prev_len] != call.prefix_token_ids raises "generation prompt does not begin with the gate-authorized token prefix" (capture.py:160-161). Compaction rewrites the middle of the context, so the prompt stops starting with the parent's exact tokens and the call fails to stage. At rebuild time there is a second net: parent.cum_len != record.prev_len raises parent_length_mismatch (rebuild.py:187-191). Either way the rollout is rejected and becomes a masked placeholder row rather than wrong training data.

There is a legitimate way to start over: a call can be admitted as a root (mode="text", no parent, prev_len 0) instead of chained (mode="token_in"). A harness that compacts and then opens a fresh root produces a second, independent tree in the same rollout — and since only the terminal's path is linearized, everything before the compaction is staged but never trained on. That is coherent, but it is worth knowing it is a silent narrowing of what the rollout contributes, not an error.

The practical limits to keep in mind. Every call on the trained path must add at least one generated token — a call that carries text but generates nothing raises empty_generation. The mask within a delta has to be all carry then all generation; anything interleaved raises invalid_mask_order. And the whole design assumes the context only ever grows by appending. Prefix caching and normal multi-turn growth fit that; trimming, summarising or reordering the context does not, and turns the rollout into a masked placeholder.

With capture on, the environment stops returning tokens entirely. Its Ray reply carries an empty message_log and one small dictionary called a receipt (nemo_gym.py:768-773). The receipt is a list of which model calls happened, in what order, and where each call's tokens were parked in TransferQueue — about 100 bytes per call, no token ids anywhere. Everything after that is a join: the receipt says which rows, TransferQueue holds what is in them, and BlackboxFinalizer puts the two together (blackbox_finalizer.py:353).

Why it is built this way

Splitting the reply in two buys three things at once. The environment cannot alter a token, because it never holds one. The Ray reply stays small no matter how long the rollout ran — a 50-turn agent trajectory returns 50 short rows rather than 50 arrays of token ids. And the expensive work — fetching, hash-checking and gluing — happens in a separate actor pool after the rollout is done, instead of on the path that is generating the next one.

The weight_version on each row is what makes staleness visible: one rollout can span a weight refresh, and the finalizer can then see that call 1 came from version 12 and call 2 from version 13, and apply the configured policy rather than silently mixing them.

The join key is the whole trust story, so it is worth knowing where it can fail. If the manifest cannot be fetched — a dead control plane, a 401, the wrong server name — the receipt comes back None, the rollout becomes a masked placeholder row, and training continues. With the shipped default (min_valid_fraction_per_group unset) a whole group of placeholders is still published, so a sustained control-plane outage produces steps that consume prompts and contribute no gradient. The signal exists — finalize/invalid_row_rate — but nothing stops on it. That is one of the review findings on this PR, not a claim that it is happening today.

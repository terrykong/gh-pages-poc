Which Gym entries list_entries() reports — and which ones actually started

Companion page for NVIDIA-NeMo/RL #3633. Links pinned to 7477f97, and to NeMo-Gym at c3bac96.

A NeMo-Gym job is described by one YAML config. Part of it is plain settings — ports, hosts. The rest is entries: named blocks that each start a server process, such as an agent or a tool server. A later PR, #3371, wants to spread those servers over several machines, so it has to ask each machine which entries it has. That is what list_entries() answers. Its first docstring line says it reports the entries the actor "actually spawned". It reports every entry the config declares, started or not — and in recipes shipping today those two sets are different.

Three entries, three fates

All three are from one real recipe, whose config_paths list enables 6 files. An entry starts a server only if something gives it an entrypoint — the script to run.

Two rules that look alike and are not

Gym asks two things before it starts a server. list_entries() asks only the first.

Gym — does this block name a server type, AND does its leaf have an entrypoint? if "entrypoint" not in server_config_dict: continue # math_formal_lean_refinement_agent stops here list_entries() — does this block name a server type? types = [key for key in GYM_SERVER_TYPE_KEYS if key in entry] # math_formal_lean_refinement_agent passes

Those two lines are Gym cli/env.py:407 and NeMo-RL nemo_gym.py:697. Nothing reports the difference at runtime. Gym does have a check for blocks that look like servers but are not quite — is_almost_server — but it returns true only when the leaf already has an entrypoint, so this shape never reaches it. The entry resolves, no process starts, and the run says nothing.

Does it work?

Nobody has run this, and there is nothing to measure. The method reads a config dictionary that is already in memory — no benchmark, no training curve, no job log applies. The PR's three unit tests pass, but that is not evidence here: every fixture leaf in them is {}, which is exactly the shape that starts no server. The tests assert that shape should be reported, so they pass because of the gap.

What does count is a test that fails on the code as written. It was run both ways — 1 failed, 3 passed against this PR, and 4 passed once list_entries() also checks for an entrypoint.

def test_list_entries_skips_an_entry_that_starts_no_server(): resolved = DictConfig({ "math_env": {"resources_servers": {"math": {"entrypoint": "app.py"}}}, "code_gen": {"resources_servers": {"code": {"host": "10.0.0.1"}}}, }) with _stub_gym_resolved_config(resolved): entries = _spun_up_actor().list_entries() assert entries == {"math_env": ["resources_servers"]}

A sweep of 34 recipe files (141 entries) found 7 of this shape, in 2 files. One is staged on purpose: that recipe invites you to uncomment a config path, and the override block sits ready for it. The other six look like leftovers from copying a file. Three sibling recipes enable the config path and carry the override block — student_rlvr1, student_rlvr2, mopd — while ifbench_teacher carries the block with no path.

What it costs today: very little. The only caller, #3371, just stores the map and prints it. No code routes work using it yet, so a name that never started produces a wrong log line, not a wrong decision. The one real failure needs a name collision: if a never-started entry shares its name with a real one on another machine, #3371 reports that an agent lives on two machines when only one of them ever ran it.
So what. The cheap fix is the docstring — say the method reports what the config declares, not what started. The stronger fix is to check for an entrypoint as well, which makes the original wording true, and costs updating the fixtures in three existing tests. Worth settling before the router that reads this map is written: after that, a name in the map is a routing decision rather than a log line.

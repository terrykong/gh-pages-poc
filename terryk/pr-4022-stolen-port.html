Why half the inference requests were never answered

Two pages on this PR, one bug each — this one: why inference requests vanished.

Training sends prompts to an inference server over HTTP and waits for the answers. In some runs the requests went out and some of them never came back, so training sat there forever. Nothing crashed and no error was printed. The cause was a second program on the same machine quietly receiving some of those requests and doing nothing with them.

Three words first

If ports and sockets are not your daily vocabulary, this is all you need:

Port — a number that says who a request is for
One machine runs many programs. A request arrives addressed to node:7431, and 7431 picks which program on that machine should get it. Think of it as an extension number on an office phone system.
Claiming a port — a program says "requests for 7431 come to me"
A program asks the operating system for that number. Normally only one program can hold a number at a time. This server deliberately turns on a setting that lets several programs hold the same number together, and the operating system then splits incoming requests between them — that is how it runs several copies of its front end without a load balancer.
Copying a process — the copy keeps whatever the original was holding
Programs start helpers by copying themselves. The copy inherits the original's open things, including any port it had claimed. So a copy can end up holding a claim it never asked for and does not know about.

Those three facts are the whole bug. The worker claimed port 7431 early, then copied itself while still holding the claim, and the copy became a second legitimate recipient of requests that it never answered.

What went wrong

Green = the server that is supposed to answer. Red = the accidental second holder of the same number. Both are valid holders as far as the operating system is concerned, so it shares the work between them.

The fix

The copy exists because the worker was holding the port claim at the moment it copied itself. The fix moves when it claims the port: hold the number 7431 as an ordinary number, and only claim it at the last moment, after all the copying is done.

The steps are the same and happen in the same order. The only change is that step 1 keeps a number instead of a claim, so step 2 has nothing to copy.

In code, the worker used to take the port claim during start-up and keep it through the whole of model loading. Now it stores the number and asks for the claim immediately before starting the server:

# start-up: keep the number, not the claim self._reserved_http_server_port = 7431 # ... model loads, helper processes get copied ... # about to start the server: now take the claim reserved_socket = receive_held_socket(7431) start_text_gen_server(server_port=7431, sock=reserved_socket)

Nobody else can take port 7431 during the gap. A separate small process claimed it at the very start and keeps holding it until the worker asks — it only lets go at the moment of handover, once the worker already has it. So waiting longer is free.

Two details worth knowing. The server does not keep the claim you hand it: it reads the number off it, drops it, and then starts several front-end processes that each claim 7431 themselves — its own docs explain why sharing one is worse. So the thing being passed around is only ever a way of saying "this number is taken". And which copy inherited the claim was never pinned down: the PR author names a likely candidate and says he is not certain, and the code that starts it asks for a fresh process rather than a copy, which would not inherit anything. The fix does not depend on finding it — hold no claim during that stretch and it stops mattering what gets copied.

What to take away. Claiming a port early and using it much later looks harmless, because in between you are "only holding" it. But anything the program copies in that window comes away holding it too, and with the shared-port setting turned on those copies are handed real requests. Keep the number, claim it at the point of use, and the whole problem disappears.

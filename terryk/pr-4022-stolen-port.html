Why a forked copy of one socket made Megatron rollouts hang forever

NVIDIA-NeMo/RL #4022 · all links pinned to b99ee92e

the stolen port the missing agent ref

Two pages on this PR, one bug each — this one: why inference requests vanished.

NeMo-Gym needs the inference server's URL before the model finishes loading, so both can start at the same time. To promise a URL that early, the driver grabs a port up front: it binds a listening socket and holds it open, then hands the URL to Gym. That socket is later given away to the worker that runs the real HTTP server, passed as a file descriptor over a Unix socket so the port is never free for even an instant. The bug is about when the worker took it.

What went wrong

Red = a step that copies or keeps the extra listener. Green = the fixed order. The only difference is where the "take the socket" step sits relative to the fork.

The child process is not doing anything wrong. It inherited a listening socket it never asked for and never calls accept() on, so every connection the kernel gives it just sits in a queue. From Gym's side the request is sent and no reply ever comes.

The fix

Hold a port number instead of a socket, and turn the number into a socket at the last possible moment. Same three steps, same port 7431:

# 1. worker start-up — keep the int, not the fd self._reserved_http_server_port = 7431 # was: receive_held_socket(7431) # 2. model loads; async checkpointing calls fork() # child copies open fds — there is no listening fd to copy # 3. HTTP server is about to start — now ask for the socket reserved_socket = receive_held_socket(7431) server_port = reserved_socket.getsockname()[1] # 7431 start_text_gen_server(server_port=7431, sock=reserved_socket)

Step 1: megatron_policy_worker.py L482-487 · step 3: megatron_worker.py L558-570

The port stays reserved the whole time. The driver's socket is still bound and listening from step 1 to step 3 — it is only closed at the hand-over itself, after the receiver already holds a copy. So waiting longer does not open a window for some other process to grab port 7431; it only shortens the time anyone in this process tree is holding a listener that could be copied by a fork.

What to take away. An open file descriptor is inherited by every child process you fork afterwards, and with SO_REUSEPORT a second listener on the same port is not an error — the kernel happily shares incoming connections with it. That makes "adopt the socket early, use it later" quietly dangerous in any process that forks in between. Holding the port number and materializing the socket at the point of use costs nothing and removes the whole class of bug.

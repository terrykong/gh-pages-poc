Why the trainer warm-up crashes at startup when CUDA graphs are on

NVIDIA-NeMo/RL #5001. Permalinks pin the PR head 5223071, Megatron-LM 3e95097 (the copy pinned inside Megatron-Bridge), and Transformer Engine 2.18 27486e0.

Before
There was no warm-up. Step 1 was the first time the trainer ran.
This PR
Adds NRL_TRAINER_WARMUP=1. The warm-up saves the trainer's random-number state, runs a fake step, then puts the state back. It saves that state with .clone() unless the tracker has a use_cudagraphable_rng flag.
Status
Open: not fixed in this PR. It only hits runs with the warm-up on and Megatron CUDA graphs on. The fix below is proposed in review comment C1 (pending), not implemented.
1 · what the switches change 2 · warm-up crash with CUDA graphs

Two pages on this PR. Read page 1 first for what the warm-up is.

Background. Megatron keeps a few named random-number streams, one per kind of parallel group, in an RNG tracker. There are two kinds of tracker. Megatron's own stores each state as a tensor. Transformer Engine's (TE's) stores each state as a torch.Generator object, so that CUDA graphs can read it. NeMo RL switches to TE's tracker whenever cuda_graph_impl is not "none". The crash, one config line to the error

  1. A run sets cuda_graph_impl: local (or any value other than "none"), or sets use_te_rng_tracker: true in model_overrides. The shipped example configs use "none", so they do not hit this.
  2. Megatron builds TE's tracker. In TE 2.18 each saved state is a torch.Generator from clone_state().
  3. The PR's check looks for a flag that only Megatron's own tracker has, so it takes the .clone() branch. torch.Generator has get_state/set_state but no clone.
  4. One more problem waits behind the crash. With cuda_graph_impl: local, the warm-up's forward/backward is the call that captures Megatron's CUDA graphs, so they are captured on the fake batch's shapes. A real batch that matches none of them hits "no matching cudagraph runners were found".

The fix: proposed in C1, not in the PR

Where the fix lands: RL only, one file, megatron_policy_worker.py, plus one row in the docs table. No Megatron or TE change: both already expose get_state/set_state on each generator.

Nothing below is implemented or run. The - lines exist at the PR head.

  1. The first hunk skips the warm-up when CUDA graphs are on, so graphs are never captured on fake shapes. It reads the value Megatron actually runs with (TransformerConfig.cuda_graph_impl).
  2. The second saves every state, whatever the tracker kind: a generator's seed and offset, or a tensor copy. This still matters with graphs off, because a run can turn on TE's tracker by hand.
  3. The third writes generator states back into the same objects. get_states() returns a new dict, so set_states is still called for tensor states. This also restores the graph-safe states that the PR currently skips, which an earlier review thread on the same line pointed out.

🔴 review comment C1 — megatron_policy_worker.py:2742   🟡 C3 — the missing worker test that would catch it

So what. If you turn on the warm-up in a Megatron run with CUDA graphs, it dies before step 1 with an AttributeError, on every rank. Leave the warm-up off for CUDA-graph runs until C1 lands. The review also asks for a unit test with a fake tracker that stores torch.Generator states: it fails today and would have caught this.

Why one import line stops every Megatron run on PR #3834

Review note for NVIDIA-NeMo/RL #3834 (multimodal Megatron generation). All permalinks pin the PR head 73f6117.

The PR adds image and video support to the Megatron generation path. To build the config it hands to Megatron-Core, it imports two classes at the top of a module: utils.py:19. Those two classes are new — they arrive with Megatron-LM #6809, which is merged upstream. But this repo does not track Megatron-Core directly; it reaches it through the Megatron-Bridge submodule, and the commit that submodule points at predates #6809. So the class the code asks for is not there, and because the import sits at module level rather than inside a function, the failure lands on anything that imports that module — including the plain text-only training worker.

Where the chain breaks

What the fix looks like

Two options. The first is the real fix; the second keeps text-only Megatron working while the first is blocked.

Option A — move the submodule forward (the real fix) 3rdparty/Megatron-Bridge-workspace/Megatron-Bridge d352aced -> a Bridge commit whose own 3rdparty/Megatron-LM contains #6809 then re-lock: uv lock Blocked today: Megatron-Bridge main still pins a Megatron-LM without #6809, so there is no Bridge commit to move to yet. Option B — make the import lazy (unblocks text-only Megatron now) # nemo_rl/models/generation/megatron/utils.py - from megatron.core.inference.config import ImageProcessingConfig, VideoProcessingConfig # module level def build_image_preprocessing_config(...) -> "ImageProcessingConfig": # quote the annotation + from megatron.core.inference.config import ImageProcessingConfig # import when called Text-only runs never call this function, so they never touch the missing class.

Option B is a workaround, not a substitute: the multimodal path still needs #6809 to run at all. It only stops the new feature from taking the existing training path down with it while the submodule waits.

Does it work?

The feature itself has real evidence. The author posted accuracy parity against vLLM for both image (CLEVR) and video (VSTAT) on a W&B project linked from the PR description, with plots in the PR body. That is the right evidence for a "does the new backend produce the same answers" question, and it is not in doubt here.

What has not been run is this branch. Only the lint-tier checks have run on head 73f6117 — no unit lane, no functional lane. The /ok to test comment on the PR points at a commit that a rebase removed from the branch, so it covers code that is no longer there.

So there is no run to show. Instead, here is a claim you can check in about a minute, with no GPU:

$ uv run --extra mcore pytest tests/unit/models/generation/test_megatron_generation.py --collect-only ImportError: cannot import name 'ImageProcessingConfig' from 'megatron.core.inference.config'

If that collects cleanly, this page is wrong and the submodule already carries #6809.

One thing worth knowing about the timing. An earlier commit on this branch bumped a dependency in a way that made uv lock check fail. That red check was the one signal pointing at the submodule being behind. A later commit reverted the bump and re-locked, which turned the check green — correctly, the lock now matches the pin. But with it green and no unit or functional CI running on this head, nothing is left that would catch the import.
So what. As it stands, merging this would break every Megatron run, not just the new multimodal one — a text-only GRPO job fails at import before it does any work. The fix is not a code change in this PR: Megatron-Bridge has to bump its own Megatron-LM to something containing #6809 first, then this repo bumps Bridge. Until then the PR is blocked on an upstream chain rather than on anything in the diff. If it needs to sit for a while, making the import lazy keeps the existing training path working in the meantime.

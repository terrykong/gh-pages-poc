The background delete can reuse the checkpoint gate that already exists

Size review of NVIDIA-NeMo/RL #4655, stacked on #4508. All permalinks pin the PR head 495ce13. Review comments are in a pending review; their links work once it is published.

Before
When a call that was cut at a checkpoint finishes, its reply waits for a synchronous delete (a TQ CLEAR) of the old chunk rows.
This PR
Behind an opt-in flag, moves that delete to a background thread. To do it, it adds a 253-line module with its own slot reservation and its own checkpoint pause/resume, wired into the worker at 4 places.
Status
Proposed — not implemented. The smaller version below is a review suggestion. A prototype passed 5 checks against the real gate class; it has not been run inside NeMo-RL.
size and reuse one failed CLEAR

Two pages on this PR — this one: what the new module repeats, and what can go.

Background. During a rollout checkpoint, a call that is still generating is cut: its tokens so far are saved as chunk rows in TQ. When the call later finishes, its final row is written and the old chunk rows are deleted. A checkpoint must not save TQ while a final-row write is half done, so the worker has a _TokenCaptureSnapshotGate: writers enter() and exit() it, and a checkpoint closes it and waits until no one is inside. Dotted words have a short explanation: hover or tap them.

The PR's background thread needs one rule: no delete may run while a checkpoint saves TQ. The gate already enforces exactly that for anything that holds a permit. Instead of taking one, the new class (BackgroundPrefixCleanup) keeps a second copy of the gate's epoch bookkeeping and adds pause, wait_paused and resume, which the checkpoint code must now call next to the gate's own calls.

What each piece does, in order: (1) the thread takes a gate permit around each CLEAR, so close_and_wait waits for a running delete and enter() holds the next one until the checkpoint reopens the gate; (2) the finishing call queues its keys only after it leaves the gate, the same reason the PR reserves outside it today; (3) the checkpoint code goes back to what #4508 has. The prototype checked: a reply returns while a CLEAR is still running; a checkpoint waits for that CLEAR; no CLEAR starts while the gate is closed; 1,024 calls blocked on a full queue plus a second checkpoint do not deadlock; 2,048 keys clear in 34–36 calls at batch size 32 (the PR's test gets 32). Do not reuse PrefixReadBatcher from #4508 instead: it returns awaited results on one event loop, while this delete is fire-and-forget from a worker thread.

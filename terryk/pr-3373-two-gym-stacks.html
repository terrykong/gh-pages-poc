How one job runs two NeMo-Gym stacks instead of one

Companion illustration for NVIDIA-NeMo/RL #3373 — wire sharded stacks into training. All permalinks pin the PR head 252da6f.

Before
A job started exactly one NeMo-Gym actor. Every environment server it needed ran on that one node, so the whole job was capped by what one node could hold.
This PR
Lets a job declare several stacks (shards), starts one actor each, and sends every prompt to the shard that hosts the environment it names.
Status
New in this PR. Open, not yet merged — it sits on top of #3372 in a stack.
two stacks in one job keeping teardown bounded

Two pages on #3373, one question each — this one: what the feature is and how it compares to the single-actor way. Background from the PRs below it in the stack: how the actors get created (#3371) and how rollouts get routed (#3372).

A NeMo-Gym stack is one Ray actor running a pile of environment servers — a tool server, a judge, whatever the recipe asks for. Training sends it prompts; it runs them and sends back rollouts. One actor was the only shape available, so adding a second heavy environment meant squeezing it onto the same node. This PR makes the count configurable. The thing every entrypoint now holds is a NemoGymShardSet — a set of actors plus a map from environment name to the actor hosting it.

Where the rows go, before and after

The config that makes two stacks

The split is by environment, because a given environment lives on exactly one shard. Each shard names its own server configs and its own port window, so two stacks on one machine cannot collide:

env: nemo_gym: config_paths: null # retract the single-stack list inherited from the parent recipe shards: - name: workplace port_range_low: 5000 port_range_high: 5499 config_paths: [ vllm_model_for_training.yaml, workplace_assistant.yaml ] - name: math port_range_low: 5500 port_range_high: 5999 config_paths: [ vllm_model_for_training.yaml, math_with_judge.yaml ] common_inherited_overlays: [ policy_model ] # every shard needs the model proxy allowed_duplicate_entries: [ policy_model ] # and it may appear in more than one

Two details are easy to miss. config_paths: null is how a child recipe removes a key it inherited — a Hydra override can blank a key but cannot delete it, so the schema reads null as absent (smoke config:37). And by default each shard gets its own node; placement_strategy: PACK relaxes that for a one-machine test, which is why the port windows have to be spelled out and must not overlap.

What setup now checks before training starts

With one actor, every prompt had somewhere to go. With several, a prompt can name an environment no shard runs — a typo, or a shard someone removed. That mistake used to surface when the first such prompt was dispatched, which can be hours in. Setup now scans the training and validation data and fails immediately (validate_dataset_agent_coverage):

hosted routes = {"workplace_assistant", "math_with_judge"} # from the 2 shards names in data = {"workplace_assistant", "math_with_judge", "code_gen"} ShardSetupError: The training dataset references routes that no shard hosts: ['code_gen']. Hosted routes: ['math_with_judge', 'workplace_assistant'].

Reading every row of a big dataset at startup would be its own cost, so the scan remembers a file by its path, size and timestamps and reads it once per process. If the file has changed underneath, it falls back to scanning the rows already in memory. Unsharded jobs skip the whole thing — one actor hosts everything, so there is nothing a scan could find (the early return).

What this buys you. Two heavy environments no longer have to fit on one node — each gets its own, with its own port window. Nothing changes for existing single-stack recipes: they take the same code path with a one-shard set, and the old single-actor helpers are gone rather than kept alongside. The cost is that a sharded config has to say which shard owns each inherited setting, and setup will now stop a run whose data names an environment nobody hosts.

What score centering adds to token capture and to the policy-gradient loss

NVIDIA-NeMo/RL #4818 (adds loss_fn.score_centering and token_capture.top_logprobs). Permalinks pin head f0d9860e.

Before
Token capture stored only the tokens vLLM sampled. The loss pushed up the sampled token, weighted by its advantage, and nothing removed the pull toward whatever vLLM happened to favor.
This PR
vLLM also returns its top-K candidates per token. They travel with the tokens to the trainer, and the loss adds one term that subtracts the update vLLM's distribution would cause on its own. Off by default.
Status
New feature, in review. The math checks out for all four importance-sampling modes, and GPU CI passes, including the score-centering smoke run and the TP/CP gather checks. Four pages on this PR, one question each — this one: what the feature adds, next to what was there.

Background. In GRPO/PPO, vLLM samples a response and the trainer then raises the probability of each sampled token in proportion to its advantage. Token capture is the existing path that ships the sampled token ids from vLLM to the trainer. Score centering (arXiv:2609.20807) needs more than the sampled token: it needs vLLM's probability for K candidates at every position. Dotted words have a short explanation: hover or tap them.

Why: the plain update hides a pull toward vLLM

Step 1, the loss NeMo-RL computes. For one sampled token y, the clipped loss is (clipped_pg.py L142–L167):

\ell = \mathrm{sg}[w]\cdot \max\!\big(-A\,r,\; -A\,\operatorname{clip}(r,\,1-\epsilon,\,1+\epsilon)\big), \qquad r = \frac{p(y)}{p_{\text{old}}(y)} = e^{\log p(y) - \log p_{\text{old}}(y)}

p is the trainer now (it gets gradients). pold is the trainer when the batch's log-probs were taken (fixed data). w = pold(y) / q(y) is the vLLM-to-trainer importance weight, detached (loss_functions.py L916); with IS off, w = 1.

Step 2, its gradient. Only log p(y) carries gradient. Because r = elog p(y) − const, the derivative of r is r times the derivative of log p(y). So for a token that is not clipped, the gradient is −A·w·r·∇log p(y). For a clipped token, the max picks the clamped term, which is a constant, so the gradient is 0. On the first optimizer step for a batch, p = pold, so r = 1. With IS off, w = 1 too. What is left is −A·∇log p(y): the same gradient as the simple loss −A·log p(y). That is all "raise log p(y), scaled by A" means.

Step 3, ∇log p(y) on the logits. p is a softmax over the logits z, so:

\log p(y) = z_y - \log \sum_j e^{z_j} \quad\Longrightarrow\quad \frac{\partial \log p(y)}{\partial z_k} = \mathbf{1}[k = y] - p_k

The first part is +1 on the sampled id only; write it as a one-hot vector ey (1 at id y, 0 everywhere else). The second part is −pk on every id. So the push is ey − p: "one-hot at the sampled id" minus "the trainer's probabilities". Every number in it is the trainer's; this is plain calculus, not importance sampling. vLLM's only role is choosing which id gets the 1. With y = 17 and trainer probabilities 0.60, 0.15 and 0.25 for the rest, that is +0.40, −0.15, −0.25: the top row below.

Now add vLLM's distribution q and subtract it again. Nothing changes; it only regroups the same push:

\underbrace{e_y - p}_{\text{plain push}} \;=\; \underbrace{\htmlClass{t2}{(e_y - q)}}_{\text{signal}} \;+\; \underbrace{\htmlClass{t4}{(q - p)}}_{\text{pull toward vLLM}}

Why q? Because y was drawn from q, so the one-hot ey, averaged over vLLM's draws, is exactly q. (Here: id 17 gets picked 72% of the time, id 4 18%, the rest 10%.)

  • The signal ey − q is "the id vLLM actually picked" minus "what vLLM picks on average". Both sides are vLLM's on purpose: it averages to exactly zero, so it only moves the model through A, when a token did better or worse than average.
  • The pull toward vLLM q − p is vLLM's distribution minus the trainer's. It has no y in it, so it is the same push whichever id was sampled. Only its size and sign change, through A.

Why the sign of A decides the direction. A training step moves each logit by A × (its part of the push). For the pull part that is A × (q − p): +0.12 on id 17, +0.03 on id 4, −0.15 on the rest. q − p is positive exactly where vLLM likes a token more than the trainer does, and negative where it likes it less. With A > 0 the step raises the logits vLLM favors more and lowers the others, so after the softmax the trainer looks more like vLLM. With A < 0 every sign flips and the trainer moves away from vLLM. "Total gap" adds up |p − q| over the three columns. Nothing in this move depends on whether id 17 was a good choice: only A's sign does. That is why it is noise from the point of view of learning, and why score centering removes it.

The pull is zero only when vLLM and the trainer agree exactly. They rarely do: they use different kernels and precision, and in async runs vLLM's weights trail the trainer's by a step or more. Score centering subtracts the pull and keeps only the signal, so on the logits the update becomes A × (sampled token − vLLM's distribution). To subtract the pull, the trainer needs q, vLLM's probability for every token.

Why only the top-K, not the full vocabulary. The exact pull needs q over the whole vocabulary at every position. That is too big to move: about 152,000 numbers per token, roughly 18.5 GiB for one 32K-token response in fp32. So the PR records only vLLM's K most likely tokens per position: about 32 MiB per response at K = 128. It is a trade-off for size. The K recorded tokens are exact. Everything else is an estimate.

How the rest is estimated. For the tokens outside the top-K, vLLM tells us only one thing: their total, 1 − (sum of the top-K), which is 0.10 here. It does not say how that 0.10 is split between those tokens. The PR assumes vLLM splits it in the same proportions as the trainer does, and scales the trainer's numbers to the right total:

The scale factor is ρ = vLLM's leftover ÷ the trainer's leftover = 0.10 ÷ 0.25 = 0.4. If vLLM really split it 0.08 / 0.02, the estimate is off in its shape but still has the right total. Both splits add up to the same leftover, so the total error is at most twice the leftover mass. The run logs that mass as 1 − score_centering_head_mass. A larger K shrinks it.

What if vLLM samples with a top_k = K filter? Then vLLM can only pick those K tokens. With processed_logprobs they sum to 1, so the leftover is 0, ρ = 0, and the recorded K tokens are vLLM's whole distribution, with nothing estimated. That case is not available today: the Gym/HTTP path forces top_k off, and this PR rejects top_k with score centering (config.py L1419). It would also need the trainer to use the same K tokens, which is what sampling-mask replay provides.

In the code, it is one extra loss term. It is computed separately at every generated position t, then averaged over positions exactly like the main loss.

  • Ht (sampler_topk_token_ids): vLLM's top-K token ids at position t, not the trainer's. The trainer looks up its own probability at those same ids, so both sides talk about the same tokens even when the trainer's own top-K would be different.
  • qt(v) (sampler_topk_logprobs): vLLM's probability for each id in Ht when it sampled. Fixed data, no gradient.
  • pt(v) (policy_logprobs_at_sampler_topk): the trainer's probability at the same ids, over the full vocabulary. Gradients flow through log p.
  • At: the token's advantage. ρt: vLLM's mass outside Ht ÷ the trainer's mass outside Ht.
\mathcal{L}_{\text{new}} = \underbrace{\htmlClass{t1}{\mathcal{L}_{\text{clipped PG}}}}_{\text{(1) unchanged}} \;+\; \underbrace{\htmlClass{t2}{\operatorname{mean}_t\, A_t \sum_{v \in H_t} \mathrm{sg}\!\left[c_{t,v}\right] \log p_t(v)}}_{\text{(2) new}}, \qquad \htmlClass{t3}{c_{t,v} = m_{t,v} - \alpha_t\, p_t(v)}

Shapes: ids [B, S, K] → trainer log-probs at those ids [B, S−1, K] → sum over K (score_centering.py L89) → [B, S−1] → × A, then the same masked mean over tokens as the main loss (loss_functions.py L1092). Prompt and tool positions are masked out. (2) is built so its gradient on the logits is the red row above, which cancels the pull. Only c depends on the importance-sampling mode, through m and α.

What each importance-sampling mode changes

Each mode weights the main loss's sampled token by a different factor w. Averaged over what vLLM samples, that weight leaves a pull of m on each top-K id and α·p on every other token. c is exactly that leftover pull, written on the top-K ids only: the "− α·p" is the rest-of-vocab part, moved onto the top-K ids because the trainer's probabilities sum to 1. Same example as above: q = 0.72, 0.18 and p = 0.60, 0.15 at ids 17 and 4, ρ = 0.4.

Bounds come from truncated_importance_sampling_ratio_min and truncated_importance_sampling_ratio (the four branches). The PPO catch: the table assumes the main loss really applies weight w. PPO clipping sets the main loss's gradient to 0 on a clipped token, but c does not know that, so the correction still pushes there. The cancellation is exact only when the PPO ratio is 1, for example with one optimizer step per batch and force_on_policy_ratio: true.

One token, both paths, same example

Example: K = 2, a response of 3 tokens after a 5-token prompt (row length 8). At the token shown, vLLM's top-2 are ids 17 and 4 with q = 0.72, 0.18 (head 0.9); the trainer has p = 0.6, 0.15 at those ids (head 0.75), so ρ = 0.1 ÷ 0.25 = 0.4. Values computed with the real function.

Where they meet: both lanes use the same staging write (TQTokenSink.stage), the same finalizer and the same loss object. After the merge point, only two things differ: two extra columns per token (fetched by the trainer only when centering is on, _train_fields_for_step), and one added loss term. Setup rejects the cases it cannot handle: non-vLLM generation, filtered sampling (top_p<1, top_k), and non-unit temperature without processed logprobs.

What it costs. The two columns are 8·T·K bytes per row (32 MiB for a 32K-token row at K=128), stored and moved twice. On the vLLM side, the per-entry Python extraction runs on the server's event loop: on CPU it took 0.83 s at 8K tokens and 2.7 s at 32K tokens with K=128, during which that server answers no other request. CI shows it runs; no throughput, memory or convergence numbers exist yet. The review asks for those, plus a guard so top_logprobs>0 without centering is not paid for nothing. The PR also changed the existing image-capture path, and that change breaks multi-turn VLM runs even with centering off: see the next page.

What score centering adds to token capture and to the policy-gradient loss

Before
Token capture stored only the tokens vLLM sampled. The loss pushed up the sampled token, weighted by its advantage, and nothing removed the pull toward whatever vLLM happened to favor.
This PR
vLLM also returns its top-K candidates per token. They travel with the tokens to the trainer, and the loss adds one term that subtracts the update vLLM's distribution would cause on its own. Off by default.

Two pages on this PR, one question each — this one: what the feature adds, next to what was there.

Background. In GRPO/PPO, vLLM samples a response and the trainer then raises the probability of each sampled token in proportion to its advantage. Token capture is the existing path that ships the sampled token ids from vLLM to the trainer. Score centering (arXiv:2609.20807) needs more than the sampled token: it needs vLLM's probability for K candidates at every position. Dotted words have a short explanation: hover or tap them.

The math: one added term

  • p (policy_logprobs_at_sampler_topk, exponentiated): the trainer's probability. Gradients flow through it.
  • q (sampler_topk_logprobs): vLLM's probability for its top-K candidates when it sampled. Fixed data.
  • A: the token's advantage. ρ = vLLM's mass outside its top-K ÷ the trainer's mass outside those same ids.
\mathcal{L}_{\text{new}} = \underbrace{\htmlClass{t1}{\mathcal{L}_{\text{clipped PG}}}}_{\text{(1) unchanged}} \;+\; \underbrace{\htmlClass{t2}{A \sum_{v \in \text{top-}K} \mathrm{sg}\!\left[c_v\right] \log p_v}}_{\text{(2) new}}, \qquad \htmlClass{t3}{c_v = q_v - \rho\, p_v}\ \ \text{(IS off)}

(1) is the existing clipped loss, untouched (ClippedPGLossFn adds the term after it). (2)'s gradient is A times "vLLM's expected direction": exact on the top-K head, and the tail modeled as ρ·p. Since the sampled token was drawn from vLLM, that expected pull cancels on average, which is the drift the paper removes. cv changes with the IS mode: plain IS gives c = 0 (no correction), TIS clamps both parts, ICEPOP drops out-of-bounds parts (compute_score_centering_term). It is exact only when the PPO ratio is 1; on a clipped token the base term is 0 but the correction still acts.

One token, both paths, same example

Example: K = 2, a response of 3 tokens after a 5-token prompt (row length 8). At the token shown, vLLM's top-2 are ids 17 and 4 with q = 0.72, 0.18 (head 0.9); the trainer has p = 0.6, 0.15 at those ids (head 0.75), so ρ = 0.1 ÷ 0.25 = 0.4. Values computed with the real function.

Where they meet: both lanes use the same staging write (TQTokenSink.stage), the same finalizer and the same loss object. After the merge point, only two things differ: two extra columns per token (fetched by the trainer only when centering is on, _train_fields_for_step), and one added loss term. Setup rejects the cases it cannot handle: non-vLLM generation, filtered sampling (top_p<1, top_k), and non-unit temperature without processed logprobs.

What it costs. The two columns are 8·T·K bytes per row (32 MiB for a 32K-token row at K=128), stored and moved twice. On the vLLM side, the per-entry Python extraction runs on the server's event loop: on CPU it took 0.83 s at 8K tokens and 2.7 s at 32K tokens with K=128, during which that server answers no other request. CI shows it runs; no throughput, memory or convergence numbers exist yet. The review asks for those, plus a guard so top_logprobs>0 without centering is not paid for nothing. The PR also changed the existing image-capture path, and that change breaks multi-turn VLM runs even with centering off: see the next page.

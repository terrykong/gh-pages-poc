Seven pages on this PR, one question each. This one: who calls whom, in what order, at a checkpoint and at a restore.

A rollout checkpoint is run by the single controller's snapshot task. It talks to Gym through the NemoGym Ray actor, which posts to Gym's own servers under /ng-control/v1/checkpoint/…. Gym saves each agent's state, and TQ (the data store that holds every finished model call's tokens) saves its own snapshot. Prefix recovery keeps all of that and adds three things, drawn in orange below: a fence on the vLLM worker, the generation cut (Gym asks the worker to copy each running call's tokens into TQ), and a splice on restore. The example is one call, chat-A: 7 prompt tokens, max_tokens 20, and 5 tokens decoded when checkpoint ckpt-9 starts.

One save and one restore, both levels in one picture

What prefix adds, and nothing else changes.

  • A hold on end-of-call writes (① and ⑫). A Ray call from RL straight to each vLLM worker actor (begin_token_capture_snapshot_fence_async). It does not pause decoding and it is not the cut. It only holds each call's end-of-call data-plane write until the TQ snapshot is saved. That write also deletes the call's chunk rows, and a snapshot that names those rows must not lose them. The code calls it a "fence"; the draft review asks to rename it (C45).
  • The cut (⑤–⑧). Gym sends it, not RL. It runs inside Gym's own prepare step, when Gym's model server closes its gate (_cut_all). The worker writes one TQ chunk per running call, and its receipt goes into Gym's commit (⑨), so the TQ save at ⑩ checks for the chunk too.
  • The splice on restore (R5–R7). Gym re-sends the call with a generation_cut field. The worker fetches the chunk, adds its 5 tokens to the prompt, lowers max_tokens to 15, and puts the 5 saved tokens back in front of the reply.

Prefix is strictly added on top of turn. Both levels take the same Gym checkpoint path (requires_environment_checkpoint), and every prefix check in the code only adds work. One small difference: in prefix mode the save is not skipped when nothing in TQ has changed, because a running call may still have new tokens (snapshots.py:626). The RL restore path has no prefix check at all: it is Gym's restored cut records that make R4 carry generation_cut.

Four things that differ from the usual picture

  1. Nothing pauses running calls or the dataloader. Only two gates close: RL stops sending new rollouts to Gym (②), and Gym's model server makes new model calls wait and holds finished replies (④). vLLM keeps decoding chat-A the whole time (the green bar). The held replies go out at ⑪.
  2. RL never asks vLLM for a cut. Gym does, because only Gym knows which calls are running and which backend URL each went to (generation_cut_requester). RL's only direct line to the worker is the write hold (① and ⑫), as a Ray call.
  3. The order is prepare → Gym commit → TQ save → Gym resume → publish. Gym resumes at ⑪, before the snapshot is published at ⑬, so new rollouts do not wait for the publish (prepared).
  4. Nothing is swapped back after a save. The cut only copied the tokens. The chunk stays in TQ; a later checkpoint adds a new chunk with only the newer tokens, and all of a call's chunks are deleted when the call ends (vllm_worker_async.py:1859).
So what. Steps ①–④ and ⑨–⑬ are calls between the controller, Gym and the worker actors. They do not care how a chat call reaches vLLM, so they work the same behind Dynamo. Only the cut (⑤–⑧) and the restore splice (R4–R7) sit on the chat path. Those are the parts #4979 has to carry; the prefix with Dynamo page shows where they go.

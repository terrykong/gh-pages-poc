Before
At the reviewed head, RL read the agent's kept calls as one list, in order. Each call had to continue the one before it, unless it started a new tree. A branch was an error.
This PR now
RL builds a graph from the kept calls, finds every call with no kept child, and walks each one back to its root. That gives one row per end call. A call shared by two rows trains in the first row only.
Status
Partly done. The whole forest from Gym and the leaf-to-root walk are in. The option in RL to choose which paths to train is not in. Which calls the harness puts in its output decides which paths train.

Nine pages on this PR, one question each. This one: what the author's redesign changed in how calls become rows.

Background. Each time the agent calls the model, Gym saves one call record: an ID and the ID of the call it continues (its parent), or none if the call starts fresh. Compaction makes a fresh start, so one rollout becomes several trees: a forest. The agent also returns its normal output, which lists the answers it kept. A rejected retry is not in that list. RL joins the two and builds training rows. Dotted words have a short explanation: hover or tap them.

Gym already sent the whole forest at the reviewed head. Its call list holds every call, rejected ones included, with parent links. That part did not change. What changed is the RL step that turns kept calls into rows, _plan_selected_calls. The old code walked the kept list top-down and required one straight line per tree. The new code sorts the end calls and walks each one back to its root. The rows below are the real output of each commit's _plan_selected_calls, run on the same four small graphs.

Same calls, old planner vs new planner

Cases 1, 2 and 4 come out the same in both versions. The new planner only changes case 3: a branch with both sides kept. That is the case subagents and summary calls create. The script is plan_old_vs_new.py: it pulls _plan_selected_calls out of each commit and runs it on Gym's own record types.

Where the two paths meet

Without compaction, RL still uses the older code, not the new planner. Both paths end in the same Gym function, verify_and_linearize. It takes one end call and walks back to the root. The only difference is who picks the end calls:

# both: Gym's list of every call + parent (RolloutReceipt.manifest) no compaction end call = the scored answer → 1 row finalize_group L742 → finalize_rollout → verify_and_linearize compaction kept calls = matched from agent output select_captured_calls end calls = kept calls with no kept child L1300 one small call list per end call → N rows finalize_rollout L1427 → verify_and_linearize # same walk, once per row

So the walk is shared. What is not shared is the choice of end calls. That choice is fixed inside each path, and there is no setting for it.

Your proposal vs what landed

ProposalAt 1fe217ce
Gym always returns the whole forest Yes, and it already did at the reviewed head. Gym's call list holds every call, rejected ones too, with its parent. The new head also needs two Gym changes that are not public yet, a new close route and an admission field (separate finding).
RL walks from each leaf back to the root Yes. One row per end call, through the same walk as the path without compaction. A shared call trains once (loss off in later rows).
Several RL options for which paths to train: main path, whole tree, subagents No. There is one planner. It trains every path to every end call that the agent's output kept, so the harness decides (case 4). The only plug-in point is RolloutSelection: any source can pass in its own list of kept calls.
Simple agent and compaction use the same reassembler Partly. They share the walk, but not the step that picks end calls (previous section). On a graph with no compaction, the new planner gives the same single row (case 1).
Subagents Not yet. More than one session in the output raises an error. The guide says live multi-agent harnesses still need separate testing.
Bottom line. The redesign gives you the forest walk you asked for, and Gym's side was already the full forest. The open design question is where "which paths to train" is decided. Today the harness decides it through the calls it returns, not an RL setting. If you want that choice in RL, the place for it is the end-call list in _plan_selected_calls (proposed, not in the PR). A small rule there would take the graph of kept calls and return which end calls get rows. Everything after it already works one end call at a time.

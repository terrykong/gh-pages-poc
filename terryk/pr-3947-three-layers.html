Why the worker venvs get built in three different Docker layers

NVIDIA-NeMo/RL #3947 — perf(docker): hardlink worker venvs into layers · all links pinned to a6e758fd

1 · why three layers 2 · what gets stored

Two pages on this PR, one question each — this one: why the venv build is split across three layers.

NeMo-RL runs each kind of Ray worker in its own virtual environment, so a vLLM worker and a Megatron worker can depend on different things. The table in pyproject.toml lists 27 workers: 9 run on the driver's own Python, and 18 get a venv of their own. Every one of those 18 contains torch and the CUDA stack, so storing 18 real copies is not an option. The old build made them out of symlinks into a shared package cache. That kept the image small but produced roughly 1.5 million symlinks, and converting the image to a squashed file took about three hours. This PR switches them to hardlinks, which cut that to about 25 minutes. The reason that change ripples into three places in the Dockerfile is one rule about how Docker stores files.

The rule: a hardlink that reaches into a lower layer is not free

A hardlink is a second name for one file on disk. Docker stacks each build step as a layer, and a layer can only add files — it cannot point into the one below. So when you hardlink to a file that lives in an already finished layer, Docker copies that file up into the current layer first. Do that for 18 venvs and you have 18 real copies of torch instead of one.

That single rule decides the whole design: a venv has to be built in the same layer as the package cache it links against. The package cache is warmed up early — at the top of the dependency step. But two things the venvs need do not exist yet at that point, and neither can be moved earlier. That is where the second and third passes come from.

Three passes, because two ingredients arrive late

Each pass only adds what became available in its own layer, so every hardlink stays inside the layer that owns the file it points at. Splitting the work is not a style choice — put pass 1 in the release layer and every wheel is copied up; put pass 3 in the dependency layer and there is no source to install yet.

How each pass knows which venv to build

All three passes need the same fact: which extras does this worker need? Pass 3 is ordinary Python and reads it from ACTOR_ENVIRONMENT_REGISTRY. Passes 1 and 2 run in a layer that has no nemo_rl source — only pyproject.toml and uv.lock were copied in. So they cannot import that registry. This PR's answer is to move the mapping into pyproject.toml, where a shell step can read it with nothing but the standard library:

a worker in the table what each pass does with it ──────────────────────────── ───────────────────────────────────────────── "…MegatronPolicyWorker" pass 1: uv sync --extra mcore (hardlinked) = ["mcore"] pass 3: add nemo_rl, editable "…TrtllmAsyncGenerationWorker" pass 1: uv sync (base only — no wheel yet) = ["trtllm"] pass 2: uv sync --extra trtllm (wheel exists) pass 3: add nemo_rl, editable "…MathEnvironment" no venv at all — runs on the driver's Python = "system"

The same table is read three times by two different readers: a small Python snippet embedded in the Dockerfile for passes 1 and 2, and the normal registry for pass 3. Keeping one table means they cannot disagree — which is the argument for moving it out of Python in the first place.

What it buys, and what it costs. Roughly 1.5 million symlinks become about three thousand, and squashing the image drops from about three hours to about twenty-five minutes. The image grows about 3%, because a few files really are duplicated. The cost is spread through the build: the Dockerfile now carries a copy of the same Python snippet in two places, and the list of workers moved out of Python into pyproject.toml. Both are fixable without giving up the speed — the snippet can live in one small file that both passes call.

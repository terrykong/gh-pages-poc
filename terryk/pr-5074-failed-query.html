Why one dead frontend leaves the vLLM worker hanging after a metrics read

NVIDIA-NeMo/RL #5074 · all links pinned to head 908f05fa · vLLM 0.29.0 (98dff2a8)

Before
There was one frontend per engine, so there was no pool and no control pipe. A failed metrics read only lost a metric.
This PR
When any pool command fails, command() stops every child frontend and shuts down the shared engine. That includes the read-only progress and snapshot queries.
Status
Open, not fixed in this PR. Raised as review comment C15 (pending until the review is published).
one Gym call, three setups a failed query stops the engine

Two pages on this PR, one question each. This one covers what happens when one frontend command fails.

Background. With http_api_server_count: 3, a vLLM worker has frontend 0 (inside the Ray actor) and 2 child processes, NRL-HTTP-1 and NRL-HTTP-2. All three share one engine core process. Frontend 0 talks to the children over a pipe with 6 commands; two of them only read state: progress (how far each running call got, read at every refit) and snapshot (data-plane counters, read every step). The first page shows the layout.

Both reads are written as best-effort by their callers. The refit code catches any error and warns that "batch age is not worth a failed refit". The snapshot loop says "metrics must never fail a step". But inside the worker, command() handles any failure by stopping the children and calling close_engines(), which shuts down the engine core. Frontend 0 never learns of it: its vLLM client was built pointing at an engine it did not start, so no monitor watches the engine, and an engine stopped by SIGTERM exits without sending the "engine dead" message.

What would fix it — proposed in review comment C15, not in the PR

Where the fix lands: RL only, one file. multi_api.py __init__ and command(). No vLLM change is needed. The worker's shutdown() already closes the engine.

Nothing below is implemented or run. When a command fails, stop only the children, remember that the pool failed, and make every later command raise. That way the caller still gets its error, the engine stays up for frontend 0, and nothing quietly returns [].

Line by line: the flag starts as False. Any command after a failure raises right away, so a later version or snapshot cannot report success with no children. On failure the children stop and the error goes up to the caller, which already handles it. Catching Exception instead of BaseException also means a cancelled call does not tear anything down. Catching the error in captured_call_progress would not help: the engine is already closed inside command() before the caller sees the error.

So what. With more than one frontend, a single dead child process turns the next metrics read into a worker that hangs, with no error and a healthy-looking /health. Fleet health, which might notice, is rejected for this setup in the same PR. The fix is a few lines in command().

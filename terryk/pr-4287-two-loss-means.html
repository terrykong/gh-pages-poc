Two ways to average the training loss on Megatron — and what this PR adds

NVIDIA-NeMo/RL #4287 · all permalinks pin the PR head 438b6b6.

Before
NeMo-RL always forced Megatron into one mode: sum every token's loss, then divide once by the token count of the whole step.
This PR
Adds a config switch. true keeps the old mode. false adds Megatron-LM's default mode: average inside each microbatch first, then average those averages.
Status
Proposed, in review. true is unchanged as far as the review can tell. false works for SFT only. The PR also crashes about 30 shipped configs at setup, which is covered on the next page.

Two pages on this PR, one question each. This one covers what the new switch does.

A training step is split into microbatches: small slices that run forward and backward one after another. Their gradients add up, and the optimizer steps once. Different microbatches hold different numbers of real (unpadded) tokens. So "the average loss" can mean two different things. Dotted words have a short explanation: hover or tap them.

The new key is policy.megatron_cfg.calculate_per_token_loss. Setup used to hard-code it to True. Now setup copies the YAML value into Megatron (setup.py#L1942). Both modes build the loss the same way until train.py#L899, where they split. In false mode the loss hands Megatron a local sum and a local token count, and Megatron does the dividing (schedules.py#L335-L341).

Why keep both? true is what NeMo-RL has always used and what loss-functions.md recommends: every token counts equally. false matches Megatron-LM's default, so an SFT run can be compared directly with a Megatron-LM run. The cost is that the gradient then depends on micro-batch size and GPU layout. The review asks for a docs note saying so, plus true-vs-false loss curves on a MoE model with CP = 2, since no training run backs the new mode yet.

Why a slow NeMo-Gym startup reports a tokenizer error

NVIDIA-NeMo/RL #3371 — the startup budget is shared on purpose; it is the error message that needs fixing. All permalinks pin the PR head 917ffc3.

one actor per node the shared deadline the duplicate check

Three pages on #3371, one question each — this one: why the tokenizer gets blamed for a slow startup. Background from the PR below it in the stack: why a shard's port range never reaches Gym (#3369).

Starting the shards happens in two passes. First every actor is told to start its Gym stack, and we wait for all of them. Then every actor is handed the tokenizer, and we wait for those. Both waits read the same clock, set once before the first pass at deadline = monotonic() + spinup_timeout. So the second pass gets whatever the first pass left over — and on a cold node the first pass is meant to use nearly all of it.

That sharing is deliberate and correct: one knob should bound the whole startup. The problem is only what the operator is told when the budget runs out.

One budget, two consumers

The last step is the part that misleads. Ray treats timeout=0 as "check once and give up", not as "wait forever" — see ray.get's own docstring. So the install does not wait at all; it raises immediately, and the message the operator reads is shard 'tools' (replica 2) did not accept the tokenizer — which points at the tokenizer, when the real story is that startup used up the clock.

Sharing the clock is right — the message is not

The tempting fix is to give the install pass a clock of its own. That is the wrong fix. spinup_timeout is meant to bound the whole job of getting shards up, and handing over the tokenizer is part of that job. Two independent budgets would mean one knob set to 1800s can hang for 3600s — nobody sets a timeout expecting that.

So the budget should stay shared, and running out of it should still fail. What has to change is what the failure says.

today NeMo-Gym shard 'tools' (replica 2) did not accept the tokenizer: ... ↑ names a shard and the tokenizer. Neither is at fault, and which replica gets named changes from run to run. better NeMo-Gym shards used the whole 1800s startup budget before the tokenizer reached every replica. Raise env.nemo_gym.spinup_timeout, or bake the Gym venvs into the image so a cold node starts faster. ↑ names the budget, and what to do about it. No shard to chase.

The code change is one branch: ask how much budget was left, and if the answer was none, say so instead of blaming the tokenizer.

for shard_name, replica, reference in installs: + remaining = max(0.0, deadline - monotonic()) try: + ray.get(reference, timeout=remaining) except BaseException as error: + if remaining <= 0.0: + raise ShardSetupError( # the budget ran out + f"... used the whole {spinup_timeout}s startup budget ..." + ) from error raise ShardSetupError( # a real tokenizer failure, unchanged f"NeMo-Gym shard '{shard_name}' (replica {replica}) did not " f"accept the tokenizer: {error}" ) from error

A genuine tokenizer failure still reports "did not accept the tokenizer" — and now that sentence is true whenever you read it.

What this costs today. Not a hang, and not a wrong result — the run fails, which is what an exhausted budget should do. The cost is diagnosis. An operator loses roughly half an hour of virtual-environment building and is then pointed at a tokenizer that is fine and a shard picked by timing, so the natural next move is to go looking at serialization rather than to raise spinup_timeout or bake the venvs into the image.

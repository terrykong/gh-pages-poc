Why a slow NeMo-Gym startup reports a tokenizer error

NVIDIA-NeMo/RL #3371 — one clock is shared by two waits. All permalinks pin the PR head 917ffc3.

one actor per node the shared deadline

Two pages on #3371, one question each — this one: why the tokenizer gets blamed for a slow startup. Background from the PR below it in the stack: why a shard's port range never reaches Gym (#3369).

Starting the shards happens in two passes. First every actor is told to start its Gym stack, and we wait for all of them. Then every actor is handed the tokenizer, and we wait for those. Both waits read the same clock, set once before the first pass at deadline = monotonic() + spinup_timeout. So the second pass gets whatever the first pass left over — and on a cold node the first pass is meant to use nearly all of it.

One budget, two consumers

The last step is the part that misleads. Ray treats timeout=0 as "check once and give up", not as "wait forever" — see ray.get's own docstring. So the install does not wait at all; it raises immediately, and the message the operator reads is shard 'tools' (replica 2) did not accept the tokenizer — which points at the tokenizer, when the real story is that startup used up the clock.

The fix, and what actually changes

One line. The install pass starts its own clock instead of reading the one the startup pass has already spent. Everything else in the block is unchanged — it only appears in the suggestion because a GitHub suggestion has to re-state the lines it replaces.

# nemo_gym.py, the tokenizer-install pass + install_deadline = monotonic() + spinup_timeout ← new clock, starts now for shard_name, replica, reference in installs: try: - ray.get(reference, timeout=max(0.0, deadline - monotonic())) + ray.get(reference, timeout=max(0.0, install_deadline - monotonic()))

Read as values, with the same cold-node run as above:

at the moment pass 2 begins, 1798s into an 1800s budget today deadline - monotonic() = 1800 - 1798 = 2s ← shared, nearly gone ... after replica 0 and 1 = 0s ← replica 2 raises with the fix install_deadline - monotonic() = 1800 - 0 = 1800s ← fresh, full budget ... after replica 0 and 1 = 1798s ← replica 2 installs

The two passes stop competing for one clock. A genuine tokenizer failure still reports "did not accept the tokenizer", which is now true when you read it; and a startup that really does overrun still fails in pass 1, where the error names the shard that was slow.

Why this is worth fixing rather than tuning. Raising spinup_timeout does not help — pass 1 grows to use it and pass 2 is still last in line. The failure also moves around: installs that already finished still return at timeout=0, so which replica trips depends on timing, and the operator sees a different shard named each run. The cost of hitting it is the whole set torn down after roughly half an hour of virtual-environment building, with an error pointing at the wrong thing.

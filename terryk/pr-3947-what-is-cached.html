Two pages on this PR, one question each — this one: what the image actually holds, and why the count dropped.

The thing being pre-built is one venv per worker class, not one per dependency set. 18 workers get a venv, and five of them are vLLM workers that end up with the same package list — because the venv directory is named after the worker, so …VllmGenerationWorker/ and …ReplayBuffer/ are separate directories. The build has to make exactly the directories the runtime will later look for, or the prefetch is wasted.

Separately, the package bytes themselves have always shipped in the image: /root/.cache/uv is a real directory in the image, not a temporary build mount, and nothing deletes it. So this PR did not change what is stored. It changed how those 18 directories point at it.

A symlink costs an inode. A hardlink does not.

Three venvs drawn; the image has 18. A symlink is a tiny file that stores a path, so it needs its own inode. A hardlink is a second name in a directory for an inode that already exists — no new inode, no new bytes.

So what is the +3% for?

Not the venvs. Hardlinking them is nearly free. The extra size comes from files that cannot be shared, plus the one case where a hardlink is refused:

what shared? why ────────────────────────────────────── ─────── ───────────────────────────── package files (torch, CUDA, …) yes hardlink to /root/.cache/uv site-packages directory tree no directories cannot be hardlinked bin/ console scripts, pyvenv.cfg no the venv's own path is baked in anything hardlinked across a layer no Docker copies it up first

The last row is the one that shapes the Dockerfile: a hardlink reaching into an already-finished layer forces Docker to copy that file up, which is why the venvs have to be built in the same layer as the cache they point at. That constraint is what splits the work into three passes. It is also why the TRT-LLM build is sent to a throwaway venv in symlink mode — hardlinking there would drag copies into the image that outlive the rm -rf.

The part worth deciding on. Five vLLM workers get five identical venv trees, because the directory is named after the worker class rather than the dependency set. With hardlinks the wasted bytes are close to zero, so this is no longer a size problem — but it is still 8 redundant directory trees out of 18. Collapsing them would mean changing the name the runtime looks up, which is a separate change from this PR and worth weighing on its own.

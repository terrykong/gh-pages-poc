Five pages on this PR, one question each. This one: why single-rollout retry needs an ablation before it is on by default.

Two paths, named the same way on every page. v1 = grpo_train, async_grpo_train, PPO and distillation. v2 (single controller) = examples/run_grpo_single_controller.py. A group is one prompt with G answers (called rollouts or rows). GRPO scores each rollout against the others in its group (calculate_baseline_and_std_per_prompt), so the rollouts of a group are meant to come from the same policy.
v1v2 (single controller)
Main No single-rollout retry. A failed /run ends the step. Re-sends the rows that never arrived (attempt loop): the failed row and every sibling still running, right away.
This PR Single-rollout retry added, off by default (DEFAULT_MAX_INFRA_ATTEMPTS_PER_ROLLOUT = 1). Siblings keep running; only the failed row is re-sent, after the stream finishes (rollout_manager.py#L1206-L1220). On by default.
After the review v1+v2 C14 One flag, off by default (for example env.nemo_gym.retry_single_rollouts: false). Off = main on both paths. On = this PR's behavior. Setup fails if the v1 row budget is above 1 while the flag is off.

Proposed in the review: default off until ablated. Nothing below has been measured.

One group, six ways

The same example as the failure-rows page: four rows take 2, 4, 7 and 9 minutes, and row 2 fails at minute 5. Assumption, not a measurement: the policy moves on one version every 4 minutes, so a rollout started at minute 5 gets k+1 and one started at minute 9 gets k+2. Each bar is colored by the version the rollout started on.

  1. v2 main already mixes versions: rows 0 and 1 are k, rows 2 and 3 are k+1. Two versions, one apart.
  2. v2 with this PR keeps row 3 on k, but row 2 waits for the stream to end and starts at minute 9 on k+2. The gap grows to two versions, and one rollout stands alone on the newest policy.
  3. Whole group redone puts all four on the same version. It throws away finished work, but the group compares like with like.
  4. v1 sync cannot mix: the weights do not change during a step. v1 async mixes only with in_flight_weight_updates on; otherwise refit waits for the batch. Both v1 lanes need the budget raised by hand, because this PR keeps it at 1.
  5. v2 records one start and one end version per group, not per rollout (L2080, L2115-L2116), so nothing downstream can tell which rollout came from which policy.

What the review asks — proposed, not in the PR

Where it lands: RL only. nemo_gym.py L1148 (the actor that both paths call) reads the flag; v1 setup checks the budget. No Gym change: Gym already supports both modes.

  • Off (default) = main. The actor does not pass route_failures_to_sidecar, and a failed /run raises and is typed the way main does it (_typed_gym_failure(error), linked at the base because this PR removes it). v2 goes back to re-sending the failed row with its running siblings at once; v1 ends the step.
  • On = this PR. Only failed rows are re-sent.
  • Fail loud. Setup raises if the v1 row budget is above 1 while the flag is off, so the setting is never silently ignored.
  • Before turning it on by default: an ablation, not part of this PR. Run the same recipe with the flag off and on, inject failures, and compare reward curves.

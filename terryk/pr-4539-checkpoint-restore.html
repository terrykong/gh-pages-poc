Status
New in this PR; the review found no bug in the logic. Not tested in CI, and one error message is wrong (last section).

TQ saves its controller first and the storage second, and it restores the storage first. Nothing else runs on the data plane during a save. Each storage unit copies its own live blobs into one file, from its own node, with ordinary file writes. Next to it, a .rows file lists which keys in each blob are still live. A blob can still hold a key that was later overwritten or cleared, and restore must not bring that key back. The example uses 4 rows (4, 5, 6, 7) of field responses, each a tensor[6] of int64 (6 token ids), saved from 3 units.

What this means in practice

  • No network transport is involved. A unit copies from its own memory, or from its SSD file, straight into the checkpoint file (save_shard). So the save works the same whatever moves bytes between machines. If puts ever came from GPU memory, the save would not change, because the rows always sit in the unit's CPU memory or on its disk.
  • The checkpoint folder must be shared storage. Every unit writes its file from its own node, and the driver writes the manifest and, on the slow path, reads every file.
  • Same units: fast, one step per unit. When the saved unit_ids match the running ones, unit k reads unit-k.shard back into its own memory. It fills RAM first and then the SSD tier (_load_in_place).
  • Different count: slow, everything goes through the driver. The driver reads every shard and puts each live key again through the normal client, so each row lands on unit row % N for the new N (_load_rerouted). Units default to one per node, so a restart on a different number of nodes takes this path.

Could NeMo-RL's own vLLM worker be the external server, so every launch shape runs the same code?

Design proposal for the #4674–#4677 stack · main at efc30951 · Dynamo PR #4905 at b0b6b32c · vLLM v0.29.0

Before
NeMo-RL's own vLLM worker runs only as a Ray actor inside the training cluster. All of NeMo-RL's vLLM extras (reshard, delta refit, MXFP8, exact prefix tokens) live in that worker.
The stack
Adds external rollout with stock vllm serve plus a plugin wheel. So reshard, delta refit, MXFP8/NVFP4 and fleet health are refused in every PR of the stack.
Status
Proposed, not implemented. Read from the code; nothing on this page has been built or run.

Seven pages on this stack, one question each. This one: an alternative design.

Background. A vLLM worker is the process that holds the model and generates rollouts. Refit copies new weights into it after each step. Today the trainer drives the worker with Ray calls, and Ray also places it on GPUs and spreads it across nodes. Dotted words have a short explanation: hover or tap them.

The idea: keep one copy of the worker code, and launch it three ways. The two ways that exist today stay as they are. The new, external way starts the same worker as a plain process on its own nodes, with no Ray. The trainer then drives it over HTTP instead of Ray calls, and weights still move over NCCL. Because it is the same code, external rollout gets every feature the worker already has, and #4905's Dynamo switch comes along too.

The last row is the real trade. Stock vLLM lets any vLLM deployment plug in, but every NeMo-RL extra must be rebuilt as a plugin. The NeMo-RL worker gets every extra for free, but the server has to match the trainer's NeMo-RL commit. The worker's own environment already installs all of nemo_rl, so splitting it into a package would mostly mean a much smaller list of dependencies.

What would have to change: proposed, not in any PR

Nothing below is implemented. Sizes come from reading the code on main and #4905.

Where it lands: RL only. No vLLM change: vLLM 0.29.0 already runs TP across nodes without Ray (headless followers), and its collective_rpc reaches workers on other nodes. No Gym change: Gym only sees base URLs.

  1. Let the worker run without Ray. Small. Choose vLLM's mp executor and pass nnodes/node_rank. Take the GPU for NUMA pinning from CUDA_VISIBLE_DEVICES, using the existing resolve_visible_gpu_id. Apply @ray.remote only in Ray mode (it already sits on a thin subclass).
  2. A follower launcher for nodes 2..N. Plain vllm serve --headless is not enough. Each node loads the worker extension from its own config, so every node must build exactly the settings node 0 builds.
  3. HTTP admin routes, and an external backend on the trainer that calls them. About 18 methods go over Ray today: refit, reshard, pause and resume, sleep, cache reset, weight version and metrics. NeMo-RL's SGLang backend already works this way: its worker is a thin wrapper that sends every control call over HTTP. A capabilities route reports the server's TP/PP layout, which reshard needs.
  4. Fleet health over HTTP. The existing hooks fit: liveness probe, restart and NCCL group rebuild. The trainer can't start processes on other nodes, so "restart" becomes "wait for Slurm to bring the URL back, then refit it before it serves". The health check must also test the engine, since /health always says ok today.
  5. Split into a package. About 25k lines move as they are. About 6 imports have to be cut. The worst is that the worker's config imports interfaces.py, which pulls in Ray.
  6. Dynamo "attach" mode. In #4905 Dynamo is already a switch on this same worker, and control never goes through Dynamo. For external, the etcd, NATS and frontend addresses come from config, not from a trainer-started runtime. Registration starts from a launch flag, not a Ray call. The shard ID must not be a Ray group index. A restarted server stays unregistered until its first refit.

The first hunk keeps today's behavior unless a launcher passes nnodes. The second leaves the Ray path alone. launch_mode is a new setting the launcher would set. Neither hunk has been run.

Not checked yet:

  • Expert parallel and vLLM-internal data parallel across nodes under the mp executor.
  • Whether reshard's metadata survives JSON as it is.
  • Whether the refit rank offsets line up across Slurm het groups.
  • How long the trainer takes to notice a dead follower node (today: only a timeout on node 0).
So what: the stack's design question is whether the external server must be stock vLLM. If it doesn't have to be, launching NeMo-RL's own worker as the external server makes reshard, delta refit, MXFP8, exact prefix tokens, fleet health and Dynamo all work, with one copy of the code. If it does, the plugin wheel has to keep copying each of those features. Settle this before the plugin wheel grows.

Why the vLLM generation actor stops answering refit calls under a backlog, and the two settings that fix it

NVIDIA-NeMo/RL #4820. Builds on #4634 (its explainer). NeMo-RL permalinks pin the PR head f386235; vLLM links pin v0.29.0, the version the repo uses.

Before
With many requests in flight, the async vLLM actor stopped running anything else for minutes at a time. Refit calls queued behind generation output, and one run hung at step 1.
This PR
Adds two settings under policy.generation.vllm_cfg: output_loop_yield_budget_ms makes vLLM's output loops take turns, and flat_logprobs stores logprobs in a few lists instead of one Python object per token.
Status
Fixed by this PR when you turn the settings on. Both are off by default, so nothing changes unless you set them.
Background. In async GRPO, one Ray actor runs vLLM's AsyncLLM. Everything on that actor shares one event loop: the loop that reads finished tokens from the GPU engine, the loop that turns them into text and logprobs, the HTTP server's requests, and every Ray call — including the refit. If one task never hands over control, every other one waits. Dotted words have a short explanation: hover or tap them.

vLLM's socket reader awaits output_socket.recv_multipart() for each message from the GPU engine. With a backlog, the next message is always already waiting, so the receive returns a finished future, and awaiting a finished future does not hand control to anyone else. The second loop, output_handler, has the same shape: it calls get_output_async() once per engine step and only yields between chunks inside one step, never between steps. So the two loops can hold the event loop for as long as the backlog lasts.

One event loop, 50 waiting messages: when does the refit call run?

The same idea fixes output_handler: the PR wraps get_output_async() so it yields once after each engine step. In the real run the loops were held for minutes, not milliseconds, because the backlog was thousands of requests deep. Yielding the reader on every message was tried first. It starved the reader against output_handler, and the backlog just moved into the socket. A time budget gives each loop a fair share.

What the two settings change

Where the change lands: RL only. A new module, output_loop_yield.py, patches vLLM's two loops right after the engine is built (vllm_worker_async.py L451). The HTTP client turns on vLLM's existing flat_logprobs option per request (L187-L192). A setup check rejects either setting when its requirements are missing (config.py L297-L322). No vLLM change: both use vLLM as it ships. The patch raises at engine start if vLLM's internals are missing, and a test in the vLLM CI lane checks the calls it relies on.

flat_logprobs attacks a second cause of stalls. By default vLLM keeps, for every generated token, a dict plus one Logprob object per candidate token. With thousands of requests in flight that is millions of small objects, and Python's full garbage collection pass over them held the GIL for up to ~25 s. vLLM's FlatLogprobs stores the same values in a few flat lists per request, and reading a position gives back the same dict. It is skipped for requests that ask for prompt logprobs, because vLLM's -inf clean-up edits throwaway copies there and the request would fail at JSON time.

So what. If async GRPO refits get slow or hang when many requests are in flight, set async_engine: true, expose_http_server: true, flat_logprobs: true and output_loop_yield_budget_ms: 20. The settings do not make token processing cheaper; they cap how long that work can block everything else. The PR only measured them turned on together.

Three pages from the #3925 review — this one: whether restoring can lose a prompt.

Every group in the recovery ledger is in one of two phases, and the difference decides everything below:

phasewhat happenedsealed siblingson restore
RESERVED claimed from the dataloader, but the sampler admission never committed — so it was never dispatched always 0 re-admitted as a batch — and this is the only phase that can be discarded
ADMITTED admission committed; dispatch happens after, so generation may have started 0 to 3 of 4 relaunched unconditionally, never dropped

The phase is set when the group is first recorded — ADMITTED if admitted else RESERVED — and moves to ADMITTED when the admission commits. That ordering is why a RESERVED group has no generated work in it: dispatch cannot happen before admission.

One line in the restore path can drop a prompt. It runs while re-admitting a batch of RESERVED groups — prompts the sampler claimed from the dataloader but never dispatched:

buffered = self._buffer.count_for_target_step(target_step) if buffered: dispatch_count = max(0, len(group_ids) - buffered) dispatch_group_ids = group_ids[:dispatch_count] for group_id in group_ids[dispatch_count:]: self._rollout_manager.discard_prompt_group(cut, group_id) # never re-served

single_controller.py:1149-1152

It fires when buffered > 0 — the replay buffer already holding a finished group for the step this batch is being admitted to. The question is whether that state is reachable on a run that can restore. It is.

The counter-example, run against the real code

The borrow is what puts a finished group into a step that was never dispatched, and it runs in both modes. There are two call sites, and the recovery one is not a no-op — it is simply done earlier, inside a checkpoint-atomic mutation cut, because ledger ownership has to transfer atomically:

# under rollout recovery — inside the mutation cut self._rollout_manager.discard_prompt_group(cut, lineage_group_id) if replacement is not None: lender_step = self._promote_into_step(target_step) # :1983 — the borrow ... # without rollout recovery — the same borrow, plainly if not self._rollout_recovery_enabled: lender_step = self._promote_into_step(target_step) # :2020

single_controller.py:1983 and :2020. The if not … guards in this area are “don’t do it twice”, not “recovery disables this”.

Group size 4, and a training step takes 3 groups. Read the three panels left to right — the first two happen live, the third after the restart.

The last row is what the probe prints. Same numbers, produced by the real _admit_reserved_prompt_groups rather than by reading it:

--- A: step 9 is empty reserved : 3 target_step assigned: 9 buffer reported : 0 already stamped for that step dispatched : 3 DISCARDED : 0 [] --- B: step 9 already holds the repayment group reserved : 3 target_step assigned: 9 buffer reported : 1 already stamped for that step dispatched : 2 DISCARDED : 1 ['dea5deb3-a9bd-45e6-8a3e-5306c64a6e11']

Only the buffer’s answer differs between the two cases. Everything else — the sampler, the ledger, the admission — is the same production code.

One reserved prompt is released and never served again. It is a RESERVED group, so no generated rollout is lost — discard_prompt_group releases “a reservation that will intentionally never be dispatched”, and the record is simply deleted. What is lost is the prompt: the dataloader cursor is already past it, so that example is not trained on this epoch.

What has to line up, and what it means for the counters

What this means for the PR. groups_considered and groups_redispatched are not redundant — their difference is exactly the count of prompts released without ever being generated. That difference is worth naming rather than leaving to subtraction.

And nothing tests it. Every scenario in the recovery matrix builds groups with admitted=True, so the RESERVED arm never runs there, and the one test that does build RESERVED groups replaces the admission with a stub — so the discard has never executed in CI. The probe above is the first time it has run.

Correction. An earlier version of this page argued the opposite — that conditions 3 and 4 were mutually exclusive because save_data_plane gated the borrow off. That was wrong: the borrow has two call sites and runs under recovery too. The probe was written to settle it by execution rather than by another reading of the code.

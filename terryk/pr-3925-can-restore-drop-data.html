Can a restore throw away a prompt?

For NVIDIA-NeMo/RL #3925. All permalinks pin a4c10a78.

recovery counters dropped prompts can restore drop data

Three pages from the #3925 review — this one: whether restoring can lose a prompt.

Short answer: no, as far as the code can be read — and it fails on a contradiction, not a coincidence. Two of the conditions required to drop a prompt at restore are controlled by the same setting, in opposite directions.

There is exactly one line in the restore path that can drop anything. It runs while re-admitting a batch of RESERVED prompt groups — ones the sampler had claimed from the dataloader but never dispatched:

buffered = self._buffer.count_for_target_step(target_step) if buffered: dispatch_count = max(0, len(group_ids) - buffered) dispatch_group_ids = group_ids[:dispatch_count] for group_id in group_ids[dispatch_count:]: self._rollout_manager.discard_prompt_group(cut, group_id) # never re-served

single_controller.py:1149-1152

It fires only when buffered > 0 — the replay buffer already holds a finished group stamped for the step this batch is being admitted to. So the question becomes: how does a step that was never dispatched already have a finished group?

The five conditions, and the one that closes

The gate is one line, and it is the whole argument:

if not self._rollout_recovery_enabled: # condition 4 lives in here lender_step = self._promote_into_step(target_step) # and rollout recovery is exactly what makes a restore possible: self._rollout_recovery_enabled = bool( restoring_rollout_recovery or (checkpointing["enabled"] and checkpointing["save_data_plane"] and ...) )

single_controller.py:2019 and :497-504. _promote_into_step is the only caller of promote_ready_group in the repo, so there is no second way to move a finished group into another step.

Also worth knowing: the groups that could be dropped have no generated work in them. Only RESERVED groups reach that code, and discard_prompt_group says so outright — it releases “a reservation that will intentionally never be dispatched.” So even in the impossible case, no rollout would be thrown away; only a prompt claim. Groups that were dispatched are ADMITTED, and every one of those is relaunched unconditionally.

What I could not rule out

This is read from the code, not observed in a run, and the restore path in question has no test coverage. Every scenario in the recovery matrix builds groups with admitted=True, so the RESERVED arm never runs there. The one test that does create RESERVED groups replaces the admission with a stub, so it never reaches the discard either.

Two things would change the answer, and neither is visible from reading:

  • a restored sampler dispatch cursor that rewinds onto a step the buffer already has groups for;
  • any future caller of promote_ready_group that is not behind the recovery gate.

What this means for the PR. If the two counters can never differ on the restore path, then groups_considered and groups_redispatched are always equal in every run that emits them, and one of them is redundant. If they can differ, the case deserves a test, because none exists. Either answer improves the change, and the author can settle it in a sentence — he wrote the recovery path.

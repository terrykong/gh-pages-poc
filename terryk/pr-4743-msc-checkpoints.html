Checkpoints in S3: how a save is marked complete without a rename, and how resume finds it

NVIDIA-NeMo/RL #4743 · feat(checkpoint): opt-in MSC (S3) checkpoint storage · permalinks pin the PR head b3ae176

Before
Checkpoints could only go to a filesystem path. A save went to a temporary folder that was renamed when done.
This PR
Adds checkpoint_dir: msc://<profile>/<prefix>. The run writes straight into the bucket and marks a finished step with an _SUCCESS file. Plain paths keep the old rename.
Status
New feature; the save-and-mark design is sound, and it has been run end to end with Megatron on GB300. Open in review: the PR's own new test fails, and a few msc:// paths still break (last section).
Background. Multi-Storage Client (MSC) is an NVIDIA library that reads and writes S3, GCS or Azure through one API. A path like msc://sbx/run means "the storage setup named sbx in the MSC config file, folder run". Megatron can already write its checkpoint shards through MSC, but only in a process where a per-process MSC switch is turned on. Dotted words have a short explanation: hover or tap them.

Object storage has no cheap rename: "renaming" a folder means copying every object in it. So the old trick, write to tmp_step_6/ and rename it to step_6/ when done (_rename_checkpoint), does not work in a bucket. For msc://, the PR writes into step_6/ from the start and, once every writer has finished, adds one small file, step_6/_SUCCESS (L405-L409). Resume only looks at steps that have that file (_msc_step_dirs), so a half-written step is never picked up.

Same save, two storage paths

One save of step 6, with save_period: 3, through both paths. Every algorithm calls the same three CheckpointManager methods; the two paths split only inside them.

Where the two paths meet. The algorithm code is the same for both. Each one calls init_tmp_checkpoint → policy.save_checkpoint → finalize_checkpoint, and the non-model files go through new helpers that accept either kind of path: save_dataloader_state, path_exists / open_path. The split happens inside CheckpointManager, on one check, self._msc is not None, in four places: start, mark complete, find latest, and delete old steps. What still differs after that: the msc:// path refuses to overwrite a finished step, and it needs save_data_plane=false, so a SingleController resume rebuilds its buffered rollouts instead of restoring them (checkpoint.py L257-L261).

Why keep both. A local or shared filesystem gets the atomic rename for free and needs no MSC config. msc:// skips the copy to a bucket after training, at the cost of a marker file and of every process that hands Megatron a path having to turn its MSC switch on first. That last cost is where most of the open review items come from.

What the review still asks for

Where the fixes land: RL only. No Megatron or MSC change is needed: both already handle msc:// once the switch is on. An earlier review also found three save or resume sites not converted yet (the Megatron value worker, async PPO resume, and sft_v2); those are in its own comments.

So what. Point checkpointing.checkpoint_dir at msc://<profile>/<prefix> and a Megatron run saves to and resumes from S3 directly. A step counts only once its _SUCCESS file exists, so a crash mid-save is safe. Plain filesystem paths behave exactly as before. Use a fresh prefix for each new run, because a finished step is never overwritten.

1 · turn vs sibling 2 · restart-only agents stall

Two pages on this PR, one question each. This one: which Gym setups can use turn.

Background. A Gym deployment has an agent (runs the multi-turn loop), a policy model server (RL's vLLM behind Gym), and resources servers (tools and state). To save a snapshot, Gym asks every server to prepare: stop taking work and reach a state it can write to disk. A server that cannot save a half-done rollout is restart-only. Dotted words have a short explanation: hover or tap them.

Gym prepares the servers one stage at a time, model before agent (PREPARE_ORDER). Once prepared, the model holds every reply until resume (release_response), and RL never turns on Gym's generation cuts, so nothing lets a call finish early (checkpoint_generation_cuts: False). A restart-only agent counts every running /run as a blocker (readiness), and those runs are waiting for the model's held replies. So the agent can never become ready. RL treats that "not ready" as a passing problem (coordinator L89) and tries again at the next snapshot.

One snapshot attempt, two Gym setups

How many Gym setups hit this: only simple_agent can save its sessions (default False; 1 of 57 agents at this Gym commit). Resources servers default to restart-only (checkpoint_mode, what it means), and 8 of 146 opt out. A restart-only resources session is live from seed to verify, so it blocks the same way. The functional test passes because Workplace is one of the setups that works. Nothing at startup or in the docs warns about the others.

What would fix it — proposed, not in the PR

Where the fix lands: Gym (one method) and RL (one check). Gym: RestartOnlyAgentParticipant says it is restart-only in its status, the way resources servers already report their mode. That fits in the unmerged Gym branch this PR already pins. RL: GymCheckpointAdapter.discover, which already runs once at setup, refuses turn when any server is restart-only.

Nothing below is implemented or run. The RL part is a sketch.

_status(name) reads the same /ng-control/v1/checkpoint/status route Gym's own discover already calls. _is_restart_only is true for {"restart_only": True} or {"mode": "restart_only"}. The run then fails at setup with a message that names the servers, before any GPU work.

The wrong fix. Gym's docs say the controller should resume, retire the blockers and prepare again (coordination.py:22-23). With a restart-only agent, every running rollout is a blocker. So each snapshot would cancel every rollout in flight, and when the snapshot interval is shorter than a rollout, no rollout ever finishes.

So what. With target_level: turn, any Gym environment other than simple_agent plus a session-saving resources server does not recover at turns. Each snapshot pauses /run dispatch for up to 300 s and then fails. After 3 failures in a row, the run stops, and before the first step it stops at the first failure. Until the setup check lands, use target_level: sibling for those environments.

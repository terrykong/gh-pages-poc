Four pages on this PR, one question each. This one: which Gym setups can use turn.

Background. A Gym deployment has an agent (runs the multi-turn loop), a policy model server (RL's vLLM behind Gym), and resources servers (tools and state). To save a snapshot, Gym asks every server to prepare: stop taking work and reach a state it can write to disk. A server that cannot save a half-done rollout is restart-only. Dotted words have a short explanation: hover or tap them.

Gym prepares the servers one stage at a time, model before agent (PREPARE_ORDER). Once prepared, the model holds every reply until resume (release_response), and RL never turns on Gym's generation cuts, so nothing lets a call finish early (checkpoint_generation_cuts: False). A restart-only agent counts every running /run as a blocker (readiness), and those runs are waiting for the model's held replies. So the agent can never become ready. RL treats that "not ready" as a passing problem (coordinator L89) and tries again at the next snapshot.

One snapshot attempt, two Gym setups

Example: rollout s1 has finished turn 1 and is in the middle of turn 2 when the snapshot starts.

How many Gym setups hit this: only simple_agent can save its sessions (default False; 1 of 57 agents at this Gym commit). Resources servers default to restart-only (checkpoint_mode, what it means), and 8 of 146 opt out. A restart-only resources session is live from seed to verify, so it blocks the same way. The functional test passes because Workplace is one of the setups that works. Nothing at startup or in the docs warns about the others.

In the setup that works: where s1 parks, and what the snapshot keeps

simple_agent has two park points (Gym calls them boundaries) in every turn: right after the model's reply (app.py:398) and after that turn's tools return (app.py:482). There is none in the middle of a tool call. So where s1 parks depends on what it is doing in turn 2:

s1 in turn 2 is…Where it parksWhat commit saves for s1After resume, no crashAfter a crash and restore
waiting on the model (the usual case) End of turn 1. Gym does not wait: the call keeps running on vLLM, and its reply is held (model.py:8-13) Turn 1, model reply and tools. The turn-2 call's tokens are left out. Gets the held reply and runs turn 2's tools. Nothing is redone. Turn 2's model call is sent again and generated from scratch.*
receiving the model's reply (already streaming) Turn 2, after the reply, before its tools. A reply that started sending is allowed to finish. Turn 1, plus turn 2's reply. Tools not run yet. Runs turn 2's tools. Runs turn 2's tools from the saved reply.
running a tool End of turn 2. Gym waits for every tool in that turn to return, inside the 300 s prepare limit. Turns 1 and 2, model replies and tools. Goes on to turn 3. Goes on to turn 3.

The tool server saves its state at commit, after every agent has parked, so no tool call is in flight when it saves. Its saved state always matches the turn the agent parked at. The second row happens only if Gym has already asked agents to park when the reply arrives; otherwise s1 starts its tools and ends up in the third row. * Gym can keep a call's partly generated tokens (a "generation cut"), but RL does not hook that up in this PR.

What would fix it — proposed, not in the PR

Where the fix lands: Gym (one method) and RL (one setting, one setup check). Gym: RestartOnlyAgentParticipant says it is restart-only in its status, the way resources servers already report their mode. That fits in the unmerged Gym branch this PR already pins. RL: a new rollout_recovery.allow_restart_only_servers setting, GymCheckpointAdapter.discover finds the restart-only servers, and _spinup_gym decides.

Nothing below is implemented or run. The RL part is a sketch. The two modes:

  • false (the default): setup fails if any Gym agent or resources server is restart-only, and the error names them. You find out before the run starts, not after 15 minutes of failed snapshots.
  • true (best effort): setup prints a warning naming those servers, and the run uses sibling. Snapshots skip the Gym phase, so nothing stalls. A crashed rollout restarts from its prompt, and the finished rollouts in its group are kept. A Gym checkpoint covers the whole deployment today, so this turns turn off for every environment in the run.

In order: the Gym agent reports itself in /status. _status(name) reads the same /ng-control/v1/checkpoint/status route Gym's own discover already calls, and _is_restart_only is true for {"restart_only": True} or {"mode": "restart_only"}. _initialize_checkpoint_adapters_concurrently already gets every replica's summary from ray.get and drops it; it passes the names up instead. _spinup_gym decides before the controller and the ledger are built, so no group is recorded as turn and no restore looks for Gym state that was never saved (single_controller.py:1273-1285).

Later: skip only the rollouts that can't be saved. This is what "best effort" should mean in the end, and it needs Gym and RL changes together. In Gym, a rollout that uses a restart-only agent or resources server does not block prepare and is not saved by any server; all servers together, or a restored rollout would go on without its tool state. In RL, the drain (L4622-4636) and the ownership check before the TQ save (L4666-4676) accept those rollouts. Restore already restarts any rollout Gym did not save from its prompt (rollout_recovery.py:527-548). Then true keeps turn for the environments that support it.

Not this. Gym's docs say the controller can resume, retire the blockers and prepare again (coordination.py:22-23). With a restart-only agent, every running rollout is a blocker, so each snapshot would cancel every rollout in flight. When the snapshot interval is shorter than a rollout, no rollout ever finishes.

So what. Today, with target_level: turn, any Gym environment other than simple_agent plus a session-saving resources server does not recover at turns. Each snapshot pauses /run dispatch for up to 300 s and then fails. After 3 failures in a row the run stops, and before the first step it stops at the first failure. Until the setting lands, use target_level: sibling for the whole run when any such environment is in it: per-environment overrides are not allowed with turn.

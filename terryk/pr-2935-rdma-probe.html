Why data_plane.backend=mooncake_cpu never actually used RDMA — and what turning it on cost

Companion illustration for NVIDIA-NeMo/RL #2935. All permalinks pin the PR head 881a433.

NeMo-RL can move rollout data between processes through a data plane. One backend, mooncake_cpu, is meant to push that data over RDMA — the network card copies memory straight to another machine without the CPU. To do that, mooncake needs the name of a network card, like mlx5_3. The old code looked that name up by walking a file path in /sys, and it cut one directory too few, so it always returned the word ports — not a card. This page shows that walk, and the second thing the fix uncovered: once RDMA really turned on, the memory settings became real allocations.

1. The path walk that could never name a card

Linux lists each card under /sys/class/infiniband/. The probe globbed one file per card and then walked back up the path to recover the card's name. dirname removes the last piece of a path; basename keeps only the last piece. The old code ran dirname twice where it needed three.

There was a second reason RDMA never ran: the transport defaulted to TCP. The old _mooncake_transport_config() read MC_MOONCAKE_PROTOCOL and returned {"protocol": "tcp"} unless you set it to rdma by hand. So a run either used TCP, or — if you did set the variable — asked for a card called ports and failed. Either way, no run over RDMA.

This PR removes the choice. mooncake_cpu is now RDMA only: a host with no usable card raises instead of quietly running over TCP, and every card on the host is offered rather than just the first one.

2. Turning RDMA on made the memory real

Mooncake reserves two blocks of host memory per process: a segment it shares with other machines, and a local buffer. Over TCP those were ordinary allocations the kernel only backs with real pages when touched. Over RDMA they are pinned with ibv_reg_mr at startup — real, resident, and not swappable. The old defaults were sized as if they were free. One process runs per GPU, so an 8-GPU host pays eight times.

The number 64 appears in both rows but means two different settings: the old local buffer, and the new segment. Every other value on this page appears once.

The new defaults live on the config class, and each backend now has its own block in the YAML rather than four settings sitting loose at the top level:

data_plane: backend: "mooncake_cpu" mooncake_cpu: # only the block named by `backend` is read global_segment_size: 68719476736 # 64 GiB per process (was 512 GiB) local_buffer_size: 4294967296 # 4 GiB per process (was 64 GiB)

3. Does it work?

Two runs, both with backend=mooncake_cpu over RDMA, and both repeated with backend=simple as a control so the data plane could be told apart from the model.

RunSetupResultW&B
llama-3.1-8B 2 nodes x 8 GPUs, 10 steps 10/10 steps, reward 0.343 → 0.437 xdsn2kek
DeepSeek-V3 32 nodes x 8 GPUs (256 GPUs), 10 steps check_metrics.py 3/3 pass; ~270–400 s/step cpqmwppy

The author reports zero falling back to TCP lines in either run, which is the thing to check given that a silent TCP fallback is exactly what used to hide the broken probe. At 2 nodes the two backends track each other step for step (reward agrees to about 0.015), so the data plane is not changing the maths.

One honest gap: on DeepSeek-V3 the metric train/token_mult_prob_error shows occasional large spikes — 37.99 on mooncake, and 2039 on simple, which never touches mooncake or RDMA at all. So the spikes belong to that model and recipe, not to this change. The recipe's own check only asserts the smallest value stays under 1.05, so it cannot see those spikes on either backend.

What this means for you. Any earlier run that claimed mooncake RDMA coverage was really running TCP, so treat those numbers as a TCP baseline. If you turn this backend on now, budget the memory: it is pinned at startup and multiplied by the number of GPUs on the node, so the 544 GiB above is the floor for an 8-GPU host, not an average. And if your host has no RDMA card, the run now stops with a clear error instead of silently running slower — set data_plane.backend=simple if that is what you want.

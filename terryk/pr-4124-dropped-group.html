Eight pages on this PR, one question each. This one: what happens when one prompt group fails.

Background. A GRPO training step needs a fixed number of prompt groups; each group is one prompt run several times (each run is a rollout). NeMo-RL normally tolerates a few lost groups: a drop budget and a minimum step size decide how many.
Why context compaction (CC) cannot absorb a drop. CC turns off both ways to absorb one. It forces the minimum to 100% (config.py L1437-1438), because each CC optimizer step must hold exactly train_global_batch_size rollouts, or it raises "CC optimizer step requires the full logical sample count" (single_controller.py L3206-3213). It also never re-sends a dropped group, because RL keeps the record of which responses the agent accepted only inside the request that ran it (guide L47). Neither the code nor the guide says why a short step would be wrong. The per-rollout advantage and the token-level loss work for any number of rollouts, so this looks like a limit of the first version, not a math requirement. Dotted words have a short explanation: hover or tap them.

The figure follows one step of 4 prompt groups with 2 rollouts each, and one bad rollout in group g1. Where the failure happens decides everything. If a model call fails, the agent still finishes and returns a result, and RL masks just that rollout (nemo_gym.py L1114-1120). If the agent itself raises, Gym answers with an HTTP 500, RL files it as an infrastructure failure, and CC drops the whole group without a retry (rollout_manager.py L2210-2214). Both ways of handling a dropped group then end the run.

How compaction is triggered, and where the length is checked

In this PR's built-in client (simple_agent_with_compaction), compaction is not set off by vLLM hitting its limit. It runs on a schedule. With a context guard set (guards.max_total_tokens, off by default), Gym also counts the prompt before every call and compacts early when it would be too long. The guard's refusal (a "guard rejection") happens only when compacting early still is not enough. The guard checks the prompt, not the reply: a reply can still run into the limit, and is then cut off (bottom box).

What would fix it — proposed, not in the PR

Nothing below is implemented or has been run.

Where the fix lands: RL code and docs (this PR), the Gym agent (Gym #3368), and a follow-up issue for retry. The ordinary path has two safety nets for a failed group: retry it, then train without it. CC turned both off. The fix puts them back, one at a time.

1 · RL, in this PR: train without the dropped group

Let a CC step train on the groups it has, the way the ordinary path does. The loss is divided by the token count and the advantage is per rollout, so nothing in the math needs the full count (page 7).

2 · Gym, in #3368: a guard rejection should not crash the agent

simple_agent_with_compaction should catch the guard's refusal, end the episode there, and return what it has, the way lane A already does. RL then masks that one rollout instead of dropping the whole group.

3 · Follow-up: retry the failed group (#4557)

The ordinary path re-runs a failed group with backoff (rollout_manager.py L2215-2219). CC skips that (L2210-2214), because RL keeps the record of which responses the agent accepted only for that one request. This can land after this PR, but it matters: at moderate scale, timeouts and transport errors are routine. Without retry, each one throws away a group the ordinary path would have recovered.

So what. Today a context guard makes a CC run less robust, not more: without a guard, an oversized request masks one rollout (lane A); with a guard, the same situation stops the run (lane B). Until fix 1 lands, any rollout error that keeps the agent from returning a result ends a context-compaction training run. With fix 1, it costs one group. With retry (#4557), most such errors would cost nothing.

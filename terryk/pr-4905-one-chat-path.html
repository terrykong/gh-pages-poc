One chat path for NeMo-Gym through Dynamo: where the chat template, the prefix splice and the TQ writes should live

Design proposal for #4979 at a1659e9d, stacked on #4905. Dynamo 1.5.1, vLLM 0.29.0.

Four pages on this stack, one question each. This one: which design to ask for.

Today
Without Dynamo, each vLLM worker serves Gym's chat calls itself. One Python path renders the chat with the checkpoint's own template and processor, splices the prefix, and writes everything to TQ once.
#4979
Dynamo's Rust frontend renders Gym's chat calls, and the engine re-runs a copy of the capture steps on tokens alone. (#4905's rollouts are not affected: they send token ids to /v1/completions, which Dynamo passes through without a template.)
Status
Proposed — not implemented. Nothing here is staged as a review comment yet. Built from reading Dynamo 1.5.1, vLLM 0.29 and the PR code; nothing was run.
Background. The Dynamo frontend takes chat calls and its KV router picks the engine. Token capture writes each call's tokens, routed experts and pixels to TQ. Dotted words have a short explanation: hover or tap them.

Each column below follows one Gym call, top to bottom. Read across a row to see where that job happens in each setup. Today, every row runs in one Python process. #4979 moves the chat template into Dynamo's Rust code (row 2) and moves the capture steps after routing, as a copy (row 3). The proposal keeps Dynamo's frontend and router in front but runs our own Python there, through Dynamo's chat_engine_factory hook. So rows 2 and 3 are the same code as today, and row 6 stays in the engine.

Three setups, one Gym call

Rows 2, 3 and 6 decide the design. In the proposal, row 2 uses the checkpoint's own template and processor code, as today. Row 3 runs before the router, so the router sees the ids the engine will really run. Row 6 keeps routed experts and pixels inside the engine process, as today.

What each step means, and where pixels and TQ go

TermWhat it is
Chat template + processorTurns chat messages into token ids. The template (Jinja text from the checkpoint) lays out the turns. The processor (Python from the checkpoint, can be custom) turns each image or video into pixel values and into the right number of image tokens.
Prefix spliceOn turn 2+, the earlier turns are swapped for the exact tokens the model produced, so training sees what the model really generated, not a re-render. splice_prefix_tokens.
TQ prefix readFetches those earlier tokens from TQ, using the chain of earlier calls Gym names.
Capture decisionNot "capture on or off". With forest training, Gym says "this call may continue an earlier one" (mode="candidate"). decide_capture_input checks the messages and decides: continue from the earlier tokens, or start fresh. It needs the messages, so it must run where the messages are.
Capture planThe small record the frontend attaches for the engine: which call this is, what it continues, and how long the earlier part is. No token arrays: the earlier tokens are already the start of the prompt.
  • Pixels: process them in the frontend. The splice and the router both need the image already expanded into its image tokens, and only the processor knows that count. So the processor has to run before routing, in the frontend. It then runs once, as today. The cost is sending pixel values to the engine: Dynamo already does this over shared memory on the same node or NIXL across nodes (vllm_processor.py L505-L556). Gap to fix: Dynamo's sender handles one modality per call (L225-L229). A call with a video and two images skips the transfer, and the engine runs the processor a second time. Today's native path has no such limit: the processor runs once, in the same process as vLLM, for any mix. So we need a sender that carries mixed calls. Otherwise the processor runs twice, and the pixels written to TQ may not be the ones the frontend used for the splice and routing.
  • TQ: read in the frontend, write in the engine. The frontend needs a read-only TQ client for the prefix and the retained-media check (L852-L967). The engine keeps the single write it has today: ids, logprobs, routed experts and pixels together (L1030-L1113). Both run inside the frontend process and the engine process, not in a new process.
  • Logprobs: our chat engine must accept and forward them. Dynamo's own vLLM chat engine refuses any call that sets logprobs or top_logprobs with a 400 (L584-L600). We need both. Score centering works by Gym adding logprobs: true, top_logprobs: K to every call (score_centering.py L38-L57), so vLLM returns the top-K candidates per token and the engine writes them to TQ. Gym calls without capture also need them to get token log probabilities back. So our chat engine must not copy that check: it passes both fields to the engine as sampling options. The values still go to TQ from the engine, not back over HTTP.
  • Why not Dynamo's Rust renderer. It silently changes prompts: it adds reasoning_content as <think> when the template doesn't use it (oai.rs L628), keeps tool arguments as strings where vLLM makes them dicts, flattens content differently, and never reads processor code. Templates and processors change often, so we should run the checkpoint's own code, not a fast copy of it.

What would change — proposed, not in any PR

Nothing below is implemented.

Where it lands: RL only. No Gym change: Gym already sends the chat call and the ng_capture context to the frontend. No Dynamo change: the hook exists in 1.5.1, but it is marked experimental.

  1. Move the chat server out of the worker. The classes inside _setup_vllm_openai_api_server (L1132-L1935) go to their own module, so both setups can import them.
  2. Split today's steps into "before the engine" and "after the engine". Before: render, capture decision, TQ read, splice, length check. After: begin capture, then the TQ write or the failure reason. Megatron already splits capture this way (TQMegatronPromptPreparer, TQMegatronTokenStager), so generalize those two instead of adding new names.
  3. Our chat engine for the frontend: a small launcher starts Dynamo's frontend with our chat_engine_factory. It runs the "before" half and sends token ids, pixels and the capture plan on through the KV router.
  4. Rename and slim the engine adapter. NativeVllmEngine becomes DynamoVllmAdapter on a backend-neutral DynamoEngineAdapter base. It runs only the "after" half, and _generate_gym is deleted. SGLang or Megatron then add a token-only adapter.
  5. Refuse the Rust renderer. Fail at startup if our chat engine is not in place, or if a config selects Dynamo's renderer, template or parsers (for example custom_jinja_template).
So what. The proposal keeps everything Dynamo is for: N frontends and KV routing. It also keeps everything today's path gets right: the checkpoint's own template and processor, one copy of the capture steps, and big arrays that never cross HTTP. #4979 as written gives up the second half. That is where the forest-training, score-centering and splice gaps come from. To fix before this works: a pixel sender for calls that mix videos and images, and passing logprobs/top_logprobs through for score centering. The other costs are sending pixels from the frontend to the engine, and depending on a hook Dynamo marks experimental.

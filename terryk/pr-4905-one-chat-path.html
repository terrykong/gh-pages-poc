Background. The Dynamo frontend takes chat calls and its KV router picks the engine. Token capture writes each call's tokens, routed experts and pixels to TQ. Dotted words have a short explanation: hover or tap them.

Each column follows one Gym call through seven steps: ① receive the call, ② apply the chat template, ③ read the earlier tokens from TQ and splice them in, ④ pick an engine, ⑤ turn images into pixels, ⑥ run the model and write the call to TQ, ⑦ reply. Dashed boxes are OS processes, and the boxes inside are the classes that run each step. Without Dynamo, all of it runs in one process per vLLM worker. Before the redesign, #4979 moved ② into Dynamo's Rust code and ran a copy of ③ after routing. The proposal, now built, keeps Dynamo's frontend and router, but runs our own Python inside the frontend process, through Dynamo's chat_engine_factory hook.

Three setups, one Gym call

Where each piece lives, as built. The Dynamo frontend is one process. Its HTTP server and KV router are Rust, and our chat engine is a Python object in that same process: Dynamo's Rust code calls into it. It renders in a pool of helper processes (render_pool.py) with the native server's render code, so ② and ⑤ match native. The TQ read for ③ happens in the chat engine, through a read-only TQTokenSource (_CaptureSource). It hands the spliced ids to the KV router in the same process (④). The call then crosses the network to one vLLM worker, a Ray actor process. There, Dynamo's Rust Worker calls DynamoVllmAdapter, which wraps vLLM's AsyncLLM in that same process. It begins capture, runs the model and does the one TQ write (⑥), using the same worker methods as the native server. The reply goes back with only the text and where the call was stored, so routed experts never leave the worker.

What each step means, and where pixels and TQ go

TermWhat it is
Chat template + processorTurns chat messages into token ids. The template (Jinja text from the checkpoint) lays out the turns. The processor (Python from the checkpoint, can be custom) turns each image or video into pixel values and into the right number of image tokens.
Prefix spliceOn turn 2+, the earlier turns are swapped for the exact tokens the model produced, so training sees what the model really generated, not a re-render. splice_prefix_tokens.
TQ prefix readFetches those earlier tokens from TQ, using the chain of earlier calls Gym names.
Capture decisionNot "capture on or off". With forest training, Gym says "this call may continue an earlier one" (mode="candidate"). decide_capture_input checks the messages and decides: continue from the earlier tokens, or start fresh. It needs the messages, so it must run where the messages are: in the frontend.
Capture planThe small record the frontend attaches for the engine (GymCallPlan): the decided capture context, how long the earlier part is, and where the splice cut. No token arrays: the earlier tokens are already the start of the prompt.
  • Pixels: processed in the frontend, as proposed. Sent differently. The splice and the router need each image already expanded into its image tokens, so the processor runs before routing, once. The proposal sent the pixels with Dynamo's own sender (shared memory or NIXL), which handles only one kind of media per call. As built, the render pool pickles the processed media (L240-L249), the plan carries it as base64 (L319-L321), and the adapter unpickles it (L323-L328). Any mix of images and video works, but large media now ride inside the call over Dynamo's request plane.
  • TQ: read in the frontend, write in the engine, as proposed. The prefix read is in the chat engine. The engine keeps the single write: ids, logprobs, routed experts and pixels together (_stage → _finish_request_capture L1046-L1130). One small change: the retained-media check (L868-L984) reads TQ in the engine, not the frontend.
  • Logprobs: accepted and forwarded, as proposed. Dynamo's own vLLM chat engine refuses logprobs and top_logprobs with a 400 (L584-L600); ours does not copy that check. Score centering has Gym add logprobs: true, top_logprobs: K to every call (score_centering.py L39-L56), and the adapter stages the sampler's top-K with extract_score_centering_samples in the same TQ write.
  • Dynamo's Rust renderer: refused. It silently changes prompts: it adds reasoning_content as <think> when the template doesn't use it (oai.rs L628), keeps tool arguments as strings where vLLM makes them dicts, and never reads processor code. The launcher and the config now fail if a run asks for it (frontend.py L38-L43, config.py L53-L64).

The proposal, step by step: what was built

Where it landed: RL only, in #4979. No Gym change: Gym already sends the chat call and the ng_capture context to the frontend. No Dynamo change: the hook exists in 1.5.1, but it is marked experimental.

  1. Move the chat server out of the worker. Built in 790feb77: the classes that lived in _setup_vllm_openai_api_server are now chat_server.py.
  2. Split the steps into "before the engine" and "after the engine". Partly. 0b7894a4 shares the render and capture decision (_render_chat_call) and the turn-end ids. Two differences: Megatron's TQMegatronPromptPreparer and TQMegatronTokenStager (L124, L443) were not generalized, and the native server kept its own copy of the steps after the render (chat_server.py L339-L436) next to Dynamo's.
  3. Our chat engine for the frontend. Built in 43efaba3: a launcher starts Dynamo's frontend with ChatEngineFactory.
  4. Slim the engine adapter. Built. DynamoVllmAdapter on the DynamoEngineAdapter base runs only the "after" half (L263-L404). The old _generate_gym copy is gone.
  5. Refuse the Rust renderer. Built (see above).

So what. #4979 now keeps everything Dynamo is for (N frontends, KV routing) and what the native path gets right: the checkpoint's own template and processor, one decision and one splice, and routed experts that never cross HTTP. What is left: pixels ride inside the call instead of shared memory or NIXL, which costs bandwidth on large images and video; Megatron does not share the halves yet; and the steps after the render still exist twice, so a change to one (such as #4506's prefix recovery) has to be made to both. The hook is still marked experimental in Dynamo.

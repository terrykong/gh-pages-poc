Why about 30 shipped configs now fail after their first rollout: a hidden default moves them to the new loss mode

NVIDIA-NeMo/RL #4287 · all permalinks pin the PR head bf55419.

Before
Setup forced Megatron's loss flag to True in code. Every config got the global token mean.
This PR
Reads the flag from the YAML. If the key is missing, it falls back to False, the new mode. The example YAMLs all say true.
Status
Open — not fixed in this PR. Raised in the review. An earlier version of the PR crashed these configs at setup. The latest push swapped that crash for this default.

Three pages on this PR, one question each. This one covers configs that never set the new key.

The flag is read with .get("calculate_per_token_loss", False) in three places: setup.py#L1942, train.py#L694 and the worker. The PR added the key to 6 example YAMLs, but not to the PPO critic block, the distillation block, or the stand-alone Nemo-Gym configs. Everything that inherits from those gets the fallback, and so the new mode, which today supports only the SFT loss. The repo's config rule forbids this kind of default (config-conventions#L112: "Never provide a non-None default").

The fix — proposed, not in the PR

Where the fix lands: RL only. Three code lines go back to a required key, and about ten root YAMLs get one line each. No Megatron-Bridge change.

Nothing below is implemented. The first hunk is repeated at the other two reads; the second goes in each root YAML (PPO value: block, distillation, Nemo-Gym Nano / Super / Lightning, modelopt, and two reference configs).

Also: mark the field required again in MegatronConfig, and delete the test that locks in the default (test_megatron_setup.py#L3052). With a required key, test_config_validation.py catches every missing root before any GPU job runs.

So what. As written, every Megatron GRPO recipe on the Nemo-Gym Nano and Super configs, every Megatron PPO critic, and every Megatron distillation run gets through setup and a full rollout, then stops on an error about a setting nobody chose. An SFT config that predates this PR keeps running, but with a different loss. Unit CI does not catch any of it. The fix is the required key plus one YAML line per root.

At the deadline, the rollout snapshot waits for the model to reach disk, though it never reads the model

NVIDIA-NeMo/RL #5056, review comment C9. Permalinks pin the PR head a97d8342.

what the PR adds overlap the two saves

Two pages on this PR, one question each. This one: why the last save takes longer than it needs to.

This PR
When the deadline hits, the run saves a trainer checkpoint and waits until it is fully on disk. Only then does it take the rollout snapshot, and then it stops.
C9 asks
Take the snapshot inside the trainer save, while the model is still being written to disk. One rename then publishes both.
Status
Proposed, not implemented. Nothing below is in the PR, and nothing here has been run or timed.
The deadline. checkpointing.checkpoint_must_save_by is a time budget such as 00:03:45:00 (days:hours:minutes:seconds), counted from when the job started. When the run is close enough to it that one more step would not fit (seconds_until_save), the next step saves a checkpoint and the run exits on its own, before the cluster’s time limit kills it mid-step. “At the deadline” means that last save.
Background: the two saves. A trainer checkpoint (folder step_N) holds the model, optimizer, and training progress. A rollout snapshot holds what the trainer checkpoint lacks: the environment’s unfinished conversations and a newer copy of the rollout queue. A snapshot is not a separate checkpoint: it lives inside the trainer checkpoint’s folder, at step_N/rollout_snapshots/snapshot_000001. Dotted words have a short explanation: hover or tap them.

The trainer save copies the model off the GPU and returns. The disk write keeps going in the background, and tmp_step_N is renamed to step_N when it finishes (_publish_when_policy_write_done). The snapshot then waits for that rename twice: in finalize_pending, and again in _resolve_anchor, which skips the snapshot unless step_N exists. Nothing in the snapshot reads the model. It needs the folder only as a place to live.

In order:

  1. The train loop already knows at the save whether the deadline is due (should_save_by_timeout, L3110), so it passes that flag into the save.
  2. After the model leaves the GPU, the snapshot runs into tmp_step_N, while the policy workers write the model to disk. It must finish before the rename starts (L4240-L4242).
  3. The step’s optimizer window has already closed (L3057, before the save at L3189), so the snapshot does not skip itself.
  4. The deadline branch keeps only print and break. The _finish_pending_save after the loop publishes both at once, with or without deferred finalize.
  5. save_at_deadline keeps its failure rule. A failed snapshot deletes its own tmp folder and warns, and the trainer checkpoint still publishes.

About +10 lines net. It also makes C6 (the test for _finish_pending_save) unnecessary, because the branch it covers goes away.

So what. The last save takes about the longer of the two saves instead of their sum. The saving is the shorter of the model’s disk write and the snapshot. Both write to the same file system, so the real saving may be smaller. The C4 GPU run should time the deadline save before and after this change. The snapshot could start even earlier, next to the GPU-to-CPU copy, but C9 keeps it after that copy so the steps stay simple.

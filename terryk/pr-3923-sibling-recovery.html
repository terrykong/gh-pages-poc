How a checkpoint keeps the generations that already finished

Companion illustration for NVIDIA-NeMo/RL #3923 (sibling-level rollout checkpointing). It stacks on #3480 and #3837, so its base is a branch, not main. All permalinks pin the head 0a93f0f.

In GRPO the same prompt is generated several times, and the group is only useful once every generation is done. The generations finish at different moments, so a checkpoint can easily land while some are finished and some are still running. Before this PR, a restart threw the whole group away and generated all of it again. This PR writes a small side file next to the checkpoint, rollout_recovery.pt, that records what each generation was doing at the save — so the finished ones can be reused and only the unfinished one is generated again.

What the save catches, and what each policy does with it

Both policies are chosen per prompt group and written into the side file, so changing the YAML later never re-interprets a group that is already saved.

How the code does it

Three steps, on the same prompt idx 7 with 3 generations.

# 1. While generating: each generation reports in as it lands. # g0 lands, then g1. g2 is still running when the checkpoint starts. ledger.mark_sibling_sealed(cut, group_id, generation_index=0, receipt=..., reward=0.5) ledger.mark_sibling_sealed(cut, group_id, generation_index=1, receipt=..., reward=0.0) # -> siblings = [sealed, sealed, dispatched]

Does it work?

Nobody has posted a run. There is no throughput number, no wall-clock saving, and no before/after count of wasted generations anywhere on the PR. The CI that would exercise this has not started either — the pull request is still waiting on the repository's contributor check.

What does exist is one test that pins the exact behaviour the figure shows, and it is worth more than the rest of the suite put together because it restarts a real process: grpo_async_gym_single_controller_sibling_recovery.sh. Phase 1 runs training until one generation of a group is finished and its partner is deliberately frozen, then checkpoints. Phase 2 starts a fresh process from that checkpoint and asserts that exactly one generation is requested again, that it carries a new id, and that the finished one keeps its original id. It is wired into the L1 suite.

The useful thing to ask for before merging is small: one resumed run with the number of generations thrown away at the restart, under both policies. That single pair of numbers is the whole argument for the feature, and right now a reader has to take it on faith.

If you turn this on. It only works when token capture is on, because a finished generation needs a durable receipt to be reusable. Asking for any non-default policy while token_capture.enabled is false is rejected at startup rather than quietly ignored, which is the right call. You can pick the policy per Gym agent or per dataset task, and the agent setting wins over the task setting. The default is sibling, so most users get the cheaper restart without changing anything.

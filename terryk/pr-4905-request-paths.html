How a generation request reaches vLLM: native, native with the router, and Dynamo

NVIDIA-NeMo/RL #4905. Permalinks pin RL head 44671d3b and Gym 5911d628.

what the PR replaces how requests reach vLLM

Two pages on this PR, one question each. This one: which classes and servers each request passes through.

Before
Two ways in: NeMo RL's own rollouts reach the worker by a Ray call, and NeMo-Gym reaches it over HTTP, either straight to each worker or through NeMo RL's router.
This PR
Adds a third way for NeMo RL's own rollouts: HTTP to Dynamo's frontend, which picks the worker by cached prompt and reaches it over Dynamo's own TCP channel. Gym with Dynamo is rejected until #4979.
Status
In review, not merged. Lanes A–C exist on main today.
Background. Each data-parallel shard runs one Ray actor, VllmAsyncGenerationWorker, which owns one vLLM AsyncLLM engine. Everything below is a different door into that same engine. N is the number of shards. Dotted words have a short explanation: hover or tap them.

Four ways in, one engine

Lanes A and D meet at _serve_rollout, so a NeMo RL rollout is sampled the same way either way. Lanes B and C meet at the worker's HTTP server. Lane D never touches that server.

Short answers

  • Is the worker's server vLLM's API server? No. It is NeMo RL's FastAPI app, but its chat route runs vLLM's own request classes, extended with mixins.
  • Does the router reuse those servers? Yes. It is a proxy in front of the same N worker URLs.
  • Does Dynamo sit in front of the worker's server? No. Its Rust frontend is the HTTP server, and it calls NativeVllmEngine inside the worker over its own TCP channel. The worker's FastAPI server is not on that path.
  • What does Dynamo replace? Lane A's Ray hop, for NeMo RL's own rollouts. The sampling code underneath is unchanged. Gym through Dynamo comes in #4979 (its page): Gym calls the frontend's /v1/chat/completions, and NativeVllmEngine handles it, again bypassing the worker's server.
So what. All four lanes end in the same AsyncLLM, so refit and pause behave the same for every caller. What Dynamo changes is who picks the shard (cached prompt blocks instead of round-robin) and the transport (HTTP plus TCP instead of a Ray call). That routing is the benefit, and the extra HTTP hop is the cost the review asks the author to measure.

With force rebuild on, does finalizer setup delete the venv Gym is running from?

NVIDIA-NeMo/RL #4760, flag token_capture.try_reuse_gym_env_for_finalizers: true plus env var NRL_FORCE_REBUILD_VENVS=true. All permalinks pin head ec3c298d.

Before
Finalizer setup force-rebuilt only its own venv folder, which nothing was running from yet.
This PR
With the reuse flag on, finalizer setup builds Gym's folder a second time. With force rebuild on, that second build deletes the folder first.
Status
Open — not fixed in this PR. Raised as review comment C1, with a proposed fix below. It needs both settings at once.

Two pages on this PR, one question each — this one: what happens to Gym when the shared venv is rebuilt.

Background. NRL_FORCE_REBUILD_VENVS=true makes every venv build start from scratch. The bisect scripts set it (bisect-run.sh), and so do the Kubernetes examples, so each commit runs against its own lock file. A venv build runs one builder task per node. Dotted words have a short explanation: hover or tap them.

Gym setup builds …NemoGym/ and starts the Gym actors from it (nemo_gym.py L2201). Later, with the reuse flag on, finalizer setup calls make_actor_runtime_env("…NemoGym") again (L203). With force rebuild on, the builder skips its "folder already exists" return (venvs.py L154) and runs shutil.rmtree on the folder (L105), then uv venv and uv sync. The Gym actors are still running from that folder the whole time.

The @lru_cache on create_local_venv does not stop this. That cache lives inside one Ray worker process. Setup builds the generation, trainer and Gym venvs in parallel, so each node has several builder workers. In a local Ray test that copied this pattern, the later Gym build landed on the worker that held the cached entry only 4 times in 10.

review comment C1 — rollout_reassembler_actor.py:203 (link added after staging)

What would fix it — proposed, not in the PR

Where the fix lands: RL only, one function. create_local_venv_on_each_node in venvs.py. Nothing below is implemented. The driver remembers what it already built in this run, so a second call for the same folder returns the path without touching it.

The key includes the venv path, so a test that changes NEMO_RL_VENV_DIR still builds. It also includes the node IDs, so a node that joins later still gets the venv. Force rebuild then means "rebuild once per run", which is what the bisect scripts want. A second call also skips the per-node placement group and builder tasks.

So what. Today this needs both the reuse flag and force rebuild. The review (C2) also asks to drop the flag, which makes reuse always on. Then every token-capture run with force rebuild would hit this, so the fix is needed either way. The symptom is a ModuleNotFoundError or a missing bin/python on the Gym side during startup, which does not look like a venv problem.

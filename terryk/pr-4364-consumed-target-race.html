Why the collector could regenerate a step that training had already used

NVIDIA-NeMo/RL #4364 · all permalinks pin the PR head fcbcd7c5.

Before
If training used up a step between two of the collector's calls, the buffer said that step still needed a full batch, so the collector generated one nobody would ever train on.
This PR
The buffer answers "0 needed" for any step training has already used, inside the same lock training uses to record it.
Status
Fixed by this PR. Steps training has not reached yet still report their real shortfall.
Background — async GRPO. A collector generates rollouts ahead of training and puts them in a replay buffer (a Ray actor). Each row is tagged with the training step it is meant for. At step N, the trainer takes exactly one batch of rows tagged N, then records N as the last used step. Dotted words have a short explanation: hover or tap them.

To pick work, the collector makes two separate actor calls: it reads the last used step (trajectory_collector.py:347), skips anything at or below it (:353), then asks how many rows a step still needs (:358). Training removes a step's rows when it uses them (replay_buffer.py:650-657). So if training uses the step between the two calls, the second call counts zero rows and reports a full batch missing.

The race, with 3 prompts per step

The fix

Where the fix lands: RL only, one method. ReplayBufferImpl.get_trajectories_needed, plus the matching docstring on the protocol. No collector change: every caller already treats 0 as "no work".

@@ replay_buffer.py L1029-L1036 · ReplayBufferImpl.get_trajectories_needed
-        """Return additional trajectories needed for ``target_step``."""
+        """Return additional trajectories needed for an unconsumed ``target_step``."""
         with self._lock:
+            # Training may consume the target after the collector reads the
+            # frontier. An empty consumed target must not become new work.
+            if target_step <= self.last_target_weight_already_generated:
+                return 0
             current_count = self._count_for_target(target_step, max_age_steps)
             return max(0, num_prompts_per_step - current_count)

Why this closes the gap: the new check reads the last used step under self._lock, the same lock sample() holds while it removes the rows and moves the last used step forward. So the check and the row count always see the same moment: either step 5 is not used yet and its rows are counted, or it is used and the answer is 0. The collector asks the same question again right before it generates (:864-875); there a 0 releases the step and hands the prompts back unused, so the one check covers that call too.

So what. Before this PR the race spent real prompts and GPU time on rows that could never be trained on, and those rows took buffer space until they aged out. After it, a step training has already used always reports 0. The new test fails on the old code with assert 2 == 0 and also fails if <= is changed to <.

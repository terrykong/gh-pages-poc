Why the collector could regenerate a step that was already trained

NVIDIA-NeMo/RL #4364 · async GRPO/PPO path only (AsyncTrajectoryCollector + ReplayBuffer; single-controller does not use this code) · all permalinks pin the PR head fcbcd7c5.

Before
If the trainer used up a step between two of the collector's questions, that step looked empty, so the collector generated a new batch for it that nobody would ever train on.
This PR
The buffer answers "0 rows needed" for any step that is already trained.
Status
Fixed by this PR. Steps not trained yet still report their real shortfall.
Three facts you need first.
  • The collector runs ahead. With weights from step 4 and a lead of 3, it may generate rows for steps 5, 6 and 7 at the same time (code). Every row in the replay buffer is tagged with the step it is for.
  • "Last trained step" is the last step the trainer has taken out of the buffer and trained on — not the last step generated. The code calls it last_target_weight_already_generated, which reads like "generated", but only the trainer's sample() moves it (code). When the trainer trains step 5, it removes step 5's rows and sets this to 5.
  • "Rows still needed" for a step is rows per step − rows in the buffer tagged with that step (get_trajectories_needed). The collector generates that many rows for the step.
Dotted words have a short explanation: hover or tap them.

The trap: a step with 0 rows in the buffer looks the same whether it was never started or was already trained, because training removes the rows. The collector tells the two apart by reading the last trained step first. But it reads that number and asks "rows still needed?" in two separate calls to the buffer, and the trainer can train the step in between.

The race, with 2 rows per step

The fix

Where the fix lands: RL only, one method. ReplayBufferImpl.get_trajectories_needed, plus the matching docstring on the protocol. No collector change: every caller already treats 0 as "no work".

@@ replay_buffer.py L1029-L1036 · ReplayBufferImpl.get_trajectories_needed
-        """Return additional trajectories needed for ``target_step``."""
+        """Return additional trajectories needed for an unconsumed ``target_step``."""
         with self._lock:
+            # Training may consume the target after the collector reads the
+            # frontier. An empty consumed target must not become new work.
+            if target_step <= self.last_target_weight_already_generated:
+                return 0
             current_count = self._count_for_target(target_step, max_age_steps)
             return max(0, num_prompts_per_step - current_count)

Why this closes the gap: the buffer now reads "last trained" itself, at the moment it counts the rows, under self._lock. sample() holds the same lock while it removes step 5's rows and moves "last trained" to 5. So the answer can only be "step 5 not trained yet: here is the real count" or "step 5 trained: 0", never the mix in ③. The collector asks the same question again just before it generates (:864-875), and there a 0 releases the step and hands the prompts back unused, so the one check covers that call too.

So what. Before this PR, the race spent a batch of prompts and GPU time on rows that could never be trained on, and those rows took buffer space until they aged out. After it, a step that is already trained always reports 0. The PR's test runs ①→②→③ with 2 rows per step (for step 0 instead of 5): the old code returns 2, the new code returns 0 (assert 2 == 0 fails without the fix).

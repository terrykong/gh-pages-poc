Forcing the policy ratio to 1 is exact only on the first optimizer step, whatever the sampler

NVIDIA-NeMo/RL #5079 · fix(sc): allow forced ratio with ready_first for GRPO, and one-epoch PPO · permalinks pin the PR head 84afc6e · background: the #4670 page on the same flag

Before
SingleController's ready_first sampler rejected force_on_policy_ratio: true unless CISPO was on, even for GRPO, where it is safe. PPO accepted it with ppo_epochs: 4 (the default), where epochs 2–4 train with no trust region. Neither trainer checked.
This PR
Drops the ready_first rejection. Adds one rule in both PPO trainers: a forced ratio needs ppo.ppo_epochs: 1.
Status
Fixed by this PR. The review found no bugs. It asks for two small cleanups (end of page).

What the flag does. force_on_policy_ratio: true skips the extra trainer forward that computes prev (the trainer's log-probs before this step's update). The loss then uses curr.detach() in its place (loss_functions.py L779-L780), so the PPO ratio is 1 and is never clipped (clipped_pg.py L152-L155).

\mathcal{L}(\theta)=-\frac{1}{N}\sum_{t}\; \htmlClass{t1}{\underbrace{\mathrm{TIS}\!\left(\frac{\pi_{\text{prev}}(o_t)}{\pi_{\text{gen}}(o_t)}\right)}_{\text{(1) fixes sampler lag}}} \cdot \htmlClass{t2}{\underbrace{\min\!\Big(r_t A_t,\;\mathrm{clip}(r_t,1-\varepsilon,1+\varepsilon)\,A_t\Big)}_{\text{(2) trust region},\;\; r_t=\pi_\theta(o_t)/\pi_{\text{prev}}(o_t)}}
  • πgen: vLLM's probability when it sampled the token. πprev: the trainer's weights at the start of the batch. πθ: the weights being trained, the only term with a gradient.
  • (1) covers the gap between the weights vLLM used and the trainer's weights. With ready_first that gap is large, so the sampler requires use_importance_sampling_correction: true. The forced ratio keeps this term, as TIS(sg[πθ] / πgen).
  • (2) covers how far the optimizer has moved from πprev within one batch. A forced ratio replaces rt with 1 and drops the clip. That is only right when πθ = πprev, which is true on the first optimizer step on a batch and on no later one.

Which runs get more than one optimizer step per batch

One rollout batch, sampled by vLLM one weight version behind the trainer (what ready_first allows). The trainer starts at weights W0. Each optimizer step moves it on: W1, W2, W3.

The sampler never decides this. ready_first only makes term (1) bigger, and TIS already handles that. What decides is the number of optimizer steps on one batch. SingleController pins that to one for every algorithm, and only PPO's ppo_epochs can raise it. value_training_mode and critic_ppo_epochs change only the critic.

What the PR changes

Where the change lands: RL only, setup checks only. No loss or trainer code changes. single_controller_utils/config.py and ppo.py, plus tests and one docs paragraph. Legacy async PPO already rejects the forced ratio (run_ppo.py L67-L68), so it needs nothing.

The first hunk is the one the CISPO-only exception (#4670) had already loosened; this PR removes the rest of it. The second and third close the gap the #4670 page noted: "PPO's ppo_epochs is not checked". No shipped PPO config sets force_on_policy_ratio: true, so no recipe breaks. The review ran the changed tests on CPU (all pass) and reverted each source change one at a time; each revert made at least one new test fail.

So what. GRPO users on SingleController can now combine ready_first with force_on_policy_ratio: true and skip the extra prev forward pass. The update is the same, since the true ratio is 1 anyway. The author's multi-node MoE run matched (reward 0.832 vs 0.830 over 14 steps). PPO users who set the flag must also set ppo.ppo_epochs: 1. Before this PR, the default of 4 silently trained 3 of every 4 epochs with no clip.

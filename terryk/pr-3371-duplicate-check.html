The duplicate-entry check a name can walk straight past

NVIDIA-NeMo/RL #3371 — one skip, written for one job, silently does a second one. All permalinks pin the PR head 917ffc3.

one actor per node the shared deadline the duplicate check

Three pages on #3371, one question each — this one: how a duplicated model engine gets past the guard. Background from the PR below it in the stack: why a shard's port range never reaches Gym (#3369).

First, what an entry is, because the rest depends on it. A Gym config is a set of top-level named entries, and each one declares which kinds of server it provides. There are three kinds, and a single entry can declare more than one. This is what a shard hands back from list_entries():

{ "math_agent": ["responses_api_agents"], # rollouts can be sent here "math_env": ["resources_servers"], # a tool server "judge_model": ["responses_api_models"], # a model engine — holds GPUs "policy_model": ["responses_api_agents", "responses_api_models"], # both at once }

So "agent" is not a separate kind of object. It is a property of a name in a given shard: this entry, here, declares responses_api_agents. That is the one kind a rollout row can name as its destination, which is why agents get their own rule. Everything else — tool servers, judge and policy model engines — is supporting machinery that rollouts never address directly.

The part that makes the bug possible: each shard loads its own list of YAML files, so the same name can declare different kinds in different shards. Nothing checks that it does not.

Two rules are applied to those names, in build_agent_shard_map():

  • Agents must live in exactly one shard — a rollout row names an agent, so two hosts would mean no single destination. That is loop 1.
  • Every other kind may be duplicated, but only on purpose — you have to list it in allowed_duplicate_entries. That is loop 2, and it exists because an accidental copy of a judge or model server quietly doubles its GPU claim.

Loop 2 opens by skipping anything loop 1 already recorded as an agent. That skip is keyed on the name alone, across the whole job — not on "was it an agent in this shard". That is the gap.

The same name, two shards: what each loop sees

The function's own docstring names this exact harm (shards.py L395-L397):

a shared YAML dropped into two shards' path lists quietly brings its judge along and doubles that judge's GPU claim

The skip is keyed on the name for the whole job. In case 2 the name is in agent_to_shard because of judged, and tools' entirely separate entry — which loop 1 skipped over, since it is not an agent there — inherits that exemption on the way past.

The fix, and why it cannot over-fire

Delete the skip. Loop 2 then considers every name, in every shard.

# nemo_gym_shards.py, loop 2 for shard_name, entries in entries_by_shard.items(): for entry in entries: - if entry in agent_to_shard: - continue if entry in hosting_shard and entry not in allowed_duplicate_entries: raise ShardSetupError(...) hosting_shard.setdefault(entry, shard_name)

Case 2 then runs like this — loop 1 is unchanged, so only loop 2 is shown:

── loop 2 · with the skip deleted ─────────────────────────────── hosting_shard = {} judged / policy_model L423 entry in hosting_shard → False no raise L431 hosting_shard = {"policy_model": "judged"} tools / policy_model L423 entry in hosting_shard → True entry not in allowed_duplicate_entries → True RAISE — fixed

The obvious worry is that agents now get checked twice and start raising for no reason. They do not, and it is worth walking the three cases:

an agent in ONE shard loop 2 sees it once, records it, no raise unchanged an agent in TWO shards loop 1 already raised; loop 2 never runs unchanged agent here, model there loop 2 now sees both and raises the fix listed in the allowlist the allowlist check still exempts it unchanged

Running the existing suite against the change confirms it: all 46 tests in the shard-schema test file still pass, and a new test for the escaping case fails before the deletion and passes after.

Why this is easy to hit in practice. A shard is a slice of the Gym config — one agent plus the tool servers and judges it needs, pulled in through a list of YAML files. Two shards pulling in one shared YAML is the normal way to reuse a judge, and top-level entry names are short and generic. Nothing anywhere enforces that a name means the same kind of thing in two different shards, which is precisely what this function exists to police.

Starting a training job while its judge pool is still loading — and what still stops it

NVIDIA-NeMo/RL #5019 (follow-up to #4542). All permalinks pin the PR head b0fb8f5.

Before
A training job attached to a separate judge pool waited until every judge was healthy before it started Ray, the trainer and Gym.
This PR
Adds EXTERNAL_VLLM_ATTACH_EARLY=1 (off by default): the job starts as soon as the pool has published its URLs, and only rollouts wait for the judges.
Status
New opt-in feature. It works when the training job is submitted by hand. Open in review: through the standard submit helper it saves nothing yet, because the helper still delays the job 15 minutes.
Background. A pool job is a separate Slurm job that serves judge models (vLLM replicas behind load balancers) for a long time. Training jobs attach to it through attach_and_run.sh, which reads the pool's URLs from a shared directory and then runs ray.sub. The pool writes two signal files there: manifest.tsv (its URLs, known once the load balancers are placed) and READY (written once every replica is healthy). Dotted words have a short explanation: hover or tap them.

Two ways to start, on the author's 124-node run

By default the job waits for READY (pool_is_ready). With the flag it waits only for manifest.tsv (manifest_is_published), which the pool now writes right after placing its load balancers (run_in_allocation.sh). Times below come from the run in the PR description; the length of the blue "init" box was not measured and is drawn only to show order.

Where the two paths wait, and where they join

The only difference is which file the wait loop checks. Both check that the pool job is the expected one and that its heartbeat is fresh:

pool_is_ready (default)

[[ -f "${pool_dir}/READY" ]] || return 1 generation=$(cat "${pool_dir}/generation") [[ "${generation%%-*}" == "${pool_job}" ]] || return 1 heartbeat_age=... # must be <= 300 s

manifest_is_published (EARLY=1)

[[ -f "${pool_dir}/manifest.tsv" ]] || return 1 generation=$(cat "${pool_dir}/generation") [[ "${generation%%-*}" == "${pool_job}" ]] || return 1 heartbeat_age=... # must be <= 300 s

After the wait, both paths run the same code. They read the same manifest.tsv, and both put the same readiness gate into the driver command (attach_and_run.sh L153-L188). That gate is what keeps rollouts from reaching a judge that is still loading, so the early start is safe. It is the same gate an inline heterogeneous job already uses. The early path only moves the init step left, under the model load.

The catch: the standard submit helper still waits 15 minutes

Where the fix lands: RL only, one file outside this PR's diff. pool_config.sh · submit_external_vllm_attached_job, plus its README lines. No change to the pool job or to attach_and_run.sh.

submit_external_vllm_attached_job adds a Slurm dependency of "pool start + 15 minutes" whenever READY is missing, which is exactly when the flag would help. The review proposes dropping the extra minutes when the flag is on. Proposed, not in the PR yet; not run.

@@ pool_config.sh L388-L390 · submit_external_vllm_attached_job
   if [[ ! -f "${pool_dir}/READY" ]]; then
-    dependency=(--dependency="after:${pool_job}+${EXTERNAL_VLLM_ATTACH_AFTER_MIN:-15}")
+    if [[ "${EXTERNAL_VLLM_ATTACH_EARLY:-0}" == 1 ]]; then
+      # Early attach only needs the pool job running; the manifest follows within seconds.
+      dependency=(--dependency="after:${pool_job}")
+    else
+      dependency=(--dependency="after:${pool_job}+${EXTERNAL_VLLM_ATTACH_AFTER_MIN:-15}")
+    fi
   fi

So what. On the 124-node run the flag let Ray, the trainer and Gym start about 7 minutes earlier, with rollouts still gated on healthy judges. Today you only get that when you submit the training job yourself. Through the helper the job starts at +15 min, after the pool is already READY. The review also asks for a one-line check for a smaller case: after a pool job is requeued, an early job can read the old generation's leftover manifest and then stop itself.

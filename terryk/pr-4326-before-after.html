Where the advantage math runs, before and after this PR

NVIDIA-NeMo/RL #4326 — compute advantages in dedicated, sharded Ray actors. Links for the new code pin the PR head 93c8818; links for the old code pin the base 7d4db00.

Before
The controller, one Ray actor (on the head node when the cluster has a dedicated Ray head), pulled every advantage input for a batch into its own memory and did the math on its own event loop. Nothing else in the controller could run meanwhile.
This PR
Adds an optional pool of CPU actors on the GPU nodes. The controller sends each one a list of row ids. Each actor reads its rows, computes, writes the advantages back, and returns a few summary numbers.
Status
In this PR, off by default. num_advantage_workers: 0 keeps the math in the controller. The review's open items are on the other two pages and in the (pending) review.

Three pages on this PR, one question each — this one: where the advantage math runs, before and after.

Background. The single controller is one CPU-only Ray actor. On one event loop it runs the rollout pump and the train pump. Training data does not pass through it: rows live in the data plane, and processes pass row ids around. The advantage stage was the exception: it pulled the actual numbers into the controller. Dotted words have a short explanation: hover or tap them.

Before and after, on the cluster

Same example in both: one chunk of 6 prompt groups with 5 responses each, so 30 rows; after the PR, 3 actors take 2 groups (10 rows) each.

Same code, different place

The two paths meet in one function. On main the math lived inside the controller's _advantage_stage. The PR moves it unchanged into AdvantageComputer.run and calls it from one of two places. With no actors it runs in the controller; otherwise the next free actor runs it:

@@ single_controller.py L5254-L5260 · _run_advantage_stage (PR head)
    async def _run_advantage_stage(self, request: AdvantageRequest) -> AdvantageOutcome:
        """Run one advantage stage on the pool, or in-process without one."""
        if not self._advantage_actors:
            return await self._advantage_computer.run(request)
        actor = await self._available_advantage_actors.get()
        try:
            outcome = await actor.run.remote(request)

The actor side is a thin wrapper (AdvantageActor.run): it checks that the request and the answer hold only small metadata, and calls the same AdvantageComputer.run with its own data-plane client. So both paths produce the same advantages; what differs is the process, what sits in memory, and what comes back. The one exception, same-prompt groups split across actors, is on the same-prompt page.

So what. The PR takes the biggest memory spike and the longest blocking stretch off the controller, which is what made it look hung at large scale. The PR reports about 10% faster steps and about 97% less advantage time on a 344-GPU run with 8 actors. With the default of 0 workers nothing moves: the controller still blocks, but it no longer keeps whole reward and advantage tensors until the step ends.

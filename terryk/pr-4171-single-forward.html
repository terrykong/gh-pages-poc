How GRPO drops a whole forward pass and still filters the same sequences

Companion illustration for NVIDIA-NeMo/RL #4171. All permalinks pin the PR head ae5a6d9.

dropping a forward pass padding used to reject good sequences

Two pages on this PR, one question each — this one: what the new mode is and how it compares to the old one.

Before
Setting grpo.seq_logprob_error_threshold forced an extra forward pass over the whole batch, just to get the policy logprobs the filter needed.
This PR
Adds loss_fn.seq_logprob_error_in_loss. The filter now runs inside the training forward, and the worker corrects the gradient afterwards.
Status
New feature, off by default. Megatron GRPO only. The author measured a 17.8% drop in mean step time.

GRPO can throw away a sequence whose logprobs from the generator and from the trainer disagree too much. The measure is a per-sequence mean of exp(|generation_logprob − policy_logprob|), and anything above seq_logprob_error_threshold is dropped (utils.py:220). The catch is the denominator. The loss divides by the total number of surviving response tokens across every rank, and each microbatch has to divide by that same number while it runs — but you only know it once every microbatch is done. The old code solved that by computing the policy logprobs up front in a separate pass. This PR solves it by dividing by the unfiltered count first and fixing the gradient at the end.

The same batch, both ways

Where the correction happens

Same three sequences, split across two microbatches: the 7-token and 4-token sequences in the first, the 9-token one in the second. Threshold 2.0.

microbatch 1 seq A (7 tok, error 1.4) -> kept seq C (4 tok, error 3.1) -> dropped, sample_mask = 0 loss_1 = (A's token loss sum) / 20 # C adds nothing microbatch 2 seq B (9 tok, error 1.1) -> kept loss_2 = (B's token loss sum) / 20 after the loop accumulated gradient = S / 20 # S = A + B contributions survivor tokens K = 7 + 9 = 16 # summed across all ranks scale_gradients(20 / 16 = 1.25) gradient = S / 16 # matches the old path then the optimizer clips

Three details make that work, and each is a line you can point at:

StepWhat it doesCode
Reject cleanly A dropped sequence has its sample_mask zeroed, so its tokens add nothing to the gradient. That is what lets the divisor be fixed afterwards. loss_functions.py:540
Count survivors once After every microbatch has run, the worker sums the survivor counts across data-parallel ranks and broadcasts them to every pipeline stage. megatron_policy_worker.py:988
Fix before clipping The multiply has to land before optimizer.step(), because Megatron does gradient clipping inside that call. If it ran after, the clip would see the wrong scale. megatron_policy_worker.py:1026

Why the old path still exists

The new mode is off by default and refuses most configurations. It needs the Megatron backend, one optimizer update per rollout batch, and a token-level loss; it rejects MTP, draft models, distillation, KL-in-reward, and the streaming trainer (grpo.py:461). The reason the list is that long is the correction itself: only the Megatron worker knows how to rescale gradients after the microbatch loop, so every other backend has to keep using the separate pass.

The two paths share exactly one piece of code — the function that scores a sequence (utils.py:220). Everything else differs, and that is deliberate: they filter at different times, divide by different denominators, and report their counts through different channels.

What you get, and what you give up. You save one forward pass over the whole batch per step — measured at 17.8% lower mean step time on a 1.5B model over 450 steps. You pay for it in two ways. Rejected sequences still cost a full forward and backward, because the filter only learns they are bad partway through. And the decision now comes from the training forward rather than a separate inference forward, so FP8 scale history and packing can change which sequences pass. The PR says plainly that bitwise agreement with the old path is not expected.

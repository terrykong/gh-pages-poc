Seven pages on this stack (#4905 and #4979), one question each. This one: which tokens decide whether the model is done thinking.

Background. A thinking model writes <think>…</think> and then its answer. Some calls force the answer into a shape: JSON for response_format, or a tool call for a structural tag. A grammar does that: at each step it blocks tokens that would break the shape. The thinking must not be blocked, so before the call starts, the engine is told reasoning_ended: True means "already done thinking, apply the grammar from the first new token". False means "wait until the model writes </think>". The deepseek_r1 rule finds the last <think> or </think> in the tokens it is given: </think> means True. Dotted words: hover or tap.

So the answer depends entirely on which tokens you hand the rule. Qwen3's chat template drops old thinking from history, so the template's tokens hold no <think> from earlier turns. Native runs a spliced prompt that keeps them, and before this PR vLLM's serving read the flag from that (old L617, vLLM serving.py). Dynamo read it from the template. The example below is one Qwen3 chat with a weather tool, as two cases.

One chat, two cases: what each path told the engine

What a wrong answer does. In case A, native's True turned on the grammar at the first token of turn 2. The model could not think before its JSON or forced tool call. In case B, False makes the grammar wait for a </think>. The model already wrote that one before the cut, so it never writes another. The grammar never turns on, and nothing checks the resumed tool call.

What the author did (7e29dcc). reasoning_ended runs once on the template's tokens. Dynamo passes the result on. Native puts it in extra_args. Then take_reasoning_ended hands it to the engine in place of vLLM's own value. The test reasoning_not_ended_by_an_earlier_turn is case A: both paths hand the engine False. The review also suggested never cutting constrained calls. The author did not, for two good reasons. Gym already skips cutting a call with response_format or a forced tool. And a rule on the worker would stop every call with tools from being cut, since vLLM turns the structural tag on for all of them. That leaves case B: a call with tools and tool_choice: auto, which Gym still cuts.

How often does case B happen? Rarely. It needs three things at once: the engine runs with a reasoning parser (vllm_kwargs.reasoning_parser, which no shipped recipe sets today), the call has tools with a parser that uses a structural tag (hermes, qwen3_engine, …), and a checkpoint cuts the call right after its </think>. One catch: even True only helps if the cut lands before the tool call starts. Cut in the middle of <tool_call>, and the restarted grammar never sees the tag's start, so it checks nothing on either answer. The real choice is not about a big bug. It is whether this PR should change native's behavior for case B (before: True, now: False) or leave that for a follow-up.

Seven pages on this stack (#4905 and #4979), one question each. This one: which tokens decide whether the model is done thinking.

Background. A thinking model writes <think>…</think> and then its answer. Some calls force the answer into a shape: JSON for response_format, or a tool call for a structural tag. A grammar does that: at each step it blocks tokens that would break the shape. The thinking must not be blocked, so the grammar needs to know when thinking is over. Dotted words: hover or tap.
The value this page is about: reasoning_ended, one bool per call.
  • What it means: "before this call writes its first new token, has the model already finished thinking?" True: yes, so the grammar applies from the first new token. False: no, so the grammar waits until the model writes </think>. None: there is no reasoning parser, so the question does not come up.
  • Who computes it: NeMo RL's reasoning_ended(request, parser, template_token_ids), which returns parser.is_reasoning_end(token_ids). For the deepseek_r1 parser, is_reasoning_end walks back through the token ids it is given and returns True if the last <think>/</think> it meets is </think>, else False.
  • Who uses it: it goes into the engine's generate(…, reasoning_ended=…), and vLLM's structured output reads it in should_fill_bitmask to decide whether the grammar is on yet.
The function is correct. The whole issue is which token ids it is given.

So the answer depends entirely on which tokens you hand the rule. Qwen3's chat template drops the thinking of every assistant turn that comes before the latest user message, so on a new user turn the template's tokens hold no <think> from earlier turns. (It keeps the thinking after a tool result, inside one user turn; see the note under the table.) Both paths run a spliced prompt that keeps them; the model sees the same tokens on both. Before this PR, native's vLLM serving computed the flag from that spliced prompt (old L617, vLLM serving.py). Dynamo read it from the template. The example below is one Qwen3 chat (thinking on, deepseek_r1 parser), as two cases.

One chat, two cases: what each path told the engine

How to read the pills: each pill is the reasoning_ended value the engine gets for turn 2. "Should be" is the correct value: True only if turn 2's own thinking is already written. The other pills are four points in time:

  2. At review: #4979 at 5c7fa69, when C84 was posted. Native is unchanged from main; Dynamo is new.
  3. Now: #4979 after the author's C84 fix, 7e29dcc (head 26d9d01). Both paths use the template's tokens.
  4. Proposed: read the template plus the saved tokens on the worker. Moved to the follow-up issue #5177; not written yet.

So: case A was wrong on native in ① and ②, and is fixed in ③. Case B was right on native in ① and ②, wrong on Dynamo in ②, and is wrong on both in ③: the fix for A broke B on native. ④ makes B right. Case C is wrong in every state, ④ included: no value of the flag can resume a half-written answer. That is why the fix is one issue, not a one-line change here.

What True and False actually do to the reply. The flag only changes anything when the call has a grammar. Without one, the model writes the same reply either way.

Case and its grammarWith FalseWith True
A: turn 2 has response_format. The reply must be {"city": …, "temp": …}. ✓ what should happen. The grammar is off while the model writes <think>which units for Tokyo…</think>. Once it sees </think>, the grammar turns on and forces the JSON. ✗ old native. The grammar is on from the first token, and the first token must start the JSON. <think> is blocked, so turn 2's reply has no thinking: just {"city": "Tokyo", …}. Training then learns from a reply the model was not allowed to think before.
B: resumed turn 2 with tools and tool_choice: auto. Its structural tag lets the model write anything until <tool_call>; after that, the arguments must match the tool's schema. ✗ now, on both paths. The grammar waits for a </think> in the new tokens. The model wrote that before the cut, so it never writes another, and the grammar never turns on. The tool call is written with nothing checking it. Usually it is still valid, but nothing guarantees it, and a bad one fails to parse. ✓ old native, and the proposed fix. The grammar is on from the first resumed token. The model writes <tool_call>, and from there its arguments are forced to match the schema.
C: like B, but the cut lands partway into the answer (a half-written JSON, or inside a <tool_call>). ✗ The grammar waits for a </think> that never comes, so nothing checks the rest of the answer. ✗ The grammar restarts from its first state. A JSON grammar demands a fresh { after {"city": "To and corrupts the reply; Gym never cuts these calls, so this cannot happen today. A tool-call grammar never sees <tool_call> again and checks nothing.

Two notes. (1) In case A with only a structural tag (tools, auto), a wrong True does little harm: the tag allows free text before <tool_call>, <think> included. The harm is with response_format and a forced tool call, whose grammar starts at the first token. (2) After a tool result, still in the same user turn, Qwen3's template keeps the previous step's thinking. There the template's tokens also end in an old </think>, so the flag is True on both paths. That is how plain vLLM behaves too, and it is outside this PR.

What the author did (7e29dcc). reasoning_ended runs once on the template's tokens. Dynamo passes the result on. Native puts it in extra_args. Then take_reasoning_ended hands it to the engine in place of vLLM's own value. The test reasoning_not_ended_by_an_earlier_turn is case A: both paths hand the engine False. The review also suggested never cutting constrained calls. The author did not, for two good reasons. Gym already skips cutting a call with response_format or a forced tool. And a rule on the worker would stop every call with tools from being cut, since vLLM turns the structural tag on for all of them. That leaves case B: a call with tools and tool_choice: auto, which Gym still cuts.

What would fix B and C — proposed in #5177, not in the PR

Nothing below is implemented. The author asked to do the resumed case in a follow-up, and the review agreed (reply C91): no run today reaches it, and case C means the fix needs a small design, not one line. #5177 tracks it. For case B, the worker already has what it needs: the flag only matters when the engine has a reasoning parser, so the worker has that parser in exactly the cases where it matters.

Where it would land: RL only. start_capture (runs on the worker on both paths), the Dynamo adapter's generate call, plus one test. No Gym change: Gym already decides which calls to cut.

# in start_capture, on the worker, after the restore is resolved — case B values template_ids = [ …"user: Tokyo?"…, …"assistant:" ] # no <think> anywhere saved_ids = [ "<think>", "use", "the", "tool", "</think>" ] # turn 2's own tokens, before the cut if call_resumes_a_cut and engine_has_reasoning_parser: ended = parser.is_reasoning_end(template_ids + saved_ids) # last one is </think> → True # native: request._template_reasoning_ended = ended # Dynamo: the adapter passes ended instead of wire["reasoning_ended"] # test: a deepseek_r1 call with tools, cut right after its </think>; # both paths must hand the engine True.

Case A does not change: a new turn has no saved tokens, so it still reads the template alone and gets False. Case C needs a choice instead of a value. JSON-grammar calls must stay uncut, as Gym's generation_cut_regenerate_reason already does. For a structural-tag call, either do not cut it once its <tool_call> has started, or accept that the rest of that call is unchecked. Tests: one parity case per cut point (inside the thinking, right after </think>, inside a tool call) with an engine reasoning parser and a grammar.

Do today's runs hit any of this? No, none of the four states. vLLM only reads reasoning_ended when the engine has a reasoning parser (structured_outputs_config.reasoning_parser, set from vllm_kwargs.reasoning_parser). Without one, should_fill_bitmask returns True and the grammar starts at the first token whatever the flag says. Every recipe here, Nano3 and Super3 included, sets its reasoning parser only under http_server_serving_chat_kwargs. That one splits the reply into thinking and answer after generation, and NeMo RL never passes it to the engine. The Gym structured-outputs data puts the JSON schema in the prompt text, not in response_format, and its tool rows use tool_choice: auto. So this is a bug waiting for the first run that sets an engine reasoning parser and sends a grammar. Case B also needs tools with a parser that uses a structural tag (hermes, qwen3_engine, …), and a checkpoint that cuts the call right after its </think>. One catch: even True only helps if the cut lands before the tool call starts. Cut in the middle of <tool_call>, and the restarted grammar never sees the tag's start, so it checks nothing on either answer. The real choice is not about a big bug. It is whether this PR should change native's behavior for case B (before: True, now: False) or leave that for a follow-up.

Two pages on this PR, one question each — this one: which exits lose the last save.

With the flag on, a save is published only by _finish_pending_save. The train loop calls it at the top of each step and once more, blocking, after the loop (L3906). But a run limited by epochs ends differently: when the data is used up, the last step is marked final and saves (L3725), the loop goes round once more, finds nothing to train, and leaves through a plain return that skips L3906. The GRPO example config ends this way: max_num_epochs: 1, max_num_steps: 1000000.

The last two steps of a 2-step run, with and without the flag

  1. Step 2 is the last step because the data is used up, so it saves. With the flag on, the save is only marked pending.
  2. The loop condition only checks max_num_steps, so the loop runs once more. Its first poll comes right after the save, so the write is not done: False.
  3. No batch is left, so the loop returns and never reaches the blocking finalize after it.
  4. run()'s cleanup calls CheckpointManager.shutdown(). The manager was never told about the pending save, so it does nothing.

An error in the step after a save takes the same route to the cleanup, in both the SingleController and SFT v2, and drops the save the same way. On main, that cleanup publishes it.

The fix — proposed in the review, not in the PR

Where the fix lands: RL only, two functions. Nothing below is implemented in the PR. Finalize a still-pending save in each run()'s cleanup, before shutdown(). One spot covers every exit: the early return, errors, and cancellation. The existing finalize after the loop stays, and the cleanup call is a no-op when nothing is pending.

  1. Both additions call the PR's own _finish_pending_save(blocking=True): wait for the write on every worker, then rename the folder. This is what main's cleanup already does through shutdown(), so a stuck worker hangs here exactly as it does today.
  2. The SingleController addition goes before shutdown(), so the rename is done before the manager's final cleanup, like a normal exit.
  3. The SFT v2 entry reuses the existing loop, which turns a failure into a warning, so it never hides the error that ended the run.
So what. With the flag on, every epoch-limited SingleController run (the GRPO example's default) finishes with exit code 0 and an unusable last checkpoint, and resume goes back one save interval. Any error in the step after a save does the same, for both loops. The PR's tests miss it because they all stop at max_num_steps. The fix is a few lines in each cleanup, plus a test: the existing exhaustion test run with the flag on.

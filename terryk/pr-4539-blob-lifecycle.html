Before
No such code. simple units keep Python objects, and Python frees them. mooncake_cpu leaves this to the Mooncake master.
This PR
Each nixl unit manages its own block of pinned memory, which other machines write into and read from directly.
Status
New in this PR; the review found no bug in these rules. Two open review items touch it (last section).

Each storage unit owns one big block of pinned memory. A put reserves a piece of it, called a blob. The client writes the bytes there by RDMA, and a commit makes the rows visible. The hard part is giving the memory back. A region must never go to a new put while an old WRITE might still land in it, or while a reader is still copying it. The figure follows row 5 from page 1, which lives on unit 2.

Three rules that stop memory from being reused too early

What could go wrongThe ruleCode
A WRITE that failed may still be landingThat region is retired: never handed out again. The same applies to space a writer reserved and never committed within 360 s. abort :638, _sweep :331
A reader is still copyingEvery read pins what it reads for 150 s. A released blob is freed only when its last pin ends. The client also times its own read, and if the read took longer than its pin, it throws the result away and reads again. _dispose :698, tq_nixl.py:511
A checkpoint is still copyingA blob being saved holds a hold. If it is released meanwhile, it is freed after the copy ends. _drop :690, save_shard :863

The time limits must fit together, and the code checks that they do when it starts (check_timeouts). A transfer may run for 120 s, so a pin lasts 150 s: 120 s plus a 30 s margin. A whole operation may take 240 s, and space that was never committed is retired after 360 s (240 + 120).

What it costs, and what the review asks

  1. Retired memory never comes back. It stays out of use until the unit restarts. This is on purpose: reusing it could put stale bytes in another row. It should be rare, since it needs a failed WRITE. The amount shows as retired_bytes in the unit's stats.
  2. A recent read can make a put wait. Memory released while it is pinned stays unusable for up to 150 s. With the SSD tier off and no other room on the unit, the put gets "busy" and retries until a pin ends (alloc :562).
  3. With SSD on, a spilled put blocks this process's gets while it waits for the disk. The client sleeps between "pending" checks while it holds its one lock. C1 · tq_nixl.py:476
  4. None of the failure paths above runs in CI. The end-to-end NIXL tests skip there. C3 · conftest.py:139

Why the single controller logged zero vLLM tokens per step, and how back-to-back windows fix it

NVIDIA-NeMo/RL #5155 · the nightly check that caught it is in #5074 · permalinks pin head 9990d4b (removed code: base fc009e6)

Before
On the single-controller path, vllm/generation_tokens and the other vllm/* step metrics came out near 0 in on-policy runs (training waits for the full batch, and nothing generates during training). Every other single-controller setup undercounted them.
This PR
Takes one starting reading before any generation, then uses each step's end reading as the next step's start.
Status
Fixed by this PR. The older training loops (grpo.py, ppo.py, grpo_sync.py) are unchanged.

Background. vLLM keeps running totals (counters) such as "tokens generated since the engine started". To get one step's number, NeMo-RL reads the counters twice and logs the difference: snapshot_step_metrics() takes the start reading, get_step_metrics() the end reading. The single controller runs generation and training as two separate loops. Dotted words: hover or tap.

The old code took the start reading inside the train pump, when it handed the step's first group to training (old _train_pump). So anything generated before that moment was missed. How much that was depends on two settings, not on the sampler:

SetupOld window caughtOld window missed
On-policy: full-batch wait, plus lookahead 0 or a colocated engineabout nothing → logs ~0the whole step's generation
Full-batch wait, lookahead ≥ 1the next batch's generation during trainingwhat was generated while training waited for its batch
Streaming (smaller first chunk)the later chunksthe first chunk, and anything before it

"Full-batch wait" means min_groups_for_streaming_train equals the batch size, so select() returns nothing until every group is ready (_finalize_selection). The fix moves the start reading to before the loops start, and keeps each end reading as the next start, so the windows touch end to end in every setup.

Two steps, two ways of drawing the window

The fix — RL only, three source files

In order: the controller reads the counters once before either loop can start generating (the restore step above it only reloads saved state). Each step end reads again, logs the difference, and keeps that reading as the next start. If a read fails, the start reading is cleared (L876-L879); the next read only sets a new start and returns {} (L885-L887). So one step shows no vllm/* numbers, instead of a number that spans the gap.

Single-controller runs now log real per-step vLLM token, length and request counts, and summing them across steps gives the run total. The windows run back to back from one step end to the next, so with async rollouts a step's numbers include generation for batches trained later — the same as before this PR, but without the gap. The review found no problems. The new tests pass locally and fail if any line of the fix is reverted.

SFT v2 moves the dataloader off the driver and into the GPU workers

Companion illustration for NVIDIA-NeMo/RL #3917 — SFT v2 stage 1 with the Megatron-Energon multimodal data path. All permalinks pin the PR head 0a45c45.

In today's SFT loop the driver holds the dataloader: it pulls a batch, then hands the whole thing to the policy, which ships the tensors out to every GPU worker (sft.py:580). This PR adds a second SFT loop that turns that around. Each data-parallel replica gets its own Megatron-Energon loader, and that loader runs inside the policy worker's own process — SFTMegatronPolicyWorker is passed as worker_extension_cls_fqn, so it replaces the policy worker class rather than adding a new actor. The controller asks the replica leaders for a batch and gets back a StepEnvelope that carries only metadata — token counts, sample ids, a handle. The image and text tensors never leave the worker that read them.

One step, with real numbers

Take the 8-GPU recipe in this PR: tensor parallel 4, so 2 data-parallel replicas. Set the global batch to 6 to keep the arithmetic small.

world = 8 GPUs, tensor_parallel = 4 → data_parallel = 8 / 4 = 2 train_global_batch_size = 6 → each loader reads 6 / 2 = 3 samples ── controller ──────────────────────────────────────────────── run_all_workers_single_data("load_next_sft_batch", run_rank_0_only_axes=REPLICATED_AXES) only the 2 replica leaders run it: rank 0, rank 4 ranks 1,2,3 and 5,6,7 are skipped — they are tensor-parallel copies ── rank 0 ───────────────────────────────────────────────────── batch = next(self._sft_loader_iterator) 3 samples, Energon shard 0 prepared = prepare_sft_batch(batch, ...) mask + pad, shared with v1 return StepEnvelope(meta=..., logical_rank=0, valid_tokens=...) ── rank 4 ───────────────────────────────────────────────────── same, but Energon shard 1 → logical_rank=1 ── controller ──────────────────────────────────────────────── logical_ranks == [0, 1] checked, or it raises train_placed_microbatches([e.meta for e in envelopes]) only meta travels. the 3-sample tensors stayed on rank 0 and rank 4.

The dispatch and the sharding are decided in two different places, and they have to agree. Which ranks are asked comes from run_rank_0_only_axes; which shard each loader reads comes from parallel_state.get_data_parallel_rank() inside the worker. We checked this arithmetic against Megatron's own rank layout for both shipped recipes and it is right, including the tricky expert-parallel case: with expert parallel 2, the expert groups span both replicas, so using the plain data-parallel group is what keeps the effective batch from being quietly halved.

Does it work?

No training run has been posted — no loss curve, no throughput number, no comparison against the v1 loop on the same config and seed. The author says those are still to come. Both new recipes are parked in disabled.txt for honest reasons (a 2-GPU recipe fits no nightly tier, and the 30B one costs about 12 GPU-hours against a budget that is nearly full), but the effect is that nothing exercises this path end to end on any schedule.

So the honest summary is: the design is sound and the rank arithmetic checks out, but nothing has run it. The thing to ask for before merging is one run of the 2-GPU recipe against the v1 loop on the same data and seed, reporting loss at the same step and wall-clock per step.

One trap worth knowing about. The lint failure prints a suggested fix: tools/config_cli.py minimize … --in-place. Do not run it. That recipe sets data._override_: true, which makes the config loader drop the inherited data block entirely — so the six keys the minimizer calls redundant have nothing to fall back to. Running it deletes max_input_seq_length and shuffle, and the run then dies at config validation with data.max_input_seq_length Field required. The second recipe inherits from this one, so both break.
What this buys, and what to watch. Taking the driver out of the data path is the point: with the loader next to the GPU that consumes its output, a multimodal batch is decoded once, in the process that needs it, instead of being built centrally and copied out. That matters most for image and video data, where the batch is large and the driver becomes the bottleneck first. The cost is that a v2 run now has two things to keep in step — which ranks read, and which shard each reader takes — and those live in different files. The guards for that are real: a mismatch raises at setup rather than training on the wrong data. Worth watching as more backends arrive in stage 2, because today the only thing keeping those two views aligned is that they are computed from the same parallel layout.

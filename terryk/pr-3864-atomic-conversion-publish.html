How NeMo-RL publishes an HF→Megatron conversion so no job ever reads a half-written one

Companion illustration for NVIDIA-NeMo/RL #3864 (overlap non-colocated Megatron inference init with policy init) and #3777. All permalinks pin the PR head 7463c341c.

The first time you train a model, NeMo-RL converts the HuggingFace weights into Megatron format and caches the result in a directory shared by every job (community_import.py:314). Before this PR the conversion wrote straight into the final path, and another job decided the cache was ready by checking that a directory named iter_0000000/ existed — so a job that looked while the first one was still writing saw a half-finished checkpoint and used it. This PR writes into a hidden directory beside the final one and then renames it into place. A rename is a single step, so anyone looking sees either nothing at all or a finished conversion — never something in between. That is what lets the training policy and the inference policy start at the same time instead of one after the other.

First, the layout on disk, because everything below is a rename between these paths. The staging directory is not inside the destination — it is a sibling, in the same parent. That is what makes the rename atomic: moving a directory within one parent is a single filesystem operation.

$NEMO_RL_MEGATRON_CHECKPOINT_DIR/ ├── Qwen2.5-1.5B/ ← the destination. code calls it output_path │ └── iter_0000000/ │ ├── ... weight shards ... │ └── run_config.yaml ← written LAST. if this exists, it is finished │ ├── .Qwen2.5-1.5B.staging-a1b2c3d4/ ← job A builds its copy here (staging_path) ├── .Qwen2.5-1.5B.staging-e5f6a7b8/ ← job B builds its copy here (staging_path) └── Qwen2.5-1.5B.displaced-9f8e7d6c/ ← where an old occupant gets shoved (displaced)

All four are siblings. The two .staging- ones start with a dot, so a plain ls does not show them. Path construction: community_import.py:309-311.

And "is it finished?" is exactly one os.path.exists call — there is no lock, no manifest, no state file:

def megatron_conversion_is_complete(path): return os.path.exists(os.path.join(path, "iter_0000000", "run_config.yaml")) # so "is the destination complete?" means, literally: # os.path.exists("$NEMO_RL_MEGATRON_CHECKPOINT_DIR/Qwen2.5-1.5B/iter_0000000/run_config.yaml")

community_import.py:68-72. Three answers are possible, and the difference between the last two is the whole bug: complete (the file is there), partial (the directory exists but the file does not), and absent (no directory at all). The function returns False for both partial and absent — it cannot tell them apart.

Writing somewhere else first, then renaming

The four steps, with the values for one job converting Qwen2.5-1.5B on 8 GPUs:

# 1. every GPU must agree on the hidden directory name, so rank 0 picks it and shares it staging_token = uuid.uuid4().hex[:8] # "a1b2c3d4" torch.distributed.broadcast_object_list([staging_token], src=0) staging_path = ".../.Qwen2.5-1.5B.staging-a1b2c3d4" # hidden: starts with a dot output_path = ".../Qwen2.5-1.5B" # the real cache path # 2. all 8 ranks write their shards into the hidden directory bridge.save_megatron_model(megatron_model, staging_path) # 3. wait for all 8 to finish writing BEFORE anyone renames torch.distributed.barrier() # 4. rank 0 alone flips it into place; the other 7 wait if torch.distributed.get_rank() == 0: publish_megatron_conversion(staging_path, output_path) torch.distributed.barrier()

Real code: community_import.py:295-323. Both barriers matter: the first stops rank 0 renaming a directory that ranks 1-7 are still writing into; the second stops ranks 1-7 reading the final path before the rename lands.

Step 4 is not just one rename, because the destination may already be occupied — by a partial conversion an earlier run was killed halfway through. Renaming a directory onto a non-empty directory fails, so publish_megatron_conversion gets two attempts, and between them it moves the occupant aside:

for attempt in range(2): if megatron_conversion_is_complete(output_path): # someone else already published? rmtree(staging_path); break # give up gladly, use theirs try: os.rename(staging_path, output_path); break # the good case except OSError: # "Directory not empty" if attempt == 1: raise # ← the only exit that gives up angrily if megatron_conversion_is_complete(output_path): continue # they finished in the gap; concede next pass displaced = output_path + ".displaced-9f8e7d6c" # stale partial in the way os.rename(output_path, displaced) # shove it aside, then retry rmtree(displaced) # delete the shoved-aside copy

Real code: community_import.py:75-126. Every exit except the raise first re-checks whether someone else already published a good copy, and steps aside if so.

Where two jobs can still collide

That raise is the one exit that does not re-check. To reach it you need two things at once. First, two jobs converting the same model at the same time — each one does the whole conversion on its own GPUs, into its own hidden directory, and then both try to publish into the same final path. Second, a stale partial conversion already sitting in that final path, left by an earlier run that was killed. The stale partial is what makes both renames fail and sends both jobs down the "move the occupant aside" path — which is where they can trip over each other.

Below, both A and B have already finished converting and are racing to publish. Neither is a reader; both are writers.

The loop does two different renames, and they move opposite things. This is the easiest part to misread:

publish os.rename(staging_path, output_path) # MY copy → the destination # both jobs do this, so they collide evict os.rename(output_path, displaced) # whatever is IN the destination → aside # both jobs also do this, to the SAME occupant

community_import.py:102 — publish · :115 — evict. Neither job's own staging directory ever disappears. In step 3 both jobs try to evict the stale partial; A gets there first, so B's evict fails with FileNotFoundError because the occupant is already gone.

Here is the whole race as a trace, in time order, with real paths. A and B are the two jobs; every line is one filesystem call:

# on disk at the start: # Qwen2.5-1.5B/iter_0000000/ exists, but NO run_config.yaml → partial # .Qwen2.5-1.5B.staging-a1b2c3d4/ A's finished copy # .Qwen2.5-1.5B.staging-e5f6a7b8/ B's finished copy A exists("Qwen2.5-1.5B/iter_0000000/run_config.yaml") → False # partial, not complete B exists("Qwen2.5-1.5B/iter_0000000/run_config.yaml") → False # same answer A rename(".Qwen…staging-a1b2c3d4" → "Qwen2.5-1.5B") → ENOTEMPTY B rename(".Qwen…staging-e5f6a7b8" → "Qwen2.5-1.5B") → ENOTEMPTY # destination is occupied by the partial A rename("Qwen2.5-1.5B" → "Qwen2.5-1.5B.displaced-9f8e7d6c") → ok # A evicts the partial. destination now ABSENT B rename("Qwen2.5-1.5B" → "Qwen2.5-1.5B.displaced-3c2d1e0f") → FileNotFoundError # B tried to evict the same partial. already gone. B exists("Qwen2.5-1.5B/iter_0000000/run_config.yaml") → False # ← THE BUG # destination is ABSENT, not complete. # "absent" and "partial" give the same False, # so B carries on as if nothing had changed. A rename(".Qwen…staging-a1b2c3d4" → "Qwen2.5-1.5B") → ok, A WINS # destination now holds a COMPLETE conversion B rename(".Qwen…staging-e5f6a7b8" → "Qwen2.5-1.5B") → ENOTEMPTY # second attempt → raise. B dies.

If B's exists(...) had landed one line later — after A's winning rename — it would have seen the finished conversion and stepped aside cleanly. The window is exactly the gap between A evicting the old occupant and A moving its own copy in.

The fix is to make that last exit behave like all the others — look once more before giving up:

except OSError: if attempt == 1: if not overwrite and megatron_conversion_is_complete(pretrained_path): rmtree(staging_path) # a peer filled the slot we freed; use theirs break raise

Does it work?

Nobody has posted a run. The PR description is the unfilled template — no before/after setup times, no convergence curve, and no GPU job has exercised the new startup ordering end to end at the time of writing. For a change whose whole point is to make startup faster, the thing to ask for is one recipe run on main and on this branch with timing/setup/total_setup_time_s reported for each.

What is pinned down is the happy path of the publish itself. A unit test runs the real thing against real directories and checks that the staged copy lands and nothing is left behind (test_community_import.py:260-307), covering three cases: an empty target, a complete one, and a stale partial one. The race above is not among them — all three run in a single process, so the two-job interleaving in step 4 cannot happen. It was reproduced separately by forcing the ordering with a barrier.

What this buys, and what is still sharp. Publishing by rename is what makes it safe for the training policy and the inference policy to start at the same time — before this, one had to finish converting before the other could look, which is exactly the wait #3777 is about. Two rough edges are left. The raise above can kill a job that had a usable conversion sitting in front of it, and because the staged directory now carries a random name, a run killed mid-conversion leaves a full-size copy behind that nothing ever deletes — the next attempt picks a new name rather than reusing it. On a shared, quota'd filesystem those add up quietly, because the leftovers start with a dot and do not show up in a plain ls.

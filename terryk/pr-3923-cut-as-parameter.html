Every data-plane write should be handed a cut

Companion note for NVIDIA-NeMo/RL #3923, and a sibling of the note on the cleanup call that escapes the cut. All permalinks pin the head 0a93f0f.

Writes to the replay buffer and the save that snapshots it must not overlap. A barrier enforces it: a writer holds a cut while it works, and a save waits for every cut to close. The question is how a function proves it holds one. Take it as a parameter and the caller cannot forget. Look it up from the call stack and they can.

The rule the ledger already follows

The recovery ledger takes the parameter, everywhere. Every one of its 14 mutating methods is def f(self, cut: DataPlaneMutationCut, ...) with cut.require_live() as its first statement — 14 parameters, 14 checks, no exceptions:

def reserve_group(self, cut: DataPlaneMutationCut, *, prompt_id: str, ...): """Create one logical group and its first physical sibling attempts.""" cut.require_live() # cannot be called without a live cut

→ rollout_recovery.py:270-288, one of 14

Counting cut: DataPlaneMutationCut parameters against require_live() calls per module shows how far that rule got:

rollout_recovery.py 14 cut parameters 14 require_live() fully adopted staleness_sampler.py 3 cut parameters 2 require_live() single_controller.py 3 cut parameters 0 require_live() replay_buffer.py 0 cut parameters 1 require_live() none of its APIs

→ the buffer's single require_live() is inside mutation() itself, not in any write it exposes

So the module that defines the cut is the one module whose writes never ask for one. That is where the nesting was added instead.

The nine writes that do not take a cut

Sources, top to bottom: commit, remove_group, remove, clear_staging_keys, commit_finalized, _remove_groups_unlocked, _clear_samples_unlocked, _validate_rollout_recovery_inventory, _clear_data_plane_samples.

The two _unlocked helpers are worth calling out, because they look like the fix and are not. Neither takes a cut; each states the requirement in prose — "while the caller owns a mutation slot" — which a reader can honor or miss with equal ease.

The three red rows are already being called from inside a cut. clear_staging_keys is reached from discard_recovery_group(cut, ...), whose caller opens the cut and passes it down; commit_finalized is called inside a mutation() as cut and simply never asks for it; and _validate_rollout_recovery_inventory writes through clear_samples holding nothing at all. For those three the change is to accept the cut that already exists at the call site.

Nesting is not an alternative to passing the cut — it is passing the cut, with the argument deleted. The nested branch mints nothing; it looks up the object the outer section stored and hands back that same instance:

depth = self._mutation_depth_by_task.get(task, 0) if depth: self._mutation_depth_by_task[task] = depth + 1 cut = self._mutation_cut_by_task[task] # the SAME cut the outer opened cut.require_live() yield cut

→ replay_buffer.py:227-239 — a task-keyed dictionary standing in for a function argument

Writing during a save is fine; asking for a second section is not

Two different things are easy to conflate here. Writing while a checkpoint is held is safe — the checkpoint holder has exclusive access, which is the best possible moment to write, and checkpoint() already yields a cut for exactly that. There is a real use waiting for it: the save path calls the inventory check with clear_unreferenced=False, and the only thing stopping it from cleaning up during a save is that hardcoded flag.

What is never right is a task that already holds a section asking the barrier for another. Today that is silently tolerated in one direction and hangs in the other, because checkpoint() never registers itself in the task maps that mutation() consults. Both shapes, run against this head:

async with b.mutation(): async with b.mutation(): # joins the outer cut, active_mutations=1 async with b.checkpoint(): async with b.mutation(): # never returns. no error, no timeout

→ 1. mutation() inside mutation(): joined, active_mutations=1
→ 2. mutation() inside checkpoint(): HUNG

Once every write takes a cut, nothing needs to open a second section, so the barrier can say so out loud. One set of tasks-in-a-section replaces both task maps, and the guard covers all four combinations — including checkpoint-inside-checkpoint, which hangs today too:

def _enter(self, task): if task in self._section_tasks: raise RuntimeError( "this task already holds a data-plane barrier section; pass the " "DataPlaneMutationCut you already have instead of opening another") self._section_tasks.add(task)

→ called at the top of both mutation() and checkpoint(); replaces _mutation_depth_by_task and _mutation_cut_by_task, which exist only to serve the nested lookup

That turns a hang into a named error that tells the next person what to do instead. The cut parameter is what stops people forgetting; this is the backstop for the case where they reach for mutation() out of habit.

One gap left in the cut itself. DataPlaneMutationCut stores the barrier that made it but never compares it, and it is not bound to a task — so a live cut handed to a spawned task keeps working after the opener exits, and the barrier drains while that child is still writing. Recording the owning task and asserting both in require_live() makes the parameter strictly stronger than the task-keyed lookup it replaces.

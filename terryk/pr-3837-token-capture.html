How training gets the exact tokens the model generated, without trusting the environment to hand them back

Companion illustration for NVIDIA-NeMo/RL #3837 — token capture through an external TransferQueue sink. All permalinks pin the PR head 648b948a.

To train on a rollout you need the exact token ids the model produced. Today NeMo-RL asks the environment for them: the agent server sends text and token ids back, and the trainer believes it — the environment sits in the middle of the token path (nemo_gym.py:895). This PR adds an opt-in second path. The vLLM worker writes each model call's new tokens straight into TransferQueue as it generates them (tq_token_sink.py:154), and the environment only ever handles short opaque keys. Afterwards a finalizer fetches those rows, re-checks their hashes, and glues them into one training row.

Where the tokens travel

One rollout, start to finish

A rollout that made 2 model calls. The first generated 3 new tokens, the second 5. The prompt was 4 tokens, so the finished training row is 12 tokens long.

1. STAGE — the vLLM worker writes each call's new tokens as it finishes them. staging partition ┌──────────────┬───────────┬───────────┬──────────────────────────┐ │ key │ prev_len │ delta_len │ token ids it added │ ├──────────────┼───────────┼───────────┼──────────────────────────┤ │ ng-7/call-1 │ 4 │ 3 │ [811, 812, 813] │ │ ng-7/call-2 │ 7 │ 5 │ [821, 822, 823, 824, 825]│ └──────────────┴───────────┴───────────┴──────────────────────────┘ Each row also carries a hash of its own contents.

TQTokenSink.stage — returns only after TransferQueue says the bytes are stored, so a call is never acknowledged before its tokens are safe.

2. LIST — the agent server records which calls happened. No tokens. ledger for rollout 7: ["ng-7/call-1", "ng-7/call-2"], last call = call-2

This is the only thing the environment holds, and it is why the environment cannot change a token: it never sees one.

3. VERIFY — the finalizer fetches those 2 rows and re-checks them. recompute hash of ng-7/call-1 -> matches keep recompute hash of ng-7/call-2 -> matches keep does call-2 start where call-1 ended? prev_len 7 == 4 + 3 yes any mismatch here and the rollout is dropped, not trained on

BlackboxFinalizer.finalize_group — the hash walk and the length chaining are done by NeMo-Gym's verify_and_linearize.

4. PUBLISH — one training row, 4 prompt + 8 generated = 12 tokens. a rollout that failed verification still publishes a row, with sample_mask = 0 so the group keeps its shape and the failed row contributes nothing to the loss

blackbox_finalizer.py:495-505 — valid rows get sample_mask = 1, rejected rows stay at 0.

Does it work?

Nobody has posted a run. The PR description and every comment on it carry no throughput number, no reward or loss curve, and no link to a training job. What it does say is that the existing unit tests still pass on a CPU machine — which shows the code imports and its tests run, not that a captured rollout trains correctly.

There is one end-to-end test, an L1 job that runs the feature on, but it reuses the checks from the run with the feature off — gen_kl_error below a threshold, and reward above zero. Neither can tell whether capture was actually used. If the setting silently stopped taking effect, the run would fall back to the old path and pass exactly the same.

The metric that would settle it already exists and already reaches the dashboard: train/token_mult_prob_error compares the engine's own logprobs against what the trainer recomputes. If a receipt assembled the wrong tokens, that number moves and nothing else does. The thing to ask for before merging is one run with capture on and one with it off, on the same recipe, reporting that number.

It cannot merge yet, for a reason unrelated to the code. The Gym submodule is pinned to the head of an open, unapproved pull request, and the Python package every import here resolves against — nemo_gym/token_id_capture/staging/ — does not exist on Gym's main branch at all. So the Gym half has to land first, and this branch then needs re-pinning to whatever commit that produces. Worth knowing: when that re-pin happens, all four capture test files hit a pytest.importorskip and quietly skip, and the test lane treats "no tests collected" as a pass. Without a guard, the day this feature loses its test coverage is the day CI goes green and says nothing.

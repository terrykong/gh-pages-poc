How a prompt's rollouts all reach the same NeMo-Gym actor

Companion illustration for NVIDIA-NeMo/RL #3372 — routing rollouts across sharded NeMo-Gym actors. All permalinks pin the PR head 33d77fc.

NeMo-Gym runs the environment that scores rollouts. Until this PR there was one Gym actor, so every row went to it. This PR lets a job run several Gym actors — the config calls each one a shard — and splits the work between them. The split is not free to make: each training prompt is generated several times, and the whole set has to be scored together, so a prompt's generations must all land on one actor. The router therefore hands out work one prompt group at a time, never one row at a time, and sends each group to the actor that serves the route name its rows carry (rollouts.py:2430).

Whole groups go to one actor — never single rows

How the replies get put back together

Each actor streams its rows back as it finishes them, so replies arrive interleaved and out of order. Four steps turn that back into whole groups, all on the same 12 rows as the figure.

1. Number every row by its place in the batch, before anything is sent. rows[0]["_rowidx"] = 0 ... rows[11]["_rowidx"] = 11

rollouts.py:2358

2. Walk the batch 3 rows at a time. Every row in a group must give the same route name, or the batch is rejected. Then look up that route's actor. The route name is the row's agent_ref.name, or its task_source if there is no agent_ref. rows 0,1,2 -> all give "math" -> math actor (bucket keeps 0,1,2) rows 3,4,5 -> all give "tools" -> tools actor (bucket keeps 3,4,5) rows 6,7,8 -> all give "math" -> math actor (bucket becomes 0,1,2,6,7,8) rows 9,10,11 -> all give "tools" -> tools actor (bucket becomes 3,4,5,9,10,11)

rollouts.py:2452 — the same-route check · nemo_gym.py:1491 — where the route name comes from · :2353 — pick the actor

3. Start both actors, then hand back whichever row finishes first. Two streams in, one stream out. tools row 4 -> math row 0 -> math row 6 -> tools row 3 -> ...

rollouts.py:2522 — wait for the first ready row · :2431 — pass it on

4. The collector files each row under row_number // 3 and releases a group only once all 3 of its rows are in. It never sees an actor name. row 4 -> group 1, holding {4} -> not ready row 0 -> group 0, holding {0} -> not ready row 6 -> group 2, holding {6} -> not ready row 3 -> group 1, holding {3,4} -> not ready row 5 -> group 1, holding {3,4,5} -> group 1 complete, released

rollouts.py:1884 — row number to group number · :1804 — the collector

Step 4 is why step 1 matters. Because the numbers are positions in the whole batch and no actor renumbers them, the collector that existed before this PR keeps working unchanged. With one actor there is one bucket and one stream, and this whole path behaves exactly as it did before.

Why groups, and not rows. Some Gym environments score a rollout by comparing it against the other generations of the same prompt. Those hold a whole group in one process and wait until it is complete. Split a group across two actors and each half waits forever for rollouts sitting in the other — the run stops with no error. Sending whole groups is what prevents it, and the code says so at rollouts.py:2438.
The size of a group is a caller-supplied number, and the wrong value is silent. The router is told how many rows make a group by num_generations_per_prompt, which defaults to 1. At 1 every row is its own group and the rows of one prompt scatter across actors — the case above. The only check is that the group size divides the batch evenly (rollouts.py:2743), and 1 divides everything, so a caller that forgets to pass it gets no warning. Every caller passes the right value by the time sharding can be switched on, so nothing is broken today — but it is worth knowing which argument holds this together.

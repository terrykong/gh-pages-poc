How a fresh PPO run starts with an already-trained critic

Companion illustration for NVIDIA-NeMo/RL #3821 (stacked on #3813, not main). All permalinks pin the PR head 6e8790c.

PPO trains two models: the policy that writes the answer, and the critic (value model) that guesses how good a state is. A fresh run starts the critic from random weights, so its guesses are noise — and training the policy on noisy advantages is worse than not training it at all. Today the only cure is ppo.policy_training_start_step: N: for the first N steps, skip the policy update (ppo.py:1617) and train only the critic. The catch is that those N steps still do the slow part in full: generation, where the policy writes out an answer for every prompt in the batch one token at a time, and then scoring, where the environment grades those answers. That work takes the same wall-clock time whether or not the policy learns anything from it. This PR adds ppo.warm_start_value_checkpoint, which points a fresh run at a critic somebody already trained.

What the N warmup steps actually buy you

How much those three steps hurt depends on how much of a step generation takes. The PR argues it hurts most on SWE and long agentic tasks, where the model writes a lot of tokens per prompt and scoring means actually running something. No timings are given, so treat that as the author's reasoning rather than a measurement.

How the seeding works

The whole feature is a choice of which directory one call reads. PPO already resolves the critic's restore paths on their own, separately from the policy's (get_resume_paths(..., model_component="value")), so seeding the critic means handing that call a different path.

# nemo_rl/algorithms/ppo.py:717-723 (the SingleController copy is setup.py:658-664) warm_start = ppo_config.warm_start_value_checkpoint # Only a fresh run reads it. On a resume, last_checkpoint_path is set and wins. if last_checkpoint_path is None and warm_start is not None: validate_warm_start_checkpoint(warm_start) # raise now if the path is wrong print(f"🔥 Warm-starting the value model from {warm_start}") value_weights_path, value_optimizer_path = checkpointer.get_resume_paths( last_checkpoint_path or warm_start, # <- the entire feature model_component="value", )

Run it on the warm-started run from the figure above. Its seed is critic_pretrain/step_370; once it has been going a while, its own latest checkpoint is my_run/step_12.

--- fresh run, key set ------------------------------------------------- last_checkpoint_path = None warm_start = "critic_pretrain/step_370" None or "critic_pretrain/step_370" -> "critic_pretrain/step_370" value weights <- critic_pretrain/step_370/value/weights value optimizer <- critic_pretrain/step_370/value/optimizer policy weights <- None # policy still starts from the base model --- the same run, resumed after a crash -------------------------------- last_checkpoint_path = "my_run/step_12" warm_start = "critic_pretrain/step_370" # still in the config "my_run/step_12" or "critic_pretrain/step_370" -> "my_run/step_12" value weights <- my_run/step_12/value/weights # its own critic, 12 steps of progress kept

That ordering is what lets the key stay in the config forever. If the warm start won instead, every resume would throw away the critic's progress and re-seed from the old checkpoint. Only the value/ subtree is read — the policy starts from the base model, the dataloader from the beginning, and the step counter at 0.

The seed directory is the ordinary layout any PPO run writes, so a previous run's checkpoint works as-is:

critic_pretrain/step_370/ ├── policy/ not read └── value/ ├── weights/ -> critic weights └── optimizer/ -> optimizer moments + where the LR schedule had got to

A path with no value/weights inside it is rejected at setup (checkpoint.py:79). Without that check a typo would print the 🔥 line and then train a random critic, because get_resume_paths never checks that the path exists.

Does it work?

Nobody has posted a run. There is no W&B link, no critic-loss curve, and no before-and-after wall-clock number on the PR. The tests that ship with it are unit tests with mocked workers — they check that the seeded paths reach the critic and that a resume ignores the key, which is the plumbing, not the claim.

The PR is straight about why it has no end-to-end test: two runs that do not share the same rollouts cannot be compared exactly, because asynchronous vLLM generation is not reproducible even at a fixed seed. That is a fair argument against an identity test. It is not an argument against showing a chart.

What to ask for before merging. One side-by-side chart from a real pair of runs: critic loss (or explained variance) and task reward for (a) a cold run with policy_training_start_step: N and (b) a warm-started run with policy_training_start_step: 0, plus the wall-clock the second one skipped. The feature rests on the claim that an offline-trained critic is a good enough substitute for online warmup, and right now nothing on the PR tests that claim.

One catch worth knowing before you turn it on. The seed is restored through the normal resume path, so on a Megatron critic, Megatron compares the seed's learning-rate schedule against the one your run builds and fails at startup on the first field that differs. Nine fields are compared. The two checked first are max_lr and min_lr, and those come from value.megatron_cfg.optimizer — not from the scheduler block. Three more are step counts that get multiplied by value.train_global_batch_size and derived from the total step budget, which PPO clamps to min(max_num_steps, max_num_epochs × batches-per-epoch) × ppo_epochs.

In plain terms: pretraining the critic at a different learning rate, a different batch size, or on a different-sized dataset will stop your PPO run from starting. The failure is loud and immediate, not silent — but the message is a raw assertion from deep inside Megatron, so it is worth knowing what it means before you see it. Set value.megatron_cfg.scheduler.override_opt_param_scheduler: true if you would rather your run's schedule win; note that this replaces the schedule's settings but still restarts from the seed's position in it. None of this applies if your critic runs on the DTensor backend rather than Megatron — that path takes the seed's schedule without checking it at all.

Three pages on #3371, one question each — this one: how the actors get created and placed. Background from the PR below it in the stack: why a shard's port range never reaches Gym (#3369).

A NeMo-Gym stack is a head server plus a pile of tool and judge subprocesses, all run by one Ray actor. One actor on one node was the whole story until now. This PR adds build_nemo_gym_actors(), which reads a shards: block and builds several actors, each with its own complete Gym stack. Two things have to be true for that to work: each actor needs a node to itself, and something has to remember which agent lives on which actor. This page is about how both happen.

From config to nodes

Three pieces do the work. _shard_instances() flattens shards and replicas into one entry per actor. The placement group asks for one bundle per entry with strategy="STRICT_SPREAD", which Ray defines as packing bundles across distinct nodes — so one bundle per actor is what buys one node per actor. And apply_shard_log_dir() gives every replica its own directory.

The startup order, and why it has to be that order

The interesting part is not the list of steps but the first one. Before any shard bundle is reserved, the code materializes the actor's runtime environment (nemo_gym.py:1389), and it must finish first — because building that environment quietly takes out a second STRICT_SPREAD placement group of its own.

Step 1 is easy to read past. make_actor_runtime_env() looks like a pure config call, but when the actor's virtual environment is uv-managed it calls create_local_venv_on_each_node(), which builds its own STRICT_SPREAD group holding one CPU on every node and only releases it when the build is done. Two STRICT_SPREAD groups asking for the same nodes at the same time is a fight you do not want during startup, which is why the runtime environment is built and finished on the line above the placement group rather than beside the actors.

Step 6 is what makes routing possible later. _discover_agent_shard_map() asks one replica of each shard for list_entries() — the names it actually spawned, read from Gym's resolved config, so entries that arrived through config_paths are included. One replica is enough, because replicas of a shard are stamped from the same merged config and host identical entries. build_agent_shard_map() turns those lists into {agent name: shard name} and rejects two things outright: an agent hosted by two shards, because a row naming it would have two destinations; and any other name in two shards unless it is listed in allowed_duplicate_entries, because a shared YAML dropped into two shards' path lists quietly brings its judge along and doubles that judge's GPU claim.

What this PR does and does not give you. It creates and places the actors and works out which agent lives where. It does not yet send any rollout to them — every production entry point still calls spinup_nemo_gym_actor(), which raises straight away if it sees a shards: block, so the sharded path cannot run in a real job yet. The routing that uses the map lands in the next PR in the stack. If you are sizing a job today, the two numbers to know are the ones that decide whether the group can be placed at all: every shard reserves 8 CPUs by default, and the job needs one free node per replica, not per shard.

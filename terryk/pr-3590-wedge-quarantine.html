How a wedged engine gets quarantined — the fix proposed in review

Review proposal on NVIDIA-NeMo/RL #3590 (not yet code in the PR). Companion to who-watches-what. Permalinks pin 8fec944.

A wedged engine is the worst failure: the worker process is alive, so the health probe passes forever — is_alive is literally return True — but generation requests sent to it never come back. No probe can detect this. Only traffic can: a request that times out is the proof. The review proposes two layers on the router's error path. Layer 1, the reflex: on a failed forward, remove that backend from the router's local serving list at once. Layer 2, the report: count those failures per URL, let the 5-second control tick collect the counts, and feed them into the health ledger through report_failure — the same call the non-Gym path already uses for failures a probe cannot see.

One wedge, tick by tick

The honest boundary: the probe's "ok" resets the failure streak (record_probe:229), so quarantine needs ≥3 reported failures inside one 5-second window. Under real load that is the common case (the table above). Under a trickle — one request per window — W bounces between HEALTHY and SUSPECT and is never condemned; the reflex keeps the cost at one cheap sacrifice per push, but the tax never ends. A fix that survives trickle load would keep a separate streak for reported failures, one the probe's ok cannot reset.

What to remember. A wedge is invisible to every probe — only a failed request proves it. The reflex drop turns the first failure into immediate local avoidance; the pulled report turns repeated failures into a real quarantine using the ledger's existing thresholds; part 4 then replaces the engine. Without the report layer, the membership push faithfully restores the wedged URL every 5 seconds and the sacrifice cycle runs for the rest of the job.

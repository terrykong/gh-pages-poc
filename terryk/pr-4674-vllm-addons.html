Seven pages on this stack, one question each. This one: what NeMo-RL adds inside vLLM, and how a stock server gets it.

Why NeMo-RL has its own chat server. Gym talks to the model in text. If the server re-tokenizes earlier assistant turns, it can get different token ids than the model actually produced, for example around tool-call whitespace. Training would then score tokens the model never sampled. So NeMo-RL's server splices the exact earlier tokens back into each new prompt (splice_prefix_tokens). It also checks sampling settings so rollouts stay on-policy, and attaches the experts each token was routed to for MoE router replay. Dotted words have a short explanation: hover or tap them.

The external server gets NeMo-RL behavior in two ways. Code that must run inside vLLM is copied into a small wheel whose only dependency is vllm==0.29.0. It loads through vLLM's vllm.endpoint_plugins hook and replaces the chat route. Code that needs NeMo-RL's data plane stays on the controller, and the plugin reaches it over HTTP. The two bugs that would bite first

  1. Router replay reads the wrong field. Stock vLLM 0.29.0 can return routes. With --enable-return-routed-experts, it puts base64 .npy data on the choice, shaped [tokens − 1, layers, experts per token] (protocol.py). The plugin looks on the message, so it always finds nothing. Even with the right field, NeMo-RL expects its own nrlre1 envelope with padded, aligned rows, and nothing converts between them. Setup also turns route return on only for managed vLLM, but still tells Gym to expect routes. So a router-replay run fails late, inside Gym, instead of at startup.
  2. The on-policy checks are gone. In the managed server, every request passes two asserts: top_k must be unset, and top_p must be set explicitly. Without the second one, vLLM fills an unset top_p from the model's generation_config.json, for example 0.95 for Qwen3. Training then assumes the top_p from NeMo-RL's config (often 1.0), while vLLM actually sampled only from the top 95%. The plugin's route has neither check.

How to share one copy — proposed, not in any PR

Nothing below is implemented. The copying already shows strain. The prefix copy's docstring says "keep this behaviorally identical", but NeMo-RL's version now accepts a set of end-of-turn ids and records media cut points. The copy does neither. For text-only vLLM the two still give the same tokens, because managed vLLM passes a single id too. The next caller that relies on the set will find the copy behind, and the 3-case parity test won't notice.

Main already has a second way to share code: the judge-pool launcher runs patches.py straight from the source checkout with runpy. That works only because patches.py imports nothing but the standard library. #4675 copies code into a wheel instead. Two ways of sharing code, and neither covers everything.

Where it lands: RL only. One new in-repo package, for example nemo_rl_vllm_ext/, allowed to import only vllm, numpy and the standard library. It holds the full prefix splice, the sampling checks, the routed-expert codec plus a stock-.npy converter, the chat-route override, the capture client and patches.py. Both openai_server_utils.py / vllm_worker_async.py and the wheel import from it, so only one copy exists and the parity test can be deleted. vllm serve loads it through vllm.endpoint_plugins and vllm.general_plugins. Managed workers call the same register functions. Today the managed path uses no vLLM plugin entry points at all; it monkey-patches and sets a worker extension class.

So what. Before #4676 merges, it should either read choice.routed_experts and convert it, or refuse remote_vllm with router replay at startup. #4674's preflight should also refuse a quantized server, since it can read that setting from /server_info. The single shared package is the real fix. Without it, every vLLM upgrade means patching two copies of the same chat route, and the copy that drifts first is the one nobody tests.

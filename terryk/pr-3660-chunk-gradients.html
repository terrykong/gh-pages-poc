Why one training step kept only the last chunk's gradients

Companion illustration for NVIDIA-NeMo/RL #3660 — "reduce and finalize gradients once per step, not per chunk". All permalinks pin the PR head 4447ddf.

In the SingleController training loop, one optimizer step is not fed in one go. Prompts arrive from generation a few at a time, so the loop feeds the trainer several chunks and only then steps the optimizer (single_controller.py:592-600). Gradients from each chunk are supposed to pile up in one buffer, and the sum is used once at the end. Between chunks the loop takes a detour to score the new prompts, and that detour calls prepare_for_lp_inference (:570), which frees the gradient buffer to save memory. Two things then went wrong, and both came from the same mistake: the code below the loop treated every chunk as if it were a whole training step.

One step, three chunks, and what was actually in the buffer

The fix: tell the worker a step is already open

The loop already knows whether it is between chunks. It just never said so. The fix passes that one fact down, and moves the end-of-step work out of the per-chunk path. Same three chunks, same numbers.

step_open = False # no gradients yet for chunk in chunks: # 3 chunks in this example prepare_for_lp_inference(keep_train_buffers=step_open) # chunk 1 -> False : buffer is empty, free it (this still saves memory) # chunk 2 -> True : buffer holds 2 -> KEEP # chunk 3 -> True : buffer holds 5 -> KEEP ... if not step_open: begin_train_step(loss_fn) step_open = True train_microbatch(chunk)

single_controller.py:571 and :592-597

Skipping the offload is only half of it. The next chunk calls prepare_for_training, which reloads the buffer — and the reload is what actually zeroed it. That reload turns out to be harmless, for a reason worth knowing:

if not keep_train_buffers: # <- the new guard move_model(model, "cpu", move_params=False, move_grads=True) # ... and on the way back in, mcore's reload: if move_grads and grad_data is not None and grad_data_size > 0: grad_data.storage().resize_(grad_data_size) grad_data.zero_() # <- this erased chunks 1 and 2 # grad_data_size is set only by a matching offload. With the offload skipped it # stays 0, the whole block is skipped, and the 2 and the 3 are still there.

megatron_policy_worker.py:2909 · mcore reload guard: param_and_grad_buffer.py:1653

For the second bug, the hook is hidden for the length of the step and run by hand once at the end. Moving it rather than deleting it matters: that one call also does the layernorm sum across tensor-parallel ranks, the tied-embedding sums across pipeline stages, and the mixture-of-experts router bias update. Deleting it would have quietly lost all of those.

begin_train_step: saved = model.config.finalize_model_grads_func # keep it model.config.finalize_model_grads_func = None # mcore now finds nothing to call finish_train_step: model.scale_gradients(1/10) # buffer is 10, N = 10 tokens saved([model], None) # None = "do not divide again" optimizer.step() # sees 1.0, not 0.5

Does it work?

Nobody has posted a training run. The PR ships no before-and-after numbers, and the author says so plainly in the thread: the comparison on the one nightly recipe that produces multiple chunks has not been run yet. So the claim that gradients are now correct rests on reading the code, not on watching a model train.

One unit test does pin the behaviour directly: it drives a step as 1, 2 and 5 chunks and asserts the end-of-step reduce happens exactly once each time (test_megatron_split_state.py:822). It runs on mock objects, though — no real gradients move.

The cheap thing to ask for before merging: one run of the streaming recipe, reporting the gradient norm at a fixed step against a single-chunk run. The PR adds a log line that makes exactly this greppable — [step] chunks=… grad_norm=… (megatron_policy_worker.py:1628). If the gradient norm still depends on how many chunks a step was split into, something is still wrong.

What this means for you. If you have run SingleController streaming training, every step that was assembled from more than one chunk trained on a fraction of its data — roughly the last chunk only — while dividing by the token count of all of them. Runs are not a little noisy; they are undertrained by about the chunk count. Anything tuned on those runs is worth re-checking after this lands. One trade-off comes with the fix: the gradient buffer and the optimizer now stay on the GPU through the scoring detour instead of being freed, so peak memory goes up. If a streaming config was sized against the old freeing behaviour, it may now run out of memory.

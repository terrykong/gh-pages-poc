Six pages on this PR, one question each — this one: how far down the stack a restart reaches.

A generation shard is one vLLM model replica. NeMo-RL gives it tensor_parallel_size × pipeline_parallel_size Ray actors, one per GPU bundle, but only the first of them loads a model: that one gets bundle_indices, which is exactly what makes it the model owner. The rest set self.llm = None and return immediately — they exist to hold their GPU bundle. The owner builds the vLLM engine with distributed_executor_backend="ray" whenever TP×PP > 1, and hands it VLLM_RAY_BUNDLE_INDICES so vLLM's own Ray workers land on those same bundles.

One replica across two nodes

Take GB200 with 4 GPUs per node and tensor parallel = 8. One replica no longer fits on a machine, and NeMo-RL notices: model_parallel_size > cluster.num_gpus_per_node switches the cluster to a single unified placement group covering every inference GPU, instead of one placement group per node.

The bundles in that unified group are flattened into topology order and sliced into consecutive chunks of TP×PP. Each chunk is one replica. With 3 replicas that is 6 nodes and 24 bundles, and each replica straddles a node boundary — the group is only ever labelled with the node of its first bundle.

So with TP=8 on 4-GPU nodes, restarting replica 2 recreates eight NeMo-RL actors — four on node 4 and four on node 5 — even though seven of them never held a model. They have to come back because they hold the bundles that vLLM's own workers are placed onto.

Steps 9 to 13 are the only ones that touch Ray actors. There is no step that reaches into vLLM to restart a tensor-parallel rank: those workers are vLLM's, made when the engine is built at step 15, so they return as a consequence rather than as an instruction.

Why not just let Ray restart the actor?

Ray can do this for you: max_restarts=-1 makes it recreate an actor forever. NeMo-RL uses that in several places — the environment actors, and the generation router. It is deliberately not used for generation workers, which take Ray's default of 0 — "the actor doesn't need to be restarted". That is what makes a RayActorError conclusive: nothing is going to bring that actor back on its own, so the probe can go straight to DEAD without waiting to see if it recovers.

The router's own docstring says why the difference exists:

max_restarts=-1 is only meaningful because of that: Ray recreates a restarted actor through __init__ alone, so a class that starts its server from a separate method comes back permanently broken.

That is exactly a generation worker. Ray would re-run __init__ and stop there — no post_init, no URL report, no place in the refit collective, and no way for the ledger to learn that any of it happened. You would get an actor that looks alive and serves nothing. Steps 14 to 17 in the table above are precisely the work Ray would skip, which is why the restart has to be driven by the application.

How far up does it restart? Up to and including every Ray actor NeMo-RL made for that one replica — all 8 in this example, on both nodes — and no further. The cluster, the unified placement group, its 24 bundles, the worker group and the other two replicas are all reused untouched. That is the point: a dead actor does not release its bundle, so the replacement lands on the same GPUs.

The one piece that can survive the kill. vLLM runs its EngineCore as an ordinary child process — no setsid, not a daemon — and every cleanup path vLLM and Ray provide runs inside the process being killed. So a SIGKILLed worker leaves the EngineCore behind, still holding its GPU, and the replacement then has nowhere to load. That is what RAY_process_group_cleanup_enabled=1 is for: it puts each worker in its own process group so the raylet can kill the leftovers. It has to be set before ray start, because the raylet reads it — setting it in the driver does nothing on a multi-node job, which is exactly the shape this page is about.

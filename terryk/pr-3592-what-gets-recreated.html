What actually gets recreated when a generation shard restarts

Companion illustration for NVIDIA-NeMo/RL #3592. Permalinks pin the PR head 5b4a732. vLLM is pinned at 0.24.0 on x86_64 and 0.25.1 on aarch64.

why it never came back what gets recreated

Two pages on this PR, one question each — this one: how far down the stack a restart reaches.

A generation shard is one vLLM model replica. NeMo-RL gives it tensor_parallel_size × pipeline_parallel_size Ray actors, one per GPU bundle, but only the first of them loads a model: that one gets bundle_indices, which is exactly what makes it the model owner. The rest set self.llm = None and return immediately — they exist to hold their GPU bundle. The owner then builds the vLLM engine with distributed_executor_backend="ray" whenever TP×PP > 1, and hands it VLLM_RAY_BUNDLE_INDICES so vLLM's own Ray workers land on those same bundles.

Who owns what, and where the restart cuts

One run with 3 generation shards and tensor parallel = 4, so 12 NeMo-RL actors. Shard 2 dies. The orange band is everything the restart recreates; everything above it is reused as-is.

The four calls, with real indices

Same run: shard 2 is dead, tensor parallel is 4. Every value below is what the code actually computes.

leader_idx = get_dp_leader_worker_idx(2) # -> 8 worker_indices = range(8, 8 + 4) # -> 8, 9, 10, 11 for worker_idx in (8, 9, 10, 11): recreate_worker(worker_idx) # replays the recorded creation call: # same placement group, same bundle, # same runtime env, fresh actor name leader = workers[8] post_init_async(leader) # rebuilds the vLLM engine -> # vLLM spawns its 4 Ray workers # and the EngineCore child url = report_dp_openai_server_base_url(leader) # a NEW port, not the old one

Two things are worth pulling out of that.

All four actors are recreated, not just the model owner. The three placeholders died with the engine too, and their bundles have to be held by a live actor before vLLM can place its workers back on them. recreate_worker replays the arguments the original creation call was made with rather than working them out again — re-deriving the placement group, bundle and rank bookkeeping would be a second copy of that logic, free to drift from the first.

The restart stops at NeMo-RL's own actors. Nothing reaches into vLLM to restart a tensor-parallel rank. Those workers are vLLM's, created when the engine is built, so they come back as a consequence of rebuilding the engine on actor 8 — not as a step anyone wrote.

The short answer to "how far up does it restart". Up to and including every Ray actor NeMo-RL made for that one shard, and no further. The cluster, the placement group, its GPU bundles, the worker group and the other two shards are all reused untouched — which is the point, because a dead actor does not release its bundle, so the replacement lands on the same GPUs.

The one piece that can survive the kill. vLLM runs its EngineCore as an ordinary child process — no setsid, not a daemon — and every cleanup path vLLM and Ray provide runs inside the process being killed. So a SIGKILLed worker leaves the EngineCore behind, still holding its GPU, and the replacement then has nowhere to load. That is what RAY_process_group_cleanup_enabled=1 is for: it puts each worker in its own process group so the raylet can kill the leftovers. It has to be set before ray start, because the raylet reads it — setting it in the driver does nothing on a multi-node job.

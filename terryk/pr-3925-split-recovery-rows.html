Why the rollout-recovery reuse ratio has no row to live in

Companion illustration for NVIDIA-NeMo/RL #3925 (telemetry for rollout checkpointing), stacked on #3924. All permalinks pin the PR head a4c10a78.

One prompt produces a group of rollouts. The group size is num_generations_per_prompt, stored per group as expected_generations. The individual rollouts inside one group are called siblings. Everything below uses a group size of 4.

After a crash the SingleController gets work back from two different places, and each place logs its own numbers:

  • Finished groups come back out of the replay buffer. All 4 siblings are already done, so nothing is regenerated. The restore path counts them and logs groups_reused (single_controller.py:818).
  • Unfinished groups sit in a separate recovery ledger. Some of their siblings finished before the crash and are kept; the rest must be run again. The redispatch path counts these and logs groups_considered, groups_redispatched, siblings_reused and siblings_redispatched (single_controller.py:1259-1269).

These two sets do not overlap. The code says so itself when it logs “N unfinished rollout group(s) next to M canonical group(s)”. So groups_considered is not a superset of groups_reused, and groups_redispatched is a subset of groups_considered only — none of it is part of groups_reused.

Both paths call _log_telemetry_metrics separately, and every call writes one W&B history row stamped with its own telemetry/wall_time_seconds. So the two counts never share a row — and W&B can only divide two numbers that sit in the same row.

A suggested fix — not in the PR today

Nothing in this section is implemented. At the pinned head, groups_reused appears exactly once in the whole repo, in the restore event. The redispatch event emits five keys and that is not one of them. This is what the review asks the author to consider, written out so the cost is easy to judge.

The restore path already knows the number. It just writes it into a different event. Carrying it into the redispatch event would put both counts on one row, and the ratio would become an ordinary W&B expression. Same numbers as the figure.

# 1. restore path — already computes the count today, unchanged load_metrics["groups_reused"] = float(restored_replay_groups) # = 7 self._log_telemetry_metrics(load_metrics, prefix="timing/rollout_recovery") # ↑ writes row 1 (wall_time 8.1) — keep this, the restore timers belong here

this part is real code today: single_controller.py:818

# 2. redispatch path — the five keys below are today's code; # the green line is the proposed addition, so row 2 can answer the question alone self._log_telemetry_metrics( { "redispatch_schedule_seconds": 0.4, "groups_considered": 9.0, # unfinished groups in the ledger "groups_redispatched": 5.0, # of those 9, relaunched "siblings_reused": 14.0, # siblings kept inside those 5 "siblings_redispatched": 6.0, # 14 + 6 = 5 groups x 4 "groups_reused": 7.0, # ← PROPOSED: the FINISHED groups, from the other event }, prefix="timing/rollout_recovery", )

the five existing keys, without the proposed line: single_controller.py:1259-1269

# 3. with that one key added, one row holds both and the panel works row 2: groups_reused = 7 groups_redispatched = 5 7 / (7 + 5) = 0.58 # 58% of the groups that came back needed no regeneration

There is a cheaper version if the author would rather not touch the code: leave the two events alone, split the one table row in the metrics doc into two, and say that groups_reused arrives on its own point and may be missing. That tells the reader the truth, but it does not give them the ratio.

Why groups_reused can go missing entirely. The restore event returns early when _rollout_checkpoint_load_metrics is None (single_controller.py:805), while the redispatch event always logs. So a run can show groups_redispatched = 5 with no groups_reused anywhere — which reads as “nothing was reused” when it really means “that number was never written”.

One more gap in the same table: groups_considered is emitted at single_controller.py:1262 but is not documented at all.

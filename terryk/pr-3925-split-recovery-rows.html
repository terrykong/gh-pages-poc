Why the rollout-recovery reuse ratio has no row to live in

Companion illustration for NVIDIA-NeMo/RL #3925 (telemetry for rollout checkpointing), stacked on #3924. All permalinks pin the PR head a4c10a78.

After a crash, the SingleController restarts and tries to keep the rollout work it had already finished. Two things happen, and each one logs its own numbers. First the restore path counts the groups it pulled back out of the replay buffer and logs groups_reused (_log_rollout_restore_metrics). Then the redispatch path counts the groups it had to generate again and logs groups_redispatched plus the sibling counts (_redispatch_restored_rollouts). Both are separate calls to _log_telemetry_metrics, and every call writes one W&B history row stamped with its own telemetry/wall_time_seconds. So the two counts never share a row — and W&B can only divide two numbers that sit in the same row.

A suggested fix — not in the PR today

Nothing in this section is implemented. At the pinned head, groups_reused appears exactly once in the whole repo, in the restore event. The redispatch event emits five keys and that is not one of them. This is what the review asks the author to consider, written out so the cost is easy to judge.

The restore path already knows the number. It just writes it into a different event. Carrying it into the redispatch event would put both counts on one row, and the ratio would become an ordinary W&B expression. Same numbers as the figure.

# 1. restore path — already computes the count today, unchanged load_metrics["groups_reused"] = float(restored_replay_groups) # = 7 self._log_telemetry_metrics(load_metrics, prefix="timing/rollout_recovery") # ↑ writes row 1 (wall_time 8.1) — keep this, the restore timers belong here

this part is real code today: single_controller.py:818

# 2. redispatch path — the five keys below are today's code; # the green line is the proposed addition, so row 2 can answer the question alone self._log_telemetry_metrics( { "redispatch_schedule_seconds": 0.4, "groups_considered": 9.0, # every group in the recovery ledger "groups_redispatched": 5.0, # had to be generated again "siblings_reused": 23.0, "siblings_redispatched": 11.0, "groups_reused": 7.0, # ← PROPOSED, not present today }, prefix="timing/rollout_recovery", )

the five existing keys, without the proposed line: single_controller.py:1259-1269

# 3. with that one key added, one row holds both and the panel works row 2: groups_reused = 7 groups_redispatched = 5 7 / (7 + 5) = 0.58 # 58% of the work survived the restart

There is a cheaper version if the author would rather not touch the code: leave the two events alone, split the one table row in the metrics doc into two, and say that groups_reused arrives on its own point and may be missing. That tells the reader the truth, but it does not give them the ratio.

Why groups_reused can go missing entirely. The restore event returns early when _rollout_checkpoint_load_metrics is None (single_controller.py:805), while the redispatch event always logs. So a run can show groups_redispatched = 5 with no groups_reused anywhere — which reads as “nothing was reused” when it really means “that number was never written”.

One more gap in the same table: groups_considered is emitted at single_controller.py:1262 but is not documented at all.

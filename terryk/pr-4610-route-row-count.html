How many route rows each vLLM or Megatron Inference call must stage, and why #4307 breaks after #4610

#4610 (vLLM turn-boundary route) meets #4307 (Megatron Inference router replay, still open). Permalinks pin #4610 at 8df2f08, #4307 at 293e5a4, and main at 3df254d.

Before
Each call staged one route row per new token (delta_len), and both length checks expected exactly that.
This PR
vLLM calls after the first stage one extra row, for the previous turn's last token. Both checks now expect delta_len + 1 for those calls.
Status
Open, not fixed in either PR. Megatron Inference (MInf) in #4307 still stages delta_len rows. Whichever PR merges second must change MInf's slice, or every multi-turn MInf rollout fails to stage.

Two pages on this PR. This one covers the row count, and why it matters for Megatron Inference.

Three numbers describe one call. Each call's tokens are the earlier tokens plus its new ones. prev_len counts the earlier tokens, which an earlier call already staged. delta_len counts the new ones (len(record.token_ids_delta)). routed_len counts the route rows the call actually stages. #4610 adds boundary_route_rows(prev_len), which is 1 when there are earlier tokens and 0 on the first call. Every staged call must then satisfy routed_len == delta_len + boundary_route_rows(prev_len).

Example: the same call 1 as page 1 (p0–p4). Call 2 adds 2 tool tokens (p5, p6) and generates 4 (p7–p10), so no two numbers below are equal.

The first call of a rollout has no earlier turn, so both backends pass. That is why single-turn runs would not show the problem.

Who checks the count

Two places check the same rule. Before #4610, both compared against delta_len. Now both add the boundary row:

  1. At capture, the token sink (TQTokenSink.stage; main version here). Both vLLM and MInf write through it (MInf's complete_call). This check fires first. For MInf call 2 it raises routed_experts must already be delta-aligned … (expected 7 rows). Gym catches the error and marks the call capture-failed (capture.py), so the rollout never gets a usable row.
  2. At rebuild, the reassembler (routed_len_mismatch; main version here). This is a second check, in case a row slips past the sink. In this case the sink has already failed, so this check never sees the call.

The two counts are not both "right" in general. The rule itself changed. MInf follows the old rule, and #4610 changed the rule in both checks and in vLLM, but not in MInf, because MInf's stager only exists on the #4307 branch. The PRs change different files, so git will not report a conflict.

What would fix it (proposed, not in either PR)

Where the fix lands: RL only, one line in MInf's stager, _delta_align_minf_routing_indices. Nothing below is implemented or run. The route assembler from #4610 already writes the extra row into p4's slot (route_assembly.py), so nothing else changes.

On call 2 this returns aligned[4:], which is 7 rows, so it passes both checks. It also gives MInf the real route for p4 instead of the −1 it uses today (MInf already writes −1, not 0…k−1, so it never had the #4355 fake-route bug). Two MInf tests in #4307 assert the old count and would need the extra row: test_megatron_stager_delta_aligns_token_in_routes and test_finalize_group_publishes_minf_routes_staged_through_the_stager.

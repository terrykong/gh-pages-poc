what it adds image-capture crash

Two pages on this PR, one question each — this one: the image-capture regression.

Background. When the model has an image processor and token capture is on, setup turns on media capture automatically (setup.py:1251). Then every captured call gets a CapturedMedia(items, tensors) (_capture_request_media). tensors holds only the images that are new in this call; an image from an earlier turn is kept, not resent. So when a call adds no image, tensors is None (capture_processed_media, type dict | None).

Two turns of one rollout, before and after

Running the real _finish_request_capture from each commit with media=CapturedMedia((), None) and centering off: base stages with attachments=None; head raises TypeError and leaves no capture state behind. The existing VLM token-capture functional tests send one image per call, so they never build a call with tensors=None.

The fix

Where the fix lands: RL only, one line plus a unit test. vllm_worker_async.py L968. No Gym change: Gym already accepts attachments=None, as the base code relied on.

With the fix, turn 2 builds {}; with centering off it stays empty and attachments or None a few lines below (L978-L982) passes None, exactly as before the PR; with centering on it holds only the two top-K tensors. Proposed in the review; not yet applied by the author. A unit test should call _finish_request_capture with CapturedMedia((), None) and check that the call is staged.

So what. Without the fix, any multi-turn VLM rollout with token capture fails on its second model call, and any text-only prompt in a VLM run fails on its first. The failure is a bare HTTP 500 with the capture call left open, so Gym does not even get a capture_failed to recover from. It does not need score centering to be on, so it reaches users who never touch the new feature.

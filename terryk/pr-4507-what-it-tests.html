Background. During GRPO training, NeMo RL runs an agent in Gym, and vLLM writes the model's replies. Every finished episode becomes a training row. A rollout snapshot saves the episodes still in progress. #4506 adds prefix recovery: if a snapshot lands while vLLM is in the middle of a reply, it keeps the tokens written so far (the prefix). After a crash, the restored run continues from those tokens and only writes the rest (the tail). Dotted words have a short explanation: hover or tap them.

The test launches the same small job three times (Qwen3-1.7B, 4 prompts × 2 tries, 1 training step): once without a crash, once killed mid-reply, and once restored from that kill (the script's three runs). Each prompt asks the agent to create one calendar event, then list the numbers 1 to N in its closing reply. That reply is long, so the kill lands inside it. Sampling uses top_p=1e-6, which makes generation almost greedy, so two runs pick the same tokens and can be compared token by token. Each run saves the exact rows the trainer trained on, and the test compares the restored run's rows with the reference rows.

Both tests use the same test hook, the same policy-call proxy and the same snapshot readers (_single_controller_turn_recovery_hook.py, _gym_recovery_snapshot_helpers.py).

So what. If this test passes, a crash in the middle of a reply costs only the tail of that reply, and the trainer sees exactly the rows a crash-free run would give it. It does not test learning: with top_p=1e-6 the policy-gradient term is 0. Before merge it still needs its first CI run. A set-aside row could also hide a wrong saved prefix (C16).

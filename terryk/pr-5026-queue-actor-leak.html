How measuring argument size leaks the policy's queue actor

NVIDIA-NeMo/RL #5026 · permalinks pin the PR head 925d381 and Ray 2.58.0

Before
The policy's small queue was pickled only by Ray, as part of each initializer's start-up call. When the group shut down, the queue's actor was freed.
This PR
Pickles every constructor argument once with plain cloudpickle, just to measure its size. The queue (about 430 bytes) is then passed on unchanged.
Status
Open, not fixed in this PR. The queue's actor now lives until the driver exits. The review proposes a smaller fix, tested on CPU Ray 2.58.0.
pickle once the leaked queue actor

Two pages on this PR, one question each. This one: the bug in the size check.

Background. Ray counts who still holds each object or actor, and frees it when the count reaches zero. That works only when Ray does the pickling itself (in a task call or ray.put). If you pickle an actor handle with plain cloudpickle, Ray cannot see where the bytes go. So it adds a reference that is never removed: it will "pin the object for the lifetime of this worker" (serialization.py L333-L340, reached for actor handles from L185-L196).

Both lm_policy and lm_value pass pre_init_communication_queue=RayQueue() to their workers. A RayQueue is a handle to its own actor. The PR's helper sizes every argument with len(cloudpickle.dumps(value)), the queue included. That one pickle is enough.

Three ways to send the same queue

The cost is one idle actor process per Policy or Value build, until the driver exits. A single training run builds only a few. Test sessions, and runs that rebuild groups (a teacher torn down mid-run, say), build many.

What would fix it — proposed, not in the PR

Where the fix lands: RL only, one file plus its tests. worker_groups.py: drop the size check and ray.put every argument. No caller changes: Ray still hands each initializer the real values.

In order: (1) ray.put pickles inside Ray, so the queue is counted and freed when its object is. It also pickles the tokenizer once instead of twice: today's 0.31 s one-time cost is the size check plus the put. (2) The group no longer keeps the refs. Ray already keeps "arguments to pending tasks" alive (Ray docs), and holding them would pin the queue again until the group object is gone. (3) The initializer's ray.get branch can never run, because Ray resolves keyword refs too (flatten_args). ray.put refuses an existing ObjectRef (worker.py L836), so those pass through as before.

So what. Tested together with the new tests on CPU Ray 2.58.0: a test that runs a real queue through the helper fails on this PR (assert 'ALIVE' == 'DEAD' after 30 s) and passes with the fix in about 0.1 s. All worker-group tests pass (35 passed, 1 skipped). The fix keeps the full speed-up and makes the helper shorter.

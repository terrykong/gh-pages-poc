Why the checkpoint barrier became reentrant, and the one call that required it

Companion note for NVIDIA-NeMo/RL #3923, and a sibling of the note on the cleanup call that escapes the cut. All permalinks pin the head 0a93f0f.

Writes to the queue and the save that snapshots it must not overlap. A barrier enforces it: a writer holds a cut while it works, and a save waits for every cut to close. Two shapes express "my caller already holds one". The older one is a parameter — the method takes the cut and works with it. The one this PR adds is invisible: ask for a cut while you already have one, and you silently get the same one back.

One call site out of four

Only clear_staging_keys() is reached from a caller that already holds a cut — discard_recovery_group(cut, ...), whose own caller opens the cut and passes it down. The other three (commit, remove_group, remove) are called from tasks holding nothing.

What the other three do instead

The queue already had a way to say this, and it is a parameter, not a property of the call stack. A public method takes the barrier; a private twin assumes the caller holds it:

# the existing shape -- two of these already shipped before this PR async def remove_group(self, group_id, *, remove_in_dp=False): async with self._data_plane_checkpoint_barrier.mutation(): return await self._remove_groups_unlocked([group_id], ...) # caller holds it # the new method does only the first half, and is called from inside a cut async def clear_staging_keys(self, staging_keys): async with self._data_plane_checkpoint_barrier.mutation(): # asks for a second await call_data_plane(self._dp_client, "clear_samples", ...)

→ _remove_groups_unlocked() and _clear_samples_unlocked() are both older than this PR; clear_staging_keys() is new

Splitting it the same way — a public clear_staging_keys that takes the barrier and a _clear_staging_keys_unlocked(cut, ...) for the one caller that already has one — removes the only reason the barrier needed to change. The body is four lines; the only thing stopping it from reusing _clear_samples_unlocked is that it targets the staging area rather than the main one.

What the change cost

Beyond the 26 lines and their tests, joining is now a property of the call stack rather than something written at the call site. async with barrier.mutation() no longer tells a reader whether it takes the barrier or quietly reuses one; that depends on who called you.

It also opened a hang. A nested request joins an outer mutation(), but nothing registers an outer checkpoint() the same way, so a request made inside a save waits for a save its own task is holding. Both shapes, run against this head:

async with b.mutation(): async with b.mutation(): # joins the outer cut, active_mutations=1 async with b.checkpoint(): async with b.mutation(): # never returns. no error, no timeout

→ 1. mutation() inside mutation(): joined, active_mutations=1
→ 2. mutation() inside checkpoint(): HUNG

Nothing here is broken today. No current path opens a cut inside a save, so the hang is a trap for the next edit rather than a live bug — and it is exactly the trap someone falls into fixing the escaping cleanup call, whose obvious repair is to wrap it in mutation(). The two notes are the same root cause seen from opposite ends: one new method took the barrier when it should have taken a cut, and another took neither.

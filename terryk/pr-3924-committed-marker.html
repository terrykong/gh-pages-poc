How a rollout snapshot survives kill -9, and the one moment it does not

Companion note for NVIDIA-NeMo/RL #3924. All permalinks pin the head c610fbb.

This PR saves rollout work to disk on a timer, so a job that dies mid-step does not have to regenerate everything. That only helps if a snapshot killed halfway through is never mistaken for a finished one. The trick is a marker file: a snapshot directory counts as real only when it contains a file named COMMITTED. The writer builds everything under a temporary name, flushes it to the disk, writes the marker last, and only then renames the directory into place. So the marker is the last thing to appear, and a reader can trust it.

The order below is the whole design, and it is 15 lines of commit_snapshot. "Flush" means fsync — asking the operating system to actually put the bytes on the disk instead of holding them in memory.

Kills A, B and C all land on the safe side. Only D leaves something behind that nothing will ever pick up.

Why D is unreachable, in the two lines that cause it

Two different pieces of code decide what a snapshot directory is, and both ask the same question. The reader skips anything without a marker:

# resolve_latest_snapshot — pick the newest snapshot to restore from for candidate in candidates: if not (candidate / ROLLOUT_SNAPSHOT_COMMITTED_FILENAME).is_file(): continue # no marker -> not a real snapshot, ignore it

rollout_checkpoint.py :545–547

And the cleanup only counts directories that have a marker, then deletes everything past the newest keep_latest_k of them:

# commit_snapshot — drop old snapshots after publishing a new one committed = sorted( child for child in root.iterdir() if child.is_dir() and _SNAPSHOT_RE.fullmatch(child.name) and (child / ROLLOUT_SNAPSHOT_COMMITTED_FILENAME).is_file() # same question ) stale_snapshots = committed[keep_latest_k:] # a marker-less dir is not in this list for stale in stale_snapshots: shutil.rmtree(stale) # ...so it is never passed to rmtree

rollout_checkpoint.py :505–518

Put those together and the gap falls out. shutil.rmtree deletes the files inside a directory before the directory itself, so the marker can go first. If the process dies right then, snapshot_3/ is left with no marker. The reader ignores it. The cleanup does not see it either. It is not wrong — nothing restores from it — it just sits there taking up disk for the rest of the run, and the run after that.

Running the real functions, with keep_latest_k = 2 and one marker removed by hand to stand in for a kill at point D:

after 3 saves -> snapshot_000002 snapshot_000003 remove one marker -> snapshot_000003 snapshot_000004 after 4 more saves -> snapshot_000003 COMMITTED=False <- three cleanups later, still here snapshot_000007 COMMITTED=True snapshot_000008 COMMITTED=True

Seven saves, retention of two, and the count on disk is three. The extra one never leaves.

The repair is already written elsewhere in the same file. When the writer picks a name it clears a leftover temporary directory first — if tmp_path.exists(): shutil.rmtree(tmp_path) — which is exactly why kill A recovers. Doing the same for a marker-less snapshot_* directory closes D. Deleting the marker before the rest of the directory also helps: then a half-finished delete leaves something the next pass can still recognise, instead of something invisible.

What this means if you turn the feature on. Snapshots are off unless you set rollout_checkpointing.interval_s, and the crash protocol itself holds up — a snapshot is either complete and readable or ignored, never half-applied. The cost of the gap is disk, not correctness: a run that gets killed during cleanup leaks one snapshot directory each time, and the retention setting will not claw it back. That matters more here than it normally would, because being killed at an awkward moment is the exact thing this feature exists to survive.

How NeMo-Gym teardown lost its 10-second limit

Companion illustration for NVIDIA-NeMo/RL #3373 — wire sharded stacks into training. All permalinks pin the PR head f93ba52.

One page on #3373. Background from the PRs below it in the stack: how the shard actors get created (#3371) and how rollouts get routed to them (#3372).

When a training run ends — cleanly or by crashing — something has to stop the NeMo-Gym servers. That happens in a finally block, so it runs even when training already failed. A shutdown that never returns there is worse than a slow one: it replaces the real training error with a job that just sits. shutdown_environments() is the helper every entrypoint calls, and it has a 10-second limit for exactly that reason (utils.py:149).

This PR changes what gets handed to that helper. It used to be one Ray actor handle; now it is a NemoGymShardSet, a plain Python object that owns several actors (setup.py:1303). The helper tells the two apart by asking whether shutdown is a remote call (utils.py:182) — and the two branches do not have the same limits.

Which branch teardown takes, before and after

Why the wait has no floor either

An unbounded wait would still be fine if the thing being waited on always finished. It does not have to. Gym's own teardown stops each child server on a 1-second then 2-second timer, so that part ends — but the last step waits on the head server with no timer at all, and that wait can never be cut short:

# Gym: nemo_gym/cli/env.py:622-623 self._head_server.should_exit = True self._head_server_thread.join() # no timeout # Gym builds the server without a shutdown limit — server_utils.py:793-797 uvicorn.Config(app, host=..., port=...) # timeout_graceful_shutdown not passed -> None # uvicorn 0.37.0: server.py:281 passes that None straight through await asyncio.wait_for(self._wait_tasks_to_complete(), timeout=self.config.timeout_graceful_shutdown) # None # uvicorn 0.37.0: server.py:300 — the loop has no clock in it while self.server_state.connections and not self.force_exit: await asyncio.sleep(0.1) # force_exit is set only from a signal handler (server.py:336), and uvicorn # refuses to install one off the main thread (server.py:316). Gym runs this # server in a daemon thread, so force_exit stays False forever.

So the loop's only exit is every open connection closing by itself (uvicorn server.py:300, :316, :336, Gym env.py:622-623). One request that cannot finish — say a call to a vLLM endpoint whose workers are already gone, which is the state teardown runs in after a crash — and nothing on the path ever returns. Nobody has reproduced that hang; what is certain is that no step between the finally block and that loop sets any limit.

The fix: pass the limit down

The 10-second value already exists and the caller already has it. It just stops one function short. Two edits carry it the rest of the way:

# 1. nemo_rl/environments/utils.py:187 — hand the owner object the caller's limit - env.shutdown() + env.shutdown(timeout=timeout) # timeout = 10.0 by default (utils.py:149) # 2. nemo_rl/environments/nemo_gym.py:1276 — accept it instead of hardcoding None -def shutdown(self) -> None: +def shutdown(self, timeout: float | None = DEFAULT_ENV_SHUTDOWN_TIMEOUT_SECONDS) -> None: shutdown_environments( {...one entry per actor...}, - timeout=None, + timeout=timeout, )

That second call already holds real Ray actor handles, so once a limit reaches it the normal ray.get(..., timeout=…) and ray.kill() path works again with no other change. One existing assertion moves with it — test_nemo_gym_utils.py:1043 currently pins timeout=None, and it predates this PR.

Worth knowing even if nothing ever hangs. Gym stops each child server on a 1-second wait, then a kill, then a 2-second wait. A stack with many child servers therefore spends minutes shutting down, where the old path gave up after 10 seconds and killed the actor. So the change is visible on every ordinary run, not just the bad one — and on a bad one, the error that actually ended training is the thing left unprinted.

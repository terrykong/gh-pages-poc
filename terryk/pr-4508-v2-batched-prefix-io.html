Four pages on this PR. The round-1 pages describe an older head. This one: how the batched path differs from the old one, today.

Background. When RL saves a checkpoint in the middle of generation, each unfinished model call writes its tokens so far to TransferQueue (TQ), one row per call. After a restart, Gym sends the call back with the keys of its saved rows, and the call continues from them instead of starting over. Dotted words have a short explanation: hover or tap them.

Before, the save loop wrote one call at a time (_checkpoint_active_generation_cut → stage_generation_prefix). Now _checkpoint_generation_cut_batched freezes calls one by one, keeps each locked, and writes up to 256 rows in one stage_generation_prefix_batch call. On restore, the new PrefixReadBatcher waits 2 ms, merges the keys of every request that asked, and runs one get.

The two paths, on one small example

Example: 3 unfinished calls (c0, c1, c2) and a batch limit of 2 rows. On restore, c1 has 2 saved rows (one from an earlier checkpoint), so the 3 requests need 4 keys.

Where the two paths meet, and what still differs

Both write paths build a row with _encode_record, which is the old single-row body moved, not new code. The per-call freeze, ack and seal logic is the old body too, now the generator _generation_cut_transaction, so a batch can keep several calls frozen at once. Both restore paths end in _resolve_usable_generation_cut, which checks the prefix digest and lets the call regenerate if anything is wrong. The new path only passes in rows it already read.

So what. The design reuses the old code well: the row encoding and the per-call logic are moved, not rewritten, and the restore still goes through the same check-or-regenerate step. What remains is size. The write side keeps a two-step handshake that only made sense for the old all-or-nothing batch, and the read side retries a failed read twice. The cuts are on the what can shrink page.

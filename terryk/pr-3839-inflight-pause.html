How a half-finished request survives a weight update in async GRPO

Companion illustration for NVIDIA-NeMo/RL #3839 — pause generation during in-flight refit. All permalinks pin the PR head cb8948d3.

In async GRPO the generation engine and the trainer run at the same time. When a training step finishes, the new weights are copied into the vLLM engine — that copy is called a refit. Setting in_flight_weight_updates: true tells the trainer not to wait for the slowest request to finish first, which is where most of the speedup comes from. But before this PR nothing stopped the engine while the copy happened: the new weight tensors were written into a model that was still running forward passes. This PR pauses the engine for the copy, and — this is the part that matters — pauses it in a mode that keeps the half-finished requests instead of throwing them away.

The window where weights change under a running forward pass

The mode is the whole trick. vLLM's pause takes a mode argument with three choices — "abort" throws in-flight requests away, "wait" lets them finish first, and "keep" freezes them where they are and picks them up on resume. This PR asks for "keep", so a request that is 5 tokens in stays 5 tokens in and finishes under the new weights.

Upstream: AsyncLLM.pause_generation, vLLM v0.25.1 — the version this repo pins.

One detail worth knowing about clear_cache. It is set from recompute_kv_cache_after_weight_updates. When it is on, the cache is wiped while the engine is frozen, which kicks every kept request back to the waiting queue so it recomputes its KV under the new weights. That is stronger than what it replaced: the old post-refit call used vLLM's default, which quietly does nothing while running requests still hold KV blocks.

Does it work?

Yes — there is a real run, not just green CI. The author ran the unchanged 30B-parameter async performance recipe for 10 steps on 32×H100 (4 nodes, 64 prompts/step × 32 generations, global batch 2048, async vLLM with in-flight updates), and reported it in the PR:

Run: W&B hm6vr3e8, linked from the PR.

Two honest caveats. That run was on an earlier commit (abf3b2a3); the later commits changed how the pause is dispatched, though for vLLM specifically the old and new code paths resolve identically, so the engine behaviour in that run is the behaviour being merged. And no before/after throughput comparison has been posted — the engines now sit idle for the transfer window, which is a real cost that the run above does not measure. If you care about the speed trade-off, that number is the one to ask for.

So what. If you run async GRPO with in_flight_weight_updates: true on async vLLM, your rollouts were previously being generated across a weight swap — some tokens produced by a model that was half old and half new. After this PR the engine stops for the copy and picks the same requests back up, so every token comes from one weight version. You pay for it with a short stall at each refit, and that stall has not been measured yet.

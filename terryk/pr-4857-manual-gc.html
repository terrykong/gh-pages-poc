How manual_gc makes every rank collect garbage at the same moment

NVIDIA-NeMo/RL #4857 · permalinks pin the PR head b4c6733.

Before
Python garbage collection runs on its own schedule in each Megatron training process. A ~1 s collection on one rank makes all the other ranks wait for it at the next sync.
This PR
Adds an opt-in flag, policy.megatron_cfg.manual_gc. It turns automatic GC off, and every rank collects together once every manual_gc_interval optimizer steps, on both v1 (train()) and v2 (finish_train_step) trainers.
Status
Partly fixed. v1 and v2 trainers collect as of b4c6733. OPD/MOPD teachers turn GC off and never collect, and the PPO value worker ignores the flag. See page 2.

Two pages on this PR. This one: what the flag does and how it compares to automatic GC.

Background. Python frees most objects right away. Objects that point at each other in a loop are only freed by the garbage collector, which runs when a process has created enough new objects. In a training job every rank is its own process, so each one decides on its own. Dotted words have a short explanation: hover or tap them.

A training step has many sync points: every rank must reach the same collective before any of them can go on. If rank 3 starts a 1 s collection mid-step, ranks 0–2 sit idle at the next collective for that second. The PR's trace on 32 nodes saw this on up to 90 of 128 ranks in one step, stretching 66 s steps to 75–85 s. The flag copies Megatron-LM's own manual_gc: turn GC off at startup, then collect on every rank at the same step boundary.

How the PR does it

Three small methods on the Megatron policy worker. The start of setup checks the config, the end of setup turns GC off, and each optimizer step counts toward the interval. Forked child processes (data workers) get normal GC back.

Code: _manual_gc_interval_from_cfg / _maybe_enable_manual_gc / _maybe_run_manual_gc, config fields in MegatronConfig. Same rule as Megatron-Bridge's training loop. Unlike Megatron, the PR rejects an interval of 0: NeMo-RL has no eval-time collect to fall back on, so 0 would mean GC off with nothing ever collecting.

So what. On v1 and v2 policy training, the flag turns many scattered, stacked pauses into one shared pause every N steps. The trade-off is memory: garbage builds up between collections, so a large interval needs a check of host memory. The PR has no run with the flag on yet; the review asks for step time and memory, flag off vs on. OPD/MOPD teachers and the PPO value worker don't get it right yet: page 2.

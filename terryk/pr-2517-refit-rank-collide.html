Why refit ranks collide when there are two vLLM instances

NVIDIA-NeMo/RL #2517 (fix the vLLM DP path). Permalinks pin head 1c42be6; vLLM links pin v0.29.0.

Before
Every refit setup gave each vLLM DP rank its own rank offset. With more than one vLLM instance, that counts the DP rank twice.
This PR
Fixes the offset in init_collective (the default NCCL refit): all DP ranks of one instance now share the instance's offset.
Status
Fixed for the NCCL refit. Open for the checkpoint-engine (NIXL) refit and the shard rebuild, which still use the old rule. Raised in the review.

Two pages on this PR, one question each. This one: which refit paths still give wrong ranks.

Background. A refit copies new weights from the trainer into vLLM every step. Before the first refit, each vLLM worker gets one rank number in a shared group, and the numbers must be exactly 0 … N−1 with no repeats. The driver sends each DP rank an offset, and the worker adds its own rank inside vLLM. Dotted words have a short explanation: hover or tap them.

When EP > TP, vLLM runs data parallel (DP) inside one engine: one instance = EP ÷ TP DP ranks that share one torch group. vLLM numbers every worker of an instance in that group: rank = dp_rank × TP + tp_rank (PP = 1 here) (parallel_state.py). The worker then computes its refit rank in resolve_rollout_rank: offset + that rank, unless one instance covers the whole rollout. So the offset must be the instance's first worker, not the DP rank's. The PR does that in init_collective, but the checkpoint-engine setup still uses one offset per DP rank.

8 generation GPUs, TP = 1, EP = 4 → two instances

Who uses which rule at head: new — the default NCCL refit (init_collective). Old — the checkpoint-engine refit, used when refit_transport is nixl or a plugin on a non-colocated run; the factory checks only "non-colocated" and "vLLM", so nothing stops this setup. Also old — the shard rebuild after a lost worker (plan_refit_membership). The nccl_reshard copy is old too, but nccl_reshard rejects EP > TP, so it cannot be reached.

The fix — proposed, not in the PR

Where the fix lands: RL only. Nothing below is implemented. worker_utils.py: one helper for the offsets. checkpoint_engine_weight_synchronizer.py and init_collective both call it. The rebuild path raises when vLLM DP is on: losing one DP rank takes down its whole instance anyway.

With the example above, resolve_vllm_rank_prefixes(8, 8, 4) returns [0,0,0,0,4,4,4,4], the green row. A unit test that checks the refit ranks come out as exactly 0 … N−1 for (8 GPUs, TP 1, EP 4) and (32 GPUs, TP 2, EP 16) locks it in. The arithmetic was checked in Python, not on GPUs.

🔴 review comment C1 — vllm_generation.py:836 C2 — turn on vLLM DP in a non-colocated nightly

So what. The PR's own nightlies are colocated, so they refit over CUDA IPC and never run any of these paths. A user who turns on vLLM DP with 2+ instances and a NIXL refit gets duplicate and out-of-range ranks at the first refit. One shared helper removes the second copy of the rule, which is the bug class membership.py itself warns about.

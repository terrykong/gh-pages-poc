Why one dead generation shard freezes the whole run — and how the weight-copy group is rebuilt without it

Companion illustration for NVIDIA-NeMo/RL #3591 (part 3/4 of the SingleController resiliency stack). Sequel to #3590 — who watches what. All permalinks pin the PR head 8779394.

Every training step, the new weights are copied from the trainer to the inference engines. That copy is called the refit. When generation runs on its own GPUs, the refit is one NCCL broadcast over a single group — model_update_group — that is built once at startup and contains every trainer rank and every generation rank (collective_weight_synchronizer.py:112). A NCCL broadcast only completes when every rank in the group calls it. So if one generation process dies, the next refit waits for a rank that will never arrive. #3590 could already notice the dead shard and stop sending it requests — but it could not stop this, and this is the part that ends the run.

The worst part is how it fails. There is no exception and no error. The process sits inside NCCL burning no CPU, and Ray still reports every actor as healthy. One observed run sat like that for about half an hour before anyone noticed.

The fix: who owns what, and which way information moves

Three processes are involved and they own different pieces. The controller is a Ray actor with no GPU (single_controller.py:82), so it is never inside a collective — which is also why it cannot pull a worker out of one. That single fact decides where each piece has to live.

Most of this diagram is not new. The probe loop, the ledger, the two relay objects, the synchronizer, is_alive() and the router all arrived with part 2. What this PR adds is marked NEW: a watchdog thread inside each GPU worker, a deadline riding every refit call, and reconcile_communicator() to rebuild afterwards.

Two things the numbering is meant to settle. ① is one sync_weights() call: the synchronizer calls the trainers and the engines itself, through the two relay objects, which is why one event reaches two workers. ② has nothing to do with the refit — it is answered by the vLLM Ray actor, one level above the engine process, so an engine that is up but failing every request still looks healthy. ③ is the reason the watchdog cannot live in the controller: a thread sitting in NCCL is not serving RPCs, so nothing sent from outside arrives. ④ is the abort surfacing as an exception through ray.get, landing back in the synchronizer, which is what triggers the rebuild.

Closing the gap in the ranks

When the group is rebuilt, the survivors are renumbered so there is no hole. Same example: 2 trainer ranks, 3 generation shards of 1 GPU each, shard 1 dies.

Why close the gap instead of leaving rank 4 where it was? Because the other weight-transfer path builds its destination layout as torch.arange(offset, offset + num_gpus). A hole in the numbering does not raise an error there — it just points every parameter at the wrong place. So the survivors are renumbered to run 0, 1, 2, … with nothing missing. That renumbering is the whole job of plan_refit_membership, a module of plain integer arithmetic with no Ray and no GPUs in it, so it can be tested on a laptop:

plan_refit_membership(surviving_shards=[0, 2], dp_size=3, total_gen_workers=3, train_world_size=2) → RefitMembership(world_size = 4, # was 5 train_world_size = 2, # unchanged: trainers are never dropped shard_prefixes = {0: 0, # shard 0 keeps its place → global rank 2 2: 1}, # shard 2 slides down one → global rank 3 workers_per_shard = 1)

The rebuild runs at the top of the weight sync (single_controller.py:1290), not when the death is noticed. That is on purpose: changing who is in a NCCL group is itself a group operation, so it is only safe at a moment when the group is idle and every rank agrees it is idle. The top of the refit is that moment. Running it every step also means a health update that arrives late or out of order fixes itself on the next step.

The third move applies to one transport only. The nccl_reshard path does not broadcast the same bytes to everyone — it cuts each parameter into pieces and sends a different piece to each generation rank. Which piece goes where is worked out once, from the number of generation ranks (nccl_reshard_weight_synchronizer.py:245). Reusing that plan after a shard is lost does not fail — the survivors simply write the pieces the dead shard used to own and leave their own pieces empty. So the plan is thrown away and worked out again, in the same _build() that the first startup uses — so every normal run exercises the rebuild code.

One subtlety worth keeping. "Gone" is deliberately not the opposite of "serving". A shard can be held back from serving requests while its process is perfectly alive — because it is failing health checks, or because it was just reloaded and still holds old weights. Those shards must still take part in the refit; for the reloaded one, the refit is exactly how it stops being out of date. So the refit asks a narrower question, over {DEAD, RESTARTING, RETIRED} only (fleet_health.py:70). Using the serving set instead would drop a shard from the group over one slow health check.

Does it work?

The piece the whole design rests on — that you can free a process already stuck inside NCCL — was measured directly. With a peer killed in the middle of a broadcast, a survivor blocked in the collective was released 0.15 s after another thread called abort(), on 2×A6000. That is the measurement that makes the watchdog possible, and it is why the code calls abort() rather than destroy(): NCCL documents destroy as an operation every rank must join, which is precisely what a dead rank cannot do. A healthy refit was timed at about 1.9 s for a 1.5B model on GB200, which is what the deadline should be set well above (config.py:194).

The end-to-end proof is thinner than it looks. There is a test that kills a shard mid-run and asserts training finishes — grpo_sc_generation_shard_recovery.sh, registered four times so it covers both transports and a kill placed inside the collective. But it needs at least 3 GPUs (2 generation shards plus a trainer), and it exits 0 with a "SKIP" message below that. The L1 runners have 2 GPUs, and a skip and a pass look identical to CI. So on the automated runs, that test has not executed. The right thing to ask for before merging is the same thing the previous PR in this stack did for its sibling test: a manual run on a machine with 3 or more GPUs, with the result posted on the PR.

What this changes. Before this PR, losing one generation engine on the non-colocated path ended the run, in the most expensive way available: a silent hang that looks healthy from the outside, so the GPUs stay booked until a human notices. After it, the run keeps training on the shards that are left. The knob is refit_timeout_s, and it is off by default — leave it unset and no watchdog thread starts and the refit path is unchanged. Set it well above a normal refit: firing early aborts a run that was only slow, while firing late just means a hang lasts a little longer before it is broken.

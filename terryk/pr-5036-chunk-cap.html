How max_groups_for_streaming_train splits a training step into chunks — and what it does not change

NVIDIA-NeMo/RL #5036. All permalinks pin the PR head 391cb0fc.

Before
The trainer had only a floor (min_groups_for_streaming_train). Once generation ran ahead, one hand-off could take the whole step, so the step became a single chunk.
This PR
Adds an optional ceiling. Each hand-off takes at most max_groups_for_streaming_train prompt groups. Default null keeps today's behavior.
Status
Chunking works as described (the author's 1-node run below). Open: whether it frees generation is not shown — asked in review comment C2.

Four pages on this PR, one question each — this one: what the new knob changes.

Where this sits. Single controller (v2) only: the _train_pump loop that hands finished rollouts to the trainer. GRPO and PPO both use it; the v1 loops (grpo_train, async_grpo_train) are untouched. A prompt group is one prompt plus all its sampled answers. A chunk is one hand-off of whole groups from the buffer to the trainer; a step is done when its chunks add up to num_prompts_per_step. Packing into micro-batches happens later, inside each chunk — see the zoomed-in picture below. How many groups go into each chunk: page 2. Dotted words have a short explanation: hover or tap them.
async_rl: min_groups_for_streaming_train: 8 # floor: wait for at least this many ready groups max_groups_for_streaming_train: 8 # NEW ceiling; null = no ceiling (default) grpo: num_prompts_per_step: 32 # a step always trains on exactly 32 groups

Inside one training step, the pump runs a chunk loop (while groups_dispatched < target; not the step loop, not the micro-batch loop). Each pass asks the sampler for between a floor and a maximum of ready groups. The maximum was always "groups still missing from this step" (L3258), so a full buffer handed over the whole step at once. The PR lowers that maximum to the cap (L3263-L3265). The step still trains on exactly 32 groups; only where the chunk boundaries fall changes.

Open question: does a cap let generation work during training?

The PR's goal is less idle generation. But generation is held back by two gates, and neither opens at a chunk boundary:

  1. Buffer slots. The rollout side takes one slot per group; trained groups give theirs back only when the step closes.
  2. The staleness limit. New prompts wait on the trainer's weight version, which moves only after the optimizer step.

So with a full buffer, both rows in the figure let generation go at the same moments. The cap may only add per-chunk work (a logprob pass, advantages and training setup for each chunk). The 1-node run shows chunk counts, not timings.

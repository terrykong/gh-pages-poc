Why a NeMo-Gym shard's port range never reaches Gym

Companion note for NVIDIA-NeMo/RL #3369 (define shard configuration). All permalinks pin the PR head b6bdd33.

#3369 adds a schema for splitting one NeMo-Gym stack across several Ray actors. Each shard can ask for its own range of TCP ports, and the merge writes that range into the shard's config. The value is checked, carried through the merge, and handed to the actor. Then the actor throws it away: _spinup overwrites both keys with values read from a field that nothing ever fills in. Gym always gets 5000–5999. The same dead path already ignores the port range in a shipped recipe.

Where the value dies

The overwrite reads from self.cfg, which is the actor's NemoGymConfig. Its port_range_low is optional, and no code anywhere sets it — build_nemo_gym_config builds the object without it. So the .get() falls back to the default every time, for sharded and unsharded jobs alike.

The fix

Move the value onto the one object the actor actually reads. Same numbers as above.

# today — build_nemo_gym_config() nemo_gym_dict = dict(env_configs["nemo_gym"]) # {"port_range_low": 15001, ...} return NemoGymConfig( model_name=model_name, initial_global_config_dict=nemo_gym_dict, # 15001 rides along in here ... ) # ... but no port_range_low field # in the actor — _spinup() low = self.cfg.get("port_range_low", 5000) # field absent -> 5000 the value dies here initial_global_config_dict["port_range_low"] = low # 15001 overwritten by 5000

Lines above: nemo_gym.py:1214, 1266–1277, 594–606.

# fixed — pop the range and pass it as a real field low = nemo_gym_dict.pop("port_range_low", 5000) # 15001 high = nemo_gym_dict.pop("port_range_high", 5999) # 20000 return NemoGymConfig( model_name=model_name, port_range_low=low, # 15001 now the actor can see it port_range_high=high, # 20000 initial_global_config_dict=nemo_gym_dict, ) # in the actor — unchanged code, different answer low = self.cfg.get("port_range_low", 5000) # -> 15001 survives

The per-shard range then works for free: apply_shard_overlay already puts each shard's range into that shard's config, so once the actor stops overwriting it, every shard gets the ports it asked for.

Does it work?

Nobody has run this. There is no before/after, because the bug was found by reading the code, not by a failing job — and it fails quietly, so no run would have flagged it on its own. What exists instead is a victim already in the tree:

examples/nemo_gym/nemotron-3-ultra/swe_teacher.yaml:413 port_range_low: 15001 what the recipe asks for port_range_high: 20000 what Gym is given: 5000–5999

That recipe is live — it has a launch script, a docs guide, and it is in the config-validation list. See swe_teacher.yaml:413–414. Every other recipe sets exactly 5000/5999, which is why this went unnoticed: for all of them the wrong answer and the right answer are the same number.

The check to ask for before merging is small: launch any Gym job with a port range that is not 5000–5999 and print the ports Gym binds. Today they come back in 5000–5999.

So what. The per-shard port range in #3369 is dead on arrival — it is validated and merged, then discarded, in this PR and in every PR of the stack above it. The same is already true of the global env.nemo_gym.port_range_low, so one shipped recipe silently runs on the wrong ports. Both are fixed by the same few lines: pass the range onto NemoGymConfig so the place the actor reads is actually filled in. Worth doing here, while the per-shard knob is still new and nobody depends on its current behaviour.

Why they finally disagree
The batch earmarked for step 2 (A, B) is still running. Everything that has landed was generated for a later step — so each mode has to answer "do I train on data meant for someone else?" differently. in_order says no and stalls; weight_fifo takes only the oldest weight cohort; windowed takes the two oldest ready; freshest-first takes the two newest and strands C.

Four modes, four different training batches, from one identical buffer. The only input that changed between them is which rule they consult.

Reading it back

in_order — “you get what was promised to you”
The stamp is assigned at dispatch, before the rollout runs, so a group's destiny never changes no matter when it finishes. C, D, E and F having landed buys them nothing — none was stamped for step 2, so the trainer waits rather than train on data meant for a later step. This is the legacy async-GRPO pattern: legacy ReplayBuffer.sample() filters to the age window, then narrows to target_weight_versions[i] == current_weight_version, stalling unless a full batch is intended for this step — "so no trajectory loses its last chance to be used for its intended training step." legacy replay_buffer.py L250-271 · InOrderSampler.select L359
Same answer ≠ same rule
Under a gated pump the modes usually agree — start_weight is stamped at dispatch, so it only increases down the buffer, and "oldest weight", "earliest dispatched" and "earmarked earliest" normally name the same groups. They come apart only when rollouts finish out of order, which is exactly the case drawn above. The example above is one where they all diverge.
sample_freshest_first changes the set, not the order
It sorts by lag before the max_prompt_groups cap bites, so D and E — groups generated for later steps — get pulled forward, and C is left to age out. Same buffer, same window, different training data. L249
“Isn’t there a FIFO where everything is used and nothing is evicted?”
Yes — in_order with min_groups_for_streaming_train = num_prompts_per_step, which is what the sync recipe sets. _finalize_selection returns None below min_prompt_groups, so the trainer waits at step N until the whole batch stamped N has landed, then takes all of it. Its evict only fires for a group that commits after its step has gone by — like A or B if they run past step 2. So the mode already exists; the guide just never says in_order is the zero-waste option and windowed the deliberately-lossy one. The cost is the mirror image: in_order idles the trainer on the slowest group in the batch, which is exactly what windowed exists to avoid.

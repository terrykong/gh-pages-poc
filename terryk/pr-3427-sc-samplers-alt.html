Prompt groups finish at different times — that's what the sampler is for

Alternate to the buffer-snapshot figure · NVIDIA-NeMo/RL PR #3427 @ db0aa28

Rollouts for one step do not finish together — a long generation can outlive the weights it started from. Every sampler is one answer to "what do I do with a group that finished at an awkward time?" Below, six groups finish at six different moments; the trainer reaches step 1 and has to choose.

Reading it back

in_order — “you get what was promised to you”
The stamp is assigned at dispatch, before the rollout runs, so a group's destiny never changes no matter when it finishes. g4 finishing early buys nothing; g2/g3 being weight-stale costs nothing. Steps are reproducible batches. This is the legacy async-GRPO pattern: legacy ReplayBuffer.sample() filters to the age window and then narrows to target_weight_versions[i] == current_weight_version, stalling unless a full batch is intended for this step — "so no trajectory loses its last chance to be used for its intended training step." legacy replay_buffer.py L250-271 · InOrderSampler.select L359
weight_fifo — “oldest data first, always”
Same batch here, different reason: it drains the lowest in-window start_weight before touching any newer one. Deterministic consumption order without needing a stamp. L315
windowed — “whatever is freshest, right now”
The only mode that will reach forward and eat g4, a group generated for a later step, because it looks solely at how stale the weights are. That keeps the trainer fed without stalling — and it is precisely why something gets left behind and aged out. The waste is the feature working, not a bug. Note sample_freshest_first changes the set, not just the order: with the default false this same buffer yields g2 + g3 instead. L235
“Isn’t there a FIFO where everything is used and nothing is evicted?”
Yes — in_order with min_groups_for_streaming_train = num_prompts_per_step, which is what the sync recipe sets. _finalize_selection returns None below min_prompt_groups, so the trainer waits at step N until the whole batch stamped N has landed, then takes all of it. Its evict can only fire for a group that commits after its step has already gone by — like g5 if it ran two steps long. So the mode already exists; the guide just never says that in_order is the zero-waste option and windowed is the deliberately-lossy one. The cost is the mirror image: in_order makes the trainer idle on the slowest group in the batch, which is exactly what windowed exists to avoid.

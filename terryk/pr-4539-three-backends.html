Three pages on this PR, one question each. This one: who talks to whom on a put and a get.

Before
Two storage backends. simple sends row bytes over ZMQ to CPU storage units. mooncake_cpu moves them over RDMA, with a Mooncake master service that tracks where every key is.
This PR
Adds a third, opt-in TQ storage backend, written in NeMo-RL (how it fits with TQ). Rows are placed by row number like simple, but the bytes move over RDMA like Mooncake, and no master service is needed.
Status
Works in the author's 86-node runs (0 hash mismatches, faster put than simple; numbers in the PR description). Open review items are in the last section.

Background. The data plane moves rollout rows (prompts, responses, logprobs, …) between the driver, the training workers and the generation workers. NeMo-RL uses TransferQueue (TQ) for this. TQ has a controller that hands out row numbers and tracks which rows are ready, and a storage backend that keeps the bytes. A put or get names keys like 5@responses (row 5, field responses). Dotted words have a short explanation: hover or tap them.

How nixl fits with TransferQueue. It is a TQ storage backend that plugs into TQ. It does not go around TQ. It is new code, though, and it lives in NeMo-RL rather than in TQ.
  • Does it go around TQ? No. NeMo-RL picks it the same way it picks the other two, by naming a TQ backend: storage_backend: "NixlStore" (transfer_queue.py:962). Every put and get still goes through TQ, and the TQ controller is still told which rows are ready (step 1 and the last step in the figures below). The only thing the controller does not keep is where the bytes are.
  • Is it a NIXL backend for TQ? Yes. It registers in the same three TQ plug-in tables that TQ's own backends use: the client (tq_nixl.py:247), the startup code that launches the units (:730), and the manager (:782). TQ's Mooncake backend registers in those same tables (mooncake_manager.py:22). The manager is a subclass of TQ's KVStorageManager and reuses its put and get. It replaces only two things: clearing rows, and checkpoints.
  • Does it change simple? No. The PR only adds a nixl branch next to the others. simple, and its storage units, work as before, and you pick one backend per run with data_plane.backend.
  • Is it custom? Yes, below the plug-in line. The storage units, the client, the byte layout and the row index are all new NeMo-RL code under nemo_rl/data_plane/. TQ at the pinned version has no NIXL storage backend, and this PR does not change TQ.

One put and one get, three ways

What is a storage unit? It is a TQ idea: a Ray actor that holds a share of the rows. TQ ships SimpleStorageUnit. NixlStorageUnit is new NeMo-RL code in this PR. It is not part of NIXL. It is a CPU-only Ray actor that owns one big block of pinned memory (16 GiB in the example config). The block is registered with NIXL so other machines can RDMA into it. The unit also keeps the row index, and it runs a small ZMQ server for control messages. NIXL itself is only the library each process uses to move the bytes.

The figures use the same example in all three backends. A client puts rows 5 and 7, field responses, and then gets them back. Each value is a tensor[6] of int64 (6 token ids, 48 bytes). The job has 3 storage units, so row 5 belongs to unit 2 (5 % 3) and row 7 to unit 1 (7 % 3).

How to read it. Step 1 and the last put step are the same in all three backends. The TQ controller hands out row numbers and is told when rows are ready, and it never touches the bytes. Only the middle steps differ:
  • simple: one ZMQ message per unit carries the bytes, and the unit's CPU unpacks them.
  • mooncake_cpu: ask a separate Mooncake master where to put the bytes (or where they are), then RDMA.
  • nixl: ask the owner unit itself for space (put) or for the location (get), then RDMA.
So nixl does still send messages before it writes. A put takes 2 small messages per owner unit (alloc, commit), and a get takes 2 (resolve_keys, unpin). It is fast for two reasons. First, the big bytes move by RDMA, and the unit's CPU never copies them. Second, only the owner unit is asked, which the client finds by arithmetic. Rows 5 and 7 live on different units, so every backend touches both units here, not just nixl. simple sends to both units at the same time, on put and on get. nixl does the same on a get, but a put finishes unit 2 before it starts unit 1.

Where they meet, and what still differs

All three are TQ storage managers, so everything above them is shared: the TQ controller and NeMo-RL's data-plane client. mooncake_cpu and nixl also share KVStorageManager.put_data / get_data, which turns a batch into row@field keys and calls the backend's put / get. They split there: MooncakeStoreClient vs NixlKVClient. simple has its own manager.

Why keep all three. simple needs no RDMA hardware. mooncake_cpu needs the Mooncake master. nixl needs RDMA and gives up running anywhere else. In return it skips the master and keeps the unit's CPU off the data path. In the author's 86-node run it cut put time per call from 1326 ms to 422 ms against simple, with get about the same (1091 vs 1032 ms).

Open review items

None of these breaks the data path in the author's runs. They are what the review asks to change before merge. Each links to its review comment.

  1. A put can block every other get in its process. The client has one lock for all NIXL and ZMQ calls, and a put keeps it while it sleeps between retries (tq_nixl.py:475). With the SSD tier on, a put that spills waits there for its whole disk write. Ask: drop the lock only while sleeping. C1 · tq_nixl.py:476
  2. The default placement puts a unit on a CPU-only Ray head. With storage_unit_placement: all the PR's own node picker, which means "GPU nodes", is skipped (transfer_queue.py:973), so every alive node gets a unit with 16 GiB of pinned memory. One-line fix. C2 · transfer_queue.py:973
  3. The end-to-end NIXL tests never run in CI. They skip unless UCX_TLS is set in the test process, and CI never sets it (conftest.py:130). Restore onto a different unit count and unit-death handling have no automated test today. C3 · conftest.py:139
  4. Config shape. The ssd and nixl blocks are untyped dicts, so a typo is ignored and SSD on without a directory writes to /tmp. The placement setting takes one word where the other backends take a list, which will break configs when NIXL moves to the shared planner. C5 · interfaces.py:171 C6 · interfaces.py:146

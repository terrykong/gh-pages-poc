How the new nixl data plane moves a row, next to simple and mooncake_cpu

Explainer for NVIDIA-NeMo/RL #4539 (data_plane.backend: nixl). NeMo-RL permalinks pin the PR head 738312b; TransferQueue links pin c516143, the version the PR uses.

Before
Two storage backends. simple sends row bytes over ZMQ to CPU storage units. mooncake_cpu moves them over RDMA, with a Mooncake master service that tracks where every key is.
This PR
Adds a third, opt-in backend: rows are placed by row number like simple, but the bytes move over RDMA like Mooncake, and no master service is needed.
Status
Works in the author's 86-node runs (0 hash mismatches, faster put than simple; numbers in the PR description). Open review items — see the last section.

Background. The data plane moves rollout rows (prompts, responses, logprobs, …) between the driver, the training workers and the generation workers. NeMo-RL uses TransferQueue (TQ) for this. TQ asks a storage backend to keep the bytes, and every row has a global row number. A put or get names keys like 5@responses (row 5, field responses). Dotted words have a short explanation: hover or tap them.

One put and one get, three ways

Same example in all three: a client puts rows 5 and 7, field responses, each a tensor[6] of int64, on a job with 3 storage units.

The unit only hands out space, keeps the row index, and pins blobs while a reader copies them. The client moves the bytes itself, one-sided over RDMA (put_segments, _get_once). Each row's owner is row % N (owner()), so a client that joins later finds rows without asking anyone.

Where they meet, and what still differs

All three are TQ storage managers, so everything above them is shared: the TQ controller and NeMo-RL's data-plane client. mooncake_cpu and nixl also share KVStorageManager.put_data / get_data, which turns a batch into row@field keys and calls the backend's put / get. They split there: MooncakeStoreClient vs NixlKVClient. simple has its own manager.

Why keep all three. simple needs no RDMA hardware. mooncake_cpu needs the Mooncake master. nixl needs RDMA and gives up running anywhere else. In return it skips the master and keeps the unit's CPU off the data path. In the author's 86-node run it cut put time per call from 1326 ms to 422 ms against simple, with get about the same (1091 vs 1032 ms).

Open review items

None of these breaks the data path in the author's runs. They are what the review asks to change before merge.

  1. A put can block every other get in its process. The client has one lock for all NIXL and ZMQ calls, and a put keeps it while it sleeps between retries (tq_nixl.py:476). With the SSD tier on, a put that spills waits there for its whole disk write. Ask: drop the lock only while sleeping.
  2. The default placement puts a unit on a CPU-only Ray head. With storage_unit_placement: all the PR's own node picker, which means "GPU nodes", is skipped (transfer_queue.py:973), so every alive node gets a unit with 16 GiB of pinned memory. One-line fix.
  3. The end-to-end NIXL tests never run in CI. They skip unless UCX_TLS is set, and CI never sets it (conftest.py:130). Restore onto a different unit count and unit-death handling have no automated test today.
  4. Config shape. The ssd and nixl blocks are untyped dicts, so a typo is ignored and SSD on without a directory writes to /tmp. The placement setting takes one word where the other backends take a list, which will break configs when NIXL moves to the shared planner.

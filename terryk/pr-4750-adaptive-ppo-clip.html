Adaptive PPO clip: which tokens it trains on, compared with icepop

NVIDIA-NeMo/RL #4750 · feat(grpo): add adaptive-ppo-clip · method from MAI-1, §3.1.1 · permalinks pin the PR head e4e546b

Before
For stale tokens in async RL, the closest option was icepop. It drops every token whose importance weight is outside a fixed [min, max], whatever the sign of its advantage.
This PR
Adds truncated_importance_sampling_type: adaptive-ppo-clip. It drops a token only on the side that matters for its advantage. Its upper bound grows or shrinks each step to steer entropy toward a target, and it saves that bound in checkpoints.
Status
New feature, in review. The filter matches the paper, and the review found no correctness bug. The review asks for cleanups, more tests and training curves (end of page).

The math: one keep-mask, two rules

Both modes need force_on_policy_ratio: true. Then the loss sets πprev to a no-gradient copy of πθ (code), so the PPO ratio is 1 and the only thing left to clip is the importance weight:

  • πgen (generation_logprobs): the probability vLLM gave the token when it sampled it, often with older weights.
  • πθ (curr_logprobs): the trainer's probability now, with a gradient.
  • w = sg[πθ] / πgen: the importance weight. Far from 1 means the token is stale. A is the token's advantage.
\mathcal{L}(\theta)=-\frac{1}{N}\sum_t\;\htmlClass{t1}{m_t}\cdot w_t\cdot A_t\,\log\pi_\theta(o_t) \qquad\begin{aligned} \text{icepop:}\quad & \htmlClass{t1}{m_t}=[\,\text{min}\le w_t\le\text{max}\,]\\ \text{adaptive:}\quad & \htmlClass{t1}{m_t}=[\,w_t\le 50\,]\cdot[\,w_t\ge\text{min}\ \text{ if } A_t<0\,]\cdot[\,w_t\le\text{max}+\htmlClass{t2}{k}\ \text{ if } A_t>0\,] \end{aligned}

How to read it. Each [ … ] is 1 if the test inside is true and 0 if it is false. A bracket whose "if" does not apply to the token counts as 1. Multiplying them means all must hold: the keep-mask m is 1 (train on the token) only when every bracket is 1, and one 0 drops the token. The code does the same with & (code). So the adaptive rule is:

  • Every token: drop it if w > 50.
  • A < 0 (a bad token the update pushes down): drop it if w < min.
  • A > 0 (a good token the update pushes up): drop it if w > max + k.

This is the paper's Eq. 6 and Eq. 9 written as a mask, with ε = 0.6 giving min = 0.4 and max = 2.5.

The offset k starts at 0 and moves once per training step (code, paper Eq. 8):

\htmlClass{t2}{k}\leftarrow\mathrm{clip}\!\left(\htmlClass{t2}{k}+0.25\cdot\mathrm{sign}\big(H^\star-\hat H\big),\;0,\;1\right), \qquad \hat H=-\frac{1}{N}\sum_t w_t\,\log\pi_\theta(o_t)

H* is tis_adaptive_ppo_clip_target_entropy (default 0.3). Ĥ is the step's approx_entropy, which the loss already logs (code). Low entropy means the policy is getting too sure of itself, so k rises and more A>0 tokens with a high w are kept. High entropy lowers k again.

Why the sign of A matters. w says how far the trainer has already moved from vLLM on this token, and in which direction: w > 1 means it now likes the token more, w < 1 means less. A says which way this update pushes. The rule: stop pushing a token further in a direction it has already gone too far, but never stop a push that brings it back.

  • Good token, w = 2.8: already liked 2.8× more. Pushing it up again could overshoot, so drop it (until k raises the cap).
  • Good token, w = 0.2: the trainer now dislikes a token that turned out good. Pushing it up moves it back, so keep it. icepop drops it.
  • Bad token, w = 0.2: already pushed far down. More could overshoot, so drop it.
  • Bad token, w = 2.8: the trainer now likes a bad token more. That is exactly what to penalize, so keep it. icepop drops it.

This is the same one-sided rule as PPO's clip, min(r·A, clip(r)·A), which for A > 0 caps only from above and for A < 0 only from below. With force_on_policy_ratio the PPO ratio is 1, so the rule moves onto w.

Why there is still an outer bound of 50. The two "keep" cases above have no cap of their own, and each token's gradient grows with w. One token with w = 1000 would outweigh the rest of the batch. The outer bound drops those spikes whatever the sign of A (the paper's Eq. 9).

Why k moves only the upper cap. This is the same idea as DAPO's clip-higher. A rare good token (small πgen) reaches a large w quickly when it is pushed up, so a tight upper cap stops rare tokens from growing, and entropy collapses. When entropy is below the target, k raises the cap and lets them grow. When entropy is above the target, k lowers the cap again. The lower cap only limits how far bad tokens are pushed down, so it has no such effect on entropy and stays fixed.

Where the code lives, and what the review asks

Where it lands: RL only. The mask is a new branch in ClippedPGLossFn.__call__, next to icepop. k lives on the loss object. The trainer moves it after each step and copies it into the checkpoint, in grpo_train, async_grpo_train, grpo_train_sync and the single controller. The workers get the new k because every trainer sends the loss object to them again on each step. The legacy PPO trainer rejects the mode.

The review asks the author to:

  • Raise an error instead of silently leaving k at 0 when approx_entropy is missing, and log the k the step actually used.
  • Drop last_entropy. It is saved and restored but nothing reads it. That leaves one plain checkpoint field for k.
  • Make the step size, k's maximum and the outer bound config keys. The paper's own recipe uses a maximum of 2.5, and the code fixes it at 1.0.
  • Test the wiring in the three older GRPO trainers, the resume path and the PPO rejection. Today, deleting any of those lines leaves all tests green.
  • Share training curves: reward, entropy against the target, k over time, and one resume.

So what. If you run async GRPO and want to keep stale tokens that are still safe to train on, this mode keeps more of the batch than icepop with the same min and max. It also adjusts itself to hold entropy near a target. It needs force_on_policy_ratio: true, so one optimizer update per rollout batch, and it does not work with the single controller's ready_first sampler. No training curves yet, so the benefit is the paper's claim, not measured in NeMo-RL.

How a model call with an image is saved mid-generation and resumed, next to a text-only call (round 2)

NVIDIA-NeMo/RL #4583, stacked on #4507 (text prefix recovery). All permalinks pin the PR head 3821aa8.

Before
A checkpoint could save a half-finished text generation and resume it later. Setup refused to turn this on when the run captured images or video.
This PR
Removes that refusal. The first saved row for an image call now stores where the image sits in the prompt and a SHA-256 hash of each image tensor, not the pixels. On resume, the image is processed again and must hash the same.
Status
New feature. The review found no bug. All 9 first-round comments are fixed. This round asks for a smaller version of the same design (see the size page).
text vs image restore what can shrink

Two pages on this PR at its current head, one question each. This one: what changes when the cut call has an image. First-round pages (older design): text vs media, size and pixel copy.

Background. In a long rollout, a checkpoint can land while vLLM is still generating a model call. Instead of throwing those tokens away, the parent PR saves them as prefix rows, one per checkpoint. After a restart, Gym sends the same request again with the list of saved rows, and vLLM continues from the saved tokens. This PR makes that work when the prompt has an image or video. Dotted words have a short explanation: hover or tap them.

Both kinds of call share the same save and resume code. An image call adds work at four points: when the call starts, it hashes each image tensor once, off the event loop (vllm_worker_async.py:1792-1797); the first cut writes the image's place in the prompt and those hashes into the row (_generation_cut_record_payload); resume reads them back from the same single read text uses (_restore_generation_cut_media); and resume processes the image again and checks it (vllm_worker_async.py:2493-2513).

One call, cut twice, then resumed

imgs f32[3,2,3] = the image's processed tensor, named imgs: 18 made-up 32-bit floats in a 3×2×3 block, which is what the unit tests use in place of real processor output. Token ids and the tensor come from test_captured_media.py:253-256; the generated ids 41–45 and the hash are illustrative. The final row's pixels are written at vllm_worker_async.py:1987-2015.

Where the two paths meet, and what still differs

They share the hard part. _resolve_generation_cut joins the rows for both, and its digest now also covers row 0's extras (:474-475), so a changed span or hash fails the same check that guards the tokens. After step 4, both use the saved tokens as the engine prompt. What still differs: vLLM needs the original image again to prefill, because a hash cannot be turned back into pixels; and the final row carries the pixels, once.

So what. This round fixed the main cost of the first design: a checkpoint no longer writes pixels, only a few dozen bytes of hash per image, and the final row is the only pixel write. The shape is right. What is left is size: the restore reads the row-0 extras before the digest check that already covers them (step 3), so it carries its own set of shape checks, and the step-4 check is spread over two functions. The second page shows what can go.

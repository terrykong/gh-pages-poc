What happens to a sampled token that the training policy filtered out — on main, and with this PR

Explainer for NVIDIA-NeMo/RL #4367, which builds on #4154 (already on main). Permalinks pin the PR head ca01e85; "main" links pin the PR's base 8661b47.

Before
On main, #4154 already removes such a token from token_mask, so the actor loss skips it — but so do the reference KL and the sequence-error check.
This PR
Keeps token_mask whole and leaves -inf in the logprobs; the loss builds its own actor mask. Reference KL now keeps the token.
Status
KL part: fixed by this PR. New problem: open — not fixed in this PR. When seq_logprob_error_threshold is set, one such token now throws away the whole response. Raised in the review.
Background. With top-k or top-p sampling, vLLM samples a token from its filtered set. The trainer recomputes the same filtering, but the two can disagree near the cut-off. Then the trainer gives the sampled token log-probability -inf: in its view the token could not be sampled. NeMo-RL compares three logprobs per token: curr, prev and generation. Dotted words have a short explanation: hover or tap them.

Before this PR, the worker replaced that -inf with 0 and removed the token from token_mask (main: loss_input.py, main: grpo.py write-back). token_mask is shared by everything after it, so the token also left the reference KL. This PR keeps -inf on valid tokens (megatron/train.py) and lets the loss drop it from the actor terms only (loss_functions.py). But one more reader of prev_logprobs runs before the loss and was not changed: the sequence-error check.

What would fix it — proposed, not in the PR

Where the fix lands: RL only. compute_seq_logprob_errors and its callers. No vLLM change: vLLM's own logprob is right; the trainer's filter is the side that disagrees.

Nothing below is implemented or run. The check must skip a -inf token only when top-k/top-p is on. With filtering off, a -inf is a real bug, and existing tests (test_single_forward_grpo.py) require that such a response is rejected. Skipping it unconditionally breaks one of them (NaN gradients).

Each caller passes exclude_unsupported=need_top_k_or_top_p_filtering(sampling_params) — the same test the workers already use to decide whether to filter (loss_input.py:269). That covers the driver call (grpo.py:2846) and the in-loss call (loss_functions.py:625). With it, the example above gives error 1.035 again and the response stays.

So what. The PR's goal — keep the KL on token 3 — is right, and the actor loss treats token 3 the same as main. But for anyone who sets seq_logprob_error_threshold together with top-k/top-p, one disagreeing token now throws away the whole response, and long responses are the most likely to contain one. No shipped recipe sets both, so CI will not catch it. Fix the check as above, and add a test with filtering on.

How Megatron token capture writes the same row that vLLM already writes

NVIDIA-NeMo/RL #4129 · Gym #2823 (merged, pinned at 9fc05c0) · Megatron-LM #7015 (merged, pinned at c711dc0) · permalinks pin RL head 0f38893.

Before
Only the vLLM backend could record the exact tokens of each model call. Asking for token capture with policy.generation.backend=megatron failed at setup.
This PR
Adds a Megatron path. Two small objects plug into hooks inside Megatron's inference engine, and both write the same row, to the same store, that vLLM writes.
Status
In review — not merged. Both outside dependencies have landed and are pinned. Open items, such as a Megatron recovery test that has not run yet in CI, are in the PR's review comments.

Token capture means: for every model call in an agent rollout, save the exact token ids the model saw and wrote, so training uses those ids instead of re-tokenizing text. Gym decides what each call is allowed to start from (its CaptureAdmission). The serving worker does two jobs: (1) before generation, rebuild the prompt so it starts with the exact tokens of the earlier turns, and (2) after generation, write the new tokens to TransferQueue (TQ) as one row and hand Gym back a small key to that row. vLLM does both jobs inside its HTTP handler. Megatron cannot, because the prompt is built inside its engine, so the PR adds two engine hooks that Megatron-LM #7015 exposes.

Where each backend does the two jobs

One two-turn call, followed through both paths

Turn 1 already happened and its row is stored under key k1. Turn 2 arrives. Gym's admission says: start from k1, whose tokens are 8 ids long. A refit (new weights) lands while turn 2 is still being generated: epoch 6 → 7.

# the same input for both backends admission.staging_chain = ["k1"] admission.prev_len = 8 template prompt (chat template re-renders turn 1 as 9 ids, then 5 new ids) = 14 ids refit during generation: epoch 6 → 7 # step 1 — resolve the prefix: fetch k1 from TQ (cache miss the first time) vLLM: _resolve_admission_prefix → [8 exact ids] # in a thread Megatron: prepare_prompt → resolve_admission_prefix → [8 exact ids] # on the engine loop # step 2 — splice: keep the 8 real ids, drop the 9 re-rendered ones, keep the 5 new ones both: replace_prefix_tokens(...) → 8 + 5 = 13 ids # check: prompt[:8] == prefix vLLM passes its tokenizer; Megatron passes eos_token_id from offload_params # step 3 — which weight version the call is stamped with vLLM: 6 # value set by set_rollout_weight_version when begin_call ran Megatron: 6 # policy_epoch = [(0, 6), (2, 7)] → first entry, the admission epoch # step 4 — stage both: TQTokenSink.stage → row under a new key k2 → Gym records k2

Same 13-id prompt, same version 6, same row. The Megatron stager logs a warning when a request spans two epochs (tq_token_sink.py:541), because async rollouts make that routine.

What still differs after they join

vLLMMegatron
Where TQ reads and writes runA worker thread; the HTTP loop keeps serving Inside the engine step; the whole model-parallel group waits for each read and write
Where the version comes fromA worker attribute set by set_rollout_weight_version The engine's own epoch, set by set_rollout_weight_version → set_generation_epoch
Streaming callsCapture is aborted for the call (:1238)Engine skips the stager (dynamic_engine.py:1564); the call has no key, so Gym masks the rollout
So what. The two backends share the parts that decide correctness: the prefix lookup, the splice, Gym's checks, and the row format. A bug fixed in any of those is fixed for both. They differ in where the work runs, and Megatron runs it inside the engine step. So a capture-on vs capture-off throughput number for Megatron is the main thing this design still owes. The review comments on the PR list the open items.

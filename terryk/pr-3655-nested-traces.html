How a Ray worker's spans nest under the driver's, across process boundaries

NVIDIA-NeMo/RL #3655 — add nemo-lens instrumentation and efficiency buckets · all links pinned to aad00c1

A span is one timed block of work with a name. Spans nest: a span opened inside another becomes its child, and a viewer draws the result as a waterfall. Inside one process that nesting is automatic — OpenTelemetry keeps the currently-open span in a ContextVar, so the next span started finds its parent by itself. Across a process boundary it is not automatic, because the child process has an empty ContextVar and no idea a parent exists. NeMo-RL runs its rollout collector as a separate Ray actor, so without help its spans start a brand-new tree. This PR fixes that for the collector by shipping the parent's ID over as a string.

The problem: two trees instead of one

The collector is not a special case of "worker" — it is the only hop wired today. See the last box on this page.

The fix: capture a dict on the driver, re-open it on each worker thread

Three steps. The same run as the figure: 2 driver steps, 2 rollout batches at weight versions 7 and 8.

# 1. DRIVER — grab the currently-open span as a plain dict. _tc_trace_carrier = current_trace_carrier() # -> {"traceparent": "00-4bf92f35…4736-00f067aa0ba902b7-01"} # Taken INSIDE rl.grpo.job, so 00f067aa0ba902b7 is that job span's ID. # Returns {} when no span is open — see the catch at the bottom.

grpo.py:4400 · definition at instrumentation.py:247, which calls OpenTelemetry's propagate.inject()

# 2. HAND-OFF — it is just an argument. No Ray magic. trajectory_collector = AsyncTrajectoryCollector.remote( ..., trace_carrier=_tc_trace_carrier, ) # In the actor: self._trace_carrier = trace_carrier or {}

grpo.py:4417 · stored at trajectory_collector.py:118

# 3. WORKER — re-open it, ONCE PER THREAD. with remote_trace_context(self._trace_carrier): _collect() # every span opened in here is now a child # of 00f067aa0ba902b7, in the driver's trace

loop thread trajectory_collector.py:413 · each batch-worker thread :603 · definition at instrumentation.py:272

Step 3 runs per thread on purpose. The open span lives in a ContextVar, and a plain threading.Thread starts with none of them — so a batch worker that skipped this would go back to emitting root spans. That is why the same two lines appear in both the collection loop and every batch worker.

Does it work?

Nobody has posted a trace. There is no screenshot, no Jaeger or Tempo link, and no run in the PR description or its comments. The code path is only reachable with an OTLP backend listening, which CI does not have.

What does exist: the round-trip is unit-tested without a backend at test_instrumentation.py:150, which builds a carrier from a recording span and asserts a span opened inside remote_trace_context lands in the same trace. The nesting rule itself is OpenTelemetry's, not this PR's — this PR only moves the string.

The honest thing to ask for before merging: one screenshot of a single trace from a short async GRPO run with span_groups: per_step,job, showing collect_rollouts nested under rl.grpo.job rather than sitting in its own trace. That is a five-minute check and it is the only thing that proves the hand-off end to end.

Your question, directly: does this lay the groundwork, or block it? It lays exactly that groundwork, and blocks nothing. traceparent is a plain string→string carrier, so the same two helpers work over HTTP headers, gRPC metadata, or a Ray argument — nothing here is Ray-specific. The library underneath also already ships traced_remote_call() and ray_dispatch_with_context(), which wrap any Ray remote call with an automatic _otel_carrier argument. NeMo-RL does not use them yet, so extending nesting to another process is "pass the dict and wrap the entry point", not new plumbing.
Two limits to know before you expect a single waterfall. (1) Only one hop is wired. The rollout collector gets a carrier; the policy, value and vLLM workers do not, so their spans still form separate traces — listed as a known gap at README.md:44. (2) The job span group has to be on. The carrier is captured from whatever span is open at that moment; with job disabled nothing is open, current_trace_carrier() returns {}, and the collector silently falls back to its own root — no error. The per_step preset deliberately drops job to keep traces small, so the merged view needs span_groups: per_step,job (or all). Both points are documented at span-groups.md:247.

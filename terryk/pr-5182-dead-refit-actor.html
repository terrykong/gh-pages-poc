What happens when the refit actor dies in the middle of a refit

This PR

Two pages on this PR — this one: what a dead refit actor does to the run.

Background. When a refit fails, the controller runs a refit recovery. It only knows one cause: a generation shard went away. So it asks which shards are absent and rebuilds the NCCL group without them. It refuses to rebuild when nothing is absent, on purpose: rebuilding over the same shards would hang on the same silent one again. The recovery needs fleet health on. Dotted words have a short explanation: hover or tap them.

The recovery looks for a dead shard, not a dead actor

With fleet health off (the default) the recovery re-raises at once, so the new-actor code never runs for a death mid-refit either. The unit tests miss this because the test's fake synchronizer always reports a rebuild, so step 4 never says no.

What would fix it — proposed, not in the PR

Where the fix lands: RL only, two files. refit_actor.py gets one check that names a dead actor, and single_controller.py calls it while waiting for the refit.

Nothing below is implemented. Idea: when a call fails with RayActorError, ping the actor. If the ping fails too, the actor is the one that died, so raise a plain RuntimeError. That is not a type the recovery catches, so the run stops and says why. A dead generation worker still answers "actor alive" to the ping and takes the existing recovery, unchanged.

🔴 review comment C1 — refit_actor.py:256

So what. Today, with fleet health on, a dead refit actor ends the run with an error that points at a shard that is fine, or quietly takes a healthy shard out. With the fix, the run ends with "the RefitActor died", which names the real cause. The cost is one narrow case that works today: fleet health on, and the actor dies between refits, when a fresh actor would have been enough. A refit actor only dies on an OOM or node loss on the controller's own node, where the controller is at risk too, so a clear stop is the safer trade.

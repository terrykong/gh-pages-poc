Three problems a review of the new fault-tolerance settings turned up

Review notes on NVIDIA-NeMo/RL #3665. All permalinks pin the PR head ad048f9; "before" behaviour is 3d873eb.

This page is the review. The other two pages are about the PR itself: part 1 — the problem it solves · part 2 — how the fix works

The PR lets a training run give up on a prompt the generation fleet cannot answer, instead of ending the run. To do that it adds five settings under async_rl.rollout_failure. Problem 1 is a real bug — the fix only works for one of the three built-in samplers, and with another one the run stops making progress. Problems 2 and 3 are about the settings themselves: one repeats a job another setting already does, and one lets an unrelated speed setting decide which failure you get. Nothing that ships today is affected, because every new setting is off by default. Examples below use 4 prompts per training step.

bug 1. With two of the three samplers, giving up on a prompt stops training

The fix works by labelling each batch with the training step it belongs to, then subtracting lost prompts from that step's target. Only the in_order sampler applies labels. For weight_fifo and windowed there is no label, so the subtraction never happens and the trainer keeps asking for a full batch that will never exist. Both loops then go quiet. The watchdog does notice, but stall_action defaults to warn, so it prints a line every 30 seconds and the job holds its GPUs until the wall clock kills it. This is pre-existing — the older max_skipped_prompts setting could already reach it — but the PR adds a second way in, and its own YAML comment suggests turning it on.

Suggested fix: reject the combination in _warn_on_inert_failure_settings, which already works out whether the sampler applies labels. It blocks nothing that works today.

design 2. Inside problem 1, a speed setting decides which failure you get

Read problem 1 first — this only happens with the same two samplers. With in_order none of this applies. The reason is easy to miss: when the sampler puts no label on a batch, neither "shrink" nor "replace" ever runs. Both bail on the same missing label — _credit_shortfall returns immediately and _take_replacement returns nothing. So the number of groups the step wants never drops from 4, min_step_batch_fraction is never consulted, and the "is 3 groups acceptable?" question is never even asked. The step just keeps wanting 4.

Because the step still wants all 4, the only thing left deciding what happens is min_groups_for_streaming_train — how many finished groups the trainer waits for before it starts a chunk of work. That is a speed setting. It exists so the trainer does not run a training pass over 2 samples, and under in_order it has no say in fault tolerance at all. Here it quietly becomes the setting that picks the failure. Below: 4 prompts per step, one given up on in the first batch.

Neither ending is written down anywhere, and nothing checks the pair. A reader has no reason to think a speed setting picks a failure mode. For in_order the two never fight, because the number of groups still wanted is worked out from the already reduced target (single_controller.py:865), so a step that legitimately shrank to 3 asks for 3 and gets 3. That part is the design working.

design 3. Two settings watching the same thing, disagreeing about it

The new max_consecutive_dropped_prompts and the existing watchdog.stall_timeout_s both answer "has the fleet stopped answering?", and both read it off the same counter — whether anything has been committed lately:

The wider point is the count. async_rl.rollout_failure goes from 9 settings to 14, and each new one arrived with a check whose only job is to say "this combination does nothing" — including a four-way one between the batch floor, the batch size, the give-up budgets and the replace mode. The default already needs it: at min_step_batch_fraction=0.9, any batch of 8 prompts or fewer can lose nothing at all, so max_consecutive_dropped_prompts is silently doing nothing.

Two of the five also have no story for tuning them. max_replacement_attempts must be at least 1, defaults to 1, and falls back to a smaller batch anyway. replacement_reserve_prompts is a low-water mark on a pool that refills a whole batch at a time, so 1 and "a full batch" behave almost the same and anything larger trips the PR's own warning. Both read as internal constants that became settings. A smaller surface that keeps every capability:

async_rl: rollout_failure: on_dropped_prompt: fail | shrink | replace # "fail" == today's default min_step_batch_fraction: 0.9 # max_replacement_attempts -> a constant # replacement_reserve_prompts -> a constant # max_consecutive_dropped_prompts -> the watchdog already does this (stall_action: abort)

Folding "0 means end the run" into a word that says so removes the special case, and drops 4 of the 5 new checks. Counter-argument worth keeping in view: a count-based budget fails faster and more predictably than a 600-second timer, so if it stays, the smaller ask is just to make the two defaults agree.

How much to trust this

Problem 1 is the only one I would call a defect, and three reviewers reached it independently by reading the code; I confirmed the boundary mismatch myself. Nobody ran any of it. None of this came from a live failure — there is no run where a worker was killed and the wedge was watched happening, and the unit tests do not cover the unlabelled sampler on the training side, which is why the suite stays green.

What would settle it in about an hour: start a short run with sampler.name: weight_fifo and max_consecutive_dropped_prompts: 1, force one prompt to fail, and watch whether training steps keep advancing. Problems 2 and 3 are judgement calls about the shape of the settings, not defects — reasonable people can disagree, and they are worth a follow-up rather than blocking the PR.

What to do with this. Nothing shipped is affected — every new setting is off by default, and no config in the repo turns one on. Before you turn them on, check which sampler your run uses: they only do what they say with in_order. Two of the shipped SingleController recipes use windowed, which is the milder of the two failures but still ends the run at its last step.

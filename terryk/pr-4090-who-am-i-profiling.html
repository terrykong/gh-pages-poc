Why the inner vLLM worker can't tell whether it is being profiled

On NVIDIA-NeMo/RL #4090 (nsys traces for every inner vLLM TP worker). All links pinned to b2237a2d.

Before
Nothing in the inner vLLM worker ran nsys, so the question never came up.
This PR
Adds a block that shells out to nsys stop, guarded by if os.environ.get("NRL_NSYS_WORKER_PATTERNS").
Status
Open — not fixed in this PR. That guard asks the wrong question. Raised in review; the fix below is proposed, not implemented.

Two different processes are involved, and only one of them can answer "should these workers be profiled?".

The outer worker is a NeMo-RL Ray actor with a name — vllm_generation_worker. It matches that name against your NRL_NSYS_WORKER_PATTERNS and decides (vllm_worker.py:577). The inner workers are vLLM's own RayWorkerProc processes. They have no NeMo-RL name, so they cannot run that match — and the outer worker's answer is never sent to them. The new code (vllm_backend.py:1681) falls back to reading the raw environment variable, which answers a different question.

The two questions are not the same

The inner workers are not being profiled and have nothing of their own to finalize. They are still the only thing that stops the megatron capture.

What would fix it — proposed, not in the PR

Nothing below is implemented. The idea is small: the answer already exists in the outer worker, so send it to the processes that need it. Ray's runtime_env is already how the outer worker configures the inner ones, so the answer can ride along with the nsys settings it is already sending.

step 1 — the plugin already builds the inner workers' runtime_env. add one key while it is there: runtime_env["nsight"] = nsight_config # already there runtime_env["env_vars"]["NRL_NSYS_INNER_PROFILED"] = "1" # proposed only runs when the outer worker asked for inner profiling, so only genuinely-profiled workers get stamped. step 2 — the guard reads the stamp instead of the pattern list: if os.environ.get("NRL_NSYS_INNER_PROFILED"): # proposed ... nsys sessions list / nsys stop ... megatron-only run -> plugin never stamps -> guard false -> no sweep vllm profiled -> plugin stamps -> guard true -> sweep runs

Step 1 goes next to vllm_nsight_plugin.py:76; step 2 replaces the guard at vllm_backend.py:1681. The older v1 executor path builds its runtime_env the same way (vllm_worker.py:840-847) and needs the same stamp, or it keeps the old guard.

Two things nobody checked. Whether Ray merges an env_vars key added inside _build_runtime_env the same way it merges nsight — it is the same dict handed to ray.remote, so it should, but that was not tested. And the stamp only reaches workers the plugin actually touched, which is the point, but it does mean the v1 path has to be converted too.

Why not just reuse what's there

Two simpler-looking options do not work:

match the pattern inside the inner worker needs a NeMo-RL worker name. RayWorkerProc has none. There is nothing to compare "*policy*" against. ask nsys "am I being profiled?" no such thing. The Nsight Systems guide documents no "you are under a profiler" variable for the profiled process. NSYS_SESSION_NAME and friends go to the callback command nsys spawns under --after-collection-start, not to the app.

So the stamp is not new information. It is the decision the outer worker already made, carried to the process that has to act on it.

What this costs you today. Profile megatron only — the documented "*policy*" example — and the vLLM workers, which are not being profiled, run nsys stop on every session on the node. The only one there is your megatron trace. How much you lose depends on when the run ends: if the profile window closes mid-run the policy stops itself first and its trace is fine; if the run ends inside the window, atexit handlers run in reverse order, generation's sweep fires first, and the megatron trace is cut short. Generation shares the node by default (colocated.enabled: true), so this is the normal setup, not an exotic one.

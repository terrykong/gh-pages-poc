Why the new cleanup step can stop the wrong trace

On NVIDIA-NeMo/RL #4090. All links pinned to b2237a2d.

Two pages on this PR — read page 1 first; this one is a review finding on top of it.

Before
No vLLM worker ran nsys, so nothing could stop anyone else's profile.
This PR
Adds the cleanup step from page 1 — each inner worker runs nsys stop so its trace is written before teardown. That part works. But it is guarded by if os.environ.get("NRL_NSYS_WORKER_PATTERNS"), and that guard asks the wrong question.
Status
Open — not fixed in this PR. Raised in review. The fix below is proposed, nobody has written it.

The cleanup step is meant to run on workers that are being profiled. The guard instead checks whether profiling was switched on anywhere in the run. Those are the same thing when you profile everything, and different when you don't.

Profiling only the training side is the case where they come apart — and it is the first example in the docs (nsys-profiling.md:70, "Profile Only Policy Workers").

What happens on a training-only profile

The vLLM workers are not being profiled and have nothing of their own to write. They are still the only thing that ends the training profile. How much you lose depends on timing: if the window closes part-way through the run, the training side stops itself first and its trace is fine; if the run ends while the window is still open, the vLLM cleanup goes first and the training trace is cut short. Generation shares the machine with training by default (colocated.enabled: true), so this is the ordinary setup.

Why it isn't simply fixed — proposed, not implemented

Nothing below is in the PR. It is written up as a review comment on the guard itself, linked at the end of this section. The obvious repair — have the inner worker check the pattern itself — does not work: matching a pattern needs a worker name, and these are vLLM's own processes, which have no NeMo-RL name. Asking nsys "am I being profiled?" does not work either; there is no such thing in its documentation.

The answer does exist, though. The vLLM generation worker worked it out at vllm_worker.py:577 and then dropped it. So the proposal is to send it along with the settings it is already sending:

when the plugin sets up an inner worker, mark it as profiled: runtime_env["nsight"] = nsight_config # already there runtime_env["env_vars"]["NRL_NSYS_INNER_PROFILED"] = "1" # proposed and have the cleanup step read that mark instead of the pattern list: if os.environ.get("NRL_NSYS_INNER_PROFILED"): # proposed ... nsys stop ... training-only run -> never marked -> no cleanup -> training trace safe vLLM profiled -> marked -> cleanup runs as page 1 describes

Two things nobody checked: whether Ray passes an env_vars key added at that point through the same way it passes the nsys settings, and that the older non-default vLLM executor path would need the same mark or it keeps the current guard.

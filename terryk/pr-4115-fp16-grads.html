Two pages on this PR, one question each — this one: what goes wrong with float16 outputs.

FSDP casts the output of every layer to the output dtype, not just the logits (_post_forward). In the backward pass, the gradient for each of those outputs lives in the same dtype. The loss is divided by the number of tokens in the whole step (global_valid_toks), so every gradient shrinks as the step gets bigger. The DTensor path has no loss scaler, and float16 cannot hold very small numbers. bf16 can.

Where the gradients land on the float16 number line

The test: real fully_shard with MixedPrecisionPolicy(param_dtype=bf16, output_dtype=…) on a 2-layer model on CPU, bf16 math, loss divided by N tokens. Error is the layer-0 weight gradient compared with float32 outputs. Not yet run on GPU.

It also fails at the top of the range: a layer output above 65,504 becomes inf in float16, then nan in the next layer. In the same test, float32 and bf16 outputs stayed finite.

The fix — proposed in the review, not in the PR yet

Where the fix lands: RL only, one function. validate_and_prepare_config in nemo_rl/models/automodel/setup.py, plus one test. No Automodel change: it applies whatever policy it is given.

Nothing below is implemented. Allow only float32, or the same dtype the math runs in:

So what. Nobody hits this by default. But a user who reads "float16 saves memory too" and sets it on a bf16 model gets a run that trains, logs normal-looking losses, and quietly drops a large share of its gradients once steps get big. The check turns that into an error at startup.

Six pages, one question each — this one: which failures recover.

Two things decide the outcome, and you need both to predict it: what the ledger already thought of the shard when the weight sync began, and how the sync then went. There is no separate state for the refit. Its fate is written entirely in the shard's state, plus one hard rule — recover at most once per sync. Below is every combination.

The rule that explains most of the grid: the retry only happens if someone can be named. Recovery is two steps in order — work out which shard to drop, rebuild the group without it, and only then retry the refit. If the first step cannot name anyone, it raises and the retry is never reached. So a crash recovers because it identifies itself: Ray reports the dead process and the probe confirms it. A hang identifies nobody, and only recovers if the ledger already held a suspect. Retrying without shrinking would be worse than not retrying — the same full fleet, the same silent rank, the same hang.

On nccl_reshard there is a second requirement: the fault must land outside the bulk transfer. An abort mid-transfer orphans work on the trainers' own devices, and no rebuild on a device in that state can succeed — so naming the shard no longer helps. Since 9a87c0123 the run detects this and ends in seconds with a named cause instead of wedging. That turns both crash cells below into transport splits, not just the hang cell.

Why a mid-refit fault — wedged or dead — is recoverable on broadcast but not on nccl_reshard. Aborting a communicator does not retire work already sitting on a CUDA stream — and on the reshard path those orphaned sends are on the trainers' devices, not the failed shard's. So nothing you do to the remote rank retires them, and torch.cuda.synchronize() never returns. Job 6485245 measured it on 4×GB200: both policy workers parked in synchronize 1801 s after their own abort had already logged. The author eliminated every alternative by measurement: killing the shard outright (job 6523731 — trainers wedged anyway), pinning the release to the caller's CUDA device (job 6582457 — still stuck, with a SIGKILLed peer), and standing the deadline down on a confirmed death (lost the race). What landed instead (9a87c0123): sync_stream_within tags its abort with a second marker, the controller refuses to enter the recovery on that tag, and the run ends with a message saying this is the known limit of the transport — exit in ~10 s for a killed shard, ~90 s for a frozen one, against 1800 s wedges before. A plain abort without the tag still recovers, and a unit test pins that boundary.

Does it work?

The abort is measured: on 2×A6000, a survivor blocked in a collective was released 0.15 s after another thread called abort(). The reshard limit is measured too — job 6485245 for the stuck synchronize, and job 6523731 as the disproof of killing the shard.

What is not measured is the whole grid end to end in CI. The recovery harness needs 3 GPUs and both lanes have 2, so those variants skip; the rows above were exercised by hand on larger hardware. The lane now registers the reshard-plus-frozen corner and makes a skip visible instead of letting it read as a pass, so at least the gap is legible.

The short version. A shard that dies is handled, whenever it is noticed. A shard that wedges is handled if the ledger already doubted it and you are on the broadcast transport. The only case with no answer is a hang nobody saw coming — and refusing to guess there is deliberate, because condemning the wrong shard reproduces the same hang one shard smaller.

Six pages, one question each — this one: which failures recover.

Page 3 walks one failure end to end. This one asks the harder question: across every way a generation shard can go wrong, which ones does the run actually survive? The answer turns on a single distinction — was the shard already known to be gone before the weight sync started, or did it go wrong during it? Those two cases take completely different routes, and only the first works on a default config.

Every failure mode, and what happens

What failsHow it is noticedSurvives?What happens
Shard process dies between refits probe gets RayActorError → record_actor_death yes Route A. Rebuilt before the next broadcast. detect #3590 · verdict + rebuild #3591
Shard process dies during a refit ray.get raises RayActorError only if armed Route B. Works when refit_timeout_s is set; otherwise the recovery wedges. #3591
Engine wedged, condemned before a refit generation times out (900 s) → report_failure ×3 eventually Route A, but condemnation takes up to 45 min — and a success resets the streak, so an intermittent engine may never reach it. #3591
Engine wedged, reaches a refit first watchdog aborts; re-probe says healthy no Run raises. The likely path, since refits run every step and condemnation takes minutes. raised in review
Refit hangs, default config nothing, until the stall watchdog no No watchdog thread exists. Run ends ~600 s later with a stall message. raised in review
Second shard dies during the retry the retry raises no Deliberate: one retry only, because retrying forever would recreate the wedge. The second shard is never even condemned — the probe ran before the retry. If you see this, something bigger is wrong. #3591, intended
Fleet drops below min_healthy_shards raise_if_exhausted no Correct outcome — a run with too few shards cannot generate. #3590, intended
A trainer dies RayActorError no No remediation. Trainers are never excluded from the group — this whole stack is about generation shards. out of scope
Why "trainers are never excluded" is the right call, not an omission. Dropping a generation shard costs throughput. Dropping a training rank changes the parallelism the model was sharded for, so the optimizer state and the model layout no longer match the world — you cannot carry on without rebuilding the trainer itself. Keeping rank 0 a trainer also keeps the broadcast root stable across every rebuild.

Does it work?

The one measured number is the abort: on 2×A6000, a survivor blocked in a collective was released 0.15 s after another thread called abort(). Everything on Route B depends on that being true, and it is.

Nothing in this table has been exercised end to end by CI. The recovery harness needs 3 GPUs and both lanes have 2, so on the PR's own green run every registered variant printed [recovery] SKIP: … found 2. and exited. Route A and the hard-death half of Route B were exercised by hand on larger hardware; the wedged-engine rows have not been run anywhere, which is consistent with them being the rows that do not work.

The short version if you are configuring a run. Set refit_timeout_s. Without it you get detection and quarantine but no refit recovery at all — and the failure mode is not a clean error, it is the recovery deadlocking behind the ranks it was supposed to rescue. A value around 300 s is ~150× a healthy refit, so it cannot fire early.

How the AutoModel training loss starts using logprob_chunk_size

NVIDIA-NeMo/RL #4114 · all permalinks pin the PR head 617d989.

Before
With tensor parallel size 1, the training loss ignored logprob_chunk_size. It turned the whole logits tensor into fp32 at once and kept a full fp32 log-softmax around for the backward pass.
This PR
Hands the loss a one-rank process group, so it takes the existing chunked path. That path works on a slice of the sequence at a time and recomputes each slice in backward.
Status
Fixed by this PR when a microbatch splits into 3 or more slices (5.87 → 2.45 GiB measured on GB300). Open: with 1–2 slices it uses more memory — see the next page.

Two pages on this PR — this one: what the change does.

Background. In RL training the loss needs the log-probability of each chosen token. That comes from the model's logits. The logits are huge, so the repo can split them along the sequence into slices of logprob_chunk_size positions. Dotted words have a short explanation: hover or tap them.

One function picks the path: get_next_token_logprobs_from_logits. If it gets a vocab-parallel group, it calls the chunked kernel ChunkedDistributedLogprob. If not, it falls through to a plain fp32 log_softmax over everything. AutoModel at tensor parallel size 1 never passed a group, so it always took the plain path. The PR passes the one-rank tensor-parallel group, which is a real group that just contains this GPU. Every reduction then runs over just this GPU, so the numbers do not change, but the chunked kernel now runs.

The change

Where it lands: RL only, two files. train.py decides when to pass the group; dtensor_policy_worker_v2.py hands in its tensor-parallel mesh. No kernel change: the chunked kernel is the one Megatron already uses.

Read in order: the guard only fires for the plain logprob loss, with no sampling filter and no context parallel. It then borrows the one-rank group. Rank 0 and the full vocabulary width tell the kernel "this GPU owns every word". The same three values are also passed to the sequence-packing wrapper, because it re-passes them per sequence and would otherwise drop them.

So what. On one GB300, a [1, 4096, 128256] bf16 microbatch with logprob_chunk_size = 512 (8 slices) goes from 5.87 GiB to 2.45 GiB of loss memory, forward plus backward. Top-k/top-p runs are unchanged at 6.36 GiB. The saving depends on the number of slices, though: with one or two slices per microbatch the chunked path costs more than the old one, and several shipped recipes are in that case — page 2.

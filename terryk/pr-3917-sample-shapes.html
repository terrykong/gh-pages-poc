Every shape an SFT sample takes, from bytes on disk to the training step

NVIDIA-NeMo/RL#3917 — SFT v2 stage 1 with the Energon multimodal data path. Permalinks pinned to 72b7cdb.

NeMo-RL now has two ways to load SFT data: the old HuggingFace path and the new Megatron-Energon one this PR adds. They read different files and build different objects, so it looks like two pipelines. It is not. Both funnel into get_formatted_message_log, which does all the tokenizing, and then into prepare_sft_batch, which produces the flat padded tensors the trainer wants. Everything between those two points is containers — four different types holding the same pair of values.

The nine shapes

One sample, all the way through

A batch of 3 conversations. Inside prepare_sft_batch the work is three calls: add_loss_mask_to_message_log marks the assistant tokens, batched_message_log_to_flat_message concatenates each conversation and pads the batch to 16, and _validate_prepared_sft_batch checks the shapes and zeroes any row that ended up with no trainable token. The Energon path can also arrive with loss_mask_mode="precomputed", which skips the first call and validates the supplied mask instead (sft.py:348).

The last two shapes: KVBatchMeta and StepEnvelope

The figure above ends the v2 path at “wrapped in StepEnvelope”. Here is what that means. The controller that drives training runs in its own Ray actor with no GPUs, and it must never touch tensors. So the prepared batch is split in two: the tensors stay in the worker process that built them, and only a description of them crosses to the controller.

So the two new types are not more containers for the sample — they are what is left when you take the sample out. KVBatchMeta is the general one, shared with the TransferQueue path and defined in data_plane/interfaces.py. StepEnvelope is the SFT-specific wrapper that adds what _run_train_step needs and nothing else.

One thing this makes precise, because it is easy to get backwards: the tensors are not immortal in one process. They stay put while the controller is deciding what to do, and then the replica leader broadcasts them over NCCL to the other ranks of its own shard. What never happens is a tensor reaching the controller, or crossing between DP shards.

What is carried and never used

You asked whether anything is excessive. Tracing every field to a reader turns up five dead ones across two of the new types. Each is written on every single sample or every single step, and nothing ever reads it back.

FieldWritten atRead by
EncodedSFTSample.packing_cost generic_sft.py:239 nothing
EncodedSFTSample.pending_sample never written either nothing
StepEnvelope.field_names sft_worker.py:166 nothing — and it duplicates meta.fields
StepEnvelope.sequence_lengths sft_worker.py:167 nothing — duplicates meta.sequence_lengths
StepEnvelope.field_fingerprints sft_worker.py:168 nothing, and it costs a hash per field per step

The last three matter most. StepEnvelope already wraps a KVBatchMeta, which carries fields and sequence_lengths already. Copying them onto the envelope creates two ways to ask the same question that can disagree. Drop all three and StepEnvelope keeps exactly the five fields the controller reads: meta, logical_rank, source_ids, load_seconds, valid_tokens.

Everything else earns its place. The two per-sample containers look like duplication — EncodedSFTSample and DatumSpec hold the same message_log and loss_multiplier — but Energon requires its own type: it must subclass Sample so the loader can restore __key__ and restart mid-shard. That one is forced, not chosen.

Where the data changes in place

Most of the pipeline copies. cook_conversation and _normalize_messages both deepcopy the messages before touching them, so the raw sample is never edited. Two steps do not copy, and both of them edit an object the caller still holds.

WhereWhat it writesInto whose object
add_loss_mask_to_message_log message["token_loss_mask"] on every message the caller's batch["message_log"] — the function returns None
_validate_prepared_sft_batch batch["sample_mask"], zeroing rows with no trainable token the batch it was asked to check

The second one is the surprising one: a function named _validate_ also repairs. It is a deliberate choice with a comment explaining it — such a row already contributed zero to the loss, so masking it beats killing a run hours in over one bad conversation — but it means prepare_sft_batch can hand back a sample_mask that differs from the loss_multiplier it was built from.

Two more edits happen in place but only to objects the function just made, so they are safe: the truncation branches in generic_sft.py:216 and processors.py:172 clip token_ids on the log they just built. The token math is the same on both sides (min(4, max_seq_length // len(message_log))); only Energon also empties every PackedTensor, because dropping the placeholder tokens while keeping the image features would leave the vision merge with nothing to scatter into.

One name that gets expensive to change: stage3. _v1_loader_projection adds a dict key literally named "stage3", holding the model family, cooker and task-encoder identities. It only appears when those components are not the defaults, which is the point: default setups keep the old fingerprint so existing checkpoints still restore, and custom ones get their components hashed in.

It is live code, not a leftover — test_v1_identity_identifies_stage3_component_selection asserts the two configs hash differently. The problem is the name. “Stage 3” here means a future milestone of the SFT v2 rollout, the same way the guards say “SFTv2 Stage 1 requires data.backend=energon”. But this repo already uses “Stage 1/2/3” for real training stages — in the Nemotron 3 Ultra guide, Stage 1 is student RLVR, Stage 2 is teacher training, Stage 3 is MOPD. Same words, unrelated meanings. And unlike the error strings, this one is hashed into a checkpoint fingerprint, so renaming it later invalidates every V1 checkpoint. Rename it now to what it holds, like components.

Does it work?

The author posted an A/B convergence run: Qwen2.5-VL-3B on CLEVR with 9×-larger image payloads, DP=8, TP=2, sequence length 8192, with the v1 loss curve and the v2 loss curve plotted together. They track. That is the right evidence for this change, because the whole claim of the page above is that the two paths produce the same tokens — a matching loss curve is what that looks like from the outside.

What it does not pin down is equality, only closeness at DP=8. There is no test that feeds one conversation through both paths and asserts the prepared tensors match, so a future edit to either container could drift without the curve visibly moving. That test is cheap to write — both encoders are already constructible in tests/unit/data/test_energon_sft.py — and it is the one thing that would hold the convergence point above in place.

If you are reading one thing: the two loaders are not two pipelines. They share the tokenizer call and they share the batch normalizer, so the tokens are identical by the time either reaches the trainer. Only the containers differ, and only in the middle. When you add a third loader, the job is to reach get_formatted_message_log with HF-shaped messages — everything after that is already written.

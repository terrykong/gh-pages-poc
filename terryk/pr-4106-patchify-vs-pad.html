Two ways to hand images to the model: pad them to the biggest, or cut them into patches

Companion illustration for NVIDIA-NeMo/RL #4106 (add PackedTensor preprocessing modes). All NeMo-RL permalinks pin the PR head 977f0f3; Megatron-Bridge links pin the submodule at 5ed9799.

A vision model is fed a batch of images, but the images are not the same size. Something has to turn a ragged pile into one tensor. NeMo-RL does that inside PackedTensor.as_tensor(). Until this PR there was one way: pad every image out to the tallest and widest in the batch, then stack them. This PR adds a second way: cut each image into 16×16 pixel squares at its own size, and lay all the squares end to end. The choice is made by get_preprocess(), which turns the new way on for the Nemotron Omni family.

These numbers come from running both modes on exactly these two images. The padded tensor holds 30720 numbers, of which 13056 are padding the model has to throw away. The patch sequence holds 17664 — exactly the pixel count of the two images, with nothing added.

Where the two paths meet again

Both paths end at the same model, and the model already knew how to do this. Megatron-Bridge's Nemotron Omni model patchifies raw pixels itself on every forward pass:

# Megatron-Bridge, modeling_nemotron_omni.py:432 if imgs_sizes is not None and imgs_sizes.numel() > 0: images = self._patchify_dynamic_images(images, imgs_sizes)

modeling_nemotron_omni.py:432 · the function itself, :558

That function takes both shapes. Hand it padded pixels and it crops each image back down using imgs_sizes, then cuts the patches. Hand it patches already, and it returns them untouched — its own docstring says "Already-patchified inputs remain accepted for Bridge/SFT callers." So the two paths converge here, at _patchify_dynamic_images, and after that point nothing differs. Following the same two images through:

# BEFORE — the model does the cutting images = [2, 3, 80, 64] # 30720 numbers, 13056 of them padding imgs_sizes = [[32, 64], [80, 48]] -> crop A back to 32x64, crop B back to 80x48 -> cut both into 16px patches = [1, 23, 768] # 17664 numbers # AFTER — NeMo-RL does the cutting, the model passes it through images = [1, 23, 768] # 17664 numbers, already patches -> returned unchanged = [1, 23, 768] # same answer, same numbers

The patch order is the same too. NeMo-RL's permute(0, 2, 4, 1, 3, 5) and the model's own permute(1, 3, 0, 2, 4) produce the same layout once you account for the extra leading dimension — patches left to right, then top to bottom, with each patch flattened colour-channel first.

What you give up

What it buys: the padding disappears. In the example above that is 13056 of 30720 numbers, 42% of the tensor, and it grows with how much the image sizes differ. That memory is saved everywhere the tensor lives — worker memory, and the copies moved between processes each step.

What it costs: the output is no longer a picture. It is [1, 23, 768] — one row of patches, with no height or width left. Any code that expects [images, channels, height, width] can no longer read it, and the spatial shape cannot be recovered from the tensor alone. Whether that is safe depends entirely on which model receives it: the Megatron path accepts patches by design, so the choice of which mode to use has to follow the model, not just the processor that produced the pixels.

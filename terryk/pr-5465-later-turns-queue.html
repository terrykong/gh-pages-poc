Which waiting model call does vLLM run next, and how does a Gym call's turn number reach it?

NVIDIA-NeMo/RL#5465 · needs NVIDIA-NeMo/Gym#6853 · RL permalinks at ed2b7e4, Gym at 83df0ded, vLLM at v0.33.0

Before
vLLM runs waiting model calls first come, first served. The next turn of an almost-finished rollout waits behind the first turns of rollouts that just started.
This PR
Adds an opt-in switch, policy.generation.vllm_cfg.prioritize_later_turns. When on, vLLM picks by priority, and Gym tags each call with minus its earlier replies, so later turns go first.
Status
Open: off by default, not merged. The review asks for 3 changes (C3–C5, below). Merging also waits until the Gym submodule points at a Gym main commit with Gym#6853.
Background. In multi-turn RL, one rollout is a chat: model reply, tool result, model reply, and so on. Each model reply is one model call to the vLLM engine. A training step waits for whole rollouts, so a rollout stuck on its last call holds the step up. Gym's turn_priority gives each call minus the number of assistant replies already in its history: the first call gets 0, the next −1, and so on. vLLM runs the smaller number first. Dotted words have a short explanation: hover or tap them.

1 · Same queue, two orders

Four rollouts each have one call waiting, in the order they arrived. The engine has room for 2 more. With fcfs, the two new rollouts get in. With priority, the two rollouts that are furthest along get in. Total work is the same. Only the order changes.

Legend: green = admitted under priority; red = admitted under fcfs while a nearly done rollout waits; orange = the cost: new rollouts start later. The PR's toy benchmark (one GB300, a 4-layer dummy model) shows later turns queuing about 11× less, new rollouts finishing later, and the same wall time. No RL run has used the switch yet.

2 · How the number travels: native vs Dynamo

Gym computes the number once. It then takes one of two roads to the same call, engine_client.generate(…, priority=−5). The Dynamo frontend refuses a top-level priority, so on that road Gym tucks the number into its nemo_rl:gym: annotation.

Real code: native — create_chat_completion hands the request to vLLM, whose serving layer passes request.priority on. Dynamo — GymCallExtras.priority reads it out of the annotation. Both roads end at the same call, with the same number. The PR's test_gym_chat_path checks that.

3 · How setup turns it on, and the review asks

Setup, after this PR (new lines green)

# driver, before any worker starts
def setup_nemo_gym_config(config):        # only Gym entry points call this
    if backend == "vllm":
        vllm_cfg.async_engine = True
        vllm_cfg.expose_http_server = True
        if vllm_cfg.prioritize_later_turns:
            vllm_kwargs.scheduling_policy = "priority"  # enable_vllm_turn_priority; refuses fcfs
            env.nemo_gym.turn_priority = True         # read once per Gym actor

# once per Gym actor (also every shard)
def _build_gym_actor_config(d):
    if d.pop("turn_priority"):
        _apply_turn_priority(d)                  # copies, then sets vllm_model.priority_by_turn = True

# later, when the vLLM workers are built
def validate_vllm_async_actor_settings(config):
    if prioritize_later_turns and scheduling_policy != "priority":
        raise "requires NeMo-Gym"               # C3: guesses "Gym ran" from the policy

Why a microbatch that fits in one slice uses more loss memory, not less

Review finding on NVIDIA-NeMo/RL #4114 · all permalinks pin the PR head 617d989.

Before
The AutoModel training loss peaked at about 12 bytes per logit, whatever logprob_chunk_size said.
This PR
Uses the chunked kernel. Its backward pass costs about 24 bytes per logit per slice, so the saving only appears once a microbatch splits into 3 or more slices.
Status
Open — not fixed in this PR. A one-line gate is proposed in the review. Numbers come from the author's GB300 figures plus a CPU replay of both kernels. They were not re-measured on a GPU.

Two pages on this PR — this one: the 1–2 slice case and the proposed fix.

The chunked kernel's backward loop builds five buffers for the slice it is working on (model_utils.py L399-L422): a zeroed gradient for the whole sequence, an fp32 copy of the slice, its softmax, and two int64 tensors that mark the chosen token. The last two come from one_hot. Only the zeroed gradient spans the whole sequence; the other four are rebuilt per slice. With many slices the per-slice part is small. With one slice, it covers every position at once and is twice the old path's total.

Who hits the one-slice case

Four shipped AutoModel recipes set logprob_chunk_size equal to max_total_sequence_length (both 4096) and use dynamic batching (gemma4-e2b, gemma4-12b, gemma4-31b, mistral-medium-3.5). No microbatch is longer than 4096 positions, so every microbatch is exactly one slice. For Gemma 4 E2B:

one full microbatch = 4096 positions × 262,144 vocab = 230 logits before this PR 230 × 12 B = 12 GiB this PR 230 × 26 B = 26 GiB ← more memory, plus the backward recompute with the gate 230 × 12 B = 12 GiB ← back to the old path

What would fix it — proposed, not in the PR

Where the fix lands: RL only, one condition in LossPostProcessor.__call__. No kernel change is needed.

Nothing above is implemented. When the gate says no, the group stays None, which is exactly the path from before the PR. So the gate cannot move any run onto a new kernel. For gemma4-e2b (4096 ≤ 2 × 4096) it restores the old 12 GiB. For the author's GB300 case (4096 > 2 × 512) it keeps the 2.45 GiB win. A cheaper backward that avoids one_hot would still leave one slice at about 16 bytes per logit, above 12, so the gate is needed either way.

🔴 review comment — train.py:653-659

So what. As written, the PR makes loss memory worse for the AutoModel recipes that already set logprob_chunk_size = max_total_sequence_length. For Gemma-sized vocabularies that is about 14 GiB more per microbatch, enough to push a run that fits today into running out of memory. The review asks for the gate above before merge, then step time and peak memory on one of these recipes.

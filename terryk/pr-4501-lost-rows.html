What RL does with a Gym row that does not come back, after #4501

NVIDIA-NeMo/RL #4501 (harden Gym turn recovery), built on #4500. Permalinks pin the PR head e36be156; "before" links pin the #4500 base dccc3fb1.

Before
In #4500, a row RL had to send again kept its old rollout ID, even if Gym was still running the first copy. One failed row ended the whole stream. A row refused during a checkpoint waited for the whole stream to end.
This PR
Re-sends a lost or failed row under a new rollout ID and queues the old one for Gym to stop. Keeps the stream going past one failed row. Re-sends a refused row on its own, right away.
Status
Done in this PR. All 7 review threads were fixed and resolved at e36be156. Unit and functional CI have not run on that head yet.

Two pages on this PR, one question each — this one: what happens to each row that goes missing.

Background. Dotted words have a short explanation: hover or tap them. For how turn recovery works overall, see the #4500 page.
  • RL sends one prompt's rows to Gym in one streamed request. Each row carries a rollout ID.
  • The recovery ledger remembers each row's current attempt, so a checkpoint knows which Gym episodes to save.
  • Ending the stream does not stop Gym. A row Gym already started keeps running until RL retires it.

Every row ends one of four ways. The new code tells them apart in _stream_rows, and decides what to re-send in _run_rollouts. The rule is simple: a row Gym started gets a new ID before it is sent again, and a row Gym never started keeps its ID.

How the code does it

Where it lands: RL only. rollout_manager.py (_stream_rows, _replace_unreturned_rows), rollout_recovery.py (new attempt per lost row), and nemo_gym.py (yields a failed row instead of raising). No Gym change: the queue of episodes to stop, and the retire call at the next checkpoint, already exist in #4500.

In order: a refused row starts its own small stream straight away (submit runs each one as a separate task). A network-type failure on one row is held until the stream ends. Any other failure still fails the whole prompt at once. Before the next attempt, every row Gym started but never returned gets a fresh attempt in the ledger: replace_dropped_dispatch marks the old one abandoned and queues its Gym episode to be stopped. The row is then stamped with the new ID. The old re-send-after-the-stream loop in #4500 (base L1484-L1506) is gone.

Two smaller changes

  • Restore check. A checkpoint now records which Gym servers saved state. On restore, RL refuses to start if one of them is missing, and names it (restore). Gym already rejects the other mismatches itself. The checkpoint file's schema goes to version 2, and an older file gets a clear "unsupported version" error.
  • A cheaper checkpoint wait. A checkpoint waits for replies already on their way back from Gym. It now checks only those episodes, every 50 ms (L4899-L4909, gym_episodes_still_held), instead of scanning every live rollout each time.
So what. Once Gym has started a row, RL never sends it again under the same ID. That ends the two-copies problem and the crash shown on the retired-ID page. The cost: an abandoned row keeps running in Gym, and keeps calling the policy, until the next checkpoint stops it. #4500 already accepts that cost for abandoned groups. With the default of 1 row attempt, nothing is re-sent at all; this matters only for runs that raise max_gym_row_attempts, plus every run that hits a checkpoint refusal.

Background. Dynamo puts one HTTP frontend in front of many inference engines and routes each request. A prefill/decode split runs prompt reading and answer writing on different engines. A refit pushes new weights from the trainer into the engines after every step. Dotted words have a short explanation: hover or tap them.

Three ways to put Dynamo in front of the engines

All three end at the same Dynamo frontend. They differ in who owns the engine workers and in which backend the dynamo flag belongs to. Main has the first one. #4905 replaces it with the second. This stack adds the third.

The two checks sit in different functions, so git merges both PRs with no conflict in these files. Only test_grpo.py conflicts. #4905 also rejects dynamo_cfg.control_timeout_s as removed, for every backend. This PR adds that key for Megatron. Part of the new config is the same code as #4905's: the frontend arguments (MegatronDynamoFrontendArgs ↔ DynamoFrontendArgs), the startup and request timeouts, and dynamo_enabled. Main has no small shared module to import them from yet: main's dynamo/config.py still holds the old backend: dynamo schema. #4905 turns that file into one.

What this PR changes now: refit with shards of different widths

The refit NCCL group lists the trainer ranks first, then each engine's ranks, shard by shard. Until now every shard had the same width, so shard i started at i × width. A prefill engine at TP 4 next to decode engines at TP 2 breaks that. RefitMembership.worker_offset() adds up the earlier widths instead, dead shards included, because the worker list never shrinks.

workers_per_shard = (4, 2, 2) # 1 prefill at TP 4, 2 decode at TP 2; 8 workers workers: 0 1 2 3 | 4 5 | 6 7 shard: 0 | 1 | 2 worker_offset(0, 1, 2) = 0, 4, 6 # an equal-width rule (i × 2) would give 0, 2, 4: wrong shard 0 dies → refit ranks after the trainers: shard 1 → 0..1, shard 2 → 2..3

All four call sites switch to it: the Megatron path and three vLLM paths. With equal widths the result is the same as before:

Merge order — proposed, not in the PR

Nothing below is implemented. Each PR is fine alone on main, so the two authors only need to agree which lands second. The second one has to:

  • keep one backend check that allows both vllm and megatron, instead of two checks that each allow one;
  • keep control_timeout_s out of #4905's removed-keys list for backend: megatron;
  • define the frontend arguments, timeouts and dynamo_enabled once, in nemo_rl/models/generation/dynamo/config.py; the Megatron config adds only control_timeout_s and the per-role layouts;
  • limit the legacy grpo.py refusal to Megatron.

The larger overlap is at the end of this stack, not in this PR. #5025 rewrites dynamo/managed_runtime.py and keeps DynamoGeneration running from a copied runtime file. #4905 deletes DynamoGeneration and also rewrites that runtime. Merging those two touches 11 of the same files.

So what. This PR is groundwork. It does nothing at run time on main, and it is safe to merge alone. The risk is a quiet one: it and #4905 give dynamo: true opposite meanings, and git will not flag it. Write the order into the PR description before either one lands.

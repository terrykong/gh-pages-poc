Where a slow thread offload spends its time, before and after this PR

PR #4732 · feat(telemetry): add executor and event-loop diagnostics · permalinks pinned to 01a5304

Before
Blocking calls were handed to a thread with asyncio.to_thread. Nothing was recorded, so a slow call was one opaque wait.
This PR
Wraps three thread hand-off sites so each wait splits into three timings and a live count, and adds a probe that measures how late the event loop runs.
Status
New metrics, off unless telemetry metrics are on. Review found no bugs; two small test comments and two doc fixes.
Background. NeMo-RL's controller and its vLLM HTTP server each run one asyncio event loop. Work that blocks (a disk read, a data-plane round trip) is sent to a small shared thread pool so the loop stays free. When the work finishes, the loop has to wake the waiting coroutine. Each of those three steps can be the slow one. Dotted words have a short explanation: hover or tap them.

The new run_in_thread(site, fn, …) replaces asyncio.to_thread(fn, …) at the chosen sites. It notes the time when the call is queued, when the thread starts it, when it finishes, and when the waiting coroutine wakes up again. It records the gaps as queue_wait, execution and result_delivery. It also keeps rl.executor.pending, a live count of calls queued or running. A separate probe, _probe_event_loop, sleeps for 1 s in a loop and records how late it wakes up.

Real run at the PR head on CPU: a one-thread pool, A sleeps 40 ms, B sleeps 20 ms, and the loop is blocked for 70 ms. Times in ms, rounded. B's 43 ms queue wait is the time A spent running, because there is only one thread.

What each number tells you

PatternWhat it meansIn the run above
high queue_wait, low executionThe thread pool is full. Calls are waiting for a free thread, not doing slow work.B: 43 queued, 25 running
high executionThe work itself is slow (disk, network, CPU). Look inside the function.A: 43
high result_delivery plus high rl.event_loop.lagThe work finished on time, but the event loop was too busy to resume the caller.A: 31, loop lag 72

The old way recorded none of these. Both A and B looked like "77 ms", and you could not tell a full thread pool from slow work or from a busy loop. Per the metrics docs, the probe only reports after the loop runs again, so it is not a hang detector.

Where the two ways meet, and where it is wired in

Both use the same thread pool. asyncio.to_thread copies the context and calls loop.run_in_executor(None, …). run_in_thread does the same at L171-L181, with timing added around the call. With metrics off it simply calls asyncio.to_thread (L149-L150), and no probe task is created. The only difference with metrics on is the bookkeeping: the author measured about 60 µs extra per call.

Wired in at three hand-off sites and two loops, RL only. data-plane calls (site data_plane.<method>) · replay-buffer restore (checkpoint_replay_load) · vLLM token capture (generation_terminal) · loop probes on the controller and the vLLM HTTP server.

Each site is a one-line swap like this one (old line at the base). The site name is a fixed label, never a request ID, so the number of metric series stays small.

So what. When a run stalls in rollout or a checkpoint restore, these timings tell you whether to add threads, speed up the work, or find what is hogging the event loop. They are off by default and cost about 60 µs per call when on. The main review ask is one test. Every data-plane call passes keyword arguments, and no test covers keyword arguments while metrics are on.

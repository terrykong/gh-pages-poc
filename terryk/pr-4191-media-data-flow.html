Four pages on this PR. This one: every place the image lives, in what form, and who reads it.

Background. TQ has two areas here: a staging area with one row per model call, and a train area with one row per finished rollout. The finalizer turns the first into the second. Gym is the environment framework that drives the conversation. It talks to the vLLM worker over HTTP, but part of Gym (its capture code) also runs inside the vLLM worker process. Dotted words have a short explanation: hover or tap them.

The dataset row never holds pixels for an image. It keeps only the image's path, inside the Gym request (processors.py:966). Just before the rollout, RL opens each image file, converts it to RGB, saves it again as a PNG, and base64-encodes those PNG bytes into a data: URL, once per unique image in the batch. The URL is not a pointer: it holds the whole image, about 1.33× the PNG size, so a 100 KB PNG becomes about 133 KB of text inside every chat request that includes it (resolve_to_image + image_to_data_url; videos are base64 of the raw file bytes) (nemo_gym_multimodal.py:145). That text travels through Gym to the vLLM worker as part of the chat request. vLLM decodes it and runs its own image processor. From there on the pixels stay in RL's hands: the worker packs them and writes them to TQ in the same call that saves the tokens. Gym passes the tensors along without reading them (Gym capture.py:241).

The five forms of an image, and who makes each

A processor and an encoder are different things. The processor is plain CPU code: it resizes and normalizes the picture into pixel numbers, and it decides how many slot tokens the image gets in the prompt. The encoder is a neural network, part of the model's weights, that runs on the GPU and turns those pixels into one feature vector per slot. Every step after the base64 text happens inside the vLLM worker that RL hosts. Nothing outside it touches the pixels.

So the prefill the model sees is text embeddings with 6 positions overwritten by A's 6 features. The learner rebuilds form 5 itself: Bridge runs its own copy of the encoder on the saved pixels (_encode_images). That is why the PR saves pixels (form 3) and not features (form 5): the learner computes the features with its own current weights, and with gradients when the encoder is being trained, so it needs the same pixels vLLM used.

The path of one image, one rollout, two model calls

Example numbers, as on page 1: a patch is 16×16 px = 768 numbers. Image A (64×96 px) is 24 patches; image B (128×160 px), added on turn 2, is 80 patches. Page 3 shows the matching tokens. Gym sends the whole conversation on each turn, so vLLM decodes and processes A again on turn 2. The worker then compares A against the image list saved with call 1 and drops it, so only B is written (vllm_worker_async.py:709). The shipped CLEVR smoke is single-turn, so turn 2 is covered by unit tests only.

Within one rollout, an image is stored once: later calls check it and skip it. Across the rollouts of one prompt, nothing is shared. Each rollout is a separate vLLM request, so each one processes, stores and trains on its own copy of A. The dataset's own pixels are not used on this path. For images, RL never makes them. For native video, the dataset code still decodes frames into the prompt (nemo_gym_multimodal.py:825), but with capture on the Gym actor returns no message log (nemo_gym.py:884), so the finalizer is the only thing that writes pixel_values. That dataset copy is unused work.

What to take away. Pixels are made once per request by vLLM and written to TQ from inside the vLLM worker. They never travel over HTTP and Gym never reads them. The learner reads them only from the finalizer's training row. The cost to watch is the group size: a prompt with G rollouts stores and trains on G copies of every image, with no sharing between them. Not measured here; nothing was run on a GPU for this page.

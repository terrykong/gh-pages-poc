Three pages on this PR, one question each — this one: when two groups with the same prompt share a baseline.

Background. GRPO scores each response against the other responses to the same prompt: advantage = (its reward − the mean reward of the other responses) ÷ their spread. That mean is the baseline. The code decides "same prompt" by comparing the prompt's tokens (torch.unique(prompts, dim=0), on prompt_ids_for_adv), not by which group a response came from. So if one call holds two groups with the same prompt text, all their responses form one pool. Dotted words have a short explanation: hover or tap them.

The single controller computes advantages one streaming chunk at a time (sampler.select). This PR then cuts each chunk into whole groups, in order, and gives one piece to each advantage actor (split_meta_by_prompt_group). The cut knows only row positions, so it can put two same-prompt groups on different actors.

The split never cuts a group. It hands out whole groups: with 3 groups of 5 responses and 2 actors, actor 1 gets groups 1–2 (10 rows) and actor 2 gets group 3 (5 rows) — never 8 and 7. The numbers change only when two different groups have the same prompt text, and the split puts them on different actors.

What the review asks — proposed, not in the PR

Where the fix lands: RL only, one comment and one new test. Nothing below is implemented. The splitter cannot keep same-prompt groups together, because it sees only metadata: the group id is random and carries no prompt text. So the ask is to state the exception, and to add a test that the split matches the whole batch when every prompt is different.

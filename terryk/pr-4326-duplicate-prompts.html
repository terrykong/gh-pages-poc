before and after same-prompt baselines DAPO & NGU design

Three pages on this PR, one question each — this one: when two groups with the same prompt share a baseline.

Background. GRPO scores each response against the other responses to the same prompt: advantage = (its reward − the mean reward of the other responses) ÷ their spread. That mean is the baseline. The code decides "same prompt" by comparing the prompt's tokens (torch.unique(prompts, dim=0), on prompt_ids_for_adv), not by which group a response came from. So if one call holds two groups with the same prompt text, all their responses form one pool. Dotted words have a short explanation: hover or tap them.

The single controller computes advantages one streaming chunk at a time (sampler.select). This PR then cuts each chunk into whole groups, in order, and gives one piece to each advantage actor (split_meta_by_prompt_group). The cut knows only row positions, so it can put two same-prompt groups on different actors.

The split never cuts a group. It hands out whole groups: with 3 groups of 5 responses and 2 actors, actor 1 gets groups 1–2 (10 rows) and actor 2 gets group 3 (5 rows) — never 8 and 7. The numbers change only when two different groups have the same prompt text, and the split puts them on different actors.

What the review asks — proposed, not in the PR

Where the fix lands: RL only. Nothing below is implemented. The review points to #4371, in this PR or right after it. Every row is already named after the id the controller gives its group ({group_id}_g0, _g1, …). Keying the baseline on that id instead of on the prompt text means two groups never share a baseline by accident, so the split no longer changes any number. If #4371 comes later, the comment edit below keeps the code honest in the meantime, and the review asks for a same-seed A/B of 0 vs 8 actors on repeated-prompt data.

So what: this is a convergence risk. Nothing crashes. On data where prompts do not repeat, 0 actors and 8 actors give the same advantages. On data that repeats prompts they do not, so two runs that differ only in num_advantage_workers train on different numbers and can converge differently, and the code comment says that cannot happen. Pre-existing: the baseline matches rows by prompt text, so on main the result already depended on chunk boundaries. New in this PR: the pool size also decides it. The fix, keying the baseline on the controller's group id, is #4371. It makes the sharded and unsharded results equal, and it changes numbers on repeated-prompt data, so it needs its own A/B run.

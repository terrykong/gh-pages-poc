Seven pages on this PR, one question each — this one: one bug, start to finish.

A generation engine that restarts comes back holding whatever weights it read off disk at startup, so the ledger parks it in STALE: the process is alive and can join a weight transfer, but it is not allowed to answer requests. The module docstring is firm that a completed weight transfer — a refit — is the only way out of STALE. The code that does the letting-out, _promote_refit_shards, asks each shard "are you STALE?" and never "were you in the group I just sent weights to?" Before this PR those two questions always had the same answer. This PR adds a way for a shard to turn STALE in the middle of a refit, and the question was never updated.

Shard 2 did not fail during this refit. It died in an earlier step and has been reloading ever since, so when this refit fixed its membership shard 2 was already RESTARTING — absent, and correctly left out. That part works. The new thing is when the reload finishes: it takes minutes and nothing blocks it, so it can land at any moment, including in the middle of a refit it was never part of.

Why nothing catches it

There is a metric that looks like it was built for exactly this. as_metrics publishes a per-shard weight version with the comment "Catches a STALE shard that somehow served: a serving shard whose weight version trails the trainer is a correctness bug, not a capacity problem."

It cannot catch it, because the number is written by the promotion rather than by the transfer. report_refit L476 is the only line in the repo that assigns it, and report_refit is only ever called from the promotion, only for shards that are STALE. So a shard that has never been restarted never goes through it and reads 0 forever, however many refits it has received — and the one shard that got nothing reads the current version, because the promotion is what put it there. The metric says the opposite of the truth in both directions.

The fix: promote the shards you actually sent weights to

The right set is already computed and already at hand. Every rebuild produces a RefitMembership.surviving_shards — the shards the communicator was built over — and the synchronizer keeps it in _built_membership. It is the list of shards that received the weights.

# today — single_controller.py L2612 for health in self._gen_fleet.snapshot(): if health.state is ShardState.STALE: # shard 2 is STALE, so it is promoted self._gen_fleet.report_refit(health.dp_shard_idx, weight_version=self._trainer_version) # shard 0 -> HEALTHY shard 1 -> HEALTHY shard 3 -> HEALTHY (never STALE, so skipped) # shard 2 -> HEALTHY with the current weight_version stamped on it
# with the group that was actually refit refitted = membership.surviving_shards # [0, 1, 3] — shard 2 was absent for health in self._gen_fleet.snapshot(): if health.state is ShardState.STALE and health.dp_shard_idx in refitted: self._gen_fleet.report_refit(...) # shard 2 stays STALE. It is not absent, so the next refit includes it, # receives the weights, and promotes it then — a few seconds later, and correct.

There are two windows where this happens, not one. The membership is fixed at the last reconcile before the transfer and the promotion runs at L3107. On the recovery path there is a second gap, between the rebuild and the promotion after the retry. The recovery one is the more likely of the two: the shard is restarting because that refit just failed, so a reload landing inside the retry is the expected case rather than bad luck.

What this costs. The shard serves training rollouts generated from an old checkpoint, and nothing reports it — no error, no crash, no metric. Rollouts from stale weights are still valid-looking text, so the run keeps going and the numbers quietly get worse. The module docstring names this as the exact outcome the design exists to prevent: "re-admitting it because it started answering probes again would feed training rollouts generated from a checkpoint hundreds of steps stale — invisible, and far worse than the outage that caused it." The rule is right; the promotion just does not enforce it.

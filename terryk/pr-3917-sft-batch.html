How an SFT batch is built: two producers, one shared normalizer

Companion illustration for NVIDIA-NeMo/RL #3917 — SFT v2 with the Megatron-Energon data path. All permalinks pin the PR head 0a45c45.

Two very different loaders feed SFT training, and they meet at one shape. The Hugging Face path collects samples with rl_collate_fn; the Energon path builds its own with GenericSFTTaskEncoder.batch(). Both emit the same two keys — message_log (a list of conversations, each a list of messages with their token ids) and loss_multiplier (one weight per conversation). From there a single function, prepare_sft_batch, turns that into padded tensors and checks them. It is called from the v1 training loop, v1 validation, and the v2 Energon worker.

The figure follows one batch of 3 conversations — 2, 5 and 7 tokens long — with make_sequence_length_divisible_by = 4, so the padded width is 8. The third conversation has no assistant turn, which is the case worth watching.

The call structure

HF path Energon path AllTaskProcessedDataset GenericSFTTaskEncoder.batch() └─ rl_collate_fn └─ runs inside the policy worker │ │ └───────────────┬──────────────────────┘ ▼ {message_log, loss_multiplier} source_ids too, on the v2 path │ ▼ prepare_sft_batch() │ ┌───────────────────┼───────────────────┐ ▼ ▼ ▼ add_loss_mask_ batched_message_ _validate_prepared_ to_message_log() _log_to_flat_ sft_batch() message() role == assistant concat + pad to 6 checks; may rewrite → token_loss_mask a multiple of 4 sample_mask

One branch is easy to miss. If the batch already carries a loss_mask_mode of "precomputed", step 1 is skipped and the existing masks are checked instead — they must be binary and the same length as their token vector. And if the batch has no message_log at all, it is taken as already prepared and goes straight to the validator (sft.py:399).

What the validator checks

Five of the six checks raise. One does not — and that is the one to know about.

CheckOn failure
All four core keys present: input_ids, input_lengths, token_mask, sample_maskValueError
All four are torch tensorsTypeError
input_ids is 2-D and token_mask matches its shapeValueError
input_lengths and sample_mask are both [B], and lengths fit inside the padded widthValueError
Every PackedTensor field has one entry per row, and sequence-aligned side tensors match input_idsValueError
An active row has at least one trainable tokenwarns and masks the row out

That last one is row r2 in the figure. A conversation with no assistant turn contributes exactly zero to the loss, so the validator sets its sample_mask to 0 and keeps going rather than killing a run hours in over one bad sample. It is the only place this function changes the batch instead of just inspecting it.

Does it work?

The seam is pinned by one good test, and it is worth naming because of how it checks: test_prepare_sft_batch_builds_mask_from_energon_message_log runs a real Energon-encoded sample through prepare_sft_batch and then rebuilds the expected mask independently, from role == "assistant", rather than asserting against a mock. So it would catch the mask logic drifting, not just the call happening.

What is not covered: no test feeds a loss_mask_mode="precomputed" batch through this function, and no test exercises the warn-and-mask row. Both are cheap to add and need no GPU. There is also no end-to-end run of the Energon path on any schedule — both new recipes sit in disabled.txt — so the thing to ask for before merging is one run of the 2-GPU recipe against the v1 loop on the same data and seed.

Why the shared function matters. The mask, the padding and the shape checks live in one place, so the Energon path cannot quietly disagree with the Hugging Face path about what a batch is. That is what makes the two loaders swappable — and it is why the interesting review question on this PR is not the loaders themselves but whether anything else got duplicated instead of shared. If you change the batch contract, change it here, and both paths move together.

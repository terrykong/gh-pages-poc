Three pages on this PR. This one: the data path on each backend, turn by turn.

Background. With token capture on, every model call writes one row into TQ: the new tokens of that call, and (for VLMs) the pixels of the images that are new in that call. When a rollout ends, the finalizer joins those rows into one training row. Each chat turn resends the whole conversation, images included, so each backend must work out which images are new. Dotted words have a short explanation: hover or tap them.

The example is the one in the PR description. Turn 1 sent text and image 1; RL saved its 7 tokens [80,99,99,99,81,12,2]. Turn 2 resends the history plus image 2. Token 99 is an image placeholder, and each image fills 3 of them once expanded. Each image is 4 patches of 12 numbers. The figure follows turn 2 through both backends, in the order the code really runs, with what goes in and comes out of each step. The middle column says whether the two backends match at that step.

Short answer: no, the steps do not take the same inputs. Both backends start from the same chat request, run the same 12-token prompt through the model, and end with the same TQ row. In between they hand on different things. vLLM expands every image in step 1 and has pixels from the start, so it checks and cuts images before generation (step 3). Megatron keeps one placeholder per image and raw bytes until the engine itself decodes and expands them (step 3), so RL can only cut to image 2 after generation (step 5), from a host copy of every image.

What is stored, and which code made it

Both paths store the pixels their own engine was fed, and the trainer reads only those: no other copy of the image reaches the training forward pass. Neither stores the dataset's HF processor output.

RL never converts pixels on either path: the TQ writer rejects any type other than the one its column is set to (tq_token_sink.py:430). The type difference is not a bug. The vision encoder converts pixels to its own weight type as its first step (_encode_images), and Megatron's generation path calls that same method (wrapper :321). So generation and training see the same values, and storing float32 only doubles the bytes. The type to store in is the vision encoder's weight type, since that is what the pixels become anyway. The two backends use different preprocessing code, so the same image can give slightly different pixels on each: rows from a vLLM run and a Megatron run are not byte-for-byte comparable.

Why the two front halves differ, and whether they should

The split comes from one fact. vLLM expands image placeholders before it runs, so RL has to know exactly where every earlier image's slot tokens sit, and it re-checks them each turn (captured_media.py:339). With Megatron-LM #7598, the Megatron engine expands them itself, after a prefix it is told is already expanded (_slice_suffix_media_metadata). So RL only needs a count. Rows 2–4 are different jobs, and merging them would put backend checks all through one function. They should stay separate.

What to take away. The PR does not build a second pipeline. From the TQ write onward, vLLM and Megatron share every line of code, and the trainer gets a [8, 12] tensor of the pixels the generator actually used. The front halves really are different jobs, because the two engines expand images at different times. The costs to watch are all on the Megatron side: float32 doubles the stored bytes, the write blocks the engine step, and every later turn copies all earlier images off the GPU.

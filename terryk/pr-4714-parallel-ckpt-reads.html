How the new checkpoint reader keeps several reads in flight per rank

NVIDIA-NeMo/RL #4714 (parallel reads for torch_dist checkpoint loads). All NeMo-RL permalinks pin the PR head d43c1e7; PyTorch links pin v2.11.0.

Before
Each rank reads its share of a Megatron checkpoint one item at a time, through one file stream. One read is in flight at a time.
This PR
With NRL_CKPT_READ_THREADS=N (N > 1), a thread pool reads the same bytes in 16 MB pieces, N at a time, while the main thread unpacks items in file order. Off by default.
Status
New in this PR, off by default — under review. The review asks to move the setting into the checkpoint config, turn it on by default with 4 threads, and make the tests catch wrong-offset reads.
Background. NeMo-RL's Megatron backend saves checkpoints in the torch_dist format. On load, Megatron hands each rank a list of items to read. PyTorch's FileSystemReader.read_data reads them. On a shared network filesystem, one request at a time leaves most of the bandwidth unused. Dotted words have a short explanation: hover or tap them.

The PR adds ckpt_parallel_read.py. Its install() runs at the start of setup_model_and_optimizer and swaps FileSystemReader.read_data for the whole worker process. The new version sorts a file's items by byte offset, then splits each item into 16 MB pieces and queues them on the pool. The main thread waits for an item's pieces, then unpacks it with a copy of PyTorch's own per-item code. It stops queuing once more than 1 GiB is read but not yet unpacked.

One file, three items, both readers

A real trace on torch 2.13 (CPU): one rank, one file, three items. The PR's limits are scaled down to 4 MiB pieces and 8 MiB read-ahead so the 12 MB tensor splits; the defaults are 16 MB and 1 GiB. Box widths show order, not measured time.

After the load both runs hold the same values: emb = 2.0, 3.0, 4.0 …, norm[0,:3] = 2.0, 3.0, 4.0, step = b"step=7".

Where the two paths meet, and what still differs

They meet at the per-item code. _load_item is PyTorch's loop body with the file slice replaced by bytes already in memory. Three things still differ after that point:

Every Megatron load in a worker runs after install(): policy init and resume, the reference model, the Megatron value model, and later load_checkpoint calls. Automodel runs never call it, so the variable does nothing there.

Turning it on, and what guards it

Set NRL_CKPT_READ_THREADS=4 in the launch environment; Ray workers inherit it. install() then checks the torch version against 2.11, 2.12 and 2.13 and raises on anything else, because _load_item is a copy of PyTorch's code and must match it.

Review suggestions (not in the PR yet). Read the thread count from policy.megatron_cfg.checkpoint.parallel_read_threads, where the other checkpoint-load settings live and where the PR description already says it is. Set it to 4 in the example configs, so it is on by default and every Megatron nightly that loads a checkpoint tests it; 1 turns it off. Drop the torch version check and let the comparison test guard upgrades: it runs PyTorch's real reader on whatever torch is installed. After it passes, a hash of PyTorch's read_data source flags upstream changes the test does not cover, and its message says how to update. PyTorch has no fix to wait for: its own read_data still reads one item at a time, with a TODO asking for this.

So what. The author measured 128 ranks, each loading an 8.8 GB share on torch 2.11 with 4 threads: per-rank read time (median) 7.2 → 3.7 s, slowest rank 11.4 → 4.8 s, and setup_model_and_optimizer (median) 37.2 → 31.6 s. The price is extra host memory on every rank while loading (up to 1 GiB of read-ahead plus about twice the largest item), and a copy of PyTorch code that has to be kept in step with each torch upgrade.

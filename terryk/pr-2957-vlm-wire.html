How images cross the TransferQueue wire in VLM GRPO

Companion illustration for NVIDIA-NeMo/RL #2957 — routing VLM GRPO through the TransferQueue trainer. All permalinks pin the PR head 4bcb4830.

In GRPO the model generates answers, then trains on them. The data plane is what carries that generated batch from the machine that made it to the machines that train on it: instead of shipping Python objects through Ray, each field is written into TransferQueue (TQ) as a column, and each worker fetches back only the columns it needs. Before this PR the data plane could carry text but not images — the write path kept only values that passed isinstance(v, torch.Tensor), and a batch's images are not a tensor. They are a PackedTensor, so they were dropped without a word. This PR gives them a lane.

The shape of the problem

Text is easy to put in a column because every row is the same kind of thing: a list of tokens. Rows differ only in length, and one number per row (its length) describes it completely.

Images are not like that. One sample may carry one image, the next may carry two, and the images need not be the same size. So a row's contents vary in several directions at once, and no single length describes a row. That is what PackedTensor exists to hold in memory — a list of tensor pieces, plus a map saying which pieces belong to which sample.

Worse, several places in the trainer assume that dimension 1 of every tensor is the sequence length, and pad or trim it to match. For an image field, dimension 1 is a patch or feature count. Padding it to a token count silently corrupts the picture.

The same two samples, seen as text and as images. Every number on this page comes from this one batch.

Four lanes, chosen by field name

The fix is a small routing table. Each field of the batch takes one of four lanes across the wire, and which lane it takes is decided by looking up its name.

Name, not type — and that is the part worth pausing on. Once a value has crossed the wire it is a plain tensor; whatever wrapper it had on the producer side is gone. The reader therefore has nothing to dispatch on except the column's name. So the PR keeps two name registries and every consumer consults them: PER_TOKEN_MULTIMODAL_FIELDS and PACKED_MULTIMODAL_FIELDS.

The codec only ever sees two types — a tensor or an object array. Everything image-specific is a name lookup, which is why the transport itself needed no new concepts.

The class structure

Only one class is involved, and it does not know the transport exists. Everything else is a frozen set of names, or a plain function that reads one.

Where padding happens, and why that moved

Padding is something the model needs, not something the transport needs. Before, a batch was squared off early so it would fit in a rectangular container, and the padding then rode all the way across. Now nothing is padded until the last possible moment, on the one worker that is about to run the forward pass.

to_wire() flatten, no padding | v write ===== TransferQueue ========== stored bytes are payload only | shapes recorded per sample v read from_wire() restore the exact shapes | v as_tensor() pad here, to THIS worker's own view | v model sees one shard's width

Two shards may pad to different widths and that is fine — the padding is scratch the model discards, so nothing has to be agreed across machines. That is what removes the need for any batch-wide pad target on the wire.

Does it work?

Yes, with one gap the author has not closed yet.

The bug this fixes was measured, not theoretical. An earlier commit on the branch records that because the write path dropped the image fields, the trainer computed its reference log probabilities without the images while generation used them — so train/token_mult_prob_error, which compares the two, sat at about 176 where a healthy run sits near 1.02.

Two full training runs are linked from the PR description:

The first of these is the good one, and it is worth saying why. That recipe trains exactly one inner step per batch of generated data, which means the training pass runs on the very same weights that produced the generation. The ratio between the two therefore has to be exactly 1. Any drift at all would mean the two passes saw different data — which is precisely what a broken wire looks like. It reads 1.000000 on all 20 steps.

The gap. TransferQueue has two storage backends. Both runs above use the simpler one. The other one, which uses remote direct memory access, is the only place where one of this PR's changes has any effect at all — it replaces a workaround that only ever ran there. That path has no run behind it at this commit, and the author says so plainly in a commit message on the branch: "the KV path the scalar-schema patch targets is NOT yet covered by a run." The right thing to ask for before merging is one existing nightly on that backend. Its unit tests pass and do not need the special hardware, but unit tests are not the thing in question here.

So what

VLM GRPO can now use the data plane, and adding the next model family is a one-line change. The reason it stays a one-line change is the decision to route on the field's name rather than its type, and to keep the image-specific knowledge in the multimodal layer instead of pushing it into the transport. TransferQueue still only knows about two things — a tensor and an opaque blob — and still knows nothing about what a patch count is.

The one habit worth carrying forward: the shapes travel beside the bytes on a per-sample channel that the transport already re-orders when it shuffles or shards. Nothing has to be re-matched by hand, which is the failure this design is most exposed to and the one it structurally avoids.

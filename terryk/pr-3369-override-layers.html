How an override can put a Gym server on a shard that never asked for it

Companion note for NVIDIA-NeMo/RL #3369 (define shard configuration). All permalinks pin the PR head b6bdd33.

port range override layers

Two pages on this PR, one question each — this one: what the override layers are allowed to override.

Sharding splits one NeMo-Gym config across several actors. The config's top-level dict-shaped keys are its entries — each one is a server Gym will start. Every entry must be claimed by exactly one shard, and parse_shard_plan enforces that: an unclaimed entry is an error, and two shards claiming one entry is an error. Then apply_shard_overlay merges two more layers on top of the claimed set — common_overrides and the shard's own overrides — and checks neither against those claims.

How code_gen reaches a shard that never claimed it

The config behind the figure: common_inherited_overlays: [policy_model], a math shard claiming math_env, a code shard claiming code_gen, and common_overrides: {code_gen: {num_workers: 64}}. The merge is four dictionaries stacked in order, and only the second was built from the claim list. The third and fourth are whatever the user wrote, copied in whole — so naming an entry there puts it back on every shard, one layer after the claim rule took it out. code_gen carries an entrypoint, so on math it is a real server that starts. Under #3371 you find out only once every actor is already up, which is when the agent-to-shard map is built and raises — so you pay the whole multi-node startup first.

The same two layers drop one key on the floor. A config_paths written into overrides is overwritten by the shard's own list with no warning, while port_range_low and port_range_high written into the very same layer do take effect. One layer, two behaviours, neither written down.

The fix

Check both layers against the claims the parser already computed, in parse_shard_plan, so the run stops before any actor starts. Same config as the figure:

# the parser already knows this by the time the claim checks finish claims = {"policy_model": "common", "math_env": "math", "code_gen": "code"} # 1. an override layer naming an entry that a different shard claims # common_overrides sets code_gen; claims say code_gen -> shard 'code' raise ShardConfigError( "common_overrides sets Gym entry 'code_gen', which shard 'code' claims. " "Move it under that shard's 'overrides'." ) # 2. config_paths written into an override layer # shard 'math' overrides: {config_paths: [x.yaml]} — dropped silently today raise ShardConfigError( "shard 'math' sets 'config_paths' in 'overrides'; use the shard's own " "config_paths field." )

Both are cheap: the parser holds claims and the entry list already, and neither check needs a Gym import or a running actor.

So what. The parser guarantees each Gym entry is claimed by exactly one shard, then two later layers are free to break that guarantee — quietly. Today the cost is a wasted multi-node startup before #3371 notices; a config_paths in the same layer is dropped and never noticed at all. Validating both layers where the claims are computed turns both into a setup-time error, and writes down what an override is actually allowed to set.

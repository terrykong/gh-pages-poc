How a single-controller run becomes one trace, even though its work runs in other Ray actors

Before
Only the sync GRPO path had spans. The single controller, the data plane and NeMo-Gym had none, and no worker call passed on the caller's trace ID.
This PR
Adds spans to the single controller (13 rl.sc.* spans), the data plane and NeMo-Gym. It also sends the caller's trace ID with every Ray call that needs it, so all of them land in one trace.

Two pages on this PR, one question each. This one: what the new trace plumbing does and how it compares to what already existed.

A span is one timed block of work. Spans started inside another span become its children, and a viewer draws them as one waterfall — but only inside one process. A Ray actor is a separate process, so its spans start a new, unrelated trace unless the caller sends its trace ID over. #3655 already did this for one actor, the rollout collector, by passing the ID once, in the constructor. This PR adds a general way: the ID rides along as a hidden keyword argument, _otel_carrier, on every call to a marked method. Both ways end in the same function, remote_trace_context, which makes the received ID the parent of every span opened inside it.

WITHOUT the ID — the same new spans would form 5 unrelated traces trace A rl.data_plane.* (policy worker 0) trace B rl.data_plane.* (policy worker 1) trace C rl.gym.run_rollouts (prompt group 0) trace D rl.gym.run_rollouts (prompt group 1) trace E rl.gym.run_rollouts (prompt group 2) WITH the ID (this PR) — 1 trace rl.sc.job └─ rl.sc.step ├─ rl.sc.generate_and_push ×3 (one per prompt group, only with span_groups: per_prompt) │ └─ rl.gym.run_rollouts └─ HTTP POST to the Gym server ← ID carried by _otel_carrier, then by aiohttp headers └─ rl.sc.policy_training └─ rl.data_plane.* ×2 ← one per worker, via train_presharded's _otel_carrier

Links: rl.sc.step · rl.sc.generate_and_push · NemoGym.run_rollouts · rl.sc.policy_training · train_presharded

What to take away. The constructor way from #3655 still serves the collector; the per-call way is what reaches workers that many steps share. Both stop at remote_trace_context, so there is one place that decides what "parent" means. The cost is that every new remote entry point needs the decorator on the worker and the kwargs spread at the call site. The PR keeps the two halves in step with source-scanning tests rather than one central dispatcher. The review asks whether RayWorkerGroup could add the ID in one place instead.

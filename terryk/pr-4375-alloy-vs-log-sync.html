How the new Loki log export compares with copying Ray logs to shared storage

Explainer for NVIDIA-NeMo/RL #4375 (opt-in Loki log export via Grafana Alloy). All permalinks pin the PR head cd0beb8.

Before
Ray writes its own logs inside the container, which are lost when the container exits. The only way to keep them was RAY_LOG_SYNC_FREQUENCY, which copies them to shared storage every N seconds.
This PR
Adds RAY_ALLOY_ENABLED=1: a Grafana Alloy process next to each Ray container that sends those logs, plus the wrapper, driver and sandbox logs, to a Loki server as they are written.
Status
Proposed — open PR, off by default. Nothing changes for a job that does not set the flag.
Background. ray.sub starts one container per node with Slurm. Ray's own processes (the per-node daemon, the scheduler, every worker) write their logs under /tmp/ray/session_*/logs inside that container. Loki is a log server; Alloy is the program that reads files and pushes them to it. Dotted words have a short explanation: hover or tap them.

Both options read the same files: the existing log-sync loop copies /tmp/ray/session_[0-9]*/logs/ with rsync (ray.sub:765-780), and the new Alloy source matches the same glob (config.alloy:10-14). They split right after the read. Log-sync writes a copy to the shared filesystem on a timer. Alloy tails each file, tags each line with labels, and pushes it over HTTPS with client certificates (config.alloy:126-160). ray.sub starts Alloy in its own session so it outlives the container's shutdown signal, and stops it on exit (ray.sub:685-708).

Same file in, two different places out

A third, unrelated path already exists: telemetry.logs_enabled sends Python log records from NeMo-RL processes over OTLP (setup.py:322-327). It never reads Ray's daemon files or the wrapper/sandbox logs, which is what both options above cover.

So what. The two options start from the same files and differ only in where the copy goes. Use log-sync when you just want the files on disk after the job. Use Alloy when you already run Loki and want to search every node's logs while the job runs. Both can be on at once. The review asks for a few small changes: a warning when Alloy exits right after starting, turning off its usage reporting, a way to use a config with a different kind of auth, and docs that say how this relates to the OTLP path.

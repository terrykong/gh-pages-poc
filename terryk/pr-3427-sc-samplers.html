How a SingleController sampler picks groups

A suggested figure for the Sampler modes section of docs/guides/single-controller.md · NVIDIA-NeMo/RL PR #3427 @ db0aa28

The thing the table can't show. The guide's sampler table has a "Train selection" column per mode, but the modes aren't three settings of one rule — they key on different fields of the buffer. Until you know which field, the rules read as interchangeable. They aren't: on the same buffer, a group that windowed trains on is one that in_order throws away.

1. Every sampler makes three decisions

A sampler is three methods, called at two different places in the loop:

MethodCalled byQuestion it answers
admitrollout pumpMay I dispatch another prompt batch right now, or must I wait for the trainer?
selecttrain pumpWhich buffered groups may this step train on?
evicttrain pumpWhich groups can never be selected again → drop & free their rows?

2. Two different keys — this is the crux

Each buffered group carries both of these. Which one the sampler reads is what separates the modes:

FieldSet whenMeansUsed by
start_weightat commit, by the producerthe policy version the rollout actually ran underwindowed, weight_fifo
target_stepat admit, by the samplerthe step this batch was reserved for, before it ranin_order only

windowed and weight_fifo ask "how stale is this data?" — a backward-looking question about what already happened. in_order asks "was this earmarked for me?" — a question answered before the rollout even started. Same buffer, different question, different answer.

4. The admit gate: how far rollout may run ahead

With in_order and max_lookahead_versions: 0 the gate blocks until dispatch_index == trainer_version, so batch N is dispatched only once the trainer reaches step N, and its target_step stamp guarantees only step N can consume it. That is exactly the on-policy/sync recipe — and it's why is_on_policy is derived from the eviction window being 0 rather than being its own flag.

5. Three behaviours the table doesn't hint at

sample_freshest_first changes which groups you train on, not just their order
On the buffer above, windowed with the default false takes buffer order → B, C, D. With true it sorts by lag and takes D, E, B — a different set, because the cap bites after the sort. L249
weight_fifo can stall on a weight that has no ready groups
Its in_window scan does not filter on ready, so an uncommitted slot at weight 4 still sets target_version = 4; the ready-filtered pass then finds nothing and the step returns (None, 0). That is the documented "waits for that weight's batch to fill" behaviour — worth saying out loud, since it looks like a deadlock in a log. L320-330
in_order must override evict, or evict and select would disagree
The default evict drops by start_weight; in_order selects by target_step. If it inherited the default, a group whose target step is still upcoming (like E) could be evicted early for being weight-stale. It overrides evict to key on target_step so the two always agree. L376

Three pages on the SingleController path, one question each — this one: which finished rollouts a step trains on.

Rollouts for one step do not finish together — a long generation can outlive the weights it started from. Every sampler is one answer to "what do I do with a group that finished at an awkward moment?" Run three training steps and the buffer already holds five groups that five rules sort four different ways.

A run, three steps in

num_prompts_per_step = 2, so prompts go out two at a time and a step trains on at most two groups. max_lookahead_versions = max_staleness_versions = 1, so generation may run one batch ahead of the trainer and the window the window-based modes select from is [2 − 1, 2] = [1, 2]. The trainer will run a step on as few as one group, because min_groups_for_streaming_train is set below num_prompts_per_step. That last one is a streaming setting — both shipped in_order recipes instead set the two equal, which changes what in_order does here. More on that below.

How the run got here
At weight 0 the gate lets two batches out at once, which fills all four slots: A and A′ for step 0, P and Q for step 1. A′ lands early and A does not, so step 0 trains on A′ alone — that is what min_groups_for_streaming_train below num_prompts_per_step buys you. Freed slots take the next batch, B and C for step 2. Step 1 gets both of its groups and the trainer reaches weight 2. Batch 3 (D and E) is allowed out but has to wait for a second free slot, so slot 4 idles until C lands. Then A finally lands, after running the entire time — two weight versions late, with the step it was meant for long gone.

Why in_order and weight_fifo agree here
They agree most of the time. start_weight and target_step are both stamped when the batch is dispatched, so "the batch meant for step 2" and "the oldest weight still in the window" usually name the same groups. They come apart when a weight bump lands part-way through reserving a batch, or when a batch is dispatched with no lookahead left to use. Note the small asymmetry in weight_fifo: it picks the target weight from every slot in the window, ready or not, so unready B pins the target at weight 1 and D and E wait even though they are sitting there finished (L528-540).
Why every step here is short — and the only reason in_order throws A away

min_groups_for_streaming_train is the floor. Set it below num_prompts_per_step and _finalize_selection hands back whatever is ready, so step 0 runs on A′ alone rather than waiting for A.

That is the only thing that makes in_order evict. A group's target step is stamped once, at dispatch, and never updated. As long as every step waits for its whole batch, no stamp can ever fall behind the trainer, so nothing is ever stale. Let a step close early and the stamps it left behind point at a step in the past, which select can never match again — so evict drops them.

Both shipped in_order recipes set the floor equal to num_prompts_per_step (min_groups_for_streaming_train: ${grpo.num_prompts_per_step} in the async exemplar and the sync one), so as shipped in_order wastes nothing: step 0 would have waited for A and trained on A + A′. The cost is the mirror image — the trainer idles on the slowest rollout in every batch. The run drawn above turns that floor down so all five modes can be compared side by side on one buffer.

Pick ready_first when throwing away rollouts is the thing you cannot afford. It is the only mode whose evict never drops anything: a group that lands late is still trained on, however far behind it is. The price is that its staleness has no bound — A was generated two weight versions ago and is used anyway. That is why setup makes ready_first require loss_fn.use_importance_sampling_correction: true and force_on_policy_ratio: false at any staleness setting, unlike the other modes, which only need the correction once you raise their staleness knob above 0 (config.py L1185-1195). Also note in_order is still the only mode PPO accepts (config.py L1117).

Three pages on the SingleController path, one question each — this one: which finished rollouts a step trains on.

Rollouts for one step do not finish together — a long generation can outlive the weights it started from. Every sampler is one answer to "what do I do with a group that finished at an awkward moment?" The answers split into two families: wait for it, or move on and maybe throw it away. in_order waits. The others do not.

A run, three steps in

num_prompts_per_step = 2, so prompts go out two at a time and a step trains on at most two groups. max_lookahead_versions = max_staleness_versions = 1, so generation may run one batch ahead of the trainer and the window the window-based modes select from is [2 − 1, 2] = [1, 2]. The run below uses a streaming floor — min_groups_for_streaming_train below num_prompts_per_step, so a step will run on as few as one group. That is what the streaming modes are built for. in_order ships with the floor set to the full batch instead, so it behaves differently here — that is the bottom row of the figure.

The whole trade, in one line
in_order never wastes a rollout and never trains on a stale one — and pays for it with an idle trainer. Every other mode keeps the trainer fed and pays somewhere else: weight_fifo and windowed throw away whatever fell out of the weight window, and ready_first throws away nothing but trains on data of unbounded staleness. There is no mode that waits for nothing and wastes nothing.

The floor is what decides whether a sampler waits

min_groups_for_streaming_train is the smallest number of groups a step will run on. Set it equal to num_prompts_per_step and _finalize_selection returns None until the whole batch has landed — the trainer blocks. Set it lower and the same code hands back whatever is ready, so the trainer keeps moving and stragglers get left behind.

Both shipped in_order recipes set it to the full batch (min_groups_for_streaming_train: ${grpo.num_prompts_per_step} in the async exemplar and the sync one), which is why the "stalls" reading is the right one to carry around. Turn the floor down and in_order would take C alone and then evict A, since the stamp is written once at dispatch and can fall behind a trainer that moved on without it (evict L606). No shipped recipe does that, so treat in_order as the mode that never throws anything away.

Why weight_fifo looks so close to in_order
start_weight and target_step are both stamped when the batch is dispatched, so "the batch meant for step 2" and "the oldest weight still in the window" usually name the same groups. The difference is what happens when one of them is late: weight_fifo takes whatever of that weight is ready and moves on, while in_order waits. Note the asymmetry that keeps weight_fifo partly in the waiting camp: it picks the target weight from every slot in the window, ready or not, so unready B pins the target at weight 1 and D and E wait even though they are sitting there finished (L528-540).
Pick ready_first when throwing away rollouts is the thing you cannot afford, and you cannot afford to wait either. It is the only mode whose evict never drops anything while still never blocking: a group that lands late is trained on, however far behind it is. The price is that its staleness has no bound — A was generated two weight versions ago and is used anyway. That is why setup makes ready_first require loss_fn.use_importance_sampling_correction: true and force_on_policy_ratio: false at any staleness setting, unlike the other modes, which only need the correction once you raise their staleness knob above 0 (config.py L1185-1195). Also note in_order is still the only mode PPO accepts (config.py L1117).

Context compaction, redesigned: the row cut moves from "after the rollout" to "inside the vLLM worker"

Explainer for NVIDIA-NeMo/RL #4124, paired with NVIDIA-NeMo/Gym #3368. RL links pin c617a2c; Gym links pin the Gym PR head b27e0db, or 17abf2d (Gym main) for code the Gym PR deletes.

Before
NeMo-RL main has no context compaction. An earlier design (never merged) had Gym send every call's full prompt tokens, and RL found the cuts afterwards.
This PR
The agent still decides when to compact, and it tells RL nothing about it. RL's vLLM worker detects the effect on each call: if the new request no longer extends the previous call's history, that call starts a new row. RL rebuilds the rows from ordinary Gym output.
Status
Proposed — open PR, not merged. It needs Gym #3368 merged and the Gym pin bumped first. Review findings are in the PR's review comments.

Five pages on this PR, one question each. This one: how the new design differs from the earlier one.

Background. A harness is the agent loop in Gym that talks to the model. On a long multi-turn task its prompt grows every turn, mostly from screenshots. Context compaction means the harness sometimes rewrites its prompt, for example by replacing old images with the text "[Earlier image omitted]". After a rewrite the new prompt no longer starts with the old one, so the two cannot share one training sequence, and one rollout becomes several training rows. TransferQueue is where the new design keeps the tokens. Dotted words have a short explanation: hover or tap them.

Both designs end with the same rows. The example below is one rollout of 5 turns, with a rewrite after every 2 actions that keeps only the newest image. It gives 3 rows: turns {1,2}, {3,4} and {5}. In each row, only the tokens the model sampled carry gradient. In both designs the agent decides when to compact. The difference is who turns that rewrite into a row boundary, when, and from what evidence. In the new design that decision is one short function, decide_capture_input. It runs inside the vLLM worker before generation starts.

Same 5 turns, two ways to find the cut

The new check runs before any tokens exist, so it cannot compare tokens. Instead it compares the harness's own messages. Gym hashes the messages of every call it served and stores that hash as a ReplaySummary. The worker hashes the start of the new request the same way. If the hashes match and the request only adds user or tool messages, it is a continuation: the worker reuses the parent's exact sampled tokens and stores only the new part. Otherwise, including a request shape the worker cannot splice, it is a new root: the request is rendered from scratch and stored in full. The harness sends only messages: no tokens, no segment IDs and no parent hint. Gym proposes the earlier call whose history the new request extends (Gym sink.py L352-388), and the worker checks that proposal.

What you gain, and what you give up

  • Gain — rows are exactly what was served. A continuation reuses the parent's sampled tokens instead of rendering them again, so a template quirk can never create a false cut or a row the model did not see.
  • Gain — much less data moves. The earlier design repeated the full prompt on every call. Here only a rewrite repeats it.
  • Gain — any harness. Gym no longer needs a special response type, so a harness keeps its own compaction policy and its normal output.
  • Give up — the second opinion. The cut now depends on one hash comparison, not a token test checked against Gym's own rewrite list. Fields the hash ignores (item IDs, the JSON spacing of tool arguments) count as "unchanged". An edit to only those fields never reaches the model. Training is still exact, because it uses the tokens that were served.
  • Give up — tolerance. A kept image whose processed pixels changed on a continuation is now an error, where the earlier design opened a new row. The harness must also return its full accepted history, or the earlier rows cannot be found.
  • Open issue — a dropped prompt group ends the whole run. A failed model call now masks only its own rollout, and its siblings still train. But when no agent result comes back (a timeout, a transport error, or an error raised inside the agent such as a context-guard rejection), or every rollout in the group fails, the whole group is dropped. Compaction requires every group in a step (config.py L1437-1438) and never replaces a dropped one, so the run stops.

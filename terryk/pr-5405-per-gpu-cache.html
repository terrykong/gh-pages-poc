Why a warm start crashed the vLLM engines on GPUs 2-3, and how one compile folder per GPU fixes it

NVIDIA-NeMo/RL #5405 · permalinks pinned to head def85037 · vLLM 0.33.0 (4ba787ec)

Before
With persistent compile caches on, the second job crashed every vLLM engine that was not on the first GPUs of its node.
This PR
Adds the GPU index to vLLM's compile cache folder names, so each GPU keeps its own compiled code.
Status
Fixed by this PR. The review found no bug in the fix. It asks for tests that fail if the fix is undone, and two PR description edits.
Background. NeMo RL can keep compiled model code between jobs (persistent compile caches). Each vLLM engine compiles into its own folder. A background script then merges all engine folders into one node copy, and the next job starts every engine from that copy, which skips about 11 s of compiling per engine. Dotted words have a short explanation: hover or tap them.

Two engines with TP=2 share a 4-GPU node: engine A on GPUs 0-1, engine B on GPUs 2-3. Both have a rank 0 and a rank 1. vLLM names each rank's compile folder rank_{rank}_{dp_rank} (backends.py#L1105, decorators.py#L593), with no GPU in the name. But the compiled code has the GPU index written into it (torch.cuda._DeviceGuard(2)). Since vLLM 0.33 the folder above it no longer depends on GPU placement either (envs.py#L2384), so A's and B's rank 0 land in the same path.

The fix, as pseudocode

Where the fix lands: NeMo RL only, two files. patches.py adds the patch; compile_cache.py runs it on every node of the engine. No vLLM change: the patch rewrites two lines of the installed vLLM on disk, until vLLM puts the GPU index in the name or the hash itself.

In vLLM, before

# GPU worker process (one per GPU), while compiling the model
hash   = sha256(env, config, code, compiler)[:10]           # no GPU placement since vllm#61211
folder = f"{root}/torch_compile_cache/{hash}/rank_{rank}_{dp_rank}"  # same path on GPU 0 and GPU 2
load_or_compile(folder)                                     # warm start: may load code for cuda:0

In vLLM, after the patch (both files)

# GPU worker process; the worker already set its GPU in init_device
hash   = sha256(env, config, code, compiler)[:10]
folder = f"{root}/torch_compile_cache/{hash}/rank_{rank}_{dp_rank}"
folder = f"{root}/torch_compile_cache/{hash}/rank_{rank}_{dp_rank}_dev{torch.cuda.current_device()}"
load_or_compile(folder)                                     # the code always matches this GPU

Real code: backends.py#L1105 (torch.compile cache), decorators.py#L593 (AOT compile cache), gpu_worker.py init_device (sets the GPU first).

In NeMo RL, where the patch is applied

# vLLM engine actor, just before it builds the engine
prepare_vllm_engine(bundle_indices)         # one Ray task per node of the engine; waits for all (ray.get)
create_engine(...)                         # only now do vLLM's GPU workers start and import vLLM

# Ray task, once per node
def _prepare_vllm_engine_on_this_node(engine_dir):
    patch_compile_cache_per_device()        # under a file lock; skip if done; raise if vLLM changed
    seed("vllm")                                  # copy the shared cache onto this node once
    copy node copy → engine_dir                   # this engine's own folder

Real code: _patch_vllm_compile_cache_per_device, _vllm_patches (loads patches.py by path, so the per-node task does not import NeMo RL's generation code).

What the review asks (open)

The review checked the fix against vLLM 0.33.0 and found no bug: each anchor matches once, the GPU is set before the folder is named, and the patch finishes on every node before vLLM's workers start. What is missing is tests that fail if the fix is undone.

  • C3 · Two CPU tests. Today no test fails if backends.py is dropped from the patch (the torch.compile cache would be shared again), or if the "vLLM changed" raise is removed. Both proposed tests pass on head and fail on each of those changes.

    🔴 review comment — test_vllm_patches.py:410

  • C4 · Check the patch actually runs. Deleting the call in _prepare_vllm_engine_on_this_node keeps CI green; the test stubs it and never checks the stub ran.

    🔴 review comment — test_compile_cache.py:164

  • C5 · PR description. It still says the bug starts in vLLM 0.32 (it is 0.33), and the cost sentence should say about 33 MB per GPU.

    🔴 review comment — patches.py:108

So what. With persistent compile caches on, a node can now run several TP engines and every one of them gets a warm start. The price is one extra compiled copy per GPU of the node. The asks above only make sure CI notices if someone later undoes the fix.

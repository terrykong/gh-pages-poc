Background
A long generation that is cut at a checkpoint saves its tokens so far as extra TQ rows, called prefix rows. When the call later finishes, it writes one final row and the prefix rows are no longer needed. Deleting them is only unsafe while a snapshot is being saved, because the snapshot may still name them. Dotted words have a short explanation: hover or tap them.

Three ways to delete the old prefix rows

Same example in each lane: a checkpoint fence starts while one call is finishing. Today, the delete (sink.clear) runs inside the gate (base code). This PR moves it to BackgroundPrefixCleanup. C30 drops the gate on final-row writes and saves the delete for the start of the next snapshot.

This PR's gain is a shorter fence: 7.93 s down to 2.55 s at depth 128. C30 keeps final-row writes and deletes out of the fence entirely. It also batches harder: one delete per worker per snapshot, not one per 32 calls. It uses the cleanup executor the stack already has, so it needs no new thread and no settings.

The cost: a checkpoint can include old prefix rows that are still waiting in the list, and a worker restart drops the list. The next restore removes those rows (clear_unreferenced=True). The abort path already works this way today.

One filter to keep: a restored call's final row (from the base PRs)

A call restored from a terminal-completion cut carries its own final row's key in the same list as its prefix rows (ack → restore). This PR filters that key out on completion only. Abort and failed restore still delete it. A test that aborts such a call fails at this head: the delete list holds 'r0/c0', the final row.

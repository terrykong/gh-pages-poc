Who owns the tensors a worker just fetched?

On NVIDIA-NeMo/RL #4107. All links pinned to 4fb9fbc.

Before
Every read from the store handed back a fresh copy, so what a training worker did to a batch stayed in that worker.
This PR
Drops the copy and returns the stored object itself. That is the speedup, and for plain tensors it is safe.
Status

Three pages on this PR, one question each — this one: what a worker can accidentally do to the store.

First, what “the store” is. It is an ordinary Python dictionary, held by LocalDataPlaneClient, that maps a field name to that field's value — {"input_ids": <a Tensor>, "pixel_values": <a PackedTensor>}. No file, no network, no separate process: the data worker builds those values and the dictionary keeps them alive so a training worker in the same process can pick them up. Handing them over used to mean copying them. This PR stops copying, which means both sides now hold the same objects.

Why one field escapes and the other does not

After step 3 there are two dictionaries pointing at one set of objects: the store's and the worker's. What happens next depends on a single thing — whether .to("cuda") builds a new object or edits the one it was given.

The difference in one line each: PackedTensor.to does self.tensors = [...]; return self — it edits itself. Tensor.to is a normal PyTorch call that returns a new tensor and leaves the old one alone.

Why nothing fails today, and the one-line fix

Step 4 is the catch: the top-level data.to("cuda") lives in the DTensor worker, and this data never reaches it. sft_v2.py:399-400 raises "SFTv2 supports only the Megatron policy backend.", and the Megatron worker never moves a whole batch — it goes to get_microbatch_iterator and moves slices it built itself. The configs agree: exactly one shipped config asks for this store (impl: local), and it sets megatron_cfg.enabled: true. It is not in the nightlies; it runs as sft_v2_energon.sh in the L1 SFT suite.

So this is a hazard, not a failure. Nothing below is implemented — this is the change suggested in review. Let the shortcut at step 3 skip PackedTensor, so it falls through to the branch below, which already builds a new wrapper:

# nemo_rl/data_plane/adapters/local.py:104 - if _is_identity_indices(indices, _value_batch_size(value)): + if not isinstance(value, PackedTensor) and _is_identity_indices( + indices, _value_batch_size(value) + ): return value

The worker then gets its own wrapper, so panel B starts looking like panel A. The images are still shared, so nothing is copied — slice puts the same image tensors into a new list.

The fix costs less than the copy it replaces. Measured on one machine's CPU, so read it as a ratio, not as throughput: on a 64-row value holding 86.7 MB of images, slice takes about 0.001 ms against about 3.2 ms for the deepcopy this PR deletes. Plain tensors skip the check and keep the full speedup.

Who owns the tensors a worker just fetched?

On NVIDIA-NeMo/RL #4107. All links pinned to 4fb9fbc.

Before
The process-local store handed out a fresh copy of every field, so anything a worker did to a fetched batch stayed inside that worker.
This PR
Drops the copy and hands back the store's own objects, to save the copying cost. That is the point of the change, and for plain tensors it is safe.
Status
Open — not fixed in this PR. No code path fails today; the one type that would break it is not reachable yet. Raised in review on #4107.

Three pages on this PR, one question each — this one: what a worker can accidentally do to the store.

Workers read training batches from a small in-process store. Before this PR, a read copied every field on the way out. This PR removes that copy: when a worker asks for every row it already has, _select_batch_value returns the stored object itself, and put_samples now keeps whatever the writer handed it. The worker then moves the batch to the GPU with BatchedDataDict.to(). That last step treats two kinds of value differently, and only one of them leaves the store alone.

The same fetch, two kinds of field

Both lanes are the same call. The loop in batched_data_dict.py:1115-1122 picks a branch by type, and lines 1119 and 1121 are the same text — the whole difference is inside each .to(). multimodal_utils.py:734-737 is the one that rebinds its own list and returns self.

Why nothing fails today

The only shipped writer to this store is Energon vision-language SFT, and that path is pinned to one backend: sft_v2.py:399-400 raises "SFTv2 supports only the Megatron policy backend." The Megatron worker cuts each batch into microbatches before moving anything, so its .to() lands on a slice it made itself, never on the stored object. The worker that does make the plain top-level data.to("cuda") call is the DTensor one, and no shipped config can route this data to it.

So this is a hazard, not a failure. It costs nothing today, and it starts costing the day someone lifts that one-backend limit. There is also a written assumption it now breaks: the docstring on PackedTensor.to argues that a bad device move cannot happen, and one of its reasons is that worker-side moves “happen post-serialization on independent copies.” The copy this PR deletes is what made them independent.

What would fix it — proposed, not in the PR

Nothing below is implemented. This is the change suggested in review.

Let the shortcut apply to everything except a PackedTensor, so that one type falls through to the branch just below it, which already builds a new wrapper:

# nemo_rl/data_plane/adapters/local.py:104 - if _is_identity_indices(indices, _value_batch_size(value)): + if not isinstance(value, PackedTensor) and _is_identity_indices( + indices, _value_batch_size(value) + ): return value

One line. PackedTensor then reaches value.slice(indices) instead.

The speedup survives, because slice shares the image data rather than copying it:

# what the worker gets back after the change fetched = store.slice([0, 1, 2, 3, 4]) fetched is store False # a new wrapper — the store is safe fetched.tensors[0] is rows[0] True # same image data — nothing was copied # and after the worker moves its batch to the GPU: store.tensors[0].device cpu # the store never followed it

multimodal_utils.py:812 appends self.tensors[physical_index] — the same tensor object, into a new list.

The fix is cheaper than the copy it replaces. Measured on one machine's CPU, so read these as a ratio and not as throughput: for a 64-row value holding 86.7 MB of images, the new slice call takes about 0.001 ms, while the deepcopy this PR removes took about 3.2 ms. Plain tensors skip the check entirely and keep their full speedup. Taking this line does not give back what the PR was for.

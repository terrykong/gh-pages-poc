How a faster MXFP8 kernel can keep its own weight layout and still take new weights every step

NVIDIA-NeMo/RL #3638 — links pin head 83c655cb and vLLM v0.29.0.

Before
Asking vLLM for its CuTeDSL dense kernel was silently replaced with CUTLASS, and the TRTLLM dense kernel failed with Unsupported MXFP8 linear kernel for refit. Only CUTLASS could take new weights.
This PR
Keeps an explicitly chosen CuTeDSL or TRTLLM kernel, and copies each step's new weights into it through vLLM's layerwise reload. The default (auto) still uses CUTLASS.
Status
New opt-in feature; works as described. Both kernels pass the GB200 refit test with CUDA graphs on. A side change in this PR has a separate bug: see page 2.

Background. In RL training the rollout engine (vLLM) gets new weights from the trainer every step; that copy is the refit. vLLM records CUDA graphs that read the weights at fixed GPU addresses, so a refit must write new values into the same tensors, never swap in new ones. Dotted words have a short explanation: hover or tap them.

After loading, every MXFP8 dense kernel may rearrange the weight into the layout it reads fastest. CUTLASS keeps the trainer's layout, so a refit can write straight into its tensors. The two kernels this PR enables do not: CuTeDSL stores the weight transposed, and TRTLLM pads the rows to a multiple of 128, shuffles them, and flattens the scale. So the PR routes these layers through vLLM's layerwise reload: load into a temporary trainer-layout copy, let the kernel rearrange it, then copy the result into the tensors the graph reads.

One dense layer, one refit, both paths

Example layer: weight [4, 256] = [output rows, inputs], one FP8 value each; scale [4, 8] = one 8-bit scale per 32 inputs (256 / 32 = 8).

The split is one check in _uses_native_layerwise_refit: it is true when the model has layers whose kernel uses_native_mxfp8_linear_refit recognizes. Those layers join the same reload as the BF16 TRTLLM MoE experts that already used it, in one pass, so neither group undoes the other's layout. If a reload fails halfway, _abort_layerwise_reload puts the set-aside tensors back and the worker refuses further refits.

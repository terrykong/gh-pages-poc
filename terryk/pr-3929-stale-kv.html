What happens to a half-finished request when the training weights change under it

NVIDIA-NeMo/RL #3929 · all links pinned at ae0ca278 · the same feature on the legacy path is #3839

In async RL the model trains and generates at the same time. Every training step copies fresh weights into the generation engine — that copy is called a refit. Requests that are only part-way through generating do not stop for it. Each of those requests carries a KV cache: the saved attention state for every token so far, computed with whatever weights were loaded at the time. So after a refit, a request keeps decoding with new weights while reading a cache built by the old ones. NeMo-RL has a flag meant to deal with this, recompute_kv_cache_after_weight_updates. On the SingleController path it did nothing.

The old behavior

The flag's old path called vLLM's reset_prefix_cache() with no arguments. In vLLM v0.25.1 that resets the shared prefix cache only when nothing is running — its own docstring says it "will only reset the KV prefix cache when there is no running requests taking KV cache." During async RL something is always running, so it returned False and changed nothing. Two layers then hid that: the NeMo-RL worker method has no return statement, so every result was None, and the caller's all(...) ran over an empty sequence and reported True.

sources — vLLM scheduler.reset_prefix_cache · the no-argument call · the all(...) over nothing

What the PR changes

Instead of trying to clear the cache after the refit, the controller now freezes the engine before it. Same request, same 9 tokens:

# 1. the controller asks the engine to pause, and passes the flag straight through clear_cache = self._async_cfg.recompute_kv_cache_after_weight_updates # True await asyncio.to_thread(self._gen.pause_generation_for_refit, clear_cache=clear_cache)

single_controller.py:3113-3117

# 2. each engine worker calls vLLM's own pause, in "keep" mode await self.llm.pause_generation(mode="keep", clear_cache=clear_cache) # mode="keep" -> the request is frozen, not cancelled: it resumes later # clear_cache -> True, so the 7 cached tokens are thrown away now

vllm_worker_async.py:1616

# 3. inside vLLM: this path DOES touch running requests, unlike the old one reset_prefix_cache(reset_running_requests=True) # the old call left this False # every running request is preempted back to the waiting queue, # which drops its KV to a reference count of 0 -- the 7 boxes are gone. # on resume the request re-reads its 7 tokens with v1, then decodes 8 and 9.

vLLM core._reset_caches · the preempt loop

The refit runs while everything is frozen, then resume_generation_after_refit() unfreezes it. The request never dies — it just loses time and recomputes 7 tokens. Backends that cannot pause keep their old behavior, and if you asked for recomputation on one of those, the run now stops with an error instead of quietly doing nothing.

Does it work?

The author ran the full 8B GRPO recipe twice on 16×H100 (2 nodes), 10 optimizer steps each, 64 prompts × 32 generations, batch 2048, sequence length 4096 — once with recomputation on and once off. Both finished cleanly.

That is a real run, and it covers the case this PR is for. It does not cover what happens when a generation worker is broken at the moment the pause is requested — no shard was killed in either run.

What to watch out for. If you set recompute_kv_cache_after_weight_updates=true on the SingleController path before this change, you were not getting recomputation — you were getting a success message. Any earlier result that assumed fresh KV after a refit was really running on stale KV, so it is worth re-checking before comparing against a run built on this PR. The freeze also costs wall-clock: a request now waits for the refit and then recomputes the tokens it had already done.

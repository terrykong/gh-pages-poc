Fixed by this PR. Both cache modes now behave as documented. Open problems on the failure path are page 2.

Two ways to handle the cache, and both are legitimate

In async RL the model trains and generates at the same time. Every training step copies fresh weights into the generation engine — that copy is a refit. A request that is only part-way through generating carries a KV cache: the saved attention state for every token so far, computed with whatever weights were loaded at the time. After a refit that saved state is out of date, and there are two accepted answers to what you do about it. NeMo-RL names them both in its own code.

ModeSettingWhat it does
Magistralrecompute_kv_cache_after_weight_updates: false Keep the stale cache. Cheaper; the request finishes using attention state from the old weights.
AREALrecompute_kv_cache_after_weight_updates: true Throw the cache away so it is rebuilt with the new weights. Costs a recompute; more correct.

the two names come from the repo — trajectory_collector.py:1121-1122

Both should work. The bug was that on SingleController you got Magistral behavior no matter which one you picked.

What you actually got when you asked for AREAL

Asking for AREAL called vLLM's reset_prefix_cache() with no arguments, which defaults to reset_running_requests=False. Upstream only clears the cache in that case "when there is no running requests taking KV cache" — and in async RL something is always running, so it did nothing and returned False. That False was then lost twice: the NeMo-RL worker method has no return statement, so every result was None, and the caller's all(...) ran over an empty sequence and reported True.

What the PR changes

Same request, same 9 tokens. The flag is now handed to the engine's own pause:

clear_cache = self._async_cfg.recompute_kv_cache_after_weight_updates # True for AREAL await asyncio.to_thread(self._gen.pause_generation_for_refit, clear_cache=clear_cache) # ... the weight swap happens here, with generation frozen ... await asyncio.to_thread(self._gen.resume_generation_after_refit)

single_controller.py:4587-4642

await self.llm.pause_generation(mode="keep", clear_cache=clear_cache) # mode="keep" -> the request is frozen, not cancelled: it continues later # clear_cache -> True reaches reset_prefix_cache(reset_running_requests=True), # which preempts the request and drops all 7 cached tokens. # False keeps them: that is Magistral, and it still works.

What to do about older results. If you ran SingleController + vLLM with recompute_kv_cache_after_weight_updates=true before this change, you were not getting AREAL — you were getting Magistral with a success message. Any comparison that assumed a fresh cache after a refit was really measuring stale-cache behavior, so it is worth re-checking before putting it next to a run built on this PR. The freeze also costs wall-clock: in AREAL mode a request now waits for the refit and then recomputes the tokens it had already done.

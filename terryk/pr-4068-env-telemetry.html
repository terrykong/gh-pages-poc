How PR #4068 splits rollout metrics by environment, and why the step median changes

NVIDIA-NeMo/RL #4068 · all permalinks pin the PR head 88ea1ab.

Before
The single-controller path logged rollout metrics for the whole step only. To get a step's median, standard deviation or percentile, the shared reducer averaged the per-group values.
This PR
Tags every rollout with its environment. Logs each metric again under environment/<name>/, plus per-environment sample counts. Computes medians, standard deviations and percentiles from all the step's raw values.
Status
Open PR, not merged. It conflicts with main and has review comments to address (see the last section).
Background: in the single-controller (SC) path, rollouts arrive as prompt groups (one prompt, several sampled answers). Each training step picks some finished groups from a buffer. Each group carries its own metrics, and one shared function, aggregate_rollout_metrics, merges them into the step's numbers. The older (V1) async GRPO loop and PPO call the same function. Dotted words have a short explanation: hover or tap them.

Each rollout now carries its environment name. The native path uses the task name (rollout_manager.py:594). The Gym path uses the agent the row was routed to (:1112). Each group writes every metric twice, once globally and once under its environment. It also writes the raw values (a histogram) and a sample_count (:1688). The step reducer then joins the raw values of all chosen groups and computes the statistics once (grpo.py:4525-4580).

One step, three groups: old and new step statistics

Where the environment name goes, and the per-environment counts

  1. Rollout. The environment name is cleaned for use in a metric path. Unsafe characters become _, plus a short hash so two names never merge (rollout_environment_metric_component).
  2. Training row. The name is stored as a rollout_environment tag on every row (payload.py:179). Rows saved by an older checkpoint have no tag and count as unknown.
  3. Trainer. environment_sample_counts reads the same final masks the loss uses (single_controller.py:5046). It logs num_samples, num_mask_sample_filtered, num_valid_samples and num_valid_tokens per environment. Logging only: masks, rewards and advantages do not change.

What to expect, and what is still open

On dashboards: after this merges, step medians, standard deviations and p95/p99 can shift for SC, async GRPO and PPO runs. That shift is the fix, not a regression: the old numbers were averages of per-group values. Means stay the same when every group has the same number of answers.

Which experts the trainer replays for the last token of each turn

NVIDIA-NeMo/RL #4610 (router replay with token capture, multi-turn), which also closes #4355. All permalinks pin the PR head 8df2f08.

Before
In a multi-turn rollout, the last token of every assistant turn except the final one was trained with made-up experts 0, 1, …, k−1 instead of the ones vLLM actually used. No metric showed it.
This PR
Each later vLLM call also keeps the route it computed for the previous turn's last token, and that route is written into the training row. Rows with no route are now marked −1, which is what #4355 asked for.
Status
Fixed by this PR. Only runs with token capture + router replay + more than one vLLM call per rollout were affected.

Two pages on this PR. This one shows which route p4 gets. Page 2 covers the row count each call stages, and why Megatron Inference (#4307) breaks after this PR.

Background. In a mixture-of-experts model, each token is sent to a few "experts" per layer. Router replay makes the trainer use the same experts vLLM chose. With token capture, each vLLM call saves only its new tokens' routes, and the pieces are joined later. Dotted words have a short explanation: hover or tap them.

vLLM records a token's experts only when the token is fed into the model. Each call returns routes for its whole sequence: the prompt (computed during prefill) and the generated tokens, joined at utils.py. The last token it samples is never fed in, so a sequence of length S comes back with S−1 routes. NeMo-RL used to fill that last row with 0, 1, …, k−1 (utils.py, before). The next turn's vLLM call does feed that token in, so it has the real route — but the old code kept only the call's new rows, experts[prev_len:] (vllm_worker_async.py, before), and threw the real route away.

The fix

Where the fix lands: RL only. The vLLM worker keeps one extra row, the route plan records it, and the route assembler writes it into the row. No Gym change: Gym stores and hashes routes as an opaque value and never checks their length (compute_extras_digest).

  1. boundary_route_rows(prev_len) is 1 for every call after the first, 0 for the first. Call 2 has prev_len = 5, so it keeps experts[4:]: 6 rows, p4–p9.
  2. The finalizer records that extra row in the plan as RouteSpan.boundary_rows (set here), and the plan's schema version goes from 2 to 3.
  3. When the row is put together, span 2 starts at position 5. Its first row goes to position 4, the last token of call 1, and the other 5 rows fill p5–p9 as before.

It also closes #4355: "no route" is now −1, not 0, 1, …

#4355 reported the same symptom from the other side. vLLM's filler for the last token was experts 0, 1, …, k−1. That looks like a real route, so the trainer replays it. The issue asked for −1 instead, the value Megatron inference already uses: on a −1 row the trainer picks the experts with its own router (fallback patch). The third hunk above, in pad_and_align_routed_expert_indices, is exactly that change. The second hunk goes one step further for p4:

The real route is better than −1 at p4. p5–p9 were generated while reading vLLM's version of p4, so replaying the experts vLLM used keeps training and inference the same. With −1, the trainer's own router could pick different experts there.

What changes for a run. In a token-capture run with router replay, every assistant turn except the last one trained its final token with experts 0, 1, …, k−1. That token's hidden state is also read by every later token through attention. After this PR it gets the experts vLLM actually used. Token-echo rollouts already did this (nemo_gym.py), and single-turn rollouts were never affected.

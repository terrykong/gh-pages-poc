Five pages on this PR, one question each. This one: what the shared Gym change does to timing on each path.

Two paths, named the same way on every page. v1 = grpo_train, async_grpo_train, PPO and distillation; each sends a whole batch to a Gym actor as one stream. v2 (single controller) = examples/run_grpo_single_controller.py; it sends one prompt group (one prompt, N answers called rows) per stream. Both call the same Gym actor, so a change to the actor reaches both.
v1v2 (single controller)
Main A failed /run raised inside the actor's stream (_stream_rollouts), so that actor's rows still running were lost. No retry: the rollout failed after the other Gym actors finished. Same raise, same lost rows. The next row attempt sent the lost rows again at once (up to max_row_attempts = 3).
This PR both · shared code The actor asks Gym for a failure row (route_failures_to_sidecar=True) and yields an infrastructure failure as a marker, so the other rows keep running.
Sends the row again at once, but the new setting defaults to 1 try: by default the rollout still fails, and now it also cancels every other Gym actor's stream. Sends the row again only after the rest of the stream finishes, so a group can finish later than on main.
After the review both · shared code As this PR: failed rows come back as markers, so the other rows keep running.
C7 · v1, aligning to v2 rename to max_row_attempts; the default stays 1 (main has no v1 row retry).
C12 · v1 · low when a row runs out of tries, keep draining the other actors, as main did.		 C13 · v2 · top item send the failed row again as soon as its marker arrives, as v1 does. The group finishes no later than on main.

Open. The PR changes both paths. C13 (v2) is the review's top ask; C7 and C12 (v1) are smaller asks.

Why the finish time matters, by path. A later group either holds up a step or trains in a later step, depending on the loop:

PathWhat a later group does
v1 · sync grpo_train, PPO, distillationThe whole step waits for the batch; no group changes step.
v1 · async_grpo_trainEach group is tied to its target step (target_weight_version), so a slow group stalls that step.
v2 (single controller) · in_order sampler (the example configs)Each group is tied to one step (InOrderSampler.select), so a slow group stalls that step.
v2 (single controller) · ready_first, windowed, weight_fifoThe finish time decides which step the group trains in and how stale it is (ReadyFirstSampler). Here the PR's later finish (16 vs 14) can move a group to a later step.

For a verifier that scores a group together (genrm_compare), the PR's own comment says “the siblings wait in /verify for the failed row until the verifier's cohort timeout”, so v2's later re-send makes that wait longer.

review comment C12 — rollouts.py:2690

Recording it as first_failure reuses the existing end of the merge, which raises once every stream has drained (L2709-L2713), and the check at L2682-L2688 then skips retries for later markers. Proposed, not run.

C13 · v2 · top item Send the failed row again as soon as its marker arrives. There is no one-line diff: _stream_rows reads one stream at a time, so it would have to merge a second one-row stream into the attempt, the way v1's _merge_nemo_gym_instance_streams already does. On the example:

# _stream_rows, attempt 1, rows 0..3 in flight
on marker for row 2 at minute 5:      # row 2 has used 1 of max_row_attempts = 3
    continue                           # today: row 2 waits for attempt 2, after row 3 lands at 9
    start a one-row stream for row 2   # proposed: row 2 runs again from 5, lands at 5 + 7 = 12
row 3 lands at 9
group done at max(9, 12) = 12         # main: 14, this PR: 16

Without C13, v2 still works; the cost is the later finish shown above, worst when a row fails early in a long rollout (up to about twice one rollout's time), and a re-sent row that starts on a newer policy than main's would (policy mix in a group). Proposed, not run.

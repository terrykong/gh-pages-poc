Four pages on this PR, one question each. This one: what the shared Gym change does to timing on each path.

Before
A failed /run raised inside the Gym actor's stream (_stream_rollouts, at the base). That ended the stream, so every other row still running on that actor was lost too.
This PR
The actor asks Gym for a failure row (route_failures_to_sidecar=True). _typed_gym_failure sorts the failure. An infrastructure failure becomes a marker, and the stream keeps going. A 4xx that describes the request still raises.
Status
In this PR. It changes both paths, because both use the same Gym actor. The two paths then send the failed row again in different ways, so a group finishes at different times on each. One case on the v1 loop loses more finished work than before (red box below).
Background. A prompt group is one prompt with N answers (rows), each a Gym /run call. The v1 driver loop (grpo_train, async_grpo_train, PPO, distillation) sends a whole batch to each Gym actor as one stream. The single controller sends one prompt group per stream. Both now get a marker for a failed row. What each one does with it is the difference.

One group, 4 rows, row 2 fails at minute 5

The numbers: row 0 takes 2 minutes, row 1 takes 4, row 2 takes 7, row 3 takes 9. Row 2's /run fails at minute 5, and a row sent again takes as long as it did the first time.

On the single controller, the new order is not always slower. It is later whenever the failure happens before the shorter of (the failed row's redo, the slowest sibling) would finish. Here that means before minute 7. A failure early in a long rollout, such as an engine that is already dead at turn 1, is the worst case: the group can take close to twice as long as one rollout.

Why the finish time matters for training

  • Single controller, in_order sampler (the one the exemplar YAMLs use). Each dispatched batch is stamped with the step it is for, and a step takes only the groups stamped for it (InOrderSampler.select: target == current_train_weight). A group that finishes later does not move to another step. The step waits for it, so the cost is a longer stall, not different data.
  • Single controller, other samplers (ready_first, windowed, weight_fifo). These pick from whatever groups are ready (ReadyFirstSampler), so the finish time decides which step a group trains in and how stale it is. Under these samplers, the later finish above changes which data each step sees.
  • v1 async_grpo_train. A group is tied to its target step (replay_buffer.py: “Only returns trajectories with target_weight_version == current_weight_version”), so a slow group stalls the step and does not move.
  • Groups scored together (genrm_compare): the PR's own comment says a re-sent row keeps the group's identity, so “the siblings wait in /verify for the failed row until the verifier's cohort timeout”.
v1 loop at the default budget of 1: one failure now throws away finished work on every Gym actor. When Gym runs as more than one actor (shards or replicas), each actor gets its own stream. Before: a failed stream was recorded as first_failure (base L2538), and the merge kept draining the other actors. On async_grpo_train their finished groups still reached the replay buffer one by one, and only then did it raise. This PR: the marker reaches record_infra_failure, which raises GymTransportError at once inside the merge (L2690). The merge's finally then cancels every stream, including healthy actors whose groups were about to land. With a single Gym actor, nothing changes. Proposed fix, not in the PR: at budget 1, record the failure as first_failure and keep draining, the way a raised stream error is handled.
So what. The Gym change keeps sibling rows alive on both paths, which saves work. The paths then differ: v1 sends the row again right away, while the single controller waits for the rest of the stream first. On the single controller, a group with an early failure can finish later than before the PR. With in_order that makes the step wait longer. With ready-first samplers it moves the group to a later step. Proposed, not in the PR: send the row again as soon as its marker arrives, the way v1 already does, to close that gap.

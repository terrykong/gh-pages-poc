A cleanup call that sits on both sides of the checkpoint barrier

Companion note for NVIDIA-NeMo/RL #3923, and a sibling of the note on giving every data-plane write a cut. All permalinks pin the head 0a93f0f. Nothing here is broken today — it is about what the code stops enforcing.

Writes to the replay buffer and the save that snapshots it must not overlap, or the snapshot records rows the replay index does not know about. A barrier enforces that: many writers may hold a mutation() slot at once, and checkpoint() waits for all of them to drain before it gets exclusive access. The rule is written down — "every live canonical TQ commit/clear and native save must use this barrier". The way a function proves it obeys the rule is to take the cut that mutation() hands out and call require_live() on it, the way _cleanup_known_finalization_request_unlocked(cut, request) does.

The new call opts out of that proof

_validate_rollout_recovery_inventory is new in this PR. It sweeps staged rows nothing references any more, and to do that it issues a live clear_samples. It takes no cut. It never calls require_live(). And it is called from inside mutation() on restore and from inside checkpoint() on save — the two sides the barrier exists to keep apart.

The save-side call passes clear_unreferenced=False, so it does not write today. That keyword is the only thing standing between an exclusive checkpoint and a live queue write, and the signature cannot express which side of the barrier the caller is on.

Why the obvious fix hangs

The natural repair is to wrap the clear in mutation(). That deadlocks on the save path. A nested mutation() joins an outer mutation() by task, but nothing registers checkpoint() the same way — so a mutation() opened inside a checkpoint waits for a checkpoint that is held by its own task. I ran both shapes against this head:

async with b.mutation(): async with b.mutation(): # joins the outer cut, active_mutations=1 async with b.checkpoint(): async with b.mutation(): # never returns. no error, no timeout

→ 1. mutation() inside mutation(): joined, active_mutations=1
→ 2. mutation() inside checkpoint(): HUNG

Is anything broken today?

No, and I want to be plain about that. The save-side call passes False, so no write escapes the barrier on any path that exists right now. I could not construct a config where it does — it would take an edit to that call site.

What the PR gives up is the enforcement. Before this change, a function that mutated the data plane said so in its signature by taking a cut; the barrier's own rule was checkable by reading the parameter list. This function is the first that mutates without that proof, its two callers sit on opposite sides of the exclusivity boundary, and the repair a reader would reach for first hangs the trainer with no error. That combination is worth a guard now rather than a debugging session later.

The cheap version. Give the function a cut: DataPlaneMutationCut parameter and call require_live() on it, exactly like the cleanup helpers beside it. The restore caller already has a cut to pass. The save caller does not and cannot get one — which is the point: it would no longer compile as a mutator, so split the read-only inventory check from the sweep and let the save path call only the read-only half.

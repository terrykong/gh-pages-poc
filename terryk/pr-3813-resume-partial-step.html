What happens to a half-finished training step when an async RL run resumes

Companion illustration for NVIDIA-NeMo/RL #3813 (drop_incomplete_targets_on_restore on the SingleController path). All permalinks pin the PR head 7b09c83.

In async RL, two loops run at once: a rollout pump that generates completions, and a train pump that trains on them. They are joined by a buffer. Under the in_order sampler each group of completions is stamped with the training step it is meant for — the sampler hands out that number when it lets a batch in (single_controller.py:622-624). A step is ready when it holds num_prompts_per_step groups. But a checkpoint only saves groups that have finished generating (replay_buffer.py:971) — so if you checkpoint while a step is still filling, it comes back short. This PR adds a flag that decides what to do about that.

A step comes back short, and there are two ways to finish it

The prompts come from a dataloader whose batch size is one step's worth (setup.py:682-685, with drop_last=True, so every batch holds exactly 6). That is why the default wastes prompts: it needs only 2, takes them from the front of a 6-prompt batch, and throws the other 4 away. It discards as many as it restored — 4 — and that is not a coincidence, it is 6 − 2.

How the flag makes the pump fill the step whole

Two small pieces of code do it, and the second one is the neat part — the flag never talks to the rollout pump at all. It just makes the pump's count come out zero.

Step 1 — at load, with drop_incomplete_targets_on_restore = True target_counts = Counter(g["target_step"] for g in groups if g["target_step"] is not None) # {7: 4} incomplete = {t for t, c in target_counts.items() if c < groups_per_step} # {7} because 4 < 6 kept = [g for g in groups if g["target_step"] not in incomplete] # [] all 4 dropped return len(kept) # 0

replay_buffer.py:1112-1139, returning at :1193. That return value is also how many buffer slots the resume takes (single_controller.py:420), so dropping groups frees their slots too.

Step 2 — the rollout pump, first batch after the resume target_step = 7 buffered = self._buffer.count_for_target_step(7) # 0 (would be 4 with the flag off) if buffered: # 0 is falsy, so this whole branch is skipped num_prompts = max(0, 6 - buffered) # never runs num_prompts = prompt_batch.size # 6 -> dispatch all 6 prompts

single_controller.py:628-638. After the drop the pump takes the same path it takes on a fresh run — it never learns that a resume happened.

Two guard rails come with it. The flag is rejected unless the sampler stamps a target step — in_order, or a custom sampler that stamps (config.py:946-955) — because with no stamps there is no step that could be short, and the flag would quietly do nothing. And the drop runs before the buffer trims an over-full checkpoint, because trimming a step-stamped checkpoint raises instead (replay_buffer.py:1147-1160); dropping first can bring the checkpoint back under the cap.

Does it work?

Yes — the author ran it. Four PPO runs to step 40, same settings: yellow is the old async path as a baseline, red is SingleController run straight through, blue is SingleController resumed from checkpoint 20 with the flag off, and green is resumed from checkpoint 20 with the flag on.

Read it for what it is: this shows the flag does no harm — you can turn it on, resume, and training carries on normally. It does not show a measurable win over the default, because blue and green both converge fine. The spike in step time near step 21 is just the cost of restarting, and it shows up for both resumed runs.

What to know before turning it on. It is off by default, so nothing changes unless you ask for it. Turn it on when you would rather a resumed step be generated all at once than be half old and half new — the default leaves 4 groups made before the crash sitting in the same step as 2 made after it. The cost is extra rollout work: those 4 groups are thrown away and made again. One catch the author calls out — on GRPO, a step that was deliberately shortened by a dropped prompt looks "incomplete" after a resume, so the flag regenerates it in full. That is wasted work, not a stall, and PPO is unaffected.

PR #3591 as it stands: what it adds on top of #3590, what changed since review, and why the weight-copy group is rebuilt rather than shrunk

Status page for NVIDIA-NeMo/RL #3591, part 3/4 of the SingleController resiliency stack. All permalinks pinned to ab0ffe2f. Background: the #3590 page (who watches what) and the earlier #3591 page (how the rebuild works). Hover any box in the figures.

Every training step copies fresh weights from the trainers to the inference engines. That copy — the refit — is one NCCL broadcast over a group spanning every trainer rank and every inference rank, built once at setup. NCCL requires every rank in the group to take part, so one dead inference rank blocks the copy forever: inside NCCL, with no error, no CPU burn, and Ray still reporting every actor healthy. #3590 could already tell that a shard was bad and stop sending it requests — but the refit group still contained it, so the next weight copy hung anyway. #3591 is what closes that gap.

1 · What this PR adds, and what was already there

The split matters because the two PRs answer different questions. #3590 decides which shard is bad and stops sending it requests. That is enough to keep generating, but not enough to keep training — the weight copy is a collective, and a collective does not care that you have stopped talking to a rank. #3591 adds the machinery that lets the copy itself survive: a way to notice the hang from inside the stuck worker, a way to break it, and a way to rebuild the group over whoever is left.

One distinction worth holding on to. absent_shards() is not the opposite of "serving". A SUSPECT or STALE shard is held back from traffic, but its process is alive and it joins the refit normally. Only DEAD, RESTARTING and RETIRED count as absent. Getting this backwards would drop live ranks out of the group and corrupt the copy.

The three fixes inside 2de01f53 are worth naming, because each was a case where the feature looked like it worked and did not:

#The bugThe fix
1 The abort was not authoritative. A refit is many broadcasts, not one. abort() nulls the communicator, so the buffer in flight returned cleanly — but the next one raised a bare RuntimeError that escaped the caller's with block before guard.fired was ever read. No RefitAborted, no recovery, and the run died reporting a missing communicator instead of the abort that caused it. Invisible on anything small enough to fit in one buffer, which is why the functional test never saw it. broadcast() now raises RefitAborted whenever the group was aborted, fixing all four guarded sites at once rather than wrapping each in a try. Plain RuntimeError is kept for the genuinely different "never initialized" case.
2 The exhaustion check could kill the recovery. Recovery marks every serving shard partial, so the serving set is empty across two awaits. The stall watchdog runs on that same loop and called raise_if_exhausted() every 30s — a tick landing in that window ended the run and blamed an exhausted fleet, killing a recovery that was about to succeed. A _recovery_window() that stands the check down, released in a finally so a raising retry cannot leak the flag on permanently.
3 Recovery cleared the counter that condemns a wedged engine. serving_shards() includes SUSPECT, so a suspect survivor was relabelled STALE and then promoted back to HEALTHY, zeroing consecutive_reported_failures — the one counter kept separate from the probe streak precisely because a wedged engine still answers is_alive(). A shard could fail generations forever and never reach the threshold. ShardHealth records the state before the demotion, and report_refit restores SUSPECT with the streak intact.

Also landed: the sync vLLM worker re-raises RefitAborted instead of folding it into return False (it was the only one of four that did not); both per-PP-stage communicator families are released before rebuild rather than stranded; reconcile_communicator returns None from the base so "this transport owns no membership" stops being reported as "no shard was absent"; the functional harness no longer loses its failure diagnostics to set -e; and refit_timeout_s is now in the exemplar YAML with a docstring that names both the enabled=True and enabled=False behaviours.

A new contract test now makes the recurring bug class impossible. The same mistake — fan a new keyword out to workers, update only some of them — happened in four places, and Ray binds actor signatures at call time, so each surfaced as a TypeError far from its cause. test_worker_refit_signatures.py reads signatures from the AST rather than by importing, because dtensor_policy_worker_v2 needs a per-worker venv that the base one lacks — an import-based check would have skipped exactly the worker that regressed.

Four comments got no reply. Three of them are fixed in the code anyway — the DTensor signature, the deadline on the generation interface, and the shrink/grow docstring below. The fourth is a promised reply about the signature test that never got posted. Nothing looks dropped, but the thread on _drain_router_failures is still unanswered.

3 · Why the group is rebuilt, not shrunk or grown

This was the open question from review, and the answer has two halves that are easy to run together. They are separate decisions, forced by different things.

Your instinct was right, and it lands on half B. The plan has to be regenerated on any membership change no matter what NCCL supports, because prepare_nccl_reshard_refit_info derives every parameter's destination from gen_world_size. Shrinking the communicator without regenerating the plan would not merely reduce the number of receivers — it would orphan the slices the dead rank owned, and the survivors would come back holding weights that were never written. Silently. Once you are regenerating the plan anyway, keeping a second membership-change path buys nothing.

Half A is independent of all of that: abort() is not chosen over destroy() for metadata reasons, but because destroy is a collective and the rank you are trying to escape is the one that cannot participate in it.

The review comment that prompted this was correct and is fixed. The docstring used to claim NCCL exported shrink but not grow, which was wrong — the pinned version exports both. The rewritten paragraph now presents the rebuild as a choice with reasons rather than a limitation, which is the honest framing.

Does it work?

Yes, on hardware, and the interesting part is what it took to prove it. Five variants of the recovery scenario now run in the L1_Functional_Tests_SingleController lane, and all CI is green on ab0ffe2f.

The finding that cost five hardware runs: a killed rank never exercises the watchdog. SIGKILL makes NCCL error out within milliseconds, so ActorDiedError wins the race every time and the deadline never fires — the mid-refit kill variants were green and had never once produced a RefitAborted. Only SIGSTOP, which leaves the rank alive and simply silent, reaches the timeout. Without the frozen variant the deadline had unit tests and signature assertions behind it, but no test had ever made a refit actually abort on hardware.

Measured on 4×GB200: the run now ends or recovers within about 40 seconds of the fault. The same scenario previously sat inside NCCL for 33 minutes before anyone noticed.

An honest limit, documented rather than hidden. A frozen-but-alive rank reaches SUSPECT and stops there — and recovery's own mark_weights_partial then makes it STALE. Neither state counts as absent, so the reconcile correctly refuses to rebuild over a fleet that still holds a silent rank, and the run ends attributably instead of recovering. The author removed an earlier test variant that asserted a rebuild in that case, because it was demanding an outcome the state machine cannot produce. That is the right call: a test asserting an impossible outcome is worse than no test.
So what. With this merged, losing one inference engine mid-run costs a rebuild and one retried weight copy instead of the whole job. Without it, a single dead shard wedges training inside NCCL until walltime expires — silently, with every actor still reporting healthy. The feature is off by default: refit_timeout_s: null starts no watchdog thread and leaves the refit path byte-for-byte unchanged, so nothing here is on the critical path of a normal run until you arm it. If you arm the deadline without generation_fleet_health.enabled, you get the abort but no recovery — still far better than an unbounded hang, and the docstring now says so plainly.

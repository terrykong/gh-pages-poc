Who reads and writes the shared compile cache, and how much

PR #4715 · permalinks pinned to head b2782355

Before
Every job compiles vLLM and the Megatron trainer from scratch.
This PR
Keeps compile caches on a shared filesystem. Each node copies them in at start, and a loop on each node copies new files back every 60 s.
Status
Open — the review keeps this design but asks for fixes. Nothing in the right-hand column below is implemented yet.
Background. One script, cache_sync.sh, does both directions. Copy-in (seed) copies one cache type, e.g. policy (vLLM) or megatron (trainer), from the shared folder to the node's local disk. Write-back (writeback, run every 60 s by a loop) copies files the node compiled back to the shared folder. A shared filesystem slows down most when many nodes open many small files at once: each open is a request to one metadata server. An earlier version of this feature was turned off for exactly that. Shared-filesystem traffic, today and after the fixes

Worked example: a job on 4 nodes with an Ultra-sized cache. The trainer cache measured ~82,000 files and the vLLM policy cache ~6,000 files.

Red = extra load on the shared filesystem, or cache work that is lost. Green = the fix the review asks for. Underlined text links to the code.

  1. Job start: seed runs rsync -a over the whole type folder on every node. The repo's own large-model launcher reads one tarball per cache to avoid this.
  2. Every 60 s: write-back lists files "newer than the copy-in" and older than 1 minute. Nothing records what was already sent, so the list never shrinks, and rsync looks up every listed file on the shared side again. In a local test, 500 files were sent on each of three passes.
  3. Trainer copy: the Megatron worker copies in the background. Anything it compiles before the copy ends looks older than the marker, so it is skipped this job and every later one.
  4. Late nodes: only SETUP_COMMAND starts the write-back loop. It needs a stop file that becomes /ENDED, and it starts an extra loop on every ray start retry.
  5. Multi-node engines: the vLLM start-up hook that would copy in on the engine's other nodes is in the description but not in the diff.

With this, the 4-node example sends the ~82,000 trainer files once over the whole job, instead of re-checking them on every 60 s pass. The same comment also asks for an owner file inside the lock folder, so a slow writer can't delete the next writer's lock.

One more blocker, separate from load. vLLM 0.29.0's cache key includes VLLM_RAY_BUNDLE_INDICES, and NeMo-RL sets it per engine when TP×PP > 1. So with TP>1, no two engines share a cache, and the shared copy mostly misses until that patch lands.

So what. The write-back idea (only new files, never overwrite, one writer at a time) is sound and better than the earlier attempt. The load problems are fixable in cache_sync.sh: read one tarball per type, and send each file once. Two more changes make the feature safe to turn on for any node: one node-start command run by the worker, and a guide (C12) with the script interface a Kubernetes/S3 setup can implement. The comment links work for everyone once the review is published.

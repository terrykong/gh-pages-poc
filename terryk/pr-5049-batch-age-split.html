How batch age counts a call that runs across a refit

NVIDIA-NeMo/RL #5049 (part 3 of the rollout-checkpointing stack, on top of #5048; see also the #5048 page). Permalinks pin the PR head c2bf309a.

Before
The only staleness number was weight_version_lag: how many updates old the oldest group in a step was. Nothing said how old the average trained token was.
This PR
Adds batch age per step to the rollout trace. Commit 1 counts each call's tokens under the version the call began on. Commit 2 also splits a call that runs across a refit, using vLLM's live token count at the pause.
Status
New feature, works as described. The review asks to land commit 1 now and move commit 2 (+486/−102 lines) to a follow-up that shows how much it changes batch age. It also flags one older ordering issue that makes both versions read high.
Background. The trainer updates the policy once per step. Each update gets a number, the version. A refit copies the new weights into vLLM while generation is paused. With token capture, each model call is stamped with the version in use when it began (vllm_worker_async.py#L754). Batch age = for every trained token, (version the step trains) − (version that made the token), averaged over tokens. Dotted words have a short explanation: hover or tap them.

vLLM keeps a paused call alive across a refit, so its later tokens come from the new weights. Commit 1 does not see that: it sums each call under its start version (commit 1). Commit 2 asks every vLLM engine, during the pause, how many tokens each running call has made (captured_call_progress), writes that as a refit_cut event, and splits the call there offline (tokens_by_version). The figure runs both on two calls trained by a step that updates version 6.

Both methods read high, never low: a token is never made by a version older than its call's stamp. Commit 1 is exact for every call that does not span a refit. The gap here is large only because one of two calls spans the refit; in a real batch most calls span none, and the PR's 6-step GPU run reports batch age only with the split, so the real gap is unknown. Call B is a separate, older issue: requests keep arriving during the pause, and the stamp only moves to the new version after resume (ordering from #3837), so neither method can count it right.

The fix — proposed, not in the PR

Where the fix lands: RL only. Drop commit 2 from this PR (c2bf309a), and move the stamp in _sync_weights so call B gets v5. No vLLM change.

Nothing below is implemented. The second piece moves the stamp to right after the pause. A request that arrives later does not run until resume, so it runs only on the new weights:

How Gym's four server kinds fit together, and what the new environment server adds

Background for NVIDIA-NeMo/RL #5340. All Gym links pin 9e2e5d0a, the Gym version RL pins. Read from the code, not run.

Before
Gym had three server kinds: model, agent, resources. An agent's /run owned the whole episode: set up the task, loop the model and tools, ask for the reward.
Now
A fourth kind, the environment server (added to Gym in late September 2026), owns the episode instead. The agent only runs the model-and-tool loop.
Status
Background only, no change. PR #5340 lets turn recovery run through these environment servers. The other two pages cover that change.

So what maps from A to B is simple: the loop (③) stays in SimpleAgent.responses, and everything around it moves up one row, out of SimpleAgent.run and into SingleAgentTurnEnvironmentServer.run. The resources and model servers don't change at all. Only who calls them for ①⑤⑥ changes. The row that changes class is the environment server: A's is a relay that reads nothing, B's runs the steps. That is the "typed" difference, explained under the class tree below. Gym's own comment lists B's steps: "seed → invoke the agent → close the agent → verify → return", and A's: "seed → turn loop → verify".

The class tree, and what “typed” means

Every server is a BaseServer, a pydantic object other servers reach by name through Gym's HTTP client. The three older kinds each have a Base… class (what the server is) and a Simple… class that adds SimpleServer (the web app). BaseEnvironmentServer extends SimpleServer directly. It is generic over its request and response types: that is what "typed" means. Each kind serves different routes. Model: /v1/responses. Agent: /run plus the newer /v1/agent_sessions. Resources: /seed_session, tools, /verify. Environment: /run with an episode request.

“Typed” is not a class or a setting in Gym. There is one base class, BaseEnvironmentServer, and every environment server subclasses it. It takes two type parameters, [Req, Resp]: the request model and the response model (its docstring: “Expose a typed episode protocol”). A subclass that fills them in and writes run() is typed. Gym checks each request against Req and runs run(), the episode steps. A subclass that leaves them out is untyped, and today that is only the relay:

So yes, an untyped kind exists, but it is only the relay, a bridge for agents that still run the whole episode themselves. New environment servers are typed. Which kind you get is decided by which server type the config names, not by a flag. The word in #5340 comes from RL's old setup check. It refused turn recovery for every environment server whose config type was not legacy_agent, and this PR deletes it (_reject_typed_environment_servers). Watch the name: single_agent_turn_legacy is typed. Its “legacy” is about the input it accepts (next section), not about being a relay.

“Legacy” in single_agent_turn_legacy: the input is what differs

"Legacy" in single_agent_turn_legacy is about the request shape, not the server. It is the same typed server, plus run_legacy, which accepts the old flat dataset row and converts it into an episode request (_episode_request_from_row). Then it runs the exact same run(). NeMo-RL sends flat rows today, so that is the server RL talks to.

Flat row (what RL sends; legacy)

{
  "responses_create_params": {"input": [
     {"role": "user", "content": "What is the capital
      of France? Put your final answer in \\boxed{}."}]},
  "expected_answer": "Paris",
  "extraction_mode": "boxed",
  "_ng_task_index": 7,      # RL adds the _ng_ keys
  "_ng_rollout_index": 0,
  "_ng_rollout_id": "r7",
  "_ng_model_sampling": {…}
}

Episode request (typed)

{
  "episode_id": {"rollout_id": "r7", "attempt": 0},
  "task": {
    "task_id": {"taskset": "string_match",
                "task_id": "7"},   # from _ng_task_index
    "task_input": {
      "responses_create_params": {…},
      "task_data": {"expected_answer": "Paris",
                    "extraction_mode": "boxed"}
    }
  },
  "model_sampling": {…}
}
Typed fieldFilled from the flat row by
episode_id_ng_rollout_id (a restored attempt arrives as r7-a1 and is split into id + attempt), else "<task_index>-<rollout_index>". L102
task.task_idthe row's task_id / problem_id / instance_id, else str(_ng_task_index). string_match rows have none of these, so the number RL sends is the task ID. This is why #5340 must re-send the same number. materialize_task
task.task_inputevery key not starting with _ng_. Extra fields go into task_data, which the resources server's /verify reads. SingleAgentTurnTaskInput
model_sampling_ng_model_sampling: RL's temperature, top-p and so on, put into the agent's model URL.

The reply is shaped to match: a flat row gets a flat result dict back (_legacy_result), and an episode request gets a typed {episode_id, task_id, result | failure}.

The other "legacy" server, legacy_agent, converts nothing. It forwards the flat row to an agent that still runs the whole episode itself, the left column above (its docstring).

So what for #5340. Turn recovery used to work only with the left column: the agent owned the episode, and legacy_agent saved nothing. The PR lets it run through the right column. There the environment server owns and saves the episode, and it checks that a resumed episode has the same task_id. Because string_match's task_id comes from _ng_task_index, RL must re-send the same number. The environment server is also where max_concurrent_episodes lives, which is the open problem on the third page.

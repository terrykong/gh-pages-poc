How the text and the image tokens travel together across turns, and where they meet the pixels

Before
Token capture already kept every call's tokens in TQ and sent Gym only text and a pointer. Image tokens were saved like any other prompt token, but no pixels were saved to match them.
This PR
Keeps that token path unchanged. It saves the pixels next to the tokens, records where each image's tokens sit, and checks old images on later turns.

Four pages on this PR. This one: what crosses the wire each turn, where the image tokens live, and where they are joined to the pixels.

Background. The chat template writes one tag per image. vLLM's image processor then replaces that tag with <img>, one image slot token per vision feature, and </img> (get_image_repl). Omni makes one slot per 4 patches of 16×16 px (processor :285). In the example, image A is 64×96 px = 24 patches = 6 slots, and image B is 128×160 px = 80 patches = 20 slots. Everything in TQ and in the learner uses the expanded form, with the slots written out. Dotted words have a short explanation: hover or tap them.

Gym never handles a token id in capture mode. Each turn it sends the chat text, the images as base64 URLs, and a pointer to the earlier rows in TQ (Gym sink.py:255). The worker reads the earlier tokens, image slots included, from TQ by that pointer. vLLM renders the whole conversation from text again, so old images are expanded and processed again too. The worker then glues the exact old tokens onto the new part of the render (the splice) and moves the image positions to match (captured_media.py:318). Tokens and pixels are joined only inside the model, by order.

Your questions, answered

QuestionAnswer
Does Gym send tokens, or media?Neither tokens nor pixels. It sends chat text with images as base64 URLs, plus a pointer to the parent rows and prev_len. The inline token field is left empty in this mode (vllm_model/app.py:724). Gym also strips token ids from the worker's reply (external_capture.py:62).
Where do the old turns' image tokens live?In the TQ row of the call that first saw the image, as ordinary prompt tokens. The worker reads them back by pointer, with a small cache (vllm_worker_async.py:758).
Does vLLM see the old images again?Yes. The request text contains A again, so vLLM decodes it, runs the processor, and runs the vision encoder on it again every turn. The recipe turns prefix caching off (yaml:55), so no old work is reused. Whether vLLM's encoder cache reuses it is not verified.
Where are old turns' pixels stored?Only in row 1, once. Row 2 stores only B's pixels and the tokens after prev_len.
How do the tokens know which images are old?They don't. The tokens for old and new images look the same. The worker decides by position: a slot run that ends before prev_len must match the record saved with row 1 (position, length, token hash, size), and anything after is new. A run across the line is rejected (captured_media.py:349).
Where do tokens and pixels meet?Only in Bridge. It finds every slot token, requires that the count equals the feature count, and fills them left to right (_merge_projected_media). Nothing ties a run of slots to a specific image except order. That holds because tokens and pixels are both joined in the same call order.
What to take away. The existing token path is unchanged: Gym carries text plus a pointer, and TQ carries the tokens, image slots included. The PR adds the pixels beside them and a record of where each image's slots sit. The costs: every turn re-processes and re-encodes all earlier images inside vLLM, and the join to the pixels is by order, with only a total-count check in the model.

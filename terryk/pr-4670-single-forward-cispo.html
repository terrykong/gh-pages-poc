How single-forward CISPO gets the same update with one less policy forward

NVIDIA-NeMo/RL #4670 · perf(cispo): support single-forward training · permalinks pin the PR head a67cc3e

Before
CISPO ran two policy forwards per step: one to get prev_logprobs, one to train. Turning on force_on_policy_ratio (which skips the first one) was rejected for CISPO.
This PR
Allows CISPO with force_on_policy_ratio: true when IS correction with TIS is on, so the trainer skips the extra forward and reuses the training forward.
Status
New feature; the math checks out. For one update per rollout, both paths give the same loss and gradient. The review asks for small cleanups (below).

Background. CISPO is a GRPO-style loss. Each token's loss is -A · w · log π, where A is the advantage and w is a weight that is clipped and not trained through. Three sets of logprobs feed w: from the rollout engine (gen), from the policy before the update (prev), and from the training forward (curr). Dotted words have a short explanation: hover or tap them.

With one optimizer update per rollout, prev and curr come from the same weights, so CISPO's own ratio curr / prev is always 1 and its clip never acts. The only thing that bounds the weight is the TIS clamp on prev / gen (loss_functions.py L760-L780). So the extra forward only produces a copy of numbers the training forward already has. With force_on_policy_ratio on, the loss uses prev = curr.detach() (L637-L638) and the trainer skips the extra forward (_skip_prev_logprobs).

Two paths, one update — same numbers

The two lanes differ only at step 2. At step 4 they become one: CISPO's ratio is 1 in both, and the same TIS clamp turns [0.2, 1.5, 8] into [0.5, 1.5, 3]. Two things follow. First, ratio_clip_min / ratio_clip_max are not read by the loss in this mode. Second, the gradient here, -A · w per token, is the same one GRPO with force_on_policy_ratio and the same TIS settings already gives; only the logged loss value differs.

What the PR changes

Where the change lands: RL only. The behavior change is one assert in ClippedPGLossFn.__init__ and one sampler check in validate_single_controller_config. No trainer change: both trainers already skip the extra forward whenever force_on_policy_ratio is on.

The PR also adds two CISPO-only branches in clipped_pg_actor_objective. They do not change any output: the existing force branch already makes the ratio exactly 1, and the CISPO line already detaches it. The review asks to drop those branches and the bounds-matching assert, since it checks two keys the loss never reads in this mode.

So what. CISPO runs with one less full policy forward per step, with the same update, as long as each rollout gets one optimizer update. Set the TIS bounds to the clip you want; in this mode they are the only clip. The PR has no step-time numbers yet, so the speedup is expected but not measured.

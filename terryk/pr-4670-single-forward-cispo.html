Single-forward CISPO: which logprob it stops computing, and why that is safe in async RL

NVIDIA-NeMo/RL #4670 · perf(cispo): support single-forward training · permalinks pin the PR head a67cc3e

Before
CISPO always ran two trainer forwards per step: one with no gradient to get prev, one to train. force_on_policy_ratio, which skips the first, was rejected for CISPO.
This PR
Allows CISPO with force_on_policy_ratio: true when IS correction with TIS is on. The trainer then skips the prev forward.
Status
New feature; the math checks out. It works in sync and async runs, but only with one optimizer update per rollout batch. The review asks for small cleanups (end of page).

The CISPO loss, one term at a time

This is what NeMo-RL computes today for CISPO with IS correction and TIS on. Each token ot gets a probability from three policies:

  • πgen (gen): vLLM's probability when it sampled the token. Comes free with the sample.
  • πprev (prev): the trainer's weights before this step's update. Costs one extra forward pass, with no gradient.
  • πθ (curr): the trainer's weights inside the training forward. The only one with a gradient.
\mathcal{L}(\theta)=-\frac{1}{N}\sum_{t}\; \htmlClass{t1}{\underbrace{\mathrm{TIS}\!\left(\frac{\pi_{\text{prev}}(o_t)}{\pi_{\text{gen}}(o_t)}\right)}_{\text{(1) IS weight}}} \cdot \htmlClass{t2}{\underbrace{\mathrm{sg}\!\left[\mathrm{clip}\!\left(\frac{\pi_\theta(o_t)}{\pi_{\text{prev}}(o_t)},\;1-\varepsilon_{\text{low}},\;1+\varepsilon_{\text{high}}\right)\right]}_{\text{(2) CISPO trust-region weight}}} \cdot \htmlClass{t3}{\underbrace{A_t\,\log\pi_\theta(o_t)}_{\text{(3) gradient flows here}}}
  • (1) IS weight: how far vLLM's sample is from the trainer. In async runs this holds the lag (vLLM used older weights). In sync runs it holds only small number differences between vLLM and the trainer. TIS(x) clamps it to [truncated_importance_sampling_ratio_min, truncated_importance_sampling_ratio] (code).
  • (2) trust-region weight: how far this optimizer update has moved from the weights at the start of the step. ε comes from ratio_clip_min / ratio_clip_max. sg[…] means no gradient goes through it (code).
  • (3): advantage times log-probability. N is the number of valid tokens (code).

The one assumption this PR uses: in the first optimizer update on a batch, πθ and πprev are the same weights. So (2) is exactly 1, and πprev can be replaced by a copy of πθ with no gradient. That is what force_on_policy_ratio: true does (code):

\mathcal{L}_{\text{1-fwd}}(\theta)=-\frac{1}{N}\sum_{t}\; \htmlClass{t1}{\mathrm{TIS}\!\left(\frac{\mathrm{sg}[\pi_\theta(o_t)]}{\pi_{\text{gen}}(o_t)}\right)} \cdot\htmlClass{t2}{1}\cdot \htmlClass{t3}{A_t\,\log\pi_\theta(o_t)} \qquad\text{(no }\pi_{\text{prev}}\text{, so no extra forward)}

Same value, same gradient. This is also the CISPO paper's own formula with πold = the policy that sampled the tokens, using the TIS bounds as its clip. When does the assumption hold?

So the row decides, not the column. The saving is the same in sync and async. Async is where (1) is far from 1, so that is where the TIS bounds matter most.

The "several updates" row, more exactly. The GRPO trainers block it: force mode requires train_global_batch_size = prompts × generations (grpo.py L850-L857). PPO's ppo_epochs is not checked (ppo.py L500-L509). For CISPO that is still sound: each update uses clamp(πθ / πgen), the CISPO paper's form with πold = the sampling policy. It just no longer equals the two-forward version. For plain PPO-clip it removes the trust region, but that gap already existed on main and this PR does not touch it.

What force_on_policy_ratio means, and why async still works

It does not mean "sync". It means: "each rollout batch gets exactly one optimizer update, so curr / prev is 1; use curr.detach() wherever prev is needed" (loss_functions.py L637-L638). The GRPO trainer checks the one-update rule at setup (train_global_batch_size == prompts × generations).

Async lag lives in the other ratio. In async RL the gap is between the weights vLLM sampled with and the trainer's weights, which is prev / gen. This mode keeps that ratio (as curr.detach() / gen, the same numbers) and TIS still clamps it. The async GRPO loop skips the extra forward the same way (grpo.py L5522), and this PR lets SingleController's async ready_first sampler use it too.

What you give up is several updates per batch, not async. The CISPO nightly recipe samples 32 × 16 = 512 sequences per step but trains in batches of 32, so it takes 16 optimizer steps per rollout (recipe L17-L28). In steps 2 to 16, curr ≠ prev, so single-forward would no longer match that recipe's two-forward math, and the GRPO trainer rejects force mode for it at setup.

Two things follow. In this mode the loss never reads ratio_clip_min / ratio_clip_max: TIS is the only clip. And the gradient, -A · w per token, is the same one GRPO with force_on_policy_ratio and the same TIS settings already gives; only the logged loss differs.

So what. If each rollout batch gets one optimizer update, CISPO can drop the prev forward and train exactly the same, in sync or async runs. Async lag is still corrected by TIS on curr / gen. If your recipe splits a batch into several optimizer steps (like the CISPO nightly), GRPO rejects this mode at setup. The PR has no step-time numbers yet, so the speedup is expected but not measured.

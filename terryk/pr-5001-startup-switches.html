What the four startup switches in #5001 move earlier, and what still runs in order

NVIDIA-NeMo/RL #5001 (builds on the Megatron compile cache from #4715). All permalinks pin the PR head 5223071.

Before
Single-controller setup reserves the vLLM workers first, then builds vLLM, NeMo-Gym and the trainer side by side. It checks the dataset's Gym routes only after Gym is up. Every job's first training step pays for torch.compile and Triton autotuning from scratch.
This PR
Four switches, all off by default, set as environment variables: start the trainer earlier, scan routes earlier, keep compile results between jobs, and run a fake first step ahead of time.
Status
New and opt-in. The review is still pending. It asks for the switches to become config keys (C2), and it found a crash in the warm-up switch when CUDA graphs are on (page 2).

Startup, before and after

What each switch does, step by step

  1. ① Early trainer build. Setup starts building the trainer on its own thread before it reserves the vLLM workers, instead of in the task pool afterwards. It only applies to runs that already load the dataset alongside the other builds (NeMo-Gym, vLLM on separate GPUs, no resume) and set cluster.segment_size. In any other run it prints a warning and is ignored. Cost: Ray creates the trainer and vLLM actors at the same time, which adds load on its control service.
  2. ② Early route scan. Each dataset row names the Gym route it needs. The PR collects those names as soon as the dataset loads, e.g. {"train": {"alpha", "beta"}} in the PR's test. Once Gym is up, the coverage check only compares sets. A split whose routes only the running Gym knows (taskset rows) is still scanned at check time.
  3. ③ Compile results kept between jobs. The two variables are passed to the Megatron workers as Triton's and torch's own TRITON_CACHE_AUTOTUNING and TORCH_COMPILE_JOB_ID. The cache sync script then also publishes torch's per-rank shape profiles. They only do anything when the persistent compile cache from #4715 is on. Kernels whose autotune configs have a pre_hook are still benchmarked in every job.
  4. ④ Trainer warm-up. Each Megatron rank runs one logprob pass and one forward/backward on a fake batch. For the 1B math example the default lengths are [512, 512, 512, 512] tokens (max length 512, packing budget 4 × 512). Then it undoes what a real step would read: no optimizer step, gradients dropped, metric trackers and RNG reset. If the trainer is ready before vLLM, setup runs it right away. Otherwise the controller runs it alongside the first rollouts, and the train pump waits for it before step 1.

So what. Nothing changes unless you set a switch. Switches ① and ② only move work earlier. ③ and ④ make step 1 cheaper, but they can also stop a run before step 1:
  • ④ with CUDA graphs on fails at startup. The fix is on page 2.
  • ④ can also run out of memory, since it uses full-size microbatches.
  • ③ can hang the first step if the ranks load shape profiles saved at different points of an earlier run.

The PR gives no before/after timings yet. The review asks for time to the end of step 1, with each switch on and off.

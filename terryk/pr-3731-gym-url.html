Move the NeMo-Gym address check to after the first refit

Two PRs that are each fine alone and break together: #3731 (open, head da7bee9) and #3569 (merged). Links marked main pin eaf02ef.

The change being asked for. Move these six lines from setup (main grpo.py:1394) to just after sync_weights() (main grpo.py:1669):
served_urls = policy_generation.dp_openai_server_base_urls if served_urls != [reserved_url]: raise RuntimeError(...)

No config change. No new assert. No change to #3731's own code — those lines live in grpo.py, which #3731 does not touch. The rest of this page is why.

When generation does not share GPUs with training, one Megatron worker (rank 0) runs an OpenAI-style HTTP server, and NeMo-Gym sends its rollout requests to that address. The list of addresses, dp_openai_server_base_urls, starts empty and is filled in exactly one place: prepare_for_generation(). #3731 waits before calling that, when the weights will arrive later by refit, so CUDA graphs capture the real weight buffers instead of ones that are about to be swapped out. #3569 reserves the server address before any worker exists, hands it to NeMo-Gym, then checks the engine really came up there. That check now runs before the engine has started.

Opening the port is not the same as answering on it

Step 2 already hands rank 0 a socket that is bound and listening, so it is tempting to think the server is up. It is not. Nothing accepts connections on that socket until step 3 runs:

prepare_for_generation() # driver └─ worker.prepare_for_generation() └─ _run_async_coordinator_start() # main megatron_worker.py:446 └─ self.base_url = _setup_openai_api_server() # main :465 ← first accept() here # and the only place base_url stops being None

main megatron_worker.py:446 · main megatron_worker.py:465

This is why moving the check is the fix, rather than changing either PR's behaviour. The engine does come up at the reserved address — just later, at the first refit. Run the check there and it passes for the right reason. The reserved port is held the whole time, and NeMo-Gym already has the address, so nothing else has to move.

The alternative would be to start the HTTP server during construction and let only the CUDA graph capture wait. That is a bigger change and a worse trade: the server needs a live coordinator, and the coordinator is part of the engine that #3731 is deliberately waiting to build. Moving one check is cheaper than splitting the engine in half.

One thing to check rather than assume: whether NeMo-Gym sends anything to that address before the first refit. There is no health check in _spinup_nemo_gym, and rollouts start after the refit, so it looks safe — but until the engine starts, that port accepts connections and never answers, so a request in that window would wait instead of failing.

Has anyone run the two together?

No. The test that would catch this, grpo_megatron_generation_async_gym.sh, sets exactly the failing combination — Megatron generation, not colocated, HTTP server on — and it runs in the fast lane (fast_L1_Functional_Tests_Megatron_4). It is green right now. It is green because #3731's branch is 2 commits behind main and does not contain #3569's check yet, so there is nothing to fail.

That makes the ask small and concrete: rebase #3731 onto current main and re-run that one lane. It takes about 13 minutes and it either reproduces the RuntimeError or proves this page wrong.

What to do. Do not merge #3731 on a green check that predates #3569 — that green came from a branch where the conflicting code does not exist. Rebase, move the six lines to after sync_weights(), and re-run Megatron_4. If the check stays where it is, every non-colocated run with NeMo-Gym stops at setup with serving [].

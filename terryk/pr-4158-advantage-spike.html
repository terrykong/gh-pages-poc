Why one wrong answer in a group of eight got an advantage of −2075

Companion illustration for NVIDIA-NeMo/RL #4158 (fix a spike in leave-one-out normalized advantage). All permalinks pin the PR head 986ef03.

Before
When every other rollout in a group scored the same, the one rollout that differed got an advantage thousands of times too large — −2075 instead of −0.95.
This PR
Skips the normalization step for a rollout whose comparison group is all one value, so the code never divides by a number that is only rounding error.
Status
Fixed by this PR. Reproduced both ways: the odd rollout's advantage goes from −2075.39 to −0.95, and the other seven do not move.

In GRPO, each rollout's advantage is its reward minus a baseline (advantage_estimator.py:119). With leave-one-out turned on, a rollout's baseline is the mean of the other rollouts for the same prompt — it never sees its own reward. With normalize_rewards also on, that advantage is then divided by the standard deviation of the same set of other rollouts (:124). When all seven of those other rollouts scored the same, their real spread is zero and that division should never happen at all. The old code decided by asking is the computed std > 0? — and the answer came back yes, because a computed spread is never exactly zero in floating point.

This is not a claim that the variance formula is buggy, and not a claim that leave-one-out is wrong. Leave-one-out is doing exactly what it should. The problem is that std > 0 is a floating-point stand-in for the question we actually care about — does this comparison set carry any signal? — and that stand-in cannot work at any precision. Computing the spread more accurately makes the spike bigger, as the numbers below show. This PR replaces the stand-in with an exact question about the inputs: are all the rewards being compared the same value?

Where the number comes from

Why no 0.0
The 0.0 is missing from those sums because of leave-one-out, not because 0² = 0. Rollout 1's baseline and spread are built from the other rollouts only, so its own reward is excluded — and the divisor is 7 rather than 8 for the same reason. Had it been dropped just for being zero, the divisor would still be 8. Including it changes everything:
leave-one-out (what runs) if the 0.0 were included
E[r²] 0.90250003 0.78968745
E[r] 0.94999993 0.83125001
std 0.00045675 0.33587566
That last row is the whole bug: taking rollout 1's own reward out leaves seven identical numbers, which have no spread at all.
Should it be 0
Yes. The true spread of seven identical numbers is exactly zero, so 0.00045675 is entirely wrong. It is non-zero only because E[r²] and (E[r])² reach nearly the same value by different routes and round differently in the last few bits. But see below — computing them more carefully does not fix the bug, it makes it worse.

Colour key — the same colour means the same number wherever it appears: E[r²] = 0.90250003 · E[r] = 0.94999993 (which is also the baseline) · the spread = 0.00000021 · the divisor = 0.00045675.

Paste this to check the arithmetic yourself — it reproduces every number above exactly, including the real function's std for this group, bit for bit:

import torch r = torch.full((7,), 0.95) # rollout 1's seven peers, float32 E_r2 = (r * r).sum() / 7 # 0.90250003 E[r²] E_r = r.sum() / 7 # 0.94999993 E[r], and the baseline var = (E_r2 - E_r**2) * (7 / 6) # 2.0861626e-07 should be exactly 0 std = var.sqrt() # 0.00045674530 the divisor (0.0 - E_r) / (std + 1e-6) # -2075.39 BEFORE this PR (0.0 - E_r) # -0.95 AFTER this PR # the 7/6: 7 peers, so x 7/(7-1). Same as torch.var(unbiased=True): torch.tensor([0.0] + [0.95]*6).var(unbiased=True) # 0.12892857 ((lambda p: (p*p).sum()/7 - (p.sum()/7)**2)(torch.tensor([0.0] + [0.95]*6))) * (7/6) # why any of this is non-zero: 0.95 has no exact float32 form float(torch.tensor(0.95)) # 0.949999988079071

What the fix does

The fix does not try to make the arithmetic more accurate. It cannot: the true spread here is zero, so any division blows up no matter how precisely the zero is computed. Instead it asks a cheaper question — are all the rewards in this rollout's comparison set the same value? It answers that by taking the smallest and the largest reward in the set and checking whether they are equal (utils.py:202-207), then skips normalizing those rollouts (advantage_estimator.py:124).

# nemo_rl/algorithms/utils.py — the new check, run per prompt group comparison_min = comparison_rewards.masked_fill(~comparison_mask, torch.inf).amin(dim=1) # rollout 1 -> 0.95 comparison_max = comparison_rewards.masked_fill(~comparison_mask, -torch.inf).amax(dim=1) # rollout 1 -> 0.95 is_trivial_distribution[prompt_idx] = comparison_min == comparison_max # -> [True, False x7] # nemo_rl/algorithms/advantage_estimator.py — normalize everything except those normalize_mask = (std > 0) & ~is_trivial_distribution # -> [False, True x7] advantages[normalize_mask] = advantages[normalize_mask] / (std.unsqueeze(-1)[normalize_mask] + epsilon)

Why a more accurate variance would be worse

The obvious repair is to compute the spread properly. torch.var does not use E[r²] − (E[r])² at all — it uses a two-pass method that is about 50 million times closer to zero on these seven numbers. Swapping it in makes the spike far worse, because a smaller divisor means a bigger quotient:

how the spread of the seven 0.95s is computed std advantage ------------------------------------------------------------------------------ this repo: (E[r²] − (E[r])²) × 7/6 0.00045675 −2075.39 torch.var(unbiased=True) 0.000000064 −892,538 the exact answer — seven equal numbers 0 −0.95 (no division)

So precision is not the lever. Any positive number in that slot produces a spike, and the better the arithmetic, the larger it gets. The only thing that helps is not dividing — which is what the PR does, decided by comparing the input rewards rather than by inspecting a rounded result.

The repo hand-rolls the formula for a reason worth knowing: it needs a separate variance for every rollout, each leaving that rollout out. It gets all eight at once by multiplying with a 1 − I mask matrix (utils.py:160). torch.var cannot express that in one call, which is why the sum-of-squares form is there at all.

Why this matters for training. An advantage of −2075 sitting next to seven values of about +0.38 does not just misprice one rollout — it dominates the gradient for the whole batch, and its size is set by a rounding error rather than by anything the model did. It shows up most on easy datasets, where nearly every rollout is correct and a lone failure is common. Note also that forcing the spread to exactly zero is not a safe alternative: the batch filter drops zero-spread rollouts, so that would delete the one failing rollout and leave the survivors all pushing the same direction.

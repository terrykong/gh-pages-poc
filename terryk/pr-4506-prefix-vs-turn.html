What prefix recovery keeps that turn recovery throws away

Explainer for NVIDIA-NeMo/RL #4506, which sits on #4501 (turn-level recovery). All permalinks pin the PR head 0c54ff7. Review comments are in a pending review; the links work once it is published.

Before
Turn-level recovery. A model call that was still decoding at the checkpoint is thrown away; after a restart it runs again from scratch, from the start of its turn.
This PR
Adds rollout_recovery.target_level: prefix. Each checkpoint also saves the tokens every running call has decoded so far, and the restarted call continues from them.
Status
New feature, opt-in. Open review findings: a stop string can come back after restore, and stop strings or presence/frequency penalties can change the output across a cut. Both are tracked in the review comments. No GPU CI has run on this PR yet.

prefix vs turn size and reuse

Two pages on this PR — this one: what prefix recovery adds next to turn recovery.

Background. In a Gym rollout, an agent server (Gym) calls the model many times. NeMo-RL's vLLM workers answer, and store each finished call's token ids as a row in TQ. Every few seconds the single controller takes a rollout snapshot. With turn recovery, Gym saves its agents in that snapshot, so a restart goes back to the last finished turn (turn recovery, explained). Dotted words have a short explanation: hover or tap them.

At each Gym checkpoint the controller first holds back terminal row writes on every vLLM worker; decoding keeps running (single_controller.py:4771). Gym then asks each worker to cut its running calls, and the worker saves the tokens decoded so far as a TQ chunk row (generation_cut_capture.py:699). After a restart the worker reads those rows back, adds them to the end of the prompt, and lowers max_tokens and min_tokens by the same count (vllm_worker_async.py:1553). It then puts the decoded text in front of the reply (:1035). A call that cannot be cut — the deadline passed, the cut lands inside a multi-byte character, or an output step was missed — falls back to the turn path.

Why keep both. Turn recovery needs nothing from the vLLM worker beyond normal token capture. Prefix recovery needs the vLLM async engine and a Gym build with the cut endpoint, and setup rejects it with multimodal capture or router replay (setup.py:1258). Any call it cannot cut simply restarts the turn way, so turn recovery stays the fallback inside prefix mode.

What it costs, and what is still open

The gain is the decode work up to the last cut: a long call keeps everything it decoded before the checkpoint instead of nothing. The price: with prefix on, the "nothing changed, skip this snapshot" shortcut is off whenever a model call is running (single_controller.py:4916), so every snapshot interval holds row writes on all workers and pauses Gym. The PR has no timing numbers for that yet.

review comment — single_controller.py:4925

Open review findings (tracked in the review comments). (1) A stop string can come back. If a call had already finished on a stop string when the cut ran, the restored reply is rebuilt from the saved ids, and decoding them brings back the stop string vLLM had cut off. This only matters when an agent sets its own stop list (:1035). (2) Some calls change across a cut. A stop string that starts before the cut and ends after it never matches, and presence / frequency penalties stop counting the restored tokens. The proposed fix marks such calls as not cuttable, so they take the turn path (:1763).

Why one replica's timing numbers disappeared, and how naming each actor fixes it

Companion illustration for NVIDIA-NeMo/RL #3374 (preserve replica identity during routing). All permalinks pin the PR head 46ae651; "before" links pin the branch point 8b97de9.

A NeMo-Gym shard is one group of Gym servers running in one Ray actor. Setting replicas: 2 on a shard starts two identical copies of it on two nodes, and the router hands each prompt group to one of them in turn. Every actor reports how long it spent, and those numbers are collected into a dictionary keyed by whatever label the router attached. Before this PR that label was the shard name. Two replicas of one shard therefore shared a key — so the second one to finish overwrote the first, and nobody was told.

Two replicas, one dictionary key

The quiet part is the top-right box. Because both replicas collapsed onto one key, the dictionary had one entry — and the merge step returns early when there is only one, handing back that entry's numbers unchanged with no /shard/ breakdown. So you did not get a wrong-looking chart with a missing series. You got a normal-looking chart whose single number was whichever replica happened to finish last.

What the fix actually does

One method replaces the old shard lookup. It walks the handles, and names the actor by position only when the shard has more than one, so an unreplicated shard reads exactly as it did before replicas existed:

def instance_label(self, handle): for shard_name, replicas in self.handles.items(): for index, replica in enumerate(replicas): if replica is handle: # 1 replica -> "tools" # 2 replicas -> "tools/0", "tools/1" return shard_name if len(replicas) == 1 else f"{shard_name}/{index}"

nemo_gym.py:1262 — replaces the old shard_name_of, which returned the shard name for every replica.

With two distinct keys the merge step now takes its other branch. It writes one entry per replica and keeps the combined number, using the maximum rather than the sum, because the replicas run at the same time and the step waits for the slowest:

for instance_label, metrics in timing_by_instance.items(): # "tools/0": 4.0, "tools/1": 9.0 for key, value in metrics.items(): merged[f"{timer_prefix}/shard/{instance_label}/{suffix}"] = value # 4.0 and 9.0, both kept merged[key] = max(merged[key], value) if key in merged else value # max(4.0, 9.0) = 9.0

rollouts.py:2475-2481. The same label is also used for the log directory, the round-robin bucket, and the text of a failure — so a slow replica, its logs and its error all carry one name.

Why this matters beyond tidier charts. Replicas exist to spread one step's work across more nodes. The reason to add a second replica is that the first one is the bottleneck — and the number you would use to check whether that worked was exactly the number being overwritten. Before this change you could double a shard's hardware and have no way to see which copy was slow.

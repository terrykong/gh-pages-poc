Three pages on this PR, one question each — this one: why a returning shard was shut out.

A run keeps several generation shards. If one dies, the earlier PRs in this stack drop it and carry on with the rest — the refit communicator is rebuilt over the survivors. But the fleet could only ever get smaller. Nothing brought a shard back, and this PR is about why that was not just a missing feature but structurally impossible.

The refit code decided whether to rebuild by asking one question: is anything absent right now? That question can tell you a shard has left. It cannot tell you one has returned — because a returned shard makes the absent set empty, which looks exactly like a healthy fleet with nothing to do.

Why a shard could never come back

Three shards, numbered 0, 1 and 2. Shard 1 dies, then its engine is restarted. Follow the row marked before: at the moment the engine comes back, the old check returns early and the communicator is never rebuilt, so shard 1 stays out for the rest of the run.

What the fix does

The new code stops asking "is anything absent" and instead compares the membership it wants against the one it last built. Same three shards, same moments — here are the two values at each step, and the decision that falls out of them.

moment wanted built equal? decision ------------------------------------------------------------------- steady state {0,1,2} {0,1,2} yes skip shard 1 dies {0,2} {0,1,2} no rebuild over {0,2} engine back up {0,1,2} {0,2} no rebuild over {0,1,2} <- the new one next refit {0,1,2} {0,1,2} yes skip

"Wanted" comes from desired_membership(), which is phrased as "what the membership should be" rather than "what changed" — that is the whole trick, because it reads the same in both directions. "Built" is remembered in _built_membership, and the comparison is one line.

Something still has to restart the engine and say when it is ready. That is EngineSupervisor.tick(), which picks up dead shards and calls restart_shard in the background. It hands the shard back through four states, and the orange one above is the interesting one:

DEAD --(restart starts)--> RESTARTING --(engine up)--> STALE --(next refit)--> HEALTHY ^^^^^^^^^^ ^^^^^ not in the collective in the collective, at all but takes no traffic

RESTARTING is treated as absent, so a rebuild that happens while the engine is still loading correctly leaves it out. STALE is the opposite: the shard is in the group, so the refit can write weights into it, but it is kept out of the serving set until that refit lands. A restarted engine only has whatever it loaded from disk, and that ordering is what stops those stale weights reaching a rollout.

What this buys you. A long run that sheds a few transient failures no longer ends permanently smaller — a shard lost at hour one can be serving again a few minutes later. It is off by default: set async_rl.generation_fleet_health.restart_dead_shards: true on top of generation_fleet_health.enabled.

Two things to know before you turn it on. Restarting does not raise the min_healthy_shards floor — a restarting shard is not serving, so a run can still stop while a restart is in flight. And a killed vLLM worker leaves its EngineCore holding the GPU unless the raylet is told to reap it, which needs RAY_process_group_cleanup_enabled=1 set before ray start, not from the driver. Without that the replacement has nowhere to load.

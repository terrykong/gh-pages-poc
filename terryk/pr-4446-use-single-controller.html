Status
Proposed: switch to the single controller instead. It already ships stronger recovery for the same failure, and the config below passes its setup checks. Nothing on this page is merged as a new recipe.
Background. NeMo RL has two ways to run GRPO with NeMo-Gym. The original loops (v1) run rollouts and training in turn, one after the other. The single controller (v2) is the newer path, and the one new work is meant to use. Its fault tolerance came in four PRs: rollout retries, engine health and a router, weight sync over survivors, and engine restart. Dotted words have a short explanation: hover or tap them.

One multi-turn rollout, one engine dies at turn 3

The config: grpo_nanov3 on the single controller

Save next to examples/nemo_gym/grpo_nanov3.yaml and run uv run examples/run_grpo_single_controller.py --config examples/nemo_gym/grpo_nanov3_single_controller.yaml. It loads through the launcher's config path and passes every setup check that runs before Ray starts, at main e12d18b. It has not been run on GPUs. Main also has tested single-controller nanov3 recipes to compare against: vLLM and Megatron generation. Green lines are the fault-tolerance switches.

defaults: grpo_nanov3.yaml

grpo:
  # No validation on the single controller yet; setup raises if any is on.
  val_period: 0
  val_at_start: false
  val_at_end: false
  async_grpo: null                  # replaced by the single controller

checkpointing:
  metric_name: null                 # no validation metric to rank by
  save_data_plane: true             # keep buffered rollouts across a resume

policy:
  generation:
    colocated:
      enabled: false                # vLLM needs its own GPUs here
      resources:
        # 32 nodes: 16 for vLLM, 16 (128 GPUs) for training. Training must divide
        # by TP2 x PP2 x CP4 = 16, and its DP (8) must divide 2048. 1 vLLM node
        # leaves 248 training GPUs, and Megatron fails at startup.
        num_nodes: 16
        gpus_per_node: 8

data_plane:                         # required on this path
  enabled: true
  impl: transfer_queue
  backend: simple
  claim_meta_poll_interval_s: 0.5
  simple:
    num_storage_units: ${mul:2, ${cluster.num_nodes}}

async_rl:
  sampler: {name: in_order, max_lookahead_versions: 1}   # = max_trajectory_age_steps: 1
  min_groups_for_streaming_train: ${grpo.num_prompts_per_step}
  max_inflight_prompts: ${grpo.num_prompts_per_step}
  max_buffered_rollouts: ${mul:${grpo.num_prompts_per_step}, 2}
  rollout_failure:
    max_infra_attempts_per_prompt: 5      # retry a prompt that failed on infrastructure
    max_consecutive_dropped_prompts: 8    # ride out an outage; any success resets it
    on_dropped_prompt: replace            # keep the step's batch size
    nemo_gym:
      max_row_attempts: 3                 # re-send only the rows that never came back
  generation_fleet_health:
    enabled: true                         # track live engines; rebuild weight sync over them
    restart_dead_shards: true             # restart a dead engine, re-add it at the next sync
  generation_router:
    enabled: true                         # Gym talks to one router URL, never a dead engine
Two costs to check before switching from v1 to v2. These are the likely reasons a job stayed on v1. If either one blocks you, #4446 is still the only way to get retries on v1.
  1. No validation. The single controller rejects val_period > 0 at setup (setup.py L1115). grpo_nanov3 validates every 5 steps.
  2. vLLM needs its own GPUs. With vLLM, the single controller requires colocated.enabled: false (config.py L1164), so the 32 nodes split 16 / 16 instead of sharing GPUs.

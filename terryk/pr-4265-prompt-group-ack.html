Ten pages on this stack — this one: #4265: the bug in prompt-group mode.

Gym keeps each finished result until RL ACKs it, and its status() says "not ready to commit" while any result is un-ACKed. Gym's retire() refuses a finished result, so an ACK is the only way to release one. In sibling mode RL records the ACK debt the moment a sibling finishes. In prompt-group mode (all siblings must succeed, or the whole group is retried) RL keeps finished siblings in a local dict, pending_group_results, and returns early until all of them are in.

Same group, two modes

What happens in prompt-group mode, step by step

  1. g0 finishes. RL puts its result in a local dict and returns early, because the group is not complete yet. No "I owe Gym an ACK" note is written for g0.
  2. The ACK note is written only when the whole group is in, by record_sealed_group_acknowledgements. Until then Gym still counts g0 as "finished, not ACKed".
  3. A snapshot starts. Gym parks g1 and g2 at a saved point and waits until nothing is running. Then it reports "not ready to commit", because g0 is finished but not ACKed.
  4. g1 and g2 stay parked. When a prepare fails, Gym wakes up only runs it had not parked yet. g1 and g2 are already parked, so they cannot finish, the group cannot complete, and g0 never gets its ACK note.
  5. RL retries prepare until the deadline. Each try gets a 409, and RL tries again until the prepare deadline (300 s by default), then gives up on this snapshot.

Worse case, if a sibling fails after g0 finished:

  1. RL throws away the whole group, including g0's result (_abandon_entire_group), and retries it as try 1.
  2. Gym still holds g0 as finished, and nothing will ever ACK it. Gym's retire() refuses finished runs, so step 3 now fails on every later snapshot, for the rest of the process.

Who hits this. Any environment whose group RL retries as a whole while turn-level checkpointing is on. Environments that score each sibling on its own hit it most: their siblings finish at different times, so a group is often half done when a snapshot starts, exactly as drawn above. Under the target-level comment on #4266 that happens when an override forces prompt_group on such an environment. GenRM compare also runs this path, but rarely stalls: its siblings all finish together once the group is scored.

This setup is meant to work, so the fix is to ACK earlier, not to reject the combination. This PR even adds record_sealed_group_acknowledgements for it. A lost /run reply strands a finished result the same way; see the lost-reply page.

What would fix it — proposed, not in the PR

Where the fix lands: RL only, two files. rollout_manager.py: the prompt-group branch of _record_streamed_completion records each sibling's ACK note when it arrives. rollout_recovery.py: one new ledger method, next to record_sealed_group_acknowledgements, that writes the note without waiting for the group to seal. No Gym change: Gym already accepts an ACK for any finished run at any time; it does not know or care about prompt groups.

Nothing below is implemented. Record each sibling's ACK debt as soon as it arrives, like sibling mode does, and keep only the seal all-or-nothing. That is safe: g0 is ACKed but not yet published, so it is not in RL's snapshot. On restore it is simply rerun under a new try number; nothing is lost or counted twice.

Scope: this only removes the stall. What the group does on restore (start over, or resume g1 and g2 from their saved turns) is set by the target level in the target-level comment on #4266. This fix works with either.

Real code this changes: rollout_manager.py:2426-2442 and a new ledger method next to record_sealed_sibling_acknowledgement that builds the ACK from the receipt without requiring the sibling to be sealed. For lost replies, see the lost-reply page.

So what. With prompt-group mode and Gym checkpointing both on, any snapshot taken while a group is partly done waits out its full prepare deadline (300 s by default in #4266) and fails. One failed group after a sibling finished blocks every later Gym-aware snapshot for the rest of the process. Recording each sibling's ACK when it arrives removes both.

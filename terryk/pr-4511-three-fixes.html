Which of this PR's three fixes change what a Megatron run does

Explainer for NVIDIA-NeMo/RL #4511 (fix(sft): preserve checkpoint initialization and optimizer resume state). Permalinks pin the PR head ef033f7, Megatron-Bridge ec83553 and Megatron-LM b4d72b7.

Before
SFT v2 ignored checkpointing.pretrained_checkpoint, and a conversion folder counted as complete if one small config file existed.
This PR
Forwards the setting to the model workers, checks every weight file before reusing a conversion, and adds one more weight sync after a resume.
Status
The first two are fixed by this PR. The resume sync does nothing at the pinned Megatron versions; the review asks to remove it.
Background. Megatron training keeps two copies of the weights: the BF16 weights the model runs on, and FP32 master copies the optimizer updates. On resume, NeMo-RL calls Megatron-Bridge's load_checkpoint, which reloads both. A Hugging Face model is first converted to Megatron's format once and cached in a folder; later runs reuse that folder. Dotted words have a short explanation: hover or tap them.

The PR makes three separate changes, one per row below:

  1. Use the configured start checkpoint in SFT v2. SFT v2 only. Before: wrong result. A fresh SFT v2 run with checkpointing.pretrained_checkpoint set ignored it, with no error, and trained from the Hugging Face weights instead. The model workers read the setting from the policy config (setup.py L899), and SFT v2 never copied it there. The other algorithms already do; the PR adds the same 3 lines. PPO and xtoken distillation still lack them (#4768).
  2. Stricter check before reusing a converted model. Every Megatron run. Before: wrong result, in a rare case. A cached Hugging Face→Megatron conversion counted as complete once its small run_config.yaml existed, even when a weight file was missing or empty. That can happen with an older conversion that was cut off, or files removed from storage. The run reused the folder, and the gap only showed up when the weights were read. megatron_conversion_is_complete now checks every weight file the checkpoint lists, so such a folder is converted again. New conversions were already safe, because they are published with one atomic rename. The check runs on every rank at startup; the review asks it to check each file once, not once per tensor.
  3. Extra weight sync after a resume. Every Megatron resume that loads optimizer state. Before: nothing was wrong. Bridge's load already leaves the weights matching the FP32 master copies. The PR calls quantize_and_sync_model_params_from_main_params again anyway. The weights come out the same, so the only effect is a slightly slower resume: one extra blocking all-gather across data-parallel ranks. The review asks to remove it.

Each change, on one small example

Row 3 has no FP8 case because Bridge's own load already runs the same sync when FP8/FP4 param gather is on (NeMo-RL turns it on with FP8 params), so the PR's call repeats it with the same result. And because every Megatron optimizer has the method, _sync_model_params_from_loaded_optimizer never walks into child optimizers.

How a forest-training run now saves and resumes, next to an ordinary capture run

PR #4200 · issues #4558, #4557 · stacked on #4124 (what forest training is) · permalinks at c9c1b020

Before
A forest-training run with checkpointing on stopped at startup: Forest checkpoint/resume is not supported initially (config.py at the base). The list of model calls picked for training lived only inside one request, so a retry or restart had nothing to rebuild from.
This PR
Saves that list in the same recovery file ordinary capture already uses, and teaches restore to load forest rows. It also lets forest groups use the normal retry budget.
Status
Implemented in this PR. Two open review items: a new unit test fails at head, and resume does not check that the forest setting or the padding size still match the checkpoint.
Background. With forest training, one agent rollout can turn into several training rows. Gym reports every model call; RL keeps a selection of which replies to train on. A recovery ledger tracks groups still being generated; finished groups wait in the replay buffer. Dotted words have a short explanation: hover or tap them.

At a checkpoint, two things are saved. Groups still generating go into the ledger: one record per rollout (a sibling), holding Gym's receipt, the reward, and now the selection (logical_selection, written in state_dict, recovery schema 4). Finished groups are saved as rows in the replay buffer; forest rows carry owner tags that say which rollout each row belongs to. On resume, prepare_for_restart keeps finished siblings and regenerates the rest. The retry path now reads the selection back from the ledger (rollout_manager.py) instead of from the request.

Same path, two extra pieces of data

The two paths share one ledger, one TQ snapshot and one restart rule. They split in two places only: the attempt record gains logical_selection, and replay restore checks owner tags instead of "one row per rollout" (replay_buffer.py). Ordinary schema-3 files still load; forest files older than schema 4 are refused.

The code that does it

Where the change lands: RL only. rollout_recovery.py saves and checks the selection; rollout_manager.py reads it back; the startup ban is deleted. No Gym change: the receipt Gym already sends is enough.

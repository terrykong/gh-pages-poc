Who packs the sequences: the loader, or the trainer?

PR #4105 · predecessor #4070 · all links pinned to f31f793

who packs the first-pack bug

Two pages on this PR, one question each — this one: what the new packing path is, and how it differs from the one that already existed.

Sequence packing glues several short training examples into one long row so the GPU is not padding its way through mostly-empty tokens. NeMo-RL already did this inside the trainer: the batch arrived as separate rows and the policy worker packed them. This PR adds a second way, where Energon — the data loader — does the packing and hands the trainer a row that is already packed. Both paths end up calling the same Megatron entry point with the same kind of argument; they differ in who does the work and what the trainer is still allowed to decide.

Where they stop being the same

The two paths meet at PackedSeqParams and from there the model code is identical. What still differs is what each one puts inside it. 

# existing path — the trainer packed, so it knows where the real tokens end
PackedSeqParams(
    cu_seqlens_q        = [0, 5, 15],   # true ends
    cu_seqlens_q_padded = [0, 8, 20],   # padded ends
    pad_between_seqs    = True,          # the two arrays differ, so: yes
)

data.py:636-657

# new path — the loader packed, and it passes the same array twice
PackedSeqParams(
    cu_seqlens_q        = [0, 8, 36],   # padded ends, not true ends
    cu_seqlens_q_padded = [0, 8, 36],   # the same tensor object
    pad_between_seqs    = False,         # they are equal, so: no
)

data.py:439-448 — the true ends [0, 5, 15] are still computed, and used to check the batch is well formed, but they are not passed on.

That is deliberate, and the code says why: a comment at data.py:436-438 explains that some consumers read cu_seqlens_q as the wrap-around point, so handing them the true ends would let a value roll into the padding. Because the two arrays are then equal, pad_between_seqs=False is the consistent answer — the attention kernel simply treats each padded stretch as the sequence. Causal masking means real tokens never look at the pad tokens behind them, and the loss mask zeroes them.

Why keep both

Turned on bypolicy.sequence_packing.enabledthat, plus data.energon.packing_buffer_size

Pack widthwhatever the batch needsalways the full max_input_seq_length

Costthe trainer re-does the work every stepevery pack carries its padding to the GPU

The new path exists because Energon streams multimodal samples and already knows their sizes as it reads them, so it can group them once instead of the trainer regrouping them every step. The price is the fixed width: a pack that only half fills max_input_seq_length still ships a full-width row. That is why the choice of packing algorithm matters more here than it did before — fewer, fuller packs is now directly fewer forward passes.

If you are reviewing this: the new path short-circuits ahead of the existing one, so the alignment checks that the old path ran at batch time (FP8 divisors, context-parallel multiples) never run. The PR moves them to startup instead, in setup_sft_v2, where a bad config is rejected before a GPU is touched. Worth checking that list against the one it replaces — it is the part of this design most likely to drift.

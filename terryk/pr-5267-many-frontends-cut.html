How one checkpoint cut reaches calls spread over several vLLM HTTP frontends

PR #5267 · based on main · permalinks pinned to head 67c4c0c0 (this PR) and base 488ff3b9

Before
A worker with more than one HTTP frontend refused prefix cuts at setup. Only a single frontend could cut.
This PR
The frontend that gets Gym's cut call runs the cut itself and asks every other frontend, over a private local port, to run it too. Each answers with the calls it saved, and the answers are merged into one receipt.
Status
New feature, under review. The receipt comes out right. The review asks for a fix to a flood of false warnings, a one-line fix for VLM capture, tests for the wiring, a CI run with 2 frontends, and an updated description and benchmark (links at the end).
Background. During an RL checkpoint, Gym asks each vLLM worker to save the tokens generated so far for every call still running. This is a generation cut. After a restore, a saved call resumes from those tokens instead of starting over. One worker can run several HTTP frontends that share one listening socket. Each frontend is an OpenAI-style HTTP server plus its own vLLM AsyncLLM client; the engine that schedules and runs the GPU is one separate process they all share. The tokens a call has decoded so far are kept in the frontend's own copy of vLLM's request state, so a cut reads them there without asking the engine. That is why a call's tokens live only in the frontend that took its request. Dotted words have a short explanation: hover or tap them.
Why it should be faster. All frontends cut at the same time, and each saves only the calls it holds, so the cut's wall time is about the slowest frontend's share, not the sum. What does not shrink: each frontend still walks Gym's whole list and builds a failure ack for every call it does not hold, and Gym's own prepare/commit and the TQ save stay the same. The timing tables in the PR description were measured on an earlier design, where a frontend skipped calls it did not hold, so they do not measure this code. It is slower when a frontend stalls: the cut then waits up to token_capture.control_timeout_s for it.

Same 3 calls, one frontend vs two

Gym's list names 3 calls: c1 is running on frontend A, c2 is running on frontend B, and c3 has not reached the worker yet. Gym's request lands on B. Nobody chooses this: all frontends wait on one shared socket, and the operating system hands each new connection to whichever frontend accepts it first.

Count the ⚠ marks: one frontend logs 1 (the call not yet arrived), two frontends log 4, because each warns about the call the other one holds. With 4 frontends and about 230 live calls, that is about 690 warning lines per cut, and the one real "not arrived yet" warning is lost among them. The receipt is still right: the merge turns a call nobody saved into a failure ack.

QuestionAnswer from the code
Where do the two paths meet?Every frontend runs the same run_cut as one frontend did before. The new part is only around it: FrontendCutFanOut starts the cuts, and merge_cut_receipts merges them. That merge moved here from the Dynamo frontend, which already fans one cut out over several engines the same way.
Can the peer call go to another node?No. Each frontend binds its private port on 127.0.0.1 (L1801). All frontends of a worker live on one node.
Who learns the peers' ports?At startup the owner frontend collects every frontend's private URL and sends the full list to all of them (L821-L826), so any frontend can lead a cut. No test checks this wiring yet.
What else is now per frontend?Cut settings go to child frontends with the capture command (L1069), so each child also starts its own prefix-writer actor (1 CPU). flush also reaches children (L2315), and prefix counts are summed over frontends (L2328).

The route, as pseudocode

Before (one frontend only)

# the frontend's serving event loop
def checkpoint_generation_cut(inventory):
    check bearer token
    return run_cut(inventory)                         # unknown call → failure ack + ⚠

After

# any frontend's serving event loop
def checkpoint_generation_cut(inventory):
    check bearer token
    if not peers:                                      # 1 frontend: path unchanged
        return run_cut(inventory)
    deadline = now + control_timeout_s                # one deadline for every frontend
    cuts = [task(run_cut(inventory) → saved acks),       # mine; ⚠ for every call I don't hold (C5)
            *[task(POST url/frontend) for url in peers]]  # each peer runs the same run_cut
    done, late = wait(cuts, until=deadline)         # all at once
    cancel(late); warn "N of M frontends late"        # their calls regenerate
    return merge_cut_receipts(inventory, done)        # unsaved call → failure ack

Real code: checkpoint_generation_cut, FrontendCutFanOut.run_cut, frontend_generation_cut.

What the review asks

The design holds up: one merge function now serves both the native frontends and Dynamo, and Gym accepts the merged receipt. The asks: stop each frontend warning about calls it doesn't hold (C5). Send media_family to child frontends, which VLM capture needs, and test that the forwarded settings match the function (C1). Test the startup wiring, where removing any one of three lines turns the feature off with every test still green (C4). Add a CI run with 2 frontends (C2). Bring the description and benchmark up to this design (C6).

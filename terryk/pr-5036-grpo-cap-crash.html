Why a chunk cap the GRPO guard accepts can still crash mid-step

NVIDIA-NeMo/RL #5036. All permalinks pin the PR head 391cb0fc.

Before
No cap and no check on GRPO chunk sizes. A warm buffer usually handed over the whole step in one chunk, so uneven chunks were rare.

Adds the cap and a setup check that a full-cap chunk splits evenly across training ranks — but not into micro-batches.

Three pages on this PR, one question each — this one: a config that passes setup and then crashes.

The trainer splits each chunk two ways. First across training ranks, then, on each rank, into micro-batches of a fixed row count. The new GRPO guard checks only the first split. With sequence packing and dynamic batching both off, the second split asserts that each rank's rows divide by the micro-batch size. One sample = one row = one answer to one prompt.

policy: {train_micro_batch_size: 8, sequence_packing: {enabled: false}, dynamic_batching: {enabled: false}} # 2 training ranks grpo: {num_prompts_per_step: 32, num_generations_per_prompt: 4} async_rl: {min_groups_for_streaming_train: 1, max_groups_for_streaming_train: 3}
  1. The guard only divides by the number of ranks, so 12 samples on 2 ranks passes.
  2. With a full buffer the pump takes 3 groups, the cap. The trainer gives each rank 6 rows.
  3. The Megatron worker cuts each rank's rows into micro-batches of 8 and the split fails: Data dict size (6) is not a multiple of the provided microbatch size (8).

The shipped example configs turn sequence packing on (grpo_math_1B.yaml), which cuts micro-batches by token count instead, so they are not affected.

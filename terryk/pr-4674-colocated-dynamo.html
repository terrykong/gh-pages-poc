Background. In colocated mode, the trainer and vLLM take turns on the same GPUs. NeMo-RL's own colocated path wakes vLLM before generation and puts it to sleep after. It copies weights with CUDA IPC handles (update_weights_via_ipc_zmq). Dotted words have a short explanation: hover or tap them.

Colocated: yes, but with IPC, not NCCL

Your plan works: start Ray on every node as ray.sub does, then add one more srun that runs vllm serve on the same nodes and GPUs. In dev mode, stock vLLM 0.29.0 already has an HTTP route for every call the colocated loop needs: /sleep, /wake_up?tags=, /is_sleeping, /reset_prefix_cache, /pause, /resume, and the weight-update routes. The catch is the copy. #4674 uses NCCL, and NCCL refuses two ranks on the same GPU in one group, so a colocated trainer rank and vLLM rank can't share a group. vLLM also ships an ipc transfer backend, with an example that does exactly this, rlhf_http_ipc.py. It matches handles by the GPU's physical ID, so the two processes don't need the same CUDA_VISIBLE_DEVICES view (receiver).

The hard parts are about processes, not endpoints:

  • Same container. CUDA IPC only works between processes that share an IPC namespace on the same host. Run vllm serve inside the same container as the Ray worker (for example srun --overlap into the same named container), or use host IPC.
  • Memory split. vLLM sizes its cache as a share of the whole GPU (--gpu-memory-utilization). Start it before the trainer allocates, or size the share to fit beside the trainer, and use sleep level 1 like the managed path.
  • Lost features. vLLM's stock IPC receiver just calls the model's weight loader. NeMo-RL's own receiver also handles FP8 and sparse refit. To keep those, load NeMo-RL's worker extension into vllm serve (--worker-extension-cls) and call it through /collective_rpc. That route only takes string arguments.
  • Safety. Posting handles over HTTP needs VLLM_ALLOW_INSECURE_SERIALIZATION=1 (pickled data). With dev mode on, anyone who can reach the port can run code on the server, so bind it to localhost.

Dynamo: same refit engine, different doors

Update: open PR #4905 replaces the managed dynamo.vllm design below. Dynamo becomes a switch on NeMo-RL's own vLLM worker, and the /engine/… refit routes go away. See one worker, three launches.

NeMo-RL's Dynamo backend is managed: NeMo-RL starts etcd, NATS and the Dynamo frontend itself, plus one Ray actor per dynamo.vllm worker. Under the hood, refit uses the same vLLM NCCL engine and sender settings as #4674. The difference is where the calls go: Dynamo sends them to each worker's own admin port, {system_url}/engine/… (refit.py). #4674 sends them to one base_url.

Could you point remote_vllm at an external Dynamo? Not as written. Preflight expects plain vLLM (/version = 0.29.0, /get_world_size, one backend). Refit expects one admin URL and one rank offset, while Dynamo has one per worker. We did not read Dynamo's own source to check which routes its frontend serves. The conclusion rests on NeMo-RL's Dynamo code going around the frontend for refit.

So what (proposal). Share the refit protocol, not the launcher. One small interface (init, start, update, finish, pause, resume) with two implementations: plain vLLM dev routes and Dynamo /engine/* routes. Then remote_vllm's config becomes "one rollout URL plus a list of admin URLs". That one change opens up three things: several external vLLM replicas, an externally launched Dynamo, and later a colocated IPC version that swaps in a different transfer backend. #4674 hard-codes one URL and NCCL today. This is the cheapest moment to add that seam, before #4675–#4677 build on top of it.

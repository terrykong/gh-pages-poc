Eight pages on this PR, one question each. This one: how the reassembler turns a rollout's captured calls into training rows.

Background. Every model call in a rollout leaves two things behind. Gym's ledger holds one small record per call, including its parent call. TransferQueue holds the call's new tokens only: the observation tokens since the parent (no gradient) plus the tokens the model generated (gradient). A call with no parent is a root; it stores its whole prompt. The reassembler joins the two stores to build training rows. Page 2 shows how the data gets there. Dotted words have a short explanation: hover or tap them.

Without CC, every request is the previous one plus new observations, so the calls form one chain. RL takes the call the agent ended on (the leaf), follows parent links up to the root, and joins the stored tokens in order (Gym _terminal_chain). Your mental model is right for this case. With CC, a rewrite breaks the chain, so the ledger has several roots. RL no longer picks one leaf. It matches the agent's final output to the calls that produced it (select_captured_calls) and cuts that list at every root (_plan_selected_calls). Each piece then goes through the same leaf-to-root walk.

The same 5 calls, without and with compaction

With compaction on, step by step. RL does not search the tree for leaves. It reads the order from the agent's output, cuts by each call's own parent field, and only then walks:

① match the agent's output to calls, left to right (gym_selection.py L175-229) output items 0-1 [reasoning 1, answer] → only c1 produced exactly these → c1 output items 2-3 [reasoning 2, answer] → c2 output items 4-5 [reasoning 3, answer] → c3 output items 6-7 [reasoning 5, answer] → c5 (c4's output is not in the conversation) selected = [c1, c2, c3, c5] ← conversation order, no tree search ② cut in one pass, looking only at each call's parent (rollout_reassembler.py L1149-1163) c1 parent: none → start chain 0: [c1] c2 parent: c1 = previous call → chain 0: [c1, c2] c3 parent: none → start chain 1: [c3] c5 parent: c3 = previous call → chain 1: [c3, c5] (a parent that is not the previous selected call is an error) ③ reuse the old row builder on each chain; it re-walks the chain as a check and joins tokens (leaf set at L1166-1172, walk in Gym rebuild.py L201-216) chain 0: c2 → c1 → stop (no parent) → row group_g0_s0 chain 1: c5 → c3 → stop (no parent) → row group_g0_s1

Step ② already knows every chain; step ③ only reuses the existing finalizer, which checks hashes and lengths and joins the stored tokens, and RL confirms it finds the same calls (L1263-1273).

Why the output and not just the tree: without compaction, the leaf's ancestors are the whole conversation. With compaction, c5's ancestors stop at c3, and nothing in the tree says c1 and c2 come first or were accepted. The agent's output is the only record of what it kept, and in what order.

What RL checks while it cuts

The cut is strict, so a wrong ledger fails loudly instead of training on the wrong tokens:

  1. A selected call must continue the call just before it, unless it is a root. Otherwise the agent's output skipped a call, and RL raises (L1156-1161).
  2. Each chain is rebuilt with the ordinary code (finalize_rollout, the same hash and length checks), and the rebuilt call order must equal the selected order (L1250-1273).
  3. All or nothing per rollout: if any chain fails, every row of that rollout is masked (L1329-1349).
  4. One advantage per rollout, not per row. GRPO runs on one reward per rollout, then copies the result to all its rows (single_controller.py L5378-5393). A rollout cut into 3 rows still counts once in its group.

So what. Your mental model holds inside each piece: every row is still built by walking one chain from its leaf up to its root. What CC adds is a step before that walk. The agent's own output decides which calls were accepted, and every root starts a new piece. That is why a rewrite now costs one extra row instead of the whole rollout. It is also why the harness must return its full accepted history: a chain missing from the output is a chain that never trains (review comment on gym_selection.py).

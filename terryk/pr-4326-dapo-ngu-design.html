Where async DAPO and "Never Give Up" would make their per-group decision — and whether moving advantages into actors gets in the way

Design note for NVIDIA-NeMo/RL #4326 (advantage stage in sharded Ray actors). All permalinks pin the PR head 93c8818.

Before
The single controller refuses use_dynamic_sampling at startup (config.py:1108). Never Give Up does not exist in the repo.
This PR
Moves the advantage math into CPU actors and splits each chunk across them, assuming every group has num_generations_per_prompt rows.
Status
Proposed — not implemented. The PR does not block DAPO. It gets in Never Give Up's way in one place, the splitter's fixed group size. #4371 (key and split by group id) removes that too (last section).
before and after same-prompt baselines DAPO & NGU design

Three pages on this PR, one question each — this one: where a whole-group decision would go.

The two features. DAPO dynamic sampling: if every response to a prompt gets the same reward, GRPO gives them all advantage 0, so the group teaches nothing. Drop it and train on another prompt instead (sync version: grpo.py:2061). Never Give Up (NGU): if every response is wrong, do not drop the prompt. With probability p, sample k more responses for it, keep the old ones, and train on the whole grown group once one is right. All-correct groups are dropped, as in DAPO. Both need one decision per group, made from its rewards. Dotted words have a short explanation: hover or tap them.

In the single controller, each prompt is handled by its own task, _dispatch_one_prompt. It calls RolloutManager.generate_and_push, which runs in the same process: it generates the group (run_rollout), gets back each response's reward as a plain float (Completion.reward), and only then writes the rows to the data plane (_tq_buffer.commit). The gap between those two lines is where both rules belong: the rewards are known, and no GPU time has been spent on the group yet. The code already has the "give up on this group, use a spare" path there (_take_replacement draws from the spare-prompt pool). Each group also gets an id from the controller when it starts, and every row is named after it, {group_id}_g0, _g1, … (payload.py:227). That id is what "one group" should mean everywhere below.

Where the decision runs

The design, step by step — proposed, not in the PR

Where it lands: RL only. DAPO: rollout_manager.py (one check before commit, one new outcome), single_controller.py (treat the new outcome like a skipped prompt), config.py (allow the flag). NGU: the same spot, plus variable-size groups (next section). No advantage-actor change for either. Nothing below is implemented or run.

What each piece does. The check uses exact reward equality, like the sync path's calculate_trivial_reward_distributions. The dropped group then goes down the existing skipped-prompt branch: a spare replaces it, or the step closes one group short (_credit_shortfall). In token-capture mode, the same check goes after the finalizer, next to min_valid_fraction_per_group. It needs one new field on FinalizedGroup, "the valid rows' rewards are all equal", computed from valid_rows. The real work is sizing: DAPO often drops 30–70% of groups, but the spare pool defaults to 1 prompt and 1 retry per group (rollout_failure), so it needs a larger pool and a cap like the sync path's dynamic_sampling_max_gen_batches.

NGU uses the same spot but loops instead of returning. The task keeps the earlier rounds' Completion objects in memory, calls run_rollout again, and commits one grown group (4, then 8, then 12 rows) under one group id, so its rows are c_g0 … c_g11. The native path already names rows by how many completions there are; token capture caps the row index at num_generations_per_prompt (rollout_manager.py:1110) and would need to allow more. Two more things change, both outside the advantage actors. First, each round needs its weight version, because NGU drops stale responses from training but keeps them in the baseline. Second, the advantage estimator must then use a separate "counts for the baseline" mask, still one baseline per group id; today it uses the training mask (valid_mask=final_sample_mask). That estimator change runs the same code in-process or in an actor.

The one place this PR gets in the way — and how the group id removes it

The sampler builds a chunk by joining whole groups, so it knows where each group starts (selected_metas[0].concat(...)). That list is lost. The PR's splitter then guesses the boundaries from num_generations_per_prompt (split_meta_by_prompt_group). With NGU's grown group, the guess can cut the group in two, and nothing fails. Real output of the repo's baseline code, 2 actors, k = 4:

chunk: b (4 rows) | c (12 rows, NGU after 3 rounds) | d (4 rows) = 20 rows splitter: 20 / 4 = "5 groups" → 3 per actor → cut at row 12, inside c c's rows round 1 (4) round 2 (4) round 3 (4) one call −0.302 × 4 −0.302 × 4 −0.302 1.0 −0.302 −0.302 split at row 12 0 × 4 0 × 4 −0.577 1.0 −0.577 −0.577 └──── actor 1: 8 all-wrong rows look like an all-equal group ────┘ by group id −0.302 × 4 −0.302 × 4 −0.302 1.0 −0.302 −0.302 (#4371) split [b c] | [d]: c stays whole; all 20 rows equal the one-call result

With a fixed size, c's 8 older wrong answers stop being pushed down. The fix is #4371, proposed and not implemented: tag every row with its group id, split the chunk where the id changes, and key the baseline on the id instead of on the prompt text. Then a group is one group whatever its size and wherever it lands. The last row above is the repo's own baseline code run that way; it matches the one-call result exactly. The same key also fixes two groups with the same prompt text, and it lets the one DAPO case only the advantage stage can see, a group whose rewards become all-equal only after masking, be reported back as a list of group ids. The other fixed-size assumptions in the code fail loudly, not silently: the checkpoint restore check (expected_group_size) and the token-capture assert (rollout_manager.py:1093).

So what. Moving advantages into actors does not make DAPO or Never Give Up harder. Both decide from rewards the controller already holds, before commit, and the advantage actors never see a dropped group. The one thing NGU needs from this PR's code is a splitter that follows group ids instead of a fixed size, which #4371 proposes. Today every group has exactly num_generations_per_prompt rows, so the current splitter is correct now.
